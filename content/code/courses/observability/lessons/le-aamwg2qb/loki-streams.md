---
title: Loki: index the labels, read the lines
version: 1
---

Loki was built on one decision, and everything about it follows: **it indexes only a small set of
labels per stream of lines, and never the lines themselves.** A *stream* is every line that shares
one set of label values. Asked what labels it has, the lab's Loki answers with one:

```
ana@obs:~/shop$ curl -s localhost:3100/loki/api/v1/labels | jq -c .data
["service_name"]
ana@obs:~/shop$ curl -s localhost:3100/loki/api/v1/label/service_name/values | jq -c .data
["mailer","orders","payments","storefront"]
ana@obs:~/shop$ curl -sG localhost:3100/loki/api/v1/series --data-urlencode 'match[]={service_name=~".+"}' | jq '.data | length'
4
```

One label, `service_name`, four values, **four streams**. Every line the shop writes, every field
of it, the order id, the trace id, the message, lives inside one of those four streams. The streams are compressed
in chunks that Loki does not index at all. A query starts by choosing streams with a label selector,
the same `{...}` syntax as a PromQL selector, and then reads the chosen streams' lines and filters
them.

That makes writing very cheap: storing a line costs compression and an append, and the index grows
with the number of streams, not with the number of lines. It also makes **reading cost depend on how
much the label selector narrows**. `{service_name="payments"}` reads a quarter of the lab's lines;
a query whose only selector matches every service reads all of them. Loki answers that with
parallelism, splitting the time range across workers, and with the advice that labels should say
*where a line came from*, service, environment, region, and never *what it says*.
