Two trees exist now: the document, and the styles. Neither can be drawn on its own — one has no
appearance and the other has no content — so the browser builds a third by joining them.

That third one is the **render tree**, and it contains exactly what will be put on the screen.

## What gets left out

The joining is not a copy. Several things in the document do not appear in the render tree at all,
and knowing which is more useful than it sounds.

**Things with no appearance by nature.** Everything in the head of the document — the title, the
meta tags, the links to stylesheets, the scripts. They matter enormously and none of them is drawn.

**Things a style removed.** An element set to `display: none` is in the document and absent here.
It occupies no space, because as far as layout is concerned it does not exist.

**Things the browser does not display at all**, such as a comment left in the markup.

And one addition, which is the reason this is a tree of its own rather than a filtered document:
**things the document never contained.** A rule that generates content before or after an element
puts a box in the render tree with no corresponding element in the document — which is why a
generated icon is visible on screen and absent when a script looks for it.

`display: none` removes the element from the render tree. It takes no space, nothing flows around
it, and the layout is computed as if it were not there. Showing it again is a layout.

`visibility: hidden` keeps it in the render tree and draws nothing. The space is still occupied,
everything around it stays where it was, and showing it again is a repaint rather than a layout.

`opacity: 0` is different again: fully drawn, fully laid out, invisible, and — importantly — still
receiving clicks.

Three ways to make something invisible, three different behaviours, and a reader who has met the
render tree can predict all three rather than remembering them.

There is a fourth that belongs beside them and is not about appearance at all: the `hidden`
attribute in the markup, which is the same as `display: none` by default and says something about
the content rather than its style. When a thing is genuinely not part of the page right now, that
is the honest way to say so.

## And the one that catches people with screen readers

Worth a paragraph, because it is a real defect and an invisible one.

`display: none` and `visibility: hidden` remove an element from what a screen reader announces, as
well as from the screen. `opacity: 0` does not: the element is still there, still focusable, still
read out — which is how a hidden menu becomes a trap where somebody tabs into things they cannot
see.

The rule that follows: **if it is not available, remove it from the render tree.** Making something
invisible and leaving it interactive is a choice, and it should be one you made on purpose.

## Boxes, which is what the tree is actually made of

One vocabulary note, because the words appear in every tool and every stylesheet.

Each entry in the render tree is a **box**, and every box has four rings: the content, then padding
inside the border, then the border, then margin outside it. That is the box model, and the argument
it causes is about which of those a declared width includes.

By the original rule, `width` is the content alone, and padding and border are added to it — so a
box declared 300 wide with 20 of padding occupies 340. It is the source of more arithmetic than any
other single rule in this field.

The modern habit is to change it once, at the top of a stylesheet, so that a declared width means
the visible width including padding and border. That single line removes an entire category of
layout surprises, and it is worth knowing what it is doing rather than copying it.

## Why this tree is rebuilt more often than you think

The render tree is not built once. Any change to the document or to a style that affects what is
drawn produces a new one, or a repaired part of one.

A class added by a script. An element inserted. A stylesheet applied late. A window resized.

Most of the time this is cheap and invisible. The reason to know it happens is the next reading:
what follows a change to the render tree is layout and paint, and those are where the cost is. A
page that rebuilds this structure sixty times a second is a page doing sixty layouts a second, and
that is a number you can see in a tool.
