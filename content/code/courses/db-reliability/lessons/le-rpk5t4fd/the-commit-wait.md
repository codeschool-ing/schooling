---
title: What a commit waits for
version: 1
---

Lesson 11's standby was **asynchronous**: the primary confirmed each commit to the application as
soon as the commit was on its own disk, and sent the log to the standby afterwards. If the primary
had died in between, the application would have been told "saved" about a transaction the standby
never received, and a promotion of the standby would have lost it. That window is small, usually
milliseconds, and it is exactly the RPO lesson 8 said only one lever closes.

The lever is **synchronous replication**: the primary does not confirm a commit until a standby has
confirmed it too. How far "confirmed" goes is a setting, `synchronous_commit`, and each value moves
the moment the application hears back further along the path lesson 11 drew:


| `synchronous_commit` | the commit returns when | lost if the primary dies at once |
|---|---|---|
| `off` | the commit is in the primary's memory | up to a fraction of a second, even with no standby |
| `local` | it is on the primary's disk | whatever the standby had not received |
| `remote_write` | the standby has **written** it, not yet flushed | only if the standby's machine fails at the same instant |
| `on` (with a synchronous standby) | the standby has **flushed** it to disk | nothing |
| `remote_apply` | the standby has **replayed** it | nothing, and it is already visible on the standby |

With no synchronous standby configured, `on` behaves like `local`, which is the situation of lesson
11 and of most servers. The setting can be changed per session and per transaction, so an application
can ask for `remote_apply` for a payment and `off` for a page-view counter on the same database. That
is often the best use of it.
