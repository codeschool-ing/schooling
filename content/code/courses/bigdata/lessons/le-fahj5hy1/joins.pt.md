**O join é a operação que o MapReduce tornou mais difícil**, e ver por quê explica metade do que o
Spark faz de diferente. Suponha que a pergunta seja a receita por categoria: as compras vêm dos
cliques, e as categorias e os preços dos 3.000 livros. Os dois precisam se encontrar no `book_id`.

**O join no reduce** é o método geral. O mapper lê as duas entradas e emite cada registro com o
`book_id` como chave, *marcado* com a origem: `B` para um livro, `P` para uma compra. O particionador
manda todo registro com o mesmo `book_id` ao mesmo reducer, que então vê o livro e todas as suas
compras juntos, e pode multiplicar. Funciona para entradas de qualquer tamanho, e embaralha as duas
inteiras: toda compra atravessa a rede para encontrar um livro de poucas dezenas de bytes.

**O join no map** é o atalho quando um dos lados é pequeno. Cada tarefa de map carrega a tabela
pequena inteira na memória antes de começar, depois lê a sua fatia da entrada grande e procura cada
registro enquanto avança. Nada é embaralhado. O `-files` do Hadoop Streaming é o meio de entrega: o
mesmo argumento que enviou o `mapper.py` pode enviar o `books.csv` a cada tarefa.

A troca é a que a aula 8 mede no Spark, onde os dois se chamam *sort-merge join* e *broadcast join*:

| | move pela rede | precisa na memória |
|---|---|---|
| join no reduce | as duas entradas, inteiras | os registros de uma chave por vez |
| join no map | a entrada pequena, uma vez por tarefa | a entrada pequena inteira, em cada tarefa |

No MapReduce quem programava escrevia um ou outro, à mão, para cada join. Escolher entre os dois
automaticamente, pelo tamanho das entradas, é uma das primeiras coisas que o planejador do Spark
faz, e a aula 6 mostra ele decidindo.
