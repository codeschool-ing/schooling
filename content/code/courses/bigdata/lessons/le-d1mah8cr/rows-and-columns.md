**A CSV file stores a table row by row; Parquet and ORC store it column by column.** Both hold the
same values. What differs is which values sit next to each other on disk, and that decides what a
reader has to get through to answer a question.

An analytical query names a few columns of a wide table: the kinds of event per day, the purchases
per category. **Stored by row, every column of every row is read to find the few that matter**,
because the values of one column are spread through the file, one per row. Stored by column, the
values of `kind` are one contiguous run, and the other columns are not touched. Lesson 6 measured the
result without explaining it: a count of distinct books read two columns of seven.

Keeping a column's values together has a second effect, as large as the first. **Values of one
column look alike**: the same few kinds, the same three devices, timestamps a second or so
apart. Alike values compress far better than the mixed values of a row, and a columnar file can
also encode them before compressing them, storing a repeated value once or a timestamp as its
difference from the last. Sections 04 and 05 measure both.

**What a columnar file is bad at is the opposite question**: one whole row, or adding rows one at a
time. Reading a row means visiting every column's run; adding one means rewriting the file. That is
why a database that serves an application stores rows and a lake that serves analysts stores
columns, and why the data moves from one to the other in batches.
