title: How HDFS is built
version: 1

**HDFS cuts every file into blocks of 128 MB and stores each block three times, on three different
machines.** Everything else in its design follows from those two numbers.

There are two kinds of process:

- **The namenode**, one per filesystem, holds the *metadata*: the tree of directories and files,
  which blocks make up each file, and which machines hold each block. It keeps all of it in memory,
  so that answering "where is this file?" never touches a disk. It stores no data.
- **A datanode** runs on every machine with a disk to offer. It stores blocks as ordinary files on
  its local filesystem and knows nothing about which file a block belongs to. Every few seconds it
  sends the namenode a *heartbeat*, and from time to time the list of every block it holds.

**Reading a file** is two conversations. The client asks the namenode which blocks make up the file
and where each one is, and then reads each block directly from a datanode that holds it, preferring
the nearest. The namenode never carries the data, which is why one namenode can serve a cluster of
thousands of machines.

**Writing a file** goes the same way in reverse. The namenode picks three datanodes for each block,
and the client sends the block to the first, which passes it on to the second as it arrives, which
passes it to the third: a *pipeline*. The write succeeds when all three hold it.

Three copies on three machines is what makes the failures of lesson 2 survivable for data, not just
for work. Lose one machine and every block it held still exists twice; the namenode notices the
missing heartbeats, sees which blocks now have only two copies, and has the survivors copy them to a
third machine. Section 06 does that.

**Why blocks so large.** A block of 128 MB takes about a second to read from one disk, so a task
reading one block spends its time reading and not starting. It also keeps the namenode's list
short: a 1 TB file is 8,000 blocks, which the namenode holds in memory without effort. The price is
paid by small files, and section 07 pays it.

**HDFS files are written once and never changed in place.** A file can be created, read, renamed,
deleted and appended to, but not edited in the middle. That suits data that arrives and is read
many times, which is what a cluster processes, and it rules out using HDFS as the disk under a
database. HBase, in lesson 12, is a database built around that rule.
