**Toda tabela de um pool de SQL dedicado é dividida em 60 distribuições, e a definição da tabela diz
como cada linha escolhe uma.** Uma consulta roda nas 60 ao mesmo tempo, cada nó de computação
trabalhando na parte dele, e termina quando a distribuição mais lenta termina. Então a pergunta que a
definição responde não é onde os dados moram, mas se o trabalho se divide por igual. Esta seção é
ensinada a partir da documentação da Microsoft; o único comando rodado aqui mostra onde o substituto
para.

## Três jeitos de pôr uma linha

| distribuição | para onde vai uma linha | serve para |
|---|---|---|
| `HASH(column)` | a distribuição para a qual o hash da coluna aponta | grandes tabelas fato, com hash numa coluna de muitos valores distintos e bem espalhados |
| `ROUND_ROBIN` | a próxima distribuição da vez | tabelas de staging carregadas rápido e lidas uma vez |
| `REPLICATE` | uma cópia inteira em cada nó de computação | tabelas de dimensão pequenas de que toda junção precisa |

**Um hash numa coluna com poucos valores enche só esse tanto de distribuições.** A Quitanda tem cinco
lojas, então uma tabela de pedidos com hash em `store` põe toda linha em no máximo cinco das 60
distribuições, e uma consulta sobre ela roda em cinco enquanto 55 esperam. Com hash em `customer_id`,
com dezenas de milhares de valores, as mesmas linhas se espalham pelas 60:

Os outros erros são mais sutis. Uma coluna de data tem muitos valores, mas uma consulta de um dia cai
então numa distribuição só, o que é desequilíbrio no tempo em vez de no armazenamento. Uma coluna que é
`NULL` com frequência manda todo nulo para um lugar só. E uma junção entre duas tabelas com hash na
coluna pela qual se unem não precisa mover dados entre nós; unidas por outra coisa, o pool primeiro
embaralha linhas pela rede, o que o plano da consulta mostra como um passo de movimentação de dados e
que costuma ser a parte mais lenta de uma consulta lenta. O conselho da documentação para tabelas de
dimensão pequenas, por volta de 2 GB comprimidos ou menos, é replicá-las, para todo nó ter a cópia que
toda junção quer.

## A definição

Num pool dedicado a escolha é escrita no `CREATE TABLE`, com o índice columnstore clusterizado que é o
armazenamento padrão de uma tabela de data warehouse:

```sql
CREATE TABLE dbo.orders (
    order_id    varchar(10) NOT NULL,
    customer_id varchar(8)  NOT NULL,
    store       varchar(12) NOT NULL,
    total_cents int         NOT NULL
)
WITH (DISTRIBUTION = HASH(customer_id), CLUSTERED COLUMNSTORE INDEX);
```

**O SQL Server não é um pool dedicado, e diz isso.** O serviço `sql` do laboratório da lição 1 é o motor
das lições 8 e 9, e não conhece a cláusula `WITH` acima. Iniciado com
`docker compose --profile sql up -d`, ele responde:

```
ana@laptop:~/azure$ docker compose exec sql /opt/mssql-tools18/bin/sqlcmd -S localhost -U sa -P Quitanda-Lab-2026 -C -Q "CREATE TABLE dbo.orders (order_id varchar(10) NOT NULL, customer_id varchar(8) NOT NULL) WITH (DISTRIBUTION = HASH(customer_id), CLUSTERED COLUMNSTORE INDEX)"
Msg 102, Level 15, State 1, Server 4d7f0bc8f6d6, Line 1
Incorrect syntax near 'INDEX'.
```

Essa recusa é a fronteira honesta desta seção. Distribuições, movimentação de dados e a divisão em 60
existem só no pool dedicado, e o plano de uma consulta de verdade contra um é algo que este curso não
consegue mostrar. O que ele consegue mostrar é a conta do outro pool, que depende de arquivos, e
arquivos rodam num notebook.
