title: Sixty distributions, and the column that fills them

**Every table in a dedicated SQL pool is split into 60 distributions, and the table's definition says
how each row picks one.** A query runs on all 60 at once, each compute node working on its share, and
finishes when the slowest distribution finishes. So the question the definition answers is not where
the data lives but whether the work divides evenly. This section is taught from Microsoft's
documentation; the one command run here shows where the stand-in stops.

## Three ways to place a row

| distribution | where a row goes | fits |
|---|---|---|
| `HASH(column)` | the distribution the column's hash points at | large fact tables, hashed on a column with many distinct, evenly spread values |
| `ROUND_ROBIN` | the next distribution in turn | staging tables loaded fast and read once |
| `REPLICATE` | a full copy on every compute node | small dimension tables that every join needs |

**A hash on a column with few values fills only that many distributions.** Quitanda has five stores, so
a table of orders hashed on `store` puts every row in at most five of the 60 distributions, and a query
over it runs on five while 55 wait. Hashed on `customer_id`, with tens of thousands of values, the same
rows spread over all 60:

The other mistakes are subtler. A date column has many values, but a query for one day then lands on one
distribution, which is skew in time rather than in storage. A column that is often `NULL` sends every null
to one place. And a join between two tables hashed on the column they join by needs no data moved
between nodes; joined on anything else, the pool first shuffles rows across the network, which the query
plan shows as a data movement step and which is usually the slowest part of a slow query. The
documentation's advice for small dimension tables, around 2 GB compressed or less, is to replicate them,
so that every node has the copy every join wants.

## The definition

In a dedicated pool the choice is written in the `CREATE TABLE`, with the clustered columnstore index
that is the default storage of a warehouse table:

```sql
CREATE TABLE dbo.orders (
    order_id    varchar(10) NOT NULL,
    customer_id varchar(8)  NOT NULL,
    store       varchar(12) NOT NULL,
    total_cents int         NOT NULL
)
WITH (DISTRIBUTION = HASH(customer_id), CLUSTERED COLUMNSTORE INDEX);
```

**SQL Server is not a dedicated pool, and says so.** The `sql` service of lesson 1's lab is the engine
of lessons 8 and 9, and it does not know the `WITH` clause above. Started with
`docker compose --profile sql up -d`, it answers:

```
ana@laptop:~/azure$ docker compose exec sql /opt/mssql-tools18/bin/sqlcmd -S localhost -U sa -P Quitanda-Lab-2026 -C -Q "CREATE TABLE dbo.orders (order_id varchar(10) NOT NULL, customer_id varchar(8) NOT NULL) WITH (DISTRIBUTION = HASH(customer_id), CLUSTERED COLUMNSTORE INDEX)"
Msg 102, Level 15, State 1, Server 4d7f0bc8f6d6, Line 1
Incorrect syntax near 'INDEX'.
```

That refusal is the honest boundary of this section. Distributions, data movement and the 60-way split
exist only in the dedicated pool, and the plan of a real query against one is something this course
cannot show. What it can show is the other pool's bill, which depends on files, and files run on a
laptop.
