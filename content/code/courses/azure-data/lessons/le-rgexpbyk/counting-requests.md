**A program does not say how many requests it sends**, and the person who wrote it usually guesses
low. A call that looks like one action can be one request or twenty, and a loop that looks harmless
can be six thousand. The bill counts every one of them, so before pricing anything this section
counts them, with a program that watches its own traffic leave.

Start Azurite if it is not running (`docker compose up -d` in `~/azure`), and save this as
`~/azure/count.py`:

Most of the time it takes goes on the six thousand small writes:

```
ana@laptop:~/azure$ python count.py
create the container        1 Create Container
6,000 taps, a blob each     6,000 Put Blob
the same taps, one blob     1 Put Blob
list 6,000 names            2 List Blobs
read every tap              6,000 Get Blob
read the day's one blob     1 Get Blob
upload 80 MiB               20 Put Block, 1 Put Block List
download 80 MiB             13 Get Blob
```

**Six thousand taps written a blob each are 6,000 `Put Blob` requests, and the same taps as one blob
are one.** Same bytes, same container, six thousand times the operations. Nothing about the data
changed except how it was cut up, and on Azure each of those requests is a write operation on the
bill.

**Listing 6,000 names took two requests**, because one page of a listing holds at most 5,000 names,
which Microsoft's reference for `List Blobs` documents, and the library asked for the second page by
itself. A listing is cheap per name: one operation for up to 5,000 of them. Reading is not. **Every
tap read back is its own `Get Blob`, 6,000 of them, where the day's one blob took one.**

## One blob, many requests

That is the library's choice, not Azure's. By default it sends a blob of up to 64 MiB in a single
`Put Blob` and anything larger as the block blob of lesson 2, in blocks of 4 MiB committed by a list.
It fetches the first 32 MiB of a download in one request and the rest in ranges of 4 MiB, so a
failure halfway costs one piece rather than the whole. The four sizes are options of the client,
`max_single_put_size`, `max_block_size`, `max_single_get_size` and `max_chunk_get_size`, and a
program moving large files can raise them. **No option makes six thousand small blobs into fewer
requests**: that is decided by how the data was cut up before the library ever saw it.

## Where Azurite stops

**Azurite answered every request and counted none of them.** An emulator has no meter, and every
number above is the program's own, made by watching its requests leave. On a real account the same
requests appear in the account's metrics as transactions, split by the name of the operation, and on
the invoice as quantities of the operations meters. Neither was looked at here, because there is no
real account in this course.
