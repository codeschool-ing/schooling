**Consistency in Cosmos DB is not the C of ACID.** It says nothing about constraints or valid
states. It answers a narrower question: when a program reads an item, may it be shown a version
older than the newest one written? The question exists because of copies. Microsoft's
documentation describes four replicas of every physical partition in each region an account is in,
and a write is acknowledged once a majority of the four have it. A read served by the fourth, a
moment later, can find the old value. An account in two regions has eight copies, and the second
region learns of each write later still.

**This section is taught from Microsoft's documentation, and none of it was run.** The emulator
keeps one copy of everything, so it never serves a stale read, and its account reports a level it
does not enforce. The programs in this lesson use the container of lesson 1's `ru.py`, Quitanda's
orders partitioned by customer, and ask what a reader of it is promised.

## The five promises

Cosmos DB names five levels, strongest first. The level is set once for the account, and a client
may ask for a weaker one, as the section on overriding shows.

| level | what a read is promised |
|---|---|
| strong | the most recent committed version, everywhere; a reader never sees an older one |
| bounded staleness | at most K versions or T seconds behind the latest write, whichever comes first, and in order |
| session | inside one session: your own writes, reads that never go backwards, writes applied in the order you made them |
| consistent prefix | some prefix of the writes in the order they were made: an older value, never a gap or a reversal |
| eventual | nothing about order or age; the copies converge when the writes stop |

**Strong is linearisable**: once a write is acknowledged, every read anywhere returns it or
something newer. Eventual is the other end, and it is weaker than it sounds: two reads in a row can
return a newer value and then an older one, because they reached different copies.

## Session, the one that is the default

**A new account is created at session consistency**, and it is the level most applications run at.
Its promises are scoped to a session, which in practice means whoever holds one token. A client that
writes an order is handed a token, and every read that carries it is served by a copy that has
already applied that write. A customer who pays and then reloads the page sees `paid`. A courier's
phone, in a different session, may still see `pending` for a moment, and will never see the order
go from `paid` back to `pending`.

That is usually exactly the right guarantee. The person who made a change sees it at once, and
everybody else sees it soon and in order. The next section shows the token travelling and a copy
refusing a read whose token it cannot honour.

## Bounded staleness, and the two numbers in it

Bounded staleness is consistent prefix with a ceiling on how far behind a read can be: K versions of
an item or T seconds, whichever is reached first. **The minimums are not free choices.** For an
account in one region the documentation gives 10 writes and 5 seconds; for an account in several
regions, 100,000 writes and 300 seconds. So in a multi-region account, bounded staleness can still
be five minutes stale in a region far from the writes, and the reason to choose it is the
guarantee about the bound, not a small one.

## Consistent prefix and eventual

Consistent prefix forbids one thing that eventual allows: seeing the writes out of order. If an
order goes `created`, `paid`, `delivered`, a reader at consistent prefix may see `created` after the
order was delivered, but never `delivered` and then `paid`. At eventual both can happen. For
Quitanda's product catalogue, where a price changes a few times a day and nobody's decision rests on
the second before the change, eventual is enough. For an order's status, which a person acts on,
session is the floor.
