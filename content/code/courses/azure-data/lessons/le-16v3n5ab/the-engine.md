**Azure SQL Database is the SQL Server engine**, the same code base Microsoft ships as a product, run
by Microsoft as a service. So the part of it that is yours, the schema, the queries and the indexes,
can be practised on SQL Server itself, in the container lesson 1 set up. The part that is Microsoft's,
the purchasing model and everything around the engine, cannot, and this section draws the line
between the two with the engine's own answers.

Start SQL Server in `~/azure`. It takes a few seconds before it accepts a connection:

```sh
docker compose --profile sql up -d
```

Every command below talks to it through `sqlcmd`, the command-line client that comes inside the
container, so nothing has to be installed on your computer. A short shell function saves typing it,
and the query this section asks twice goes into a variable:

```sh
sql() { docker compose exec -T sql /opt/mssql-tools18/bin/sqlcmd -S localhost -U sa -P Quitanda-Lab-2026 -C -W -s '|' "$@"; }
Q="SELECT COUNT(*) AS orders, SUM(total_cents) AS cents FROM dbo.orders WHERE customer_id = 17"
```

`-C` trusts the container's own certificate, `-W` drops the spaces SQL Server pads every column with,
and `-s '|'` puts a bar between columns. Then the orders. Save this as `~/azure/orders.sql`: one
table, and a hundred thousand orders of seven thousand customers, generated by the engine itself so
that nothing has to be downloaded:

`orders.sql`:

```sql
CREATE DATABASE quitanda;
GO
USE quitanda;
CREATE TABLE dbo.orders (
  order_id    int IDENTITY PRIMARY KEY,
  customer_id int NOT NULL,
  placed_at   datetime2(0) NOT NULL,
  total_cents int NOT NULL
);
WITH n AS (SELECT TOP (100000) ROW_NUMBER() OVER (ORDER BY (SELECT NULL)) AS i
           FROM sys.all_objects a CROSS JOIN sys.all_objects b)
INSERT dbo.orders (customer_id, placed_at, total_cents)
SELECT i % 7000, DATEADD(minute, i * 5, '2026-01-01'), 1500 + (i * 37) % 30000 FROM n;
SELECT COUNT(*) AS orders FROM dbo.orders;
GO
```

```
ana@laptop:~/azure$ sql < orders.sql
Changed database context to 'quitanda'.

(100000 rows affected)
orders
------
100000

(1 rows affected)
```

## What the engine says it is

**`SERVERPROPERTY('EngineEdition')` is the engine's own answer to what it is running as**, and it is
the line between this lab and the service:

```
ana@laptop:~/azure$ sql -Q "SELECT CAST(SERVERPROPERTY('EngineEdition') AS int) AS engine_edition, CAST(SERVERPROPERTY('Edition') AS varchar(40)) AS edition, CAST(DATABASEPROPERTYEX('quitanda', 'ServiceObjective') AS varchar(20)) AS service_objective"
engine_edition|edition|service_objective
--------------|-------|-----------------
3|Enterprise Developer Edition (64-bit)|NULL

(1 rows affected)
```

**3 is the full engine, here in the Developer edition that SQL Server ships free for development and
testing.** Microsoft's documentation lists the other answers, and two of them are this lesson and the
next: **5 is Azure SQL Database, and 8 is Azure SQL Managed Instance**. That is not run here, and
there is no transcript of it; it is the one-line check that tells a program, or you, which of the
three it has been connected to. `ServiceObjective` is the same kind of line from the other side. On
Azure it names what the database was bought as, `S0` or `GP_Gen5_2` or one of the names in the next
section. Here it is `NULL`, because nothing was bought: the purchasing model is the control plane,
and no emulator answers it.

## The part that is yours

Quitanda's support screen asks for one customer's orders, every time a customer calls:

```
ana@laptop:~/azure$ sql -d quitanda -Q "SET STATISTICS IO ON; $Q" | cut -d, -f1-2
orders|cents
------|-----
15|256935

(1 rows affected)
Table 'orders'. Scan count 1, logical reads 337
ana@laptop:~/azure$ printf 'SET SHOWPLAN_TEXT ON\nGO\n%s\nGO\n' "$Q" | sql -d quitanda | grep -oE '(Clustered )?Index (Scan|Seek)'
Clustered Index Scan
```

**Fifteen orders, and 337 pages read to find them.** `STATISTICS IO` counts the 8 KB pages the engine
touched, and `SHOWPLAN_TEXT`, filtered here to the one operator that matters, says why: a
`Clustered Index Scan` reads the whole table, because nothing tells the engine where customer 17's
rows are. The index that does:

```
ana@laptop:~/azure$ sql -d quitanda -Q "CREATE INDEX ix_orders_customer ON dbo.orders (customer_id) INCLUDE (total_cents)"
ana@laptop:~/azure$ sql -d quitanda -Q "SET STATISTICS IO ON; $Q" | cut -d, -f1-2
orders|cents
------|-----
15|256935

(1 rows affected)
Table 'orders'. Scan count 1, logical reads 2
ana@laptop:~/azure$ printf 'SET SHOWPLAN_TEXT ON\nGO\n%s\nGO\n' "$Q" | sql -d quitanda | grep -oE '(Clustered )?Index (Scan|Seek)'
Index Seek
```

**From 337 pages to 2, by one statement that costs nothing to run again on Azure.** That is the work
the previous section left on your side, and it is where the next section's bill comes from. On Azure
SQL Database the database is bought as a fixed amount of compute and IO, and a query that reads 337
pages where it needed 2 spends that amount more than a hundred and sixty times faster. Buying a bigger tier makes the scan
quicker. It does not make it necessary, and it is billed every hour whether the index is missing or
not.

SQL Server holds about 2 GB of memory while it runs, so stop it with lesson 1's
`docker compose --profile '*' down` when you are done; the next lesson builds its databases again.
