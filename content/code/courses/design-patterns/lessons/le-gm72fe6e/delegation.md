**Delegation is composition put to work: an object holds another and forwards calls to it, adding
what it needs on the way.** The counting shelf from the first section, written this way, holds a
`Shelf` instead of being one. It survives both versions of `shelf.py`, for a reason that is worth
seeing precisely.

People sometimes describe delegation as inheritance done by hand, the same thing with more typing.
The typing is real. The sameness is not: a held object calls its own methods on itself, never on
the object holding it, so the self-call that broke `CountingShelf` cannot reach the wrapper at all.


Your `shelf.py` is the second version, the one that extends the list. Run it:

```
ana@laptop:~/patterns/composition$ python3 counted.py
on the shelf: 4
counted:      4

```

Now put the first `shelf.py` back, the one whose `add_all` loops over `add`, and run it again:

```
ana@laptop:~/patterns/composition$ python3 counted.py
on the shelf: 4
counted:      4
is a Shelf?   False
```

Four both times. **The wrapper depends on what `Shelf`'s methods do, never on how they do it**,
which is exactly the dependency the author of `Shelf` can see and keep.

## What delegation costs

The last line of each run is the first cost. A `CountedShelf` is not a `Shelf`, so code that checks
`isinstance(x, Shelf)`, or a Java method declared to take a `Shelf`, refuses it. The cure is to
depend on a description of the methods instead of a class: a `Protocol` in Python, an `interface`
in Java, Go and TypeScript, which is how lesson 1's `Channel` worked. Lesson 4 makes that a
principle.

The second cost is the forwarding. A wrapper around a class with twenty methods needs twenty
one-line methods, nineteen of which add nothing. Python offers a shortcut, and it is a trap:

```python
class CountedShelf:
    def __getattr__(self, name):
        return getattr(self._shelf, name)
```

`__getattr__` is called for any attribute the wrapper does not have, so every method of `Shelf` is
forwarded without being written. (Not `len()`, as it happens: Python looks special methods up on
the class and never through `__getattr__`, so `__len__` still has to be written out.) It works
today. The day `Shelf` gains an `add_many`, the wrapper
forwards it silently and uncounted, and the report is wrong again, with nothing in `counted.py`
having changed. **Forwarding everything automatically brings back the coupling that delegation
was meant to remove**, one new method at a time. Write the forwarding out, and let a new method of
the inner object be something the wrapper decides to offer.

## The same idea in the other three languages

| language | how a wrapper forwards | what happens when the inner type gains a method |
|---|---|---|
| Python | one method per forwarded call, or `__getattr__` | written out: nothing; `__getattr__`: forwarded silently |
| Java | one method per call, often generated by the IDE | nothing until somebody writes the method |
| Go | embed the struct: `type CountedShelf struct { *Shelf; added int }` | promoted automatically, like `__getattr__` |
| TypeScript | one method per call | nothing until somebody writes the method |

Go's embedding deserves a sentence of its own. It promotes the inner type's methods onto the outer
one, so it saves the typing, and the inner `AddAll` still calls the inner `Add`, so the double count
cannot happen. It shares `__getattr__`'s weakness, though: a method added to `Shelf` appears on
`CountedShelf` without anybody choosing it. Kotlin has a keyword for the same idea, `class
CountedShelf(s: Shelf) : Shelf by s`, which forwards everything and lets you override what you
change.

## Delegation is not only for wrappers

`CountedShelf` keeps the interface of the thing it holds, which makes it a wrapper; lesson 6 calls
that shape a decorator. More often an object delegates to parts with interfaces of their own: a
loan asks its fine rule for a number, a member asks its channel to deliver. The mechanism is the
same, and it is what the next section uses to change a loan's behaviour while the program runs.
