title: "Snapshots: a saved fold"

**A snapshot is the folded state of a stream saved at some version, so that the next rebuild loads it
and folds only the events that came after.** It is a cache. The events stay in the store, untouched,
and a snapshot can be deleted at any moment without losing anything; the next rebuild just takes
longer.

The misconception to drop is that a snapshot replaces history, so that old events can be archived
once one exists. They cannot. Projections still read from position 0, `evolve` may be fixed and the
snapshot found wrong, and the events are the record somebody may have to audit. A snapshot speeds up
one question, "what is the state now?", and nothing else.

## When to take one

**Not before the fold is measurably slow.** A stream of a few hundred events folds in a fraction of
a millisecond, and a snapshot adds a table, a format and a way to be wrong. The usual policy, once
it is needed, is a snapshot every N events, written after a command when the stream crosses the next
multiple, or by a background job. Many systems never need one, because they choose streams that stay
short: a stream per loan instead of a stream per member ends when the book comes back.

## The way a snapshot goes wrong

**A snapshot freezes the output of today's `evolve`.** Suppose a bug in `evolve` forgot that a
correction lowers the fine. Every snapshot taken while the bug lived carries the wrong balance, and
fixing `evolve` does not fix them, because the rebuild starts from the stored state and folds only
what came after. The remedy is to version snapshots with the code that made them, and to throw them
all away when `evolve` changes: the next rebuild folds from version 1 under the fixed code and saves
a correct one. **Snapshots are disposable by design, and a system that cannot delete them all safely
has turned a cache into a second source of truth.**

The same freezing applies to the snapshot's format. `Member` here is saved as JSON with three keys;
add a field to the dataclass and old snapshots lack it. Deleting them is the simplest migration
there is, which is one more reason to keep them disposable. Events have no such escape, and the last
section of the lesson is about what to do instead.
