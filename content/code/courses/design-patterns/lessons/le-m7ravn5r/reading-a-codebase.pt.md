**No código que outra pessoa escreveu, os padrões raramente trazem o nome.** Uma classe chamada
`CatalogueDecorator` é a exceção. Muito mais vezes o padrão está lá só no formato: uma classe que
guarda um objeto do mesmo tipo que ela finge ser, um dicionário de strings para construtores, um
método que converte um vocabulário em outro. Reconhecer esses formatos é como você lê uma base de
código mais depressa, e é também como você percebe quando um padrão foi aplicado sem a força que o
justificaria.

Os nomes numa base de código são um mau guia nos dois sentidos. Um `Manager` ou um `Helper` pode
esconder três padrões, e uma classe chamada `Factory` às vezes não constrói nada. Leia primeiro a
estrutura e depois os nomes.

## Um arquivo com três padrões e nenhum rótulo

Este programa é o tipo de coisa que se encontra num repositório de verdade. Leia-o antes das notas
e tente dar nome ao que vê.

Duas consultas foram contadas na estante, e quem chamou nunca soube que um catálogo estava
embrulhado e o outro traduzido. Essa invisibilidade é para o que os padrões servem, e é também por
isso que você precisa ler os construtores para achá-los.

## As perguntas que distinguem os formatos

Vários padrões se parecem de longe, porque todos são composição mais polimorfismo, como a lição 1
disse. Duas perguntas separam a maioria deles: **o que a classe guarda, e é a mesma interface que a
classe oferece?**


| o que você vê | o que costuma ser |
|---|---|
| guarda um objeto da própria interface e repassa para ele, acrescentando algo | decorator, ou proxy se o que acrescenta é controle: cache, acesso, preguiça |
| guarda um objeto de outra interface e oferece a sua | adapter |
| guarda um de uma família de objetos intercambiáveis e delega um passo a ele | strategy |
| guarda uma lista de chamáveis e chama todos quando algo acontece | observer |
| um dicionário ou um `match` de nomes para classes ou construtores | factory |
| uma classe cujos métodos chamam cada um vários outros objetos em ordem | facade |
| um objeto com `execute` ou `__call__` e os dados para fazer aquilo depois | command |

A tabela é uma ajuda de leitura. Um proxy e um decorator têm a mesma estrutura e diferem só na
intenção, e nenhuma quantidade de olhar para o código resolve a intenção; a mensagem do commit ou a
pessoa que o escreveu talvez resolva.

## Quando o formato não tem força por trás

Reconhecer um padrão é metade da leitura. A outra metade é perguntar a que força ele responde ali,
com o teste da frase da seção 02. `CountingCatalogue` responde a *precisamos saber com que
frequência a estante é consultada, sem mudar a estante*: uma força real, atendida barato. Se o mesmo
arquivo tivesse um `CatalogueFactoryProvider` que devolvesse a factory que devolve
`ShelfCatalogue`, você procuraria a segunda implementação e o teste que a usa, e se nenhum dos dois
existisse teria achado a generalidade especulativa da seção anterior.

Em Java e C#, os frameworks acrescentam formatos próprios: anotações que fazem de uma classe um
singleton, um proxy gerado em tempo de execução em volta de um serviço. Esses padrões são reais e
invisíveis no código-fonte, e a documentação do framework é o único lugar onde estão escritos. Código
Go mostra menos padrões com nome, porque interfaces pequenas e funções como valores reduzem a
maioria deles a poucas linhas.
