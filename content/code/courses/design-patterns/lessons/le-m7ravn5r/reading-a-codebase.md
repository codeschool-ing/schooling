**In code somebody else wrote, patterns rarely carry their names.** A class called
`CatalogueDecorator` is the exception. Far more often the pattern is there in shape only: a class
that holds an object of the same type it pretends to be, a dictionary from strings to
constructors, a method that converts one vocabulary into another. Recognising those shapes is how
you read a codebase faster, and it is also how you notice when a pattern was applied without the
force that would justify it.

The names in a codebase are a poor guide in both directions. A `Manager` or a `Helper` can hide
three patterns, and a class called `Factory` sometimes builds nothing. Read the structure first and
the names second.

## The questions that tell shapes apart

Several patterns look alike from a distance, because they are all composition plus polymorphism,
as lesson 1 said. Two questions separate most of them: **what does the class hold, and is that the
same interface the class offers?**

| what you see | what it usually is |
|---|---|
| holds one object of its own interface and forwards to it, adding something | decorator, or a proxy if what it adds is control: caching, access, laziness |
| holds an object of a different interface and offers yours | adapter |
| holds one of a family of interchangeable objects and delegates one step to it | strategy |
| holds a list of callables and calls them all when something happens | observer |
| a dictionary or `match` from names to classes or constructors | factory |
| a class whose methods each call several other objects in order | facade |
| an object with an `execute` or `__call__` and the data to do it later | command |

The table is a reading aid. A proxy and a decorator have the same structure and differ only in
intent, and no amount of staring at the code settles intent; the commit message or the person who
wrote it might.

## When the shape has no force behind it

Recognising a pattern is half the reading. The other half is asking which force it answers here,
with the sentence test of section 02. `CountingCatalogue` answers *we need to know how often the
shelf is consulted, without changing the shelf*: a real force, cheaply met. If the same file had a
`CatalogueFactoryProvider` that returned the factory that returned `ShelfCatalogue`, you would look
for the second implementation and the test that uses it, and if neither existed you would have found
the previous section's speculative generality.

In Java and C#, frameworks add shapes of their own: annotations that make a class a singleton, a
proxy generated at run time around a service. Those patterns are real and invisible in the source,
and the framework's documentation is the only place they are written down. Go code shows fewer
named patterns, because small interfaces and functions as values make most of them a few lines.
