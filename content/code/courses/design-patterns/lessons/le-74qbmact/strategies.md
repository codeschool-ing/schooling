---
title: "Four answers to a full queue, with numbers"
version: 1
---

**When the producer will not wait and the queue is full, there are four things to do with the next
value: keep it anyway, throw it away, throw away the older ones instead, or stop the producer.**
They are called buffer, drop, latest and block. The libraries offer all four, often as one line
each, and which one fits depends on the data, whichever library you use.

The mistake is to treat the choice as a technical default and pick whichever one loses nothing.
Losing nothing has a cost too, and the program below puts numbers on all four so that the costs can
be compared. Twelve scans arrive, one a tick; the catalogue handles one every third tick; the queue
holds two. The clock is simulated, so the counts are the same on every run.

## Reading the four rows

*buffer* handled all twelve and lost none, which is what people want from it. Its backlog reached
nine, and the queue was supposed to hold two: with no bound it simply grew. Scan 12 arrived at tick
12 and was handled at tick 36, so **the newest information was 24 ticks old by the time anyone saw
it**. This is `flood.py` from the last section on a smaller scale, and it is fine only when the
burst is known to end.

*drop* handled five and lost seven. It kept the early scans and threw away new ones while the queue
was full, so the last scan of the morning, number 12, is among the lost. If the scans were readings
of a thermometer, that would be a poor trade: the latest temperature is the one that matters.

*latest* handled four, the fewest, and every one of them was the newest value at the time it was
handled: 3, 6, 9 and 12. The catalogue never worked on stale data and finished at tick 12, the
same moment the scanner did. It lost eight scans, the most of any strategy, and for some data that
is exactly right.

*block* handled all twelve, lost none and never held more than two. The price moved to the
producer: the scanner finished at tick 31 instead of 12, because it spent most of the morning
waiting. The catalogue finished at tick 36 either way, so block and buffer did the same useful work;
block simply refused to hold the difference in memory.

## Choosing by what the value means

The useful question is: if this value is lost, what is wrong afterwards?

| the data | lose one and… | strategy |
|---|---|---|
| loans being returned | a book stays on loan for ever | block, or buffer with a bound and an alarm |
| copies of *Iracema* on the shelf, sent on every change | nothing: the next value replaces it | latest |
| page views counted for a weekly report | the count is a little low | drop, if it is measured |
| a file being imported | rows are missing | block: a file can wait |

A return is a fact: losing one is a bug a member will find. A shelf count is a state: only the
present one matters, so keeping the latest is not a loss of anything anybody needs. Analytics can
often survive drops if somebody counts them, because a report that is two per cent low and says so
is still a report. And block suits every producer that is a program rather than the world: a file
reader, a batch import, a query.

**Whatever you choose, count what it loses.** `strategies.py` reports `lost` for a reason. A drop
strategy that drops silently is the shape of failure that looks like quiet: the dashboard shows
fewer returns and nobody can tell a slow day from an overflowing queue. A counter, a log line or a
metric turns the loss into something a person can see and decide about.

## Where each one lives

The four appear under these names in the libraries of section 08: Reactor and RxJava have
`onBackpressureBuffer`, `onBackpressureDrop` and `onBackpressureLatest`, and demand-based blocking
is the default between Reactive Streams stages. Python's `queue.Queue(maxsize=n)` blocks, and its
`put_nowait` raises `queue.Full` instead, which is how you build drop or latest by hand. Go's
buffered channel blocks, and a `select` with a `default` case drops. Over a network, TCP's flow
control is block: a receiver whose buffer is full advertises a window of zero, and the sender stops
sending until it opens.
