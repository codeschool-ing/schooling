**An entity is an object defined by its identity rather than by its attributes: it stays the same
thing while everything about it changes.** A member of the library changes her phone number, her
address and even her name, and she is still the member who has three books out. What makes her the
same is an identifier that the library gave her and never changes. Lesson 11 drew the strategic
lines; this lesson fills one context, lending, with the tactical patterns Evans described, starting
with this one.

The wrong idea is that two objects are the same when their fields are equal. For people, copies and
loans that is false in both directions. Two members called Ana Souza, with the same phone because
they share a house, are two members. One member whose every field has been edited is one member.
Code that compares entities by their fields will one day merge two people or split one, and
neither mistake raises an error.

attributes are only what is true about the member today.**

## Where the id comes from

An entity needs its id from the moment it exists, which rules out the convenient answer of letting
the database assign one on insert: until the row is written, the object has no identity and cannot
be compared, put in a set or referred to from another aggregate. Three common choices:

| source | example | trade |
|---|---|---|
| the domain already has one | a library card number, an ISBN, a tax number | meaningful, but it belongs to somebody else and can be wrong or change |
| generated by the application | `uuid.uuid4()`, or a short code like `m-014` | available at once, meaningless, never changes |
| a sequence from the database | `INSERT ... RETURNING id` | short, but the object has no id until it is saved |

The library uses its own card numbers, `m-` followed by digits, issued when a member joins. A card
number is shown to the member and typed at the desk, so it has to be short; it is safe as an
identity because the library issues it and never reissues it.

## In your language

Python compares objects by identity in memory unless a class says otherwise, which is why
`entities.py` writes `__eq__` and `__hash__`. The other three languages have the same choice to
make, in their own syntax:

| language | equality by id |
|---|---|
| Java | override `equals` and `hashCode` to use the id; a `record` would compare every field, which is right for a value object and wrong here |
| Go | compare `a.ID == b.ID` explicitly; `==` on two structs compares every field, and on two pointers compares addresses |
| TypeScript | compare `a.id === b.id`; `===` on two objects compares references, and there is no operator to override |

Java's `record` and Go's struct equality are the defaults that compare fields, and both are exactly
what the next section wants for a different kind of object.
