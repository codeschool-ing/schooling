Spans are created with `tracer.start_as_current_span(name)` as a `with` block. The span starts when
the block is entered and ends when it is left, and while it is open it is the **current span**, so
any span started inside it becomes its child without being told. That is why the five spans of a
sale nest under the request's span with no ids passed by hand.

The image needs the OpenTelemetry SDK and its OTLP exporter, pinned like the rest:

```
# requirements.txt
psycopg[binary]==3.2.10
prometheus-client==0.26.0
opentelemetry-sdk==1.45.1
opentelemetry-exporter-otlp-proto-http==1.45.1
```

And the Dockerfile copies the two new programs into the image, so that one image serves both
services:

```dockerfile
# Dockerfile
FROM python:3.12.15-slim
WORKDIR /srv
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app.py payments.py telemetry.py .
CMD ["python", "app.py"]
```

## Manual or automatic

Every span here is created by hand, which is the clearest way to see what a span is. OpenTelemetry
also has **instrumentation libraries** that create the common ones for you: one for psycopg makes a
span per query, one for the HTTP server a span per request, one for `urllib` a span per call with the
header injected. A real service usually uses those for the plumbing and adds spans by hand only for
its own steps, like `sign` here. Both produce the same kind of span, and Jaeger cannot tell which
made which.
