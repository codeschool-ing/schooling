venda agora chama o payments. Aqui está o `app.py` inteiro desta aula em diante; as métricas e os

Os spans são criados com `tracer.start_as_current_span(name)` como um bloco `with`. O span começa
quando o bloco é aberto e termina quando ele é deixado, e enquanto está aberto ele é o **span atual**,
então qualquer span começado dentro dele vira filho dele sem que ninguém diga. É por isso que os cinco
spans de uma venda se aninham sob o span do pedido sem nenhum id passado à mão.

A imagem precisa do SDK do OpenTelemetry e do exportador OTLP dele, fixados como o resto:

```
# requirements.txt
psycopg[binary]==3.2.10
prometheus-client==0.26.0
opentelemetry-sdk==1.45.1
opentelemetry-exporter-otlp-proto-http==1.45.1
```

E o Dockerfile copia os dois programas novos para a imagem, para que uma imagem sirva os dois
serviços:

```dockerfile
# Dockerfile
FROM python:3.12.15-slim
WORKDIR /srv
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app.py payments.py telemetry.py .
CMD ["python", "app.py"]
```

## Manual ou automático

Todo span aqui é criado à mão, que é o jeito mais claro de ver o que é um span. O OpenTelemetry
também tem **bibliotecas de instrumentação** que criam os comuns para você: uma para o psycopg faz um
span por consulta, uma para o servidor HTTP um span por pedido, uma para o `urllib` um span por
chamada com o cabeçalho injetado. Um serviço real costuma usar essas para o encanamento e acrescentar
spans à mão só para os próprios passos, como o `sign` aqui. As duas produzem o mesmo tipo de span, e o
Jaeger não sabe dizer qual fez qual.
