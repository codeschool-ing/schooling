---
title: Start from the questions, not the entities
version: 1
---

Relational design starts from the **entities**: shows, venues, tickets, buyers. Each gets a table,
the relations between them get keys, the data is normalised so each fact lives in one place, and
the queries are written afterwards. That works because a join can assemble any answer from the
pieces.

Designing for a NoSQL database runs the other way. **You start from the access patterns**, the
questions the program will ask, with how often and how fast, and shape the data so that each
common question is answered by reading one thing in one place. Facts are copied wherever a
question needs them, which is **denormalisation**, and the copies are kept in step by the program.

For the box office, the list looks like this:

| access pattern | how often | what it needs |
|---|---|---|
| hold a seat for ten minutes while the buyer pays | every purchase, bursts at a ticket drop | one key, set only if absent, that expires |
| show a show's page: name, venue, date, artists, prices | thousands per sale | everything about one show, in one read |
| record each ticket scanned at the door, by show and time | thousands a minute on a show night | fast appends, read back by show in time order |
| "people who went to this show also went to…" | on every show page | walk from a show to its buyers to their other shows |
| tickets sold per minute, for the last month | a dashboard, refreshed constantly | numbers by time, older ones in coarser buckets |

Five patterns, five different shapes, and **no single layout serves all of them well**. That is the
point of the families, and the rest of the lesson takes one row each.

The habit that matters is the one this table forces: **writing the questions down before choosing
the database**. A team that picks a NoSQL database first and discovers its access patterns later
discovers them as queries the database cannot answer, and the answer then is usually a second
database, which section 10 is about.
