k6 is a load-testing tool written in Go that takes its tests as JavaScript. It runs from its own
image, so there is nothing to install: every run in this lesson is `docker run` on
`grafana/k6:2.3.0`, with `--network host` so that `localhost:8080` is the lab machine's port, the
script on standard input, and `-q` with `--log-output=none` to keep the output to the summary.

A k6 test is a **scenario** that calls a function. This one uses the `constant-arrival-rate`
executor, the open model: it starts the function `RATE` times a second whatever happens, with as
many virtual users (*VUs*) as it needs to keep that rate, up to `maxVUs`. Save it as `sale.js`:

```javascript
// sale.js
import http from "k6/http";
import { Counter } from "k6/metrics";

const RATE = Number(__ENV.RATE || 50);
const DURATION = __ENV.DURATION || "20s";
const sold = new Counter("sold");
const refused = new Counter("refused");
const failed = new Counter("failed");

export const options = {
  scenarios: {
    sales: {
      executor: "constant-arrival-rate",
      rate: RATE,
      timeUnit: "1s",
      duration: DURATION,
      preAllocatedVUs: 100,
      maxVUs: 1000,
    },
  },
  summaryTrendStats: ["med", "p(95)", "p(99)", "max"],
};

export default function () {
  const event = Math.floor(Math.random() * 50) + 1;
  const answer = http.post(`http://localhost:8080/events/${event}/tickets`, null,
    { headers: { "X-Buyer": `buyer-${__VU}-${__ITER}` } });
  if (answer.status === 201) sold.add(1);
  else if (answer.status === 429 || answer.status === 503) refused.add(1);
  else failed.add(1);
}

export function handleSummary(data) {
  const m = data.metrics;
  const d = m.http_req_duration.values;
  const count = (name) => (m[name] ? m[name].values.count : 0);
  const ms = (v) => `${v.toFixed(1)} ms`;
  return {
    stdout: [
      `asked     ${RATE} a second for ${DURATION}`,
      `answered  ${m.http_reqs.values.count} = ${m.http_reqs.values.rate.toFixed(1)} a second`,
      `latency   p50 ${ms(d.med)}  p95 ${ms(d["p(95)"])}  p99 ${ms(d["p(99)"])}  max ${ms(d.max)}`,
      `sold ${count("sold")}  refused ${count("refused")}  failed ${count("failed")}` +
        `  never sent ${count("dropped_iterations")}`,
    ].join("\n") + "\n",
  };
}
```

- **The scenario**: `RATE` sales a second, 50 unless the environment says otherwise, for `DURATION`.
  100 virtual users are ready at the start, and more are created if the answers are slow.
- **The function** buys a ticket for a random show out of 50, as a different buyer every time, so
  lesson 9's per-buyer limit never applies. It counts every answer as sold, refused (`429` or `503`)
  or failed (anything else, including no answer at all).
- **`handleSummary`** replaces k6's own end-of-test report, which runs to forty lines, with four.
  *Never sent* is k6's `dropped_iterations`: arrivals it could not start because every virtual user
  was busy. It matters in section 07.

Fifty sales a second, for twenty seconds:

```
ana@lab:~/tickets$ docker run --rm -i --network host grafana/k6:2.3.0 run -q --log-output=none - < sale.js
asked     50 a second for 20s
answered  1001 = 50.0 a second
latency   p50 38.4 ms  p95 49.0 ms  p99 383.3 ms  max 620.1 ms
sold 1001  refused 0  failed 0  never sent 0
```

**1,001 sales in twenty seconds, 50.0 a second**, exactly what was asked, because the box office
kept up. The median sale took 38 ms. The 99th percentile, 383 ms, says that about ten sales were far
slower than the rest. This was the first load since the stack started, and a test that starts cold
measures the warm-up along with everything else: connections being opened, caches being filled.
Tests usually run a short warm-up first, or report the first seconds apart. A rate that is kept exactly is the sign that the system had capacity to spare;
when it cannot be kept, the gap between *asked* and *answered* is the first number to read.
