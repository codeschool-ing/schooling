O k6 é uma ferramenta de teste de carga escrita em Go que recebe os testes em JavaScript. Ele roda da
própria imagem, então não há nada para instalar: toda execução desta aula é um `docker run` em
`grafana/k6:2.3.0`, com `--network host` para que `localhost:8080` seja a porta da máquina do
laboratório, o script na entrada padrão, e `-q` com `--log-output=none` para deixar a saída só no
resumo.

Um teste do k6 é um **cenário** que chama uma função. Este usa o executor `constant-arrival-rate`, o
modelo aberto: ele começa a função `RATE` vezes por segundo aconteça o que acontecer, com quantos
usuários virtuais (*VUs*) precisar para manter essa taxa, até `maxVUs`. Salve-o como `sale.js`:

```javascript
// sale.js
import http from "k6/http";
import { Counter } from "k6/metrics";

const RATE = Number(__ENV.RATE || 50);
const DURATION = __ENV.DURATION || "20s";
const sold = new Counter("sold");
const refused = new Counter("refused");
const failed = new Counter("failed");

export const options = {
  scenarios: {
    sales: {
      executor: "constant-arrival-rate",
      rate: RATE,
      timeUnit: "1s",
      duration: DURATION,
      preAllocatedVUs: 100,
      maxVUs: 1000,
    },
  },
  summaryTrendStats: ["med", "p(95)", "p(99)", "max"],
};

export default function () {
  const event = Math.floor(Math.random() * 50) + 1;
  const answer = http.post(`http://localhost:8080/events/${event}/tickets`, null,
    { headers: { "X-Buyer": `buyer-${__VU}-${__ITER}` } });
  if (answer.status === 201) sold.add(1);
  else if (answer.status === 429 || answer.status === 503) refused.add(1);
  else failed.add(1);
}

export function handleSummary(data) {
  const m = data.metrics;
  const d = m.http_req_duration.values;
  const count = (name) => (m[name] ? m[name].values.count : 0);
  const ms = (v) => `${v.toFixed(1)} ms`;
  return {
    stdout: [
      `asked     ${RATE} a second for ${DURATION}`,
      `answered  ${m.http_reqs.values.count} = ${m.http_reqs.values.rate.toFixed(1)} a second`,
      `latency   p50 ${ms(d.med)}  p95 ${ms(d["p(95)"])}  p99 ${ms(d["p(99)"])}  max ${ms(d.max)}`,
      `sold ${count("sold")}  refused ${count("refused")}  failed ${count("failed")}` +
        `  never sent ${count("dropped_iterations")}`,
    ].join("\n") + "\n",
  };
}
```

- **O cenário**: `RATE` vendas por segundo, 50 a não ser que o ambiente diga outra coisa, por
  `DURATION`. 100 usuários virtuais ficam prontos no começo, e mais são criados se as respostas
  forem lentas.
- **A função** compra um ingresso para um show aleatório entre 50, como um comprador diferente a cada
  vez, para que o limite por comprador da aula 9 nunca se aplique. Ela conta cada resposta como
  vendida, recusada (`429` ou `503`) ou falha (qualquer outra coisa, inclusive nenhuma resposta).
- **O `handleSummary`** troca o relatório de fim de teste do próprio k6, que tem quarenta linhas, por
  quatro. *Never sent* é o `dropped_iterations` do k6: chegadas que ele não conseguiu começar porque
  todo usuário virtual estava ocupado. Ele importa na seção 07.

Cinquenta vendas por segundo, por vinte segundos:

```
ana@lab:~/tickets$ docker run --rm -i --network host grafana/k6:2.3.0 run -q --log-output=none - < sale.js
asked     50 a second for 20s
answered  1001 = 50.0 a second
latency   p50 38.4 ms  p95 49.0 ms  p99 383.3 ms  max 620.1 ms
sold 1001  refused 0  failed 0  never sent 0
```

**1.001 vendas em vinte segundos, 50,0 por segundo**, exatamente o que foi pedido, porque a
bilheteria acompanhou. A venda mediana levou 38 ms. O percentil 99, 383 ms, diz que umas dez vendas
foram bem mais lentas que o resto. Esta foi a primeira carga desde que a pilha subiu, e um teste que
começa frio mede o aquecimento junto com todo o resto: conexões sendo abertas, caches sendo
preenchidos. Testes costumam rodar um aquecimento curto antes, ou relatar os primeiros segundos à
parte. Uma taxa mantida exatamente é o sinal de que o sistema tinha capacidade sobrando; quando ela
não pode ser mantida, a diferença entre *asked* e *answered* é o primeiro número a ler.
