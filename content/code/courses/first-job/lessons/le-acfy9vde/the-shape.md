A live exercise lasts twenty to sixty minutes, and the interviewer is looking for **how you think, not
only whether you finish**. They can only see the thinking you say out loud, so the exercise has a shape
that makes it visible:

1. **Repeat the problem back** in your own words. It catches misunderstandings in the first minute, when
   they are cheap.
2. **Ask one question** about what is unclear: the input, the edge, what counts as done. Interviewers
   often leave something out on purpose to see whether you ask.
3. **Say the plan** before doing it: *I'll read the file line by line, count each status, and print the
   counts.* Now the interviewer can follow, and can stop you if the plan is wrong.
4. Do the simplest version that works. Not the elegant one. A correct, plain answer is worth more than
   an elegant one that is half written when time runs out.
5. **Test it aloud** with one normal case and one edge case.
6. **Improve it, if there is time**, and say what you would do with more.

What the exercise looks like depends on the role:

::: track it-support networks-infra
**In support and infrastructure** the live exercise is usually practical rather than code: a lab machine
that cannot reach the network, a user account that cannot log in, or a whiteboard with an office to connect.
The same six steps apply. Repeating the problem is *so the user can see the intranet but not the internet*;
the question is *does this happen for everybody, or one machine?*; the plan is the method from the
tech-support course, said out loud before you touch anything.
:::

::: track *
**In development and data roles** the live exercise is usually a small function, a query or a change to
existing code in a shared editor, and the language is often yours to choose. Choose the one you are fastest
in, not the one on the advert, unless they ask for a specific one.
:::
