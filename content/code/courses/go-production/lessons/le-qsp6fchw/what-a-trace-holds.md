title: What a trace holds
version: 1

**A trace file is a list of events, and every event names three things: a thread, a processor and
a goroutine.** Those are the scheduler's three parts, which `go-concurrency` lesson 2 described:
`M` is an operating-system thread, `G` is a goroutine, and `P` is a processor in Go's sense, the
permission to run Go code. There are `GOMAXPROCS` of them, four on the lab machine, and a goroutine
runs only while some thread holds a `P` for it. Most of what a trace says is a goroutine or a `P`
changing state, with the time to the nanosecond.

`go tool trace` normally serves the file to a browser. It also has a debug flag, `-d=parsed`, that
prints every event as a line of text, and that is the quickest way to see what is inside. **The
format is for debugging the tool and nobody promises to keep it**, but it is plain text and `grep`
reads it. The four-worker trace from section 02, as lines, and the three of them `pcount` wrote
itself:

```
ana@vm:~/trace-hits$ go tool trace -d=parsed w4.trace | wc -l
8496346
```

```
ana@vm:~/trace-hits$ go tool trace -d=parsed w4.trace | grep -E 'Task(Begin|End)|Log '
M=11293 P=0 G=1 TaskBegin Time=847368444032 ID=1 Parent=18446744073709551615 Type="count"
M=11296 P=0 G=1 Log Time=848326411968 Task=1 Category="lines" Message="3000000"
M=11296 P=0 G=1 TaskEnd Time=848326412544 ID=1 Parent=18446744073709551615 Type="count"
```

The three are the annotations `pcount` added itself: the `count` task beginning, the message
`trace.Logf` left, and the task ending, all on goroutine 1 and each on whichever thread was running
it at that moment. The two timestamps are 957,968,512 nanoseconds apart, which is the 958ms the
program printed. `Parent=18446744073709551615` is the largest 64-bit number, and it means the task
has no parent. The file of 5,257,509 bytes prints as **8,496,346 lines**, because most events are
a few bytes in the binary format and a stack takes several lines in the dump.

## What kinds of event

Counted by kind, the fourth word of each event line:

```
ana@vm:~/trace-hits$ go tool trace -d=parsed w4.trace | awk '/^M=/ {print $4}' | sort | uniq -c | sort -rn
 960547 StateTransition
  54853 Metric
  16378 RangeEnd
  16378 RangeBegin
   3002 RegionEnd
   3002 RegionBegin
    237 Label
      2 Sync
      1 TaskEnd
      1 TaskBegin
      1 Log
```

| kind | what it records |
|---|---|
| `StateTransition` | a goroutine or a `P` moving between states, such as `Runnable->Running` |
| `Metric` | a runtime figure at a moment: the heap size, the heap goal, `GOMAXPROCS` |
| `RangeBegin`, `RangeEnd` | a stretch of runtime work, almost all of it the garbage collector's |
| `RegionBegin`, `RegionEnd`, `TaskBegin`, `TaskEnd`, `Log` | your annotations, from `runtime/trace` |
| `Label` | a name attached to a goroutine, such as `GC (dedicated)` on a collector's worker |
| `Sync` | a point where the reader has met every thread and goroutine so far, with a clock reading |

**Almost everything is a state transition.** A goroutine is `Running` on a `P`, `Runnable` when it
could run and has no `P`, `Waiting` when it is blocked on something, or in a `Syscall`. A `P` is
`Running` or `Idle`. Each change of state is one event, so 960,547 of them in under a second is the
scheduler's whole day, written down.

## Why goroutines stopped

A goroutine that goes from `Running` to `Waiting` carries a reason, and the reasons are the first
thing worth counting:

```
ana@vm:~/trace-hits$ go tool trace -d=parsed w4.trace | grep -o 'Running->Waiting Reason="[^"]*"' | sort | uniq -c | sort -rn
   1045 Running->Waiting Reason="chan receive"
    454 Running->Waiting Reason="sync"
    404 Running->Waiting Reason="system goroutine wait"
    396 Running->Waiting Reason="chan send"
    197 Running->Waiting Reason="GC mark assist wait for work"
    119 Running->Waiting Reason="preempted"
     94 Running->Waiting Reason="GC background sweeper wait"
     41 Running->Waiting Reason="sleep"
```

Each one names a line of `pcount` or a part of the runtime. **`chan receive` is a worker's `range
batches` finding the channel empty**: 1,045 times, a worker finished a batch before the reader had
the next one ready. `chan send` is the opposite, the reader finding every slot full because the
workers were behind, 396 times. `sync` is a wait on a lock or a semaphore; `pcount` with four
workers takes no lock of its own, so section 04 has to find out whose these are. The `GC` reasons
and `system goroutine wait` belong to the runtime's own goroutines.

The collector deserves a count of its own, because the reader turns each line into a new string
and every one of them is garbage a moment later:

```
ana@vm:~/trace-hits$ go tool trace -d=parsed w4.trace | grep -c 'RangeBegin.*GC concurrent mark phase'
94
```

**Ninety-four collections in under a second.** A CPU profile shows that cost as time in runtime
functions; the trace shows when each collection happened and what the program's goroutines were
doing meanwhile. Lesson 19 is the collector itself.

## Your own events

`pcount` made one task, 3,001 regions and one message:

```
ana@vm:~/trace-hits$ go tool trace -d=parsed w4.trace | grep -o 'RegionBegin .*' | grep -o 'Type=.*' | sort | uniq -c
      1 Type="merge"
   3001 Type="parse"
```

Three million lines in batches of a thousand is 3,000 batches, and **the 3,001st is the empty one**
the reader sends after its loop, because three million divides exactly. The region shows it
honestly; nothing else in the program would. The three kinds of annotation differ in scope:

| | call | covers |
|---|---|---|
| region | `trace.WithRegion(ctx, "parse", fn)`, or `trace.StartRegion` and `End` | a stretch of one goroutine; it must end on the goroutine that began it |
| task | `ctx, task := trace.NewTask(ctx, "count")` and `task.End()` | one logical operation, across every goroutine that uses its context |
| log | `trace.Log(ctx, category, message)`, `trace.Logf` | one moment, with a category you can filter on |

The type names of regions should be few, `go doc runtime/trace.WithRegion` says, because they are
used to group them; a request id belongs in a `Log`, not in a region's name.

## The browser view

`go tool trace w4.trace` reads the file, prepares it, and opens a browser on a local address,
printing `Trace viewer is listening on` and the address it chose. `-http=127.0.0.1:6060` picks the
address yourself. The first page is an index:

| link on the index page | what it shows |
|---|---|
| View trace by proc, View trace by thread | the timeline: one row per `P`, or per thread, with the goroutine on it at each moment |
| Goroutine analysis | goroutines grouped by where they started, each one's time split by state |
| Network blocking profile, Synchronization blocking profile, Syscall profile, Scheduler latency profile | waiting time turned into a profile, the same four kinds `-pprof` writes |
| User-defined tasks, User-defined regions | your annotations, with the distribution of their durations |
| Minimum mutator utilization | the share of the processors left to your goroutines in the worst window of each length, which is where GC pauses show |

Read it row by row. The reader, **G1**, alternates between running and reading the file, the
thinner, dimmer bars being `read` system calls. The four workers start the window blocked in
`sync`, and stay there until after the collector has begun its mark phase at 1 ms. Then each one is
runnable for a while before a `P` is free, runs for a fraction of a millisecond, and blocks on
`chan receive` because the reader has nothing ready. **In these four milliseconds the workers
spend more time waiting than parsing**, and every kind of waiting in the picture is a different
cause: the collector, the reader, the shortage of processors. A CPU profile would show the
parsing and none of the rest. Section 04 puts numbers on the whole run.
