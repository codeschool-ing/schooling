title: O que um trace guarda
version: 1

**Um arquivo de trace é uma lista de eventos, e cada evento cita três coisas: uma thread, um
processador e uma goroutine.** São as três partes do escalonador que a lição 2 de `go-concurrency`
descreveu: `M` é uma thread do sistema operacional, `G` é uma goroutine, e `P` é um processador no
sentido do Go, a permissão para rodar código Go. Existem `GOMAXPROCS` deles, quatro na máquina do
laboratório, e uma goroutine só roda enquanto alguma thread segura um `P` para ela. Quase tudo o que
um trace diz é uma goroutine ou um `P` mudando de estado, com a hora até o nanossegundo.

O `go tool trace` normalmente serve o arquivo para um navegador. Ele também tem uma flag de
depuração, `-d=parsed`, que imprime cada evento como uma linha de texto, e esse é o caminho mais
rápido para ver o que tem dentro. **O formato serve para depurar a ferramenta e ninguém promete
mantê-lo**, mas é texto puro e o `grep` lê. O trace de quatro workers da seção 02, em linhas, e as
três que o próprio `pcount` escreveu:

```
ana@vm:~/trace-hits$ go tool trace -d=parsed w4.trace | wc -l
8496346
```

```
ana@vm:~/trace-hits$ go tool trace -d=parsed w4.trace | grep -E 'Task(Begin|End)|Log '
M=11293 P=0 G=1 TaskBegin Time=847368444032 ID=1 Parent=18446744073709551615 Type="count"
M=11296 P=0 G=1 Log Time=848326411968 Task=1 Category="lines" Message="3000000"
M=11296 P=0 G=1 TaskEnd Time=848326412544 ID=1 Parent=18446744073709551615 Type="count"
```

As três são as anotações que o próprio `pcount` acrescentou: o começo da tarefa `count`, a mensagem
deixada pelo `trace.Logf` e o fim da tarefa, todas na goroutine 1 e cada uma na thread que a rodava
naquele momento. Os dois timestamps estão a 957.968.512 nanossegundos um do outro, que são os 958ms
que o programa imprimiu. `Parent=18446744073709551615` é o maior número de 64 bits e quer dizer que
a tarefa não tem pai. O arquivo de 5.257.509 bytes vira **8.496.346 linhas**, porque a maioria dos
eventos ocupa poucos bytes no formato binário e uma pilha ocupa várias linhas no dump.

## Que tipos de evento

Contados por tipo, a quarta palavra de cada linha de evento:

```
ana@vm:~/trace-hits$ go tool trace -d=parsed w4.trace | awk '/^M=/ {print $4}' | sort | uniq -c | sort -rn
 960547 StateTransition
  54853 Metric
  16378 RangeEnd
  16378 RangeBegin
   3002 RegionEnd
   3002 RegionBegin
    237 Label
      2 Sync
      1 TaskEnd
      1 TaskBegin
      1 Log
```

| tipo | o que registra |
|---|---|
| `StateTransition` | uma goroutine ou um `P` mudando de estado, como `Runnable->Running` |
| `Metric` | um número do runtime num instante: o tamanho do heap, a meta do heap, o `GOMAXPROCS` |
| `RangeBegin`, `RangeEnd` | um trecho de trabalho do runtime, quase todo do coletor de lixo |
| `RegionBegin`, `RegionEnd`, `TaskBegin`, `TaskEnd`, `Log` | as suas anotações, vindas do `runtime/trace` |
| `Label` | um nome ligado a uma goroutine, como `GC (dedicated)` num worker do coletor |
| `Sync` | um ponto em que o leitor já conheceu todas as threads e goroutines até ali, com uma leitura de relógio |

**Quase tudo é transição de estado.** Uma goroutine está `Running` num `P`, `Runnable` quando
poderia rodar e não tem `P`, `Waiting` quando está bloqueada em alguma coisa, ou numa `Syscall`. Um
`P` está `Running` ou `Idle`. Cada mudança de estado é um evento, então 960.547 deles em menos de
um segundo são o dia inteiro do escalonador, anotado.

## Por que as goroutines pararam

Uma goroutine que passa de `Running` para `Waiting` leva um motivo, e os motivos são a primeira
coisa que vale contar:

```
ana@vm:~/trace-hits$ go tool trace -d=parsed w4.trace | grep -o 'Running->Waiting Reason="[^"]*"' | sort | uniq -c | sort -rn
   1045 Running->Waiting Reason="chan receive"
    454 Running->Waiting Reason="sync"
    404 Running->Waiting Reason="system goroutine wait"
    396 Running->Waiting Reason="chan send"
    197 Running->Waiting Reason="GC mark assist wait for work"
    119 Running->Waiting Reason="preempted"
     94 Running->Waiting Reason="GC background sweeper wait"
     41 Running->Waiting Reason="sleep"
```

Cada um aponta para uma linha do `pcount` ou para uma parte do runtime. **`chan receive` é o `range
batches` de um worker encontrando o canal vazio**: 1.045 vezes, um worker terminou um lote antes de a
leitora ter o próximo pronto. `chan send` é o contrário, a leitora encontrando todas as vagas
ocupadas porque os workers estavam atrasados, 396 vezes. `sync` é uma espera por um lock ou um
semáforo; o `pcount` com quatro workers não pega lock nenhum dele, então a seção 04 tem de descobrir
de quem são essas esperas. Os motivos com `GC` e o `system goroutine wait` pertencem às goroutines
do próprio runtime.

O coletor merece uma contagem própria, porque a leitora transforma cada linha numa string nova, e
cada uma vira lixo logo depois:

```
ana@vm:~/trace-hits$ go tool trace -d=parsed w4.trace | grep -c 'RangeBegin.*GC concurrent mark phase'
94
```

**Noventa e quatro coletas em menos de um segundo.** Um profile de CPU mostra esse custo como tempo
em funções do runtime; o trace mostra quando cada coleta aconteceu e o que as goroutines do programa
faziam enquanto isso. A lição 19 trata do coletor em si.

## Os seus próprios eventos

O `pcount` criou uma tarefa, 3.001 regiões e uma mensagem:

```
ana@vm:~/trace-hits$ go tool trace -d=parsed w4.trace | grep -o 'RegionBegin .*' | grep -o 'Type=.*' | sort | uniq -c
      1 Type="merge"
   3001 Type="parse"
```

Três milhões de linhas em lotes de mil dão 3.000 lotes, e **o 3.001º é o vazio** que a leitora envia
depois do laço, porque três milhões divide exato. A região mostra isso com honestidade; nada mais no
programa mostraria. Os três tipos de anotação diferem no alcance:

| | chamada | cobre |
|---|---|---|
| região | `trace.WithRegion(ctx, "parse", fn)`, ou `trace.StartRegion` e `End` | um trecho de uma goroutine; precisa terminar na goroutine que a começou |
| tarefa | `ctx, task := trace.NewTask(ctx, "count")` e `task.End()` | uma operação lógica, em todas as goroutines que usam o contexto dela |
| log | `trace.Log(ctx, category, message)`, `trace.Logf` | um instante, com uma categoria pela qual dá para filtrar |

Os nomes de tipo das regiões devem ser poucos, diz o `go doc runtime/trace.WithRegion`, porque
servem para agrupá-las; o id de uma requisição vai num `Log`, não no nome de uma região.

## A visão no navegador

O `go tool trace w4.trace` lê o arquivo, prepara-o e abre um navegador num endereço local,
imprimindo `Trace viewer is listening on` e o endereço escolhido. `-http=127.0.0.1:6060` escolhe o
endereço por você. A primeira página é um índice:

| link na página de índice | o que mostra |
|---|---|
| View trace by proc, View trace by thread | a linha do tempo: uma fileira por `P`, ou por thread, com a goroutine que estava nela a cada momento |
| Goroutine analysis | as goroutines agrupadas por onde começaram, com o tempo de cada uma dividido por estado |
| Network blocking profile, Synchronization blocking profile, Syscall profile, Scheduler latency profile | o tempo de espera transformado em profile, os mesmos quatro tipos que o `-pprof` grava |
| User-defined tasks, User-defined regions | as suas anotações, com a distribuição das durações |
| Minimum mutator utilization | a fração dos processadores deixada às suas goroutines na pior janela de cada tamanho, que é onde as pausas do GC aparecem |
