title: Keeping generated code honest
version: 1
---

Two things can be true of a repository at once: the generated files build, and they no longer match
the source that is supposed to produce them. **Generated code stays honest through three habits**:
the files are committed, they are marked so that tools and people leave them alone, and a check in
continuous integration regenerates them and fails if anything moved. A fourth decision, which
version of the generator runs, makes the check mean the same thing on every machine.

## Committed, like the rest of the source

A habit from other languages says generated files are build output, like a binary, and belong in
`.gitignore`. **In Go they are source, and they are committed.** Section 02 gave the reason:
`go build` never runs `go generate`. A clone without `class_string.go` builds a `classes` that
prints numbers where the names were, and a clone without `owners_gen.go` does not build at all.
Somebody who requires your module downloads exactly what you committed, and nothing on their side
will generate the rest.

`~/gen-hits` becomes a repository here. The log is data, not source, so `.gitignore` holds one line:

```
access.log
```

```
ana@vm:~/gen-hits$ git add . && git commit -qm "hits, with generated code" && git ls-files "*_string.go" "*_gen.go"
internal/owner/owners_gen.go
internal/status/class_string.go
```

Both generated files are tracked, beside the sources that asked for them. Committing them has a cost
you see in review: a one-line change to a directive can arrive with a long diff in a file nobody
wrote. **Reviewers read the source change and skim the generated one**, and the header line is what
tells them which is which.

## The line that says "generated"

`go help generate` fixes the form: a line matching the regular expression
`^// Code generated .* DO NOT EDIT\.$`, before the first line of the file that is neither a comment
nor blank. Both headers in `hits` match it, stringer's and the one `genowners` writes. A near miss
does not count: `DO NOT EDIT` without the final full stop, or the line placed after `package`, and
the file is handwritten as far as any tool can tell.

**The standard library answers the question for any tool built on it**, with one function:

```
ana@vm:~/gen-try$ go doc go/ast IsGenerated | head -5
package ast // import "go/ast"

func IsGenerated(file *File) bool
    IsGenerated reports whether the file was generated by a program,
    not handwritten, by detecting the special comment described at
```

The go command's own tools use it. `go fix`, which rewrites code to newer idioms, refuses to touch a
generated file, and two small files in `~/gen-try` show the difference. `legacy/old.go`:

```go
package legacy

// Echo returns what it was given.
func Echo(v interface{}) interface{} { return v }
```

And `legacy/old_gen.go`, which no generator wrote, with only the header to tell them apart:

```go
// Code generated by nothing at all: this line is the whole test; DO NOT EDIT.

package legacy

// EchoGen returns what it was given.
func EchoGen(v interface{}) interface{} { return v }
```

```
ana@vm:~/gen-try$ go fix -diff ./legacy; echo $?
--- /home/ana/gen-try/legacy/old.go (old)
+++ /home/ana/gen-try/legacy/old.go (new)
@@ -1,4 +1,4 @@
 package legacy
 
 // Echo returns what it was given.
-func Echo(v interface{}) interface{} { return v }
+func Echo(v any) any { return v }
1
```

`-diff` prints the change instead of making it, and exits 1 because there is one. **The same
`interface{}` sits in both files, and only the handwritten one is offered `any`**: a fix applied to
a generated file would be undone by the next `go generate`, so `go fix` skips it. Formatting is the
exception. `gofmt` has no exemption for generated files, as lesson 6 noted, which is why a good
generator formats its own output.

## Regenerate, and compare

The check is two commands, and they need a working tree that matches the last commit:

```sh
go generate ./...
git diff --exit-code
```

**`git diff --exit-code` exits 1 when the working tree differs from what was committed**, and 0 when
it does not. Run on a clean `hits`, generation changes nothing:

```
ana@vm:~/gen-hits$ go generate ./... && git diff --exit-code; echo $?
0
```

Now the mistake section 03 said the compiler would not catch. A colleague decides the report should
print `4xx` rather than `ClientError`. stringer's `-linecomment` flag uses each constant's line
comment as its name, and `class.go` already carries `// 1xx` to `// 5xx`. So they add the flag to
the directive, see the build pass, and commit:

```
ana@vm:~/gen-hits$ sed -i "s/-type=Class$/-type=Class -linecomment/" internal/status/class.go && go build ./... && git commit -qam "print 4xx, not ClientError" && echo committed
committed
```

Every check that compiles passed: the guard in `_()` looks at values, and no value changed. The
commit holds a directive that says one thing and a `class_string.go` that does another. **The
continuous integration step finds it**, because it generates again and compares:

```
ana@vm:~/gen-hits$ go generate ./... && git diff --exit-code; echo $?
0
```

The diff is the whole report: the header now names `-linecomment`, and the names string shrank from
53 bytes to 15. Exit status 1 fails the step, and the fix is for the author to commit what
`go generate` wrote. With the new file in place, the report reads the way the colleague wanted:

```
ana@vm:~/gen-hits$ go run ./cmd/classes < access.log
Class(0)           0
Informational      0
Success        10058
Redirection     2421
ClientError     4998
ServerError     2523
```

**`git diff` sees only files git already tracks.** A new directive whose output was never committed
at all leaves an untracked file, and `git diff --exit-code` passes over it in silence.
`git status --porcelain` lists untracked files too, so a stricter step fails when its output is not
empty: `test -z "$(git status --porcelain)"`. These lines belong in a script that a hook and the CI
job both call, the arrangement lesson 6 section 05 built for formatting.

## Which stringer runs

The check only means something if every machine runs the same generator. A directive can name one in
three ways, and they differ in exactly that:

| the directive says | which version runs | the cost |
|---|---|---|
| `stringer -type=Class` | whatever `stringer` is first on the `PATH` of whoever generates | every author installs it, and two of them can disagree |
| `go run golang.org/x/tools/cmd/stringer@v0.52.0 -type=Class` | v0.52.0, written in the directive | the version is repeated in every directive that uses the tool |
| `go tool stringer -type=Class` | the version `go.mod` requires, v0.52.0 here | the tool's modules appear in `go.mod` as `// indirect` |

**The bare name is what the Go tree's own 31 stringer directives use**, which leaves the version to
whoever regenerates those files. On a team, the bare name is how two laptops can produce two
different `class_string.go` files from one commit, and the check then fails for one of them. The
header does not help you tell them apart: stringer wrote `stringer -type=Class` in it whichever way
it was started.

`go get -tool` recorded the third form in section 03, and `go tool` with no arguments lists it with
the tools that ship with Go:

```
ana@vm:~/gen-hits$ go tool | tail -1
stringer (golang.org/x/tools/cmd/stringer)
```

**`go tool stringer` builds the tool at the version `go.mod` requires, checks its modules against
`go.sum` like any dependency, and keeps the built executable in the build cache** for the next run.
Upgrading it is the same `go get -tool` with a newer version after the `@`, and the change lands in
`go.mod`, where a reviewer sees it; `go get -tool golang.org/x/tools/cmd/stringer@none` removes it.
A generator kept inside the module, like section 04's `genowners`, needs none of this: `go run` on
its import path builds the version in the same commit.

## When you only need the bytes

Section 04 turned `owners.txt` into Go. The other way to get a file into a program is `//go:embed`,
from `go-concurrency` lesson 24: the bytes of `owners.txt` compiled into the binary as a string or a
`[]byte`, and parsed when the program starts. Embedding needs no generator and has nothing to go
stale, since the build reads the file itself every time.

What it gives up is the moment of checking. A duplicate path in an embedded list is found when
`hits` starts, on whatever machine it runs, by a parser that ships inside the binary. A duplicate in
a generated list is found by the author, at `go generate`, before anything is committed. The rule of
thumb that follows is to **embed when the program needs the content as data, and generate when it
needs it as Go**. A template, a page or a certificate is data; a method, a type or a table the
compiler can check is Go.
