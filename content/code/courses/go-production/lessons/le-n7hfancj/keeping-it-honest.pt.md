Duas coisas podem ser verdade num repositório ao mesmo tempo: os arquivos gerados compilam, e já não
batem com o código que deveria produzi-los. **O código gerado se mantém honesto com três hábitos**:
os arquivos são commitados, são marcados para que ferramentas e pessoas os deixem em paz, e uma
verificação na integração contínua os regenera e falha se algo mudou. Uma quarta decisão, que
versão do gerador roda, faz a verificação significar a mesma coisa em toda máquina.

## Commitados, como o resto do código

Um hábito vindo de outras linguagens diz que arquivos gerados são saída de build, como um binário, e
pertencem ao `.gitignore`. **Em Go eles são código-fonte, e são commitados.** A seção 02 deu o
motivo: o `go build` nunca roda o `go generate`. Um clone sem o `class_string.go` compila um
`classes` que imprime números onde estavam os nomes, e um clone sem o `owners_gen.go` nem compila.
Quem exige o seu módulo baixa exatamente o que você commitou, e nada do lado dessa pessoa vai gerar
o resto.

O `~/gen-hits` vira um repositório aqui. O log é dado, não código, então o `.gitignore` tem uma
linha:

```
access.log
```

```
ana@vm:~/gen-hits$ git add . && git commit -qm "hits, with generated code" && git ls-files "*_string.go" "*_gen.go"
internal/owner/owners_gen.go
internal/status/class_string.go
```

Os dois arquivos gerados são rastreados, ao lado dos fontes que os pediram. Commitá-los tem um custo
que aparece na revisão: uma mudança de uma linha numa diretiva pode chegar com um diff longo num
arquivo que ninguém escreveu. **Quem revisa lê a mudança no fonte e passa os olhos na gerada**, e a
linha de cabeçalho é o que diz qual é qual.

## A linha que diz "gerado"

O `go help generate` fixa a forma: uma linha que case com a expressão regular
`^// Code generated .* DO NOT EDIT\.$`, antes da primeira linha do arquivo que não seja comentário
nem esteja em branco. Os dois cabeçalhos do `hits` casam com ela, o do stringer e o que o
`genowners` escreve. Quase não conta: `DO NOT EDIT` sem o ponto final, ou a linha posta depois do
`package`, e o arquivo é escrito à mão para qualquer ferramenta.

**A biblioteca padrão responde à pergunta para qualquer ferramenta construída sobre ela**, com uma
função:

```
ana@vm:~/gen-try$ go doc go/ast IsGenerated | head -5
package ast // import "go/ast"

func IsGenerated(file *File) bool
    IsGenerated reports whether the file was generated by a program,
    not handwritten, by detecting the special comment described at
```

As ferramentas do próprio comando go a usam. O `go fix`, que reescreve código para idiomas mais
novos, se recusa a tocar num arquivo gerado, e dois arquivinhos em `~/gen-try` mostram a diferença.
`legacy/old.go`:

```go
package legacy

// Echo returns what it was given.
func Echo(v interface{}) interface{} { return v }
```

E o `legacy/old_gen.go`, que nenhum gerador escreveu, só com o cabeçalho para diferenciá-los:

```go
// Code generated by nothing at all: this line is the whole test; DO NOT EDIT.

package legacy

// EchoGen returns what it was given.
func EchoGen(v interface{}) interface{} { return v }
```

```
ana@vm:~/gen-try$ go fix -diff ./legacy; echo $?
--- /home/ana/gen-try/legacy/old.go (old)
+++ /home/ana/gen-try/legacy/old.go (new)
@@ -1,4 +1,4 @@
 package legacy
 
 // Echo returns what it was given.
-func Echo(v interface{}) interface{} { return v }
+func Echo(v any) any { return v }
1
```

O `-diff` imprime a mudança em vez de aplicá-la, e sai com 1 porque há uma. **O mesmo `interface{}`
está nos dois arquivos, e só o escrito à mão recebe a oferta de `any`**: uma correção aplicada a um
arquivo gerado seria desfeita pelo próximo `go generate`, então o `go fix` o pula. A formatação é a
exceção. O `gofmt` não isenta arquivos gerados, como a lição 6 observou, e por isso um bom gerador
formata a própria saída.

## Regenerar, e comparar

A verificação são dois comandos, e eles precisam de uma árvore de trabalho igual ao último commit:

```sh
go generate ./...
git diff --exit-code
```

**O `git diff --exit-code` sai com 1 quando a árvore de trabalho difere do que foi commitado**, e com
0 quando não difere. Rodada num `hits` limpo, a geração não muda nada:

```
ana@vm:~/gen-hits$ go generate ./... && git diff --exit-code; echo $?
0
```

Agora o erro que a seção 03 disse que o compilador não pegaria. Uma colega decide que o relatório
deve imprimir `4xx` em vez de `ClientError`. A flag `-linecomment` do stringer usa o comentário de
linha de cada constante como nome, e o `class.go` já tem `// 1xx` a `// 5xx`. Então ela acrescenta a
flag à diretiva, vê o build passar e commita:

```
ana@vm:~/gen-hits$ sed -i "s/-type=Class$/-type=Class -linecomment/" internal/status/class.go && go build ./... && git commit -qam "print 4xx, not ClientError" && echo committed
committed
```

Toda verificação que compila passou: o guarda em `_()` olha valores, e nenhum valor mudou. O commit
tem uma diretiva que diz uma coisa e um `class_string.go` que faz outra. **O passo da integração
contínua encontra isso**, porque gera de novo e compara:

```
ana@vm:~/gen-hits$ go generate ./... && git diff --exit-code; echo $?
diff --git a/internal/status/class_string.go b/internal/status/class_string.go
index 55047f8..e69ebf7 100644
--- a/internal/status/class_string.go
+++ b/internal/status/class_string.go
@@ -1,4 +1,4 @@
-// Code generated by "stringer -type=Class"; DO NOT EDIT.
+// Code generated by "stringer -type=Class -linecomment"; DO NOT EDIT.
 
 package status
 
@@ -15,9 +15,9 @@ func _() {
 	_ = x[ServerError-5]
 }
 
-const _Class_name = "InformationalSuccessRedirectionClientErrorServerError"
+const _Class_name = "1xx2xx3xx4xx5xx"
 
-var _Class_index = [...]uint8{0, 13, 20, 31, 42, 53}
+var _Class_index = [...]uint8{0, 3, 6, 9, 12, 15}
 
 func (i Class) String() string {
 	idx := int(i) - 1
1
```

O diff é o relatório inteiro: o cabeçalho agora cita `-linecomment`, e a string de nomes encolheu de
53 bytes para 15. O status 1 reprova o passo, e a correção é a autora commitar o que o
`go generate` escreveu. Com o arquivo novo no lugar, o relatório fica como a colega queria:

```
ana@vm:~/gen-hits$ go run ./cmd/classes < access.log
Class(0)           0
1xx                0
2xx            10058
3xx             2421
4xx             4998
5xx             2523
```

**O `git diff` só enxerga arquivos que o git já rastreia.** Uma diretiva nova cuja saída nunca foi
commitada deixa um arquivo não rastreado, e o `git diff --exit-code` passa por ele em silêncio. O
`git status --porcelain` lista também arquivos não rastreados, então um passo mais rigoroso falha
quando a saída dele não é vazia: `test -z "$(git status --porcelain)"`. Essas linhas cabem num script
que um hook e o job de CI chamam, o arranjo que a lição 6 seção 05 montou para a formatação.

## Qual stringer roda

A verificação só significa algo se toda máquina rodar o mesmo gerador. Uma diretiva pode nomeá-lo de
três jeitos, e eles diferem exatamente nisso:

| a diretiva diz | que versão roda | o custo |
|---|---|---|
| `stringer -type=Class` | o `stringer` que estiver primeiro no `PATH` de quem gera | cada autor o instala, e dois deles podem discordar |
| `go run golang.org/x/tools/cmd/stringer@v0.52.0 -type=Class` | a v0.52.0, escrita na diretiva | a versão se repete em toda diretiva que usa a ferramenta |
| `go tool stringer -type=Class` | a versão que o `go.mod` exige, aqui a v0.52.0 | os módulos da ferramenta aparecem no `go.mod` como `// indirect` |

**O nome puro é o que as 31 diretivas do stringer da própria árvore do Go usam**, o que deixa a
versão a cargo de quem regenera esses arquivos. Numa equipe, o nome puro é como dois notebooks podem
produzir dois `class_string.go` diferentes a partir de um commit, e a verificação então falha para
um deles. O cabeçalho não ajuda a diferenciá-los: o stringer escreveu `stringer -type=Class` nele,
seja qual for o jeito como foi iniciado.

O `go get -tool` registrou a terceira forma na seção 03, e o `go tool` sem argumentos a lista junto
com as ferramentas que vêm com o Go:

```
ana@vm:~/gen-hits$ go tool | tail -1
stringer (golang.org/x/tools/cmd/stringer)
```

**O `go tool stringer` compila a ferramenta na versão que o `go.mod` exige, confere os módulos dela
no `go.sum` como qualquer dependência e guarda o executável no cache de build** para a próxima vez.
Atualizar é o mesmo `go get -tool` com uma versão mais nova depois do `@`, e a mudança cai no
`go.mod`, onde quem revisa a vê; `go get -tool golang.org/x/tools/cmd/stringer@none` a remove. Um
gerador guardado dentro do módulo, como o `genowners` da seção 04, não precisa de nada disso: o
`go run` sobre o caminho de import dele compila a versão do mesmo commit.

## Quando você só precisa dos bytes

A seção 04 transformou o `owners.txt` em Go. O outro jeito de pôr um arquivo num programa é o
`//go:embed`, da lição 24 do `go-concurrency`: os bytes do `owners.txt` compilados no binário como
string ou `[]byte`, e analisados quando o programa inicia. Embutir não precisa de gerador e não tem
nada que fique velho, já que o build lê o próprio arquivo toda vez.

O que se perde é o momento da verificação. Um caminho duplicado numa lista embutida é encontrado
quando o `hits` inicia, em qualquer máquina onde rode, por um analisador que vai dentro do binário.
Um duplicado numa lista gerada é encontrado por quem escreve, no `go generate`, antes de qualquer
commit. A regra prática que decorre disso é **embutir quando o programa precisa do conteúdo como
dado, e gerar quando precisa dele como Go**. Um template, uma página ou um certificado são dados; um
método, um tipo ou uma tabela que o compilador pode conferir são Go.
