A generator is not a special kind of program. **It is an ordinary Go program that reads something
and writes a `.go` file**, and the directive that runs it is one line. The Go source tree's 78
`go run` directives work that way: a program run from source, with no installation step. This section writes one for `hits`, small
enough to read whole.

## A list somebody else keeps

Every path on the site belongs to a team, and the team that answers at three in the morning keeps
the list. They do not write Go, and they should not have to. The list is a text file,
`internal/owner/owners.txt`:

```
# Which team answers for which path: the path, then the team.
/                frontend
/static/app.js   frontend
/static/app.css  frontend
/login           accounts
/api/users       accounts
/api/orders      payments
/api/orders/42   payments
/health          platform
```

The program `hits` wants is a function from a path to a team. That could read the file at run time,
and the last part of section 05 weighs that option. **Here the list becomes Go before the program is
built**: a map literal in a generated file, with the mistakes in the list caught by a generator that
says which line is wrong. The generator lives in `tools/genowners/main.go`, beside `genlog`:

The package that uses the map holds the directive, and only the directive and one function are
written by hand. `internal/owner/owner.go`:

```go
// Package owner says which team answers for a path of the site.
package owner

//go:generate go run example.com/hits/tools/genowners -in owners.txt -out owners_gen.go

// Of returns the team that owns path, or "nobody" for a path not on the
// list.
func Of(path string) string {
	if team, ok := byPath[path]; ok {
		return team
	}
	return "nobody"
}
```

**The directive names the generator by its import path**, `example.com/hits/tools/genowners`.
`go run ../../tools/genowners` would also work, since the directive runs in `internal/owner`, but it
breaks the day somebody moves the package one level deeper; the import path means the same thing
from every directory of the module. `byPath` is used here and defined nowhere yet, so until the
generator has run, the package does not compile.

## Running it

```
ana@vm:~/gen-hits$ go generate -x ./internal/owner
go run example.com/hits/tools/genowners -in owners.txt -out owners_gen.go
ana@vm:~/gen-hits$ cat internal/owner/owners_gen.go
// Code generated by genowners from owners.txt; DO NOT EDIT.

package owner

// byPath maps each path to the team that owns it.
var byPath = map[string]string{
	"/":               "frontend",
	"/static/app.js":  "frontend",
	"/static/app.css": "frontend",
	"/login":          "accounts",
	"/api/users":      "accounts",
	"/api/orders":     "payments",
	"/api/orders/42":  "payments",
	"/health":         "platform",
}
ana@vm:~/gen-hits$ gofmt -l internal/owner; echo $?
0
```

`package owner` came from `$GOPACKAGE`, and the header names `owners.txt` because that is what the
directive passed as `-in`. Compare the entries with the template that wrote them. **The template put
each entry at the start of its line with one space after the colon; the file has a tab in front and
the values aligned in a column**, and that is `format.Source`. `gofmt -l` lists the files it would
change and listed none. A generator that skips this step writes files that the formatting check of
lesson 6 then fails on every run. The fix has to go in the generator, since an edit to the output
lasts until the next `go generate`.

The map in use, from `cmd/teams/main.go`, which counts the log by team:

```go
// Command teams counts an access log's requests by the team that owns each
// path. It reads standard input.
package main

import (
	"fmt"
	"maps"
	"os"
	"slices"

	"example.com/hits/internal/owner"
	"example.com/hits/internal/tally"
)

func main() {
	s, err := tally.Count(os.Stdin)
	if err != nil {
		fmt.Fprintln(os.Stderr, "teams:", err)
		os.Exit(1)
	}
	byTeam := map[string]int{}
	for path, n := range s.ByPath {
		byTeam[owner.Of(path)] += n
	}
	for _, team := range slices.Sorted(maps.Keys(byTeam)) {
		fmt.Printf("%-9s %5d\n", team, byTeam[team])
	}
}
```

```
ana@vm:~/gen-hits$ go run ./cmd/teams < access.log
accounts   5088
frontend   7503
payments   5045
platform   2364
```

The four teams account for all 20,000 lines, and no line fell to `nobody`, because every path
`genlog` writes is on the list. `frontend` is the largest because it owns three of the eight paths.

## When the list is wrong

Somebody adds a line for `/login` without noticing it is already there, and the next person to
generate finds out:

```
ana@vm:~/gen-hits$ echo "/login  security" >> internal/owner/owners.txt && go generate ./internal/owner; echo $?
genowners: owners.txt:10: /login is already on line 5
exit status 1
internal/owner/owner.go:4: running "go": exit status 1
1
ana@vm:~/gen-hits$ sed -i "\$d" internal/owner/owners.txt && go generate ./internal/owner && echo regenerated
regenerated
```

Three programs reported, each in its own words. **The first line is the generator's**, naming the
file and both lines involved. `exit status 1` is `go run`, passing on its child's status. The third
line is go generate, naming the directive that failed, `owner.go:4`, and stopping; it exited 1 in
turn, so a script or a CI step that runs `go generate` stops too. `owners_gen.go` was not touched,
because `run` writes only after everything has been read and formatted. The `sed` removed the last
line and the generator ran cleanly again.

**Make a generator as strict as a compiler**, because it is the only place the mistake is still in
the reader's terms. Without the duplicate check the template would have written two `"/login"` keys,
and the build would have failed later, inside a file nobody edits, with
`duplicate key "/login" in map literal` pointing at `owners_gen.go`.
