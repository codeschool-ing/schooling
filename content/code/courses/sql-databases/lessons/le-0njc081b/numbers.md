title: Numbers, and the one that costs money

A column's type is not a box that holds anything. It is a promise about every value that will ever
be in it, enforced on every write, for as long as the table exists. Choosing one is the cheapest
decision in this lesson to get right and the most expensive to meet later.

## The integers

| type | range | when |
|---|---|---|
| `smallint` | ±32 thousand | almost never worth the saving |
| `integer` | ±2.1 billion | the default for counts, quantities and most keys |
| `bigint` | ±9.2 quintillion | ids on a table that will be busy, and anything counting bytes or microseconds |

**The one real decision is `integer` against `bigint` for a primary key.** Two point one billion
sounds like plenty until you remember that ids are not reused: a table that inserts and deletes a
million rows a day exhausts `integer` in six years while never holding more than a few million
rows at once.

Migrating a key from `integer` to `bigint` afterwards is not a small job — it rewrites the table,
and every foreign key pointing at it. So for anything that could ever be high-volume — events,
logs, messages, orders on a busy system — **use `bigint` and stop thinking about it.** The four
extra bytes per row are not a cost anybody has ever regretted.

## The decimals, and this is the section that matters

```sql
total numeric(12,2)   -- exact:      12 digits, 2 after the point
rate  double precision -- approximate: about 15 significant digits
```

`numeric` stores digits. `real` and `double precision` store binary approximations, and **a tenth
is not representable in binary** any more than a third is in decimal. The consequence, in a
database that has never been touched by a bug:

```sql
SELECT 0.1::double precision + 0.2::double precision = 0.3::double precision;
```

```
 ?column?
----------
 f
```

False. Not a rounding display issue — the two values are genuinely different numbers.

Now put a thousand invoices in a `double precision` column and total them. The answer is wrong by
a few cents. It is small enough that nobody notices for a year, and large enough that an accountant
eventually does, and by then the wrong numbers are in reports somebody has acted on.

> **Money goes in `numeric`. Always, without argument, in every database, forever.**

The scale is the count of digits after the point: `numeric(12,2)` is up to ten digits of currency
and two of cents. Pick the scale from the currency and not from the display — some currencies have
no minor unit and some financial calculations want four.

**What `real` and `double precision` are for**: measurements. A temperature, a latitude, a
duration in seconds, a weight. Things where the fifteenth significant digit is noise anyway, and
where arithmetic speed matters because you are doing millions of operations.

## Dividing integers surprises everybody once

```sql
SELECT 7 / 2;
```

```
 ?column?
----------
        3
```

Integer divided by integer is integer, and the remainder is discarded — not rounded, discarded.
`SELECT 7 / 2.0` gives `3.5`, because one operand being decimal makes the operation decimal.

This one reaches production regularly, in the shape of a percentage that is always zero:

```sql
SELECT count(*) FILTER (WHERE paid_at IS NOT NULL) / count(*) AS paid_share FROM invoices;
-- 0, always, for any table where not everything is paid
```

Cast one side and it works. It is worth knowing now because the error is silent and the answer is
plausible.

## The identity column

```sql
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```

`GENERATED ALWAYS` refuses a value you supply, which is what you want: the column is the
database's to fill, and an insert that tries to set it is a bug. `GENERATED BY DEFAULT` allows one,
which is occasionally needed when restoring data and is otherwise a loophole.

You will meet the older `serial` in existing schemas:

```sql
id serial PRIMARY KEY      -- older PostgreSQL; still works
id bigserial PRIMARY KEY   -- the bigint version
```

`serial` is not a type. It is shorthand that creates an `integer` column, a sequence, and a default
— which means the sequence is a separate object with its own permissions and its own ways of
getting out of step. `IDENTITY` is the standard SQL spelling, it is what new tables should use, and
it is one of the few places where the newer way is simply better.

**And the gaps are not a defect.** A transaction that takes a number and rolls back does not give
it back, so `1, 2, 5, 6` is a healthy table. Any code that assumes ids are contiguous — paging by
id arithmetic, counting rows from the maximum — is wrong, and was wrong on the day it was written.
