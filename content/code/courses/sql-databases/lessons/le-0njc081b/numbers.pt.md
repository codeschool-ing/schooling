O tipo de uma coluna não é uma caixa que guarda qualquer coisa. É uma promessa sobre todo valor que
um dia estará nela, imposta a cada escrita, enquanto a tabela existir. Escolher é a decisão mais
barata desta aula de acertar e a mais cara de encontrar depois.

## Os inteiros

| tipo | alcance | quando |
|---|---|---|
| `smallint` | ±32 mil | quase nunca vale a economia |
| `integer` | ±2,1 bilhões | o padrão para contagens, quantidades e a maioria das chaves |
| `bigint` | ±9,2 quintilhões | ids numa tabela movimentada, e tudo que conta bytes ou microssegundos |

**A única decisão real é `integer` contra `bigint` numa chave primária.** Dois bilhões e cem
milhões parece bastante até você lembrar que ids não são reaproveitados: uma tabela que insere e
apaga um milhão de linhas por dia esgota o `integer` em seis anos sem nunca guardar mais que alguns
milhões de linhas ao mesmo tempo.

Migrar uma chave de `integer` para `bigint` depois não é trabalho pequeno — reescreve a tabela, e
toda chave estrangeira que aponta para ela. Então para qualquer coisa que possa ser de alto volume
— eventos, logs, mensagens, pedidos num sistema movimentado — **use `bigint` e pare de pensar
nisso.** Os quatro bytes a mais por linha não são um custo de que alguém já se arrependeu.

## Os decimais, e esta é a seção que importa

```sql
total numeric(12,2)    -- exato:       12 dígitos, 2 depois da vírgula
rate  double precision -- aproximado:  cerca de 15 dígitos significativos
```

`numeric` guarda dígitos. `real` e `double precision` guardam aproximações binárias, e **um décimo
não é representável em binário**, do mesmo modo que um terço não é em decimal. A consequência, num
banco em que nenhum bug jamais encostou:

```sql
SELECT 0.1::double precision + 0.2::double precision = 0.3::double precision;
```

```
 ?column?
----------
 f
```

Falso. Não é um problema de exibição de arredondamento — os dois valores são genuinamente números
diferentes.

Agora ponha mil faturas numa coluna `double precision` e some. A resposta erra por alguns centavos.
É pequeno o bastante para ninguém notar por um ano, e grande o bastante para um contador acabar
notando, e a essa altura os números errados estão em relatórios sobre os quais alguém agiu.

> **Dinheiro vai em `numeric`. Sempre, sem discussão, em todo banco, para sempre.**

A escala é a contagem de dígitos depois da vírgula: `numeric(12,2)` é até dez dígitos de moeda e
dois de centavos. Escolha a escala pela moeda e não pela exibição — algumas moedas não têm unidade
menor e alguns cálculos financeiros querem quatro.

**Para que servem `real` e `double precision`**: medições. Uma temperatura, uma latitude, uma
duração em segundos, um peso. Coisas em que o décimo quinto dígito significativo é ruído de todo
jeito, e em que velocidade de aritmética importa porque você faz milhões de operações.

## Dividir inteiros surpreende todo mundo uma vez

```sql
SELECT 7 / 2;
```

```
 ?column?
----------
        3
```

Inteiro dividido por inteiro é inteiro, e o resto é descartado — não arredondado, descartado.
`SELECT 7 / 2.0` dá `3.5`, porque um operando decimal torna a operação decimal.

Esse chega em produção com regularidade, na forma de um percentual que é sempre zero:

```sql
SELECT count(*) FILTER (WHERE paid_at IS NOT NULL) / count(*) AS paid_share FROM invoices;
-- 0, sempre, em qualquer tabela onde nem tudo está pago
```

Converta um lado e funciona. Vale saber agora porque o erro é silencioso e a resposta é plausível.

## A coluna de identidade

```sql
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```

`GENERATED ALWAYS` recusa um valor que você forneça, que é o que você quer: a coluna é do banco, e
uma inserção que tente defini-la é um bug. `GENERATED BY DEFAULT` permite um, o que é ocasionalmente
necessário ao restaurar dados e é uma brecha no resto do tempo.

Você vai encontrar o antigo `serial` em esquemas existentes:

```sql
id serial PRIMARY KEY      -- PostgreSQL mais antigo; ainda funciona
id bigserial PRIMARY KEY   -- a versão bigint
```

`serial` não é um tipo. É atalho que cria uma coluna `integer`, uma sequência e um default — o que
significa que a sequência é um objeto separado com permissões próprias e modos próprios de sair de
sincronia. `IDENTITY` é a grafia do padrão SQL, é o que tabelas novas devem usar, e é um dos poucos
lugares em que o jeito mais novo é simplesmente melhor.

**E os buracos não são defeito.** Uma transação que pega um número e é desfeita não o devolve, então
`1, 2, 5, 6` é uma tabela saudável. Qualquer código que suponha ids contíguos — paginar por
aritmética de id, contar linhas a partir do máximo — está errado, e estava errado no dia em que foi
escrito.
