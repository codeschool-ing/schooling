title: "R8: o que o build de release remove"

**O R8 lê o app inteiro, bibliotecas incluídas, e mantém só o que pode ser alcançado a partir do
código que roda.** Depois encurta os nomes do que sobrou e o otimiza. A aula 1, seção 08, encontrou
27,82 MB de dex num APK de debug que mostrava uma frase, e o `android analyze` reclamou disso. Aqui
estão os builds de debug e de release do flavour `play` do mesmo app, lado a lado:

```
ana@vm:~/planner$ ls -l app/build/outputs/apk/play/debug/app-play-debug.apk app/build/outputs/apk/play/release/app-play-release.apk
-rw-r--r-- 1 ana ana 11663286 Oct 30 17:41 app/build/outputs/apk/play/debug/app-play-debug.apk
-rw-r--r-- 1 ana ana   757882 Oct 30 17:42 app/build/outputs/apk/play/release/app-play-release.apk
ana@vm:~/planner$ android analyze app/build/outputs/apk/play/release/app-play-release.apk 2>&1 | sed -e "s/.*\r//" | grep -E "Dex|R8"
 - Uncompressed Dex Size: 1130676 bytes (1.08 MB)
 - Dex Marker Metadata: R8 Enabled=true, D8 Enabled=false, Full Mode=true
 - Dex Heuristic Obfuscation: 97.89%
ana@vm:~/planner$ wc -l app/build/outputs/mapping/playRelease/mapping.txt
116141 app/build/outputs/mapping/playRelease/mapping.txt
ana@vm:~/planner$ grep -E "^(com.example.planner.MainActivity|androidx.activity.ComponentActivity|androidx.compose.ui.platform.AndroidComposeView) " app/build/outputs/mapping/playRelease/mapping.txt
androidx.activity.ComponentActivity -> k9:
androidx.compose.ui.platform.AndroidComposeView -> h2:
com.example.planner.MainActivity -> com.example.planner.MainActivity:
```

**De 11,7 MB para 0,76 MB**, e de 27,82 MB de dex na aula 1 para 1,08 MB aqui. Quase toda a diferença
é código de biblioteca que o planner nunca chama: o R8 segue cada chamada a partir dos pontos de
entrada do app, a activity do manifesto e o que ela compõe, e descarta cada classe e método que nunca
alcança. O `isShrinkResources` então descarta os recursos que nada mais referencia. `R8 Enabled=true`
e `Full Mode=true` são o que a análise relata para um build de release do AGP 9.5.

## Os nomes que ele muda, e o arquivo que desfaz isso

O R8 também renomeia, e o último comando acima mostra os dois desfechos. `ComponentActivity`, a
classe do AndroidX que a activity do planner estende, agora é `k9`, e a view em que o Compose desenha
é `h2`. Um relatório de crash de um build de release cita, portanto, classes como `h2`, que ninguém
consegue ler. **`MainActivity` manteve o nome**, porque o manifesto a cita como texto e o R8 mantém
tudo o que o manifesto referencia. **`mapping.txt` é o dicionário de volta**, escrito a cada build de
release: 116.141 linhas aqui, cada classe numa linha própria com os campos e métodos dela indentados
abaixo. Guarde-o com cada versão publicada, porque um stack trace só pode ser traduzido com o mapping
do build exato que o produziu. O Google Play desofusca os relatórios de crash automaticamente quando
o mapping é enviado com o bundle; a ferramenta `retrace`, das command-line tools, faz o mesmo no seu
computador.

## Quando o R8 remove demais

O R8 só consegue seguir as chamadas que vê no código. Qualquer coisa alcançada por **reflexão**, pelo
nome de uma classe num texto, é invisível para ele, e acaba removida ou renomeada. Os casos comuns
são adaptadores de JSON que acham campos pelo nome, que a aula 14 encontra, e classes citadas em XML.
Bibliotecas que dependem de reflexão trazem regras próprias no AAR, que o plugin aplica; para as suas
próprias classes, o `proguard-rules.pro` aceita uma linha `-keep`:

```properties
# A model read by reflection, if the planner ever had one
-keep class com.example.planner.data.** { *; }
```

**Não executado**: o planner não alcança nada por reflexão, então esta regra é um exemplo e não está
no arquivo que a seção 02 construiu. O sintoma de uma regra que falta é um app que funciona em
`debug` e quebra em `release`, e esse é o argumento para testar o build de release antes de publicar,
não só o de debug.
