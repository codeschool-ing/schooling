The obvious way to combine a filter with a search is to run the search you already have and then
throw away the results that fail the filter. That is **post-filtering**, and it has one property
that makes it dangerous: **it never returns more than k results, and it can return fewer, down to
none.** Nothing goes back to fetch replacements for what the filter removed.

`store.py` keeps the metadata in arrays beside the vectors and offers both orders, so they can be
compared on the same question:

```schooling-example

    },

    },
    {

    }

```

```python
from store import post_filter, pre_filter

for text, key, value in [("I was charged twice", "category", "payments"),
                         ("how do I return a book", "lang", "pt")]:
    print(f"{text!r} where {key} = {value!r}, k = 3")
    print("  post-filter:", post_filter(text, 3, key, value))
    print("  pre-filter: ", pre_filter(text, 3, key, value))
```

  pre-filter:  [('h22', 0.564), ('h21', 0.261), ('h25', 0.112)]

**The first question asked for 3 payment articles and got 2.** The three nearest articles were
*Charged twice for one order*, a returns article and *A payment that was declined*; the filter
dropped the returns article and nothing took its place. The payments category has other articles,
and the pre-filter found the third, `h25`, at 0.112.

**The second asked for 3 Portuguese articles and got none.** The three nearest articles to an
English question are English, so a filter applied after them keeps nothing, although the help
centre has three Portuguese articles. The pre-filter returns all three, and its scores show
something else worth knowing: 0.1, 0.017 and −0.005, which is lesson 1's finding again. An English
model cannot rank Portuguese text, so the filter can choose the right subset and the order inside
it is still noise. A filter fixes *which* rows; it does nothing for a model that cannot read them.

The rule of thumb that follows: post-filtering keeps, on average, the share of the k results that
the filter passes. A filter that passes one row in fifty keeps one result in fifty.

## The same thing inside PostgreSQL

That rule applies wherever the filter comes after the search, including inside a database that
never mentions it. `messages.py` fills a table with 5,000 rows of random vectors, one row in 50
marked `pt` and one in 10 marked `es`, and builds the HNSW index lesson 14 built. Then `ten.sql`
asks, for eight different query rows, for the 10 nearest rows in each language:

```python
import numpy as np
import psycopg
from pgvector.psycopg import register_vector

rng = np.random.default_rng(17)
V = rng.standard_normal((5000, 384)).astype(np.float32)
V /= np.linalg.norm(V, axis=1, keepdims=True)
lang = ["pt" if i % 50 == 0 else "es" if i % 10 == 1 else "en" for i in range(5000)]

with psycopg.connect(autocommit=True) as conn:
    conn.execute("CREATE EXTENSION IF NOT EXISTS vector")
    register_vector(conn)
    conn.execute("CREATE TABLE messages (id int PRIMARY KEY, lang text, embedding vector(384))")
    with conn.cursor().copy("COPY messages FROM STDIN WITH (FORMAT BINARY)") as copy:
        copy.set_types(["int4", "text", "vector"])
        for i, v in enumerate(V):
            copy.write_row((i, lang[i], v))
    conn.execute("CREATE INDEX ON messages USING hnsw (embedding vector_cosine_ops)")
    conn.execute("ANALYZE messages")
```

```sql
SELECT q.id AS query_row,
       (SELECT count(*) FROM (SELECT m.id FROM messages m WHERE m.lang = 'pt'
                              ORDER BY m.embedding <=> q.embedding LIMIT 10) AS t) AS pt,
       (SELECT count(*) FROM (SELECT m.id FROM messages m WHERE m.lang = 'es'
                              ORDER BY m.embedding <=> q.embedding LIMIT 10) AS t) AS es
FROM messages q WHERE q.id BETWEEN 1 AND 8 ORDER BY q.id;
```

**Every query asked for 10 rows and none got them.** The Portuguese column holds 0 or 1, the
Spanish one between 2 and 6. Nothing failed, and nothing warned. The plan says why:

```
ana@lab:~/emb$ psql -c "EXPLAIN (COSTS OFF) SELECT id FROM messages WHERE lang = 'pt' ORDER BY embedding <=> (SELECT embedding FROM messages WHERE id = 1) LIMIT 10"
                          QUERY PLAN                           
---------------------------------------------------------------
 Limit
   InitPlan 1 (returns $0)
     ->  Index Scan using messages_pkey on messages messages_1
           Index Cond: (id = 1)
   ->  Index Scan using messages_embedding_idx on messages
         Order By: (embedding <=> $0)
         Filter: (lang = 'pt'::text)
(7 rows)
```

The `Filter` line sits under the `Index Scan`. The index walks its graph and yields the nearest
rows it found, `hnsw.ef_search` of them, 40 by default as lesson 16 showed, and PostgreSQL checks
the language of each one as it comes out. Forty candidates of which one in fifty is Portuguese is
less than one Portuguese row on average, which is what the first column shows. The planner chose
this plan itself: the query does not say *search first*, and nothing on the screen suggests it.

Raising `ef_search` widens the candidate list, and the counts climb:
