O jeito óbvio de combinar um filtro com uma busca é rodar a busca que você já tem e depois jogar
fora os resultados que não passam no filtro. Isso é a **pós-filtragem** (post-filtering), e ela tem
uma propriedade que a torna perigosa: **nunca devolve mais de k resultados, e pode devolver menos,
até nenhum.** Nada volta para buscar substitutos para o que o filtro removeu.

`store.py` guarda os metadados em arrays ao lado dos vetores e oferece as duas ordens, para que
possam ser comparadas na mesma pergunta:

```python
from store import post_filter, pre_filter

for text, key, value in [("I was charged twice", "category", "payments"),
                         ("how do I return a book", "lang", "pt")]:
    print(f"{text!r} where {key} = {value!r}, k = 3")
    print("  post-filter:", post_filter(text, 3, key, value))
    print("  pre-filter: ", pre_filter(text, 3, key, value))
```

**A primeira pergunta pediu 3 artigos de pagamento e recebeu 2.** Os três artigos mais próximos
eram *Charged twice for one order* (cobrado duas vezes por um pedido), um artigo de devolução e *A
payment that was declined* (um pagamento recusado); o filtro descartou o artigo de devolução e nada
ocupou o lugar dele. A categoria de pagamentos tem outros artigos, e o pré-filtro achou o terceiro,
`h25`, com 0,112.

**A segunda pediu 3 artigos em português e não recebeu nenhum.** Os três artigos mais próximos de uma
pergunta em inglês estão em inglês, então um filtro aplicado depois deles não guarda nada, embora a
central de ajuda tenha três artigos em português. O pré-filtro devolve os três, e as notas dele
mostram mais uma coisa que vale saber: 0,1, 0,017 e −0,005, que é de novo a descoberta da aula 1.
Um modelo inglês não consegue ordenar texto em português, então o filtro consegue escolher o
subconjunto certo e a ordem dentro dele continua sendo ruído. Um filtro resolve *quais* linhas; não
faz nada por um modelo que não consegue lê-las.

A regra prática que sai disso: a pós-filtragem guarda, em média, a fração dos k resultados que o
filtro deixa passar. Um filtro que deixa passar uma linha em cinquenta guarda um resultado em
cinquenta.

## A mesma coisa dentro do PostgreSQL

Essa regra vale onde quer que o filtro venha depois da busca, inclusive dentro de um banco de dados
que nunca menciona isso. `messages.py` enche uma tabela com 5.000 linhas de vetores aleatórios, uma
linha em 50 marcada `pt` e uma em 10 marcada `es`, e constrói o índice HNSW que a aula 14 construiu.
Depois `ten.sql` pede, para oito linhas de consulta diferentes, as 10 linhas mais próximas em cada
idioma:

```python
import numpy as np
import psycopg
from pgvector.psycopg import register_vector

rng = np.random.default_rng(17)
V = rng.standard_normal((5000, 384)).astype(np.float32)
V /= np.linalg.norm(V, axis=1, keepdims=True)
lang = ["pt" if i % 50 == 0 else "es" if i % 10 == 1 else "en" for i in range(5000)]

with psycopg.connect(autocommit=True) as conn:
    conn.execute("CREATE EXTENSION IF NOT EXISTS vector")
    register_vector(conn)
    conn.execute("CREATE TABLE messages (id int PRIMARY KEY, lang text, embedding vector(384))")
    with conn.cursor().copy("COPY messages FROM STDIN WITH (FORMAT BINARY)") as copy:
        copy.set_types(["int4", "text", "vector"])
        for i, v in enumerate(V):
            copy.write_row((i, lang[i], v))
    conn.execute("CREATE INDEX ON messages USING hnsw (embedding vector_cosine_ops)")
    conn.execute("ANALYZE messages")
```

```sql
SELECT q.id AS query_row,
       (SELECT count(*) FROM (SELECT m.id FROM messages m WHERE m.lang = 'pt'
                              ORDER BY m.embedding <=> q.embedding LIMIT 10) AS t) AS pt,
       (SELECT count(*) FROM (SELECT m.id FROM messages m WHERE m.lang = 'es'
                              ORDER BY m.embedding <=> q.embedding LIMIT 10) AS t) AS es
FROM messages q WHERE q.id BETWEEN 1 AND 8 ORDER BY q.id;
```

**Toda consulta pediu 10 linhas e nenhuma recebeu.** A coluna do português tem 0 ou 1, a do espanhol
entre 2 e 6. Nada falhou, e nada avisou. O plano diz por quê:

```
ana@lab:~/emb$ psql -c "EXPLAIN (COSTS OFF) SELECT id FROM messages WHERE lang = 'pt' ORDER BY embedding <=> (SELECT embedding FROM messages WHERE id = 1) LIMIT 10"
                          QUERY PLAN                           
---------------------------------------------------------------
 Limit
   InitPlan 1 (returns $0)
     ->  Index Scan using messages_pkey on messages messages_1
           Index Cond: (id = 1)
   ->  Index Scan using messages_embedding_idx on messages
         Order By: (embedding <=> $0)
         Filter: (lang = 'pt'::text)
(7 rows)
```

A linha `Filter` fica debaixo do `Index Scan`. O índice anda pelo grafo e entrega as linhas mais
próximas que encontrou, `hnsw.ef_search` delas, 40 por padrão como a aula 16 mostrou, e o PostgreSQL
confere o idioma de cada uma conforme ela sai. Quarenta candidatos dos quais um em cinquenta está em
português dá menos de uma linha em português em média, que é o que a primeira coluna mostra. O
planejador escolheu esse plano sozinho: a consulta não diz *busque primeiro*, e nada na tela sugere
isso.

Subir o `ef_search` alarga a lista de candidatos, e as contagens sobem:
