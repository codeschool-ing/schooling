**The shop's vault is declared with everything lesson 16 asked for, and gives the application one role.**

```bicep
// vault.bicep
param appPrincipalId string

resource vault 'Microsoft.KeyVault/vaults@2023-07-01' = {
  name: 'kv-shop-prod'
  location: 'brazilsouth'
  properties: {
    tenantId: subscription().tenantId
    sku: { family: 'A', name: 'standard' }
    enableRbacAuthorization: true
    enableSoftDelete: true
    softDeleteRetentionInDays: 90
    enablePurgeProtection: true
    publicNetworkAccess: 'Disabled'
  }
}

// Key Vault Secrets User: read secret values, nothing else
var secretsUser = subscriptionResourceId('Microsoft.Authorization/roleDefinitions', '4633458b-17de-408a-b874-0445c86b69e6')

resource appReads 'Microsoft.Authorization/roleAssignments@2022-04-01' = {
  name: guid(vault.id, appPrincipalId, secretsUser)
  scope: vault
  properties: {
    roleDefinitionId: secretsUser
    principalId: appPrincipalId
    principalType: 'ServicePrincipal'
  }
}

output vaultUri string = vault.properties.vaultUri
```

```
ana@laptop:~/azure/vault$ bicep build vault.bicep; echo "exit status $?"
exit status 0
ana@laptop:~/azure/vault$ jq -r '.resources[] | .type' vault.json
Microsoft.KeyVault/vaults
Microsoft.Authorization/roleAssignments
```

Four settings carry the decisions. **`enableRbacAuthorization: true`** puts access to secrets under Azure
RBAC, the same role assignments as everything else, instead of the vault's older *access policies*, which
are a second permission system with its own list nobody remembers to review. **Soft delete for 90 days**
and **purge protection**, from the previous section. And **`publicNetworkAccess: 'Disabled'`**: the vault
answers only on a private endpoint, which lesson 20 builds.

The role assignment gives the application's **managed identity** the built-in role *Key Vault Secrets
User*, identified by its fixed GUID, at the scope of this one vault. That role reads secret values and
does nothing else: it cannot list keys, cannot write, cannot change who has access. `guid()` makes the
assignment's name deterministic from the vault, the principal and the role, so deploying twice does not
create two assignments. Managed identities are `azure-foundations` lesson 8; the point here is that
**the application holds no credential to reach the vault at all**: Azure vouches for it.

## The secret that is not in the template

Bicep can create a secret, and that is where vaults leak. This file takes the password as a parameter and
writes it into the vault:

```bicep
// leaky.bicep
param dbPassword string

resource vault 'Microsoft.KeyVault/vaults@2023-07-01' existing = {
  name: 'kv-shop-prod'
}

resource secret 'Microsoft.KeyVault/vaults/secrets@2023-07-01' = {
  parent: vault
  name: 'db-password'
  properties: {
    value: dbPassword
  }
}
```

```
ana@laptop:~/azure/vault$ bicep lint leaky.bicep; echo "exit status $?"
/home/ana/azure/vault/leaky.bicep(2,7) : Warning secure-secrets-in-params: Parameter 'dbPassword' may represent a secret (according to its name) and must be declared with the '@secure()' attribute. [https://aka.ms/bicep/linter-diagnostics#secure-secrets-in-params]
exit status 0
```

The linter noticed the name and asked for `@secure()`, and it is right, and it is still a warning with an
exit status of 0. Even with `@secure()`, a password that passes through a template has passed through a
pipeline, a parameter file or an environment variable on its way. **The shop never writes secret values
in Bicep.** The template creates the vault and the access; the values are set once, by a person, with
`az keyvault secret set`, or generated by the service that owns them, such as a database that creates its
own credentials. That command was not run here: there is no vault.
