**Uma tela que se redesenha 60 vezes por segundo dá a cada quadro 16,7 milissegundos**; uma que se
redesenha 120 vezes dá 8,3. Se um quadro não fica pronto a tempo, o anterior continua na tela por mais
um intervalo, e uma coisa em movimento que deveria ter avançado parece parar e depois pular. É isso que
chamam de jank, e num celular, onde tudo rola e desliza, todo mundo nota na hora.

## Qual thread perde o quadro

A aula 1 desenhou três lugares onde o trabalho acontece. Uma animação pode ser conduzida por qualquer
uma de duas threads:

| conduzida por | a cada quadro | o que pode pará-la |
|---|---|---|
| a thread do JavaScript | o JavaScript calcula o novo valor e o manda para a view nativa | qualquer trabalho naquela thread: uma renderização, um laço longo, o parse de uma resposta grande |
| a thread de UI | o lado nativo calcula o valor a partir de uma descrição que recebeu uma vez | quase nada; é a thread que desenha |

**Uma animação conduzida pelo JavaScript engasga sempre que o app está ocupado**, e é justamente quando
algo muda na tela: uma lista carregando, um toque sendo tratado. Esse é o argumento inteiro a favor das
ferramentas desta aula. Cada uma descreve a animação uma vez e deixa a thread de UI rodá-la.

## O que pode sair da thread do JavaScript

Nem tudo. O lado nativo consegue animar um valor sem o JavaScript só se a propriedade que ele muda não
pede um layout novo. **Transformações (mover, escalar, girar) e opacidade se qualificam; largura,
altura, padding e tudo o mais que o Yoga precisa recalcular, não.** Essa restrição molda o jeito de
escrever animações: a barra do planner não anima a largura, anima uma escala horizontal, que parece a
mesma coisa e fica na thread de UI.
