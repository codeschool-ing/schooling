**A screen that redraws 60 times a second gives each frame 16.7 milliseconds**; one that redraws 120
times gives it 8.3. If a frame is not ready in time, the previous one stays on screen for another
interval, and a moving thing that should have advanced appears to stop and then jump. That is what
people call jank, and on a phone, where everything scrolls and slides, it is noticed at once.

## Which thread misses the frame

Lesson 1 drew three places work happens. An animation can be driven from either thread:

| driven by | each frame | what can stop it |
|---|---|---|
| the JavaScript thread | JavaScript computes the new value and sends it to the native view | any work on that thread: a render, a long loop, parsing a big response |
| the UI thread | the native side computes the value from a description it was given once | very little; it is the thread that draws |

**An animation driven from JavaScript stutters whenever your app is busy**, which is exactly when
something is changing on screen: a list is loading, a press is being handled. That is the whole argument
for the tools in this lesson. Each one describes the animation once and lets the UI thread run it.

## What can move off the JavaScript thread

Not everything. The native side can animate a value without JavaScript only if the property it changes
does not need a new layout. **Transforms (moving, scaling, rotating) and opacity qualify; width, height,
padding and anything else Yoga must recompute do not.** That constraint shapes how animations are
written: the planner's bar does not animate its width, it animates a horizontal scale, which looks the
same and stays on the UI thread.
