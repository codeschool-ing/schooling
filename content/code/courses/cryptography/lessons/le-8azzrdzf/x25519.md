**X25519 is Diffie-Hellman on Curve25519: each side's secret is a 32-byte private key, the value it
sends is its 32-byte public key, and the shared secret is 32 bytes.** It is the default key exchange
in TLS 1.3, SSH, Signal and WireGuard, and it is what the toy of the previous section looks like at
real size.

## Ana and Bruno, again

The lab has an X25519 pair for each of them. The public halves are what each would send:

```
ana@lab:~/lab$ cat keys/x25519-ana.pub keys/x25519-bruno.pub
-----BEGIN PUBLIC KEY-----
MCowBQYDK2VuAyEASTbzLBVkMLZYXweeov2PfYEtT5ofFaRNGCwbTD0AaRI=
-----END PUBLIC KEY-----
-----BEGIN PUBLIC KEY-----
MCowBQYDK2VuAyEAhULFT23bDRg+0PZvKDTwvrRc7SlAQWOXgnIfa4B/yAs=
-----END PUBLIC KEY-----
```

Ana combines her private key with Bruno's public key; Bruno combines his private key with Ana's:

```
ana@lab:~/lab$ openssl pkeyutl -derive -inkey keys/x25519-ana.key -peerkey keys/x25519-bruno.pub | xxd -p -c 32
1d3d4704e495e9da6c993a3bb7d20b8906d2d1e8c06a85c5610a27d42bf97436
ana@lab:~/lab$ openssl pkeyutl -derive -inkey keys/x25519-bruno.key -peerkey keys/x25519-ana.pub | xxd -p -c 32
1d3d4704e495e9da6c993a3bb7d20b8906d2d1e8c06a85c5610a27d42bf97436
```

The same 32 bytes, computed separately from opposite halves. Nothing in those two PEM blocks lets
anybody else compute them.

## From shared secret to keys

The shared secret is a point on a curve encoded as bytes, and its bits are not uniformly random. It
is never used directly as an AES key. **HKDF** (RFC 5869), a key derivation function built from
HMAC, turns it into keys of the right length, and a label, the *info*, makes keys for different
purposes come out unrelated:

```
ana@lab:~/lab$ openssl kdf -keylen 32 -kdfopt digest:SHA256 -kdfopt info:vereda-session -kdfopt hexkey:$(openssl pkeyutl -derive -inkey keys/x25519-ana.key -peerkey keys/x25519-bruno.pub | xxd -p -c 32) HKDF
D6:B1:28:59:90:C5:95:FD:99:BC:42:92:27:A1:51:4C:B7:C6:43:40:6A:36:D6:61:F4:00:5C:08:95:F6:05:B4
```

TLS 1.3 runs HKDF many times over one shared secret, with labels such as `c hs traffic` and
`s ap traffic`, to get separate keys for each direction and each stage of the connection. A key
compromised for one purpose says nothing about the others.

## Why curves won this job

The classic exchange of the previous section works with a 2048-bit prime and is still supported, as
*finite-field* Diffie-Hellman (`ffdhe2048` and up in TLS 1.3). X25519 replaced it in practice for
the reasons lesson 2 gave for curves in general: the values sent are 32 bytes instead of 256, the
computation is much faster, and the curve was designed so that the obvious implementation is also
the safe one. Every public key of 32 bytes is a valid input, so a whole category of checks that
finite-field implementations got wrong does not exist.

X25519 is for **agreeing** on a key, and nothing else. It does not sign: that is Ed25519, the same
curve in a different role, and the two keys are not interchangeable.
