**Asymmetric cryptography gives each party two keys: a public key that anybody may have and a
private key that only its owner holds.** They are made together, as a pair, and what one does
the other undoes. That removes the problem lesson 1 left open: Vereda's server can publish its
public key to the whole internet, and a patient's browser that has never met the server can still
use it.

## A pair is made, not chosen

A key pair is generated by a program from random bytes, in one step. With OpenSSL the command is
`genpkey`, naming the algorithm:

```sh
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 -out server.key
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out server.key
openssl genpkey -algorithm ED25519 -out signer.key
```

Each run gives a different key, which is the point, so the lab does not use these. Its pairs are
derived from fixed labels by `vlab/keys.py`, so that the transcripts below come out the same on
your machine. Here they are:

```
ana@lab:~/lab$ ls keys/rsa-2048.* keys/p256.* keys/ed25519-ana.*
keys/ed25519-ana.key
keys/ed25519-ana.pub
keys/p256.key
keys/p256.pub
keys/rsa-2048.key
keys/rsa-2048.pub
```

Every pair is two files. The `.key` file is the private key and the `.pub` file is the public one.
A public key is short and harmless to print:

```
ana@lab:~/lab$ cat keys/ed25519-ana.pub
-----BEGIN PUBLIC KEY-----
MCowBQYDK2VwAyEAputVssQeGrq75yYKhthuhas/ZiniEYjnFcuBvjmLkmc=
-----END PUBLIC KEY-----
```

That is the whole of Ana's Ed25519 public key, in PEM: Base64 between two marker lines, which
lesson 11 takes apart. It could be pasted into an e-mail, a web page or a commit without losing
anything.

## The public key comes from the private one

The two halves are not independent. **The private key contains everything needed to compute the
public key**, so OpenSSL can rebuild the `.pub` file from the `.key` file alone:

```
ana@lab:~/lab$ openssl pkey -in keys/ed25519-ana.key -pubout | cmp - keys/ed25519-ana.pub && echo "derived from the private key: identical"
derived from the private key: identical
```

The reverse is impossible, and the whole field rests on that asymmetry. Computing the public key
from the private one takes a fraction of a second. Computing the private key from the public one
would mean solving a mathematical problem nobody knows how to solve in any reasonable time for keys
of the right size: factoring for RSA, the discrete logarithm on a curve for elliptic curves. The
next two sections say what each problem is, at the level needed to choose between them.

## What a public key file says

Asked to describe a public key, OpenSSL names the algorithm and prints the key itself:

```
ana@lab:~/lab$ openssl pkey -pubin -in keys/ed25519-ana.pub -noout -text
ED25519 Public-Key:
pub:
    a6:eb:55:b2:c4:1e:1a:ba:bb:e7:26:0a:86:d8:6e:
    85:ab:3f:66:29:e2:11:88:e7:15:cb:81:be:39:8b:
    92:67
```

Thirty-two bytes, and nothing else. There is no owner's name in it, no date and no domain. **A
public key on its own says nothing about whose key it is.** Anybody can generate a pair and claim
the public half belongs to Vereda. Binding a key to a name is the job of a certificate, and lessons
8 and 9 build that binding. Until then, a public key received from somewhere is only as
trustworthy as the channel it came through.

## What the private key file must never do

The `.key` file is the one secret in all of this, and its handling decides everything:

- **it never leaves the machine that uses it.** A server's private key lives on the server, or
  better in a hardware module that signs without ever exporting it (lesson 8 comes back to this);
- **it is readable by the service that needs it and by nobody else**, which on Linux means mode
  `600` and the service's own user;
- **it is never committed**, pasted into a ticket or sent to a colleague "just for a moment".
  Lesson 17 is about how often that happens anyway.

A private key that leaks is replaced, not repaired. The pair is discarded, a new one generated, and
everything that trusted the old public key told to stop.
