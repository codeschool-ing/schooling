A aula 11 respondeu **quem está pedindo**. Esta aula responde **o que a pessoa pode fazer**, que é a
**autorização**, e a primeira coisa a achar é onde a API do agenda responde isso errado. Dê a ela uma
terceira conta, a Carla, que se inscreve em eventos e não organiza nenhum:

```
ana@vm:~/agenda$ uv run python manage.py shell -v 0 -c "from django.contrib.auth.models import User; User.objects.create_user('carla', 'carla@example.org', 'k7-meadow-harbour-23')"
```

O `doors.py` tenta quatro requisições como quatro pessoas e imprime o status de cada uma. Salve em
`~/agenda`:

**A Carla mudou os dois eventos.** O `IsAuthenticatedOrReadOnly` faz uma pergunta só, se existe algum
usuário, e qualquer conta responde sim. Os `400` da última linha são o mesmo buraco: a requisição
chegou ao serializer, que recusou um evento vazio, então criar um com um corpo de verdade teria
funcionado para qualquer pessoa com conta.

## Dois códigos, duas perguntas

A coluna anônima é 401, e a aula 11 mostrou por quê:

```
ana@vm:~/agenda$ curl -si -X PATCH http://127.0.0.1:8000/api/events/testing-dojo/ -H 'Content-Type: application/json' -d '{}' | grep -iE '^(HTTP|www-authenticate)|detail'
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Token
{"detail":"Authentication credentials were not provided."}
```

| | 401 Unauthorized | 403 Forbidden |
|---|---|---|
| quer dizer | **não sei quem você é** | **sei quem você é, e não** |
| vem com | `WWW-Authenticate`, dizendo como entrar | nada para tentar |
| o cliente deve | entrar, ou mandar um token, e tentar de novo | parar: pedir de novo não vai ajudar |

Os nomes são históricos e enganam, já que o 401 trata de autenticação; o que importa é que um cliente
consegue agir sobre a diferença. A aula 6 recebeu 403 numa escrita anônima porque a
`SessionAuthentication` não tem esquema para nomear num cabeçalho `WWW-Authenticate`, e então o DRF
responde 403; com a `TokenAuthentication` em primeiro, a mesma requisição é um 401.
