Lesson 11 answered **who is asking**. This lesson answers **what they may do**, which is
**authorisation**, and the first thing to find is where agenda's API answers it wrongly. Give it a
third account, Carla, who registers for events and organises none:

**Carla changed both events.** `IsAuthenticatedOrReadOnly` asks one question, whether there is a
user at all, and any account answers yes. The `400`s in the last line are the same hole: the request
reached the serializer, which refused an empty event, so creating one with a real body would have
worked for anybody with an account.

## Two codes, two questions

The anonymous column is 401, and lesson 11 showed why:

```
ana@vm:~/agenda$ curl -si -X PATCH http://127.0.0.1:8000/api/events/testing-dojo/ -H 'Content-Type: application/json' -d '{}' | grep -iE '^(HTTP|www-authenticate)|detail'
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Token
{"detail":"Authentication credentials were not provided."}
```

| | 401 Unauthorized | 403 Forbidden |
|---|---|---|
| means | **I do not know who you are** | **I know who you are, and no** |
| comes with | `WWW-Authenticate`, naming how to log in | nothing to try |
| the client should | log in, or send a token, and try again | stop: asking again will not help |

The names are historical and misleading, since 401 is about authentication; what matters is that a
client can act on the difference. Lesson 6 got 403 for an anonymous write because
`SessionAuthentication` has no scheme to name in a `WWW-Authenticate` header, and DRF then answers
403 instead; with `TokenAuthentication` first, the same request is a 401.
