---
title: What belongs in the environment
version: 1
---

agenda's code has been carrying facts about one machine: `DEBUG = True`, a secret key `startproject`
wrote, a database reached through the local socket as ana, a JWT key pasted into `app/security.py`
in lesson 11. On a server each of those is wrong, and two of them are dangerous. The answer most
projects follow is the one the **Twelve-Factor App** wrote down: **configuration that varies between
deployments lives in the environment**, and the code reads it from there.

The **environment** is a set of names and values every process inherits from whatever started it.
Python sees it as `os.environ`:

```
ana@vm:~/agenda$ uv run python -c "import os; print(os.environ.get('DJANGO_DEBUG'))"
None
ana@vm:~/agenda$ DJANGO_DEBUG=1 uv run python -c "import os; print(os.environ.get('DJANGO_DEBUG'))"
1
```

The same code printed two different values, and nothing in it changed. That is the property wanted:
one codebase, deployed to a laptop, a test server and production, each telling it what it needs to
know.

The test for each value is whether it would change if the same code ran somewhere else. The
installed apps would not; the database host would. **Secrets** are values of the second kind that
must also never be written where somebody could read them: not in the code, not in git, not in a log.
