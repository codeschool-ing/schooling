O Alembic mantém uma **cadeia de scripts de migração**, cada um nomeando o anterior, e uma tabela no
banco registrando a qual deles chegou. Prepare-o no projeto:

```
ana@vm:~/agenda-api$ uv run alembic init migrations
Creating directory /home/ana/agenda-api/migrations ...  done
Creating directory /home/ana/agenda-api/migrations/versions ...  done
Generating /home/ana/agenda-api/migrations/script.py.mako ...  done
Generating /home/ana/agenda-api/migrations/README ...  done
Generating /home/ana/agenda-api/migrations/env.py ...  done
Generating /home/ana/agenda-api/alembic.ini ...  done
Please edit configuration/connection/logging settings in /home/ana/agenda-api/alembic.ini before proceeding.
```

Duas edições antes de ele conseguir fazer qualquer coisa. No `alembic.ini`, a linha `sqlalchemy.url`
guarda um texto de exemplo; troque pela URL da engine. No `migrations/env.py`, a linha
`target_metadata = None` é aquilo com que o autogenerate compara o banco; aponte-a para o metadata dos
models:

```
ana@vm:~/agenda-api$ grep -n "^sqlalchemy.url" alembic.ini
89:sqlalchemy.url = postgresql+psycopg:///agenda_api
ana@vm:~/agenda-api$ grep -n -A2 "import Base" migrations/env.py
21:from app.models import Base
22-
23-target_metadata = Base.metadata
```

Agora peça uma migração. O `--autogenerate` compara `Base.metadata` com o banco e escreve a
diferença; o `--rev-id` chama a revisão de `0001` em vez de uma sequência hexadecimal aleatória, o que
mantém os arquivos em ordem quando listados:

```
ana@vm:~/agenda-api$ uv run alembic revision --autogenerate --rev-id 0001 -m "events and registrations"

porque é isso mesmo**: o arquivo é um rascunho escrito comparando dois esquemas, e a próxima seção é o
caso em que o rascunho está errado. Aqui ele está certo, então aplique:

```

A tabela é a que o `show_sql.py` imprimiu, com nomes para as restrições que o PostgreSQL escolheu:
`registrations_event_id_email_key` é a regra de um endereço por evento.

## Linhas, por uma session

As tabelas estão vazias. Os três eventos ainda moram em `app/store.py`, então um script de uso único
pode copiá-los. Salve o `seed.py`:

```python
# seed.py
from sqlalchemy.orm import Session

from app.db import engine
from app.models import Event
from app.store import EVENTS

with Session(engine) as session:
    session.add_all(Event(**data) for data in EVENTS.values())
    session.commit()
    print("added", len(EVENTS), "events")
```

```
ana@vm:~/agenda-api$ uv run python seed.py
added 3 events
ana@vm:~/agenda-api$ uv run alembic current
INFO  [alembic.runtime.migration] Context impl PostgresqlImpl.
INFO  [alembic.runtime.migration] Will assume transactional DDL.
0001 (head)
```

A **session** é a unidade de trabalho do ORM: o `add_all` entrega objetos a ela, nada é mandado até o
`commit`, e então ela os escreve numa transação. O `alembic current` lê a tabela `alembic_version`,
que agora guarda uma linha, `0001`.
