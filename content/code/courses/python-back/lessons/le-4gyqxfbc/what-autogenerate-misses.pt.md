---
title: O que o autogenerate não enxerga
version: 1
---

O autogenerate compara duas listas de tabelas e colunas. Isso funciona para uma coluna adicionada ou
removida, e é exatamente o errado para uma renomeada. Suponha que `venue` deva se chamar `place`: mude
o nome do atributo em `app/models.py` e peça uma migração:

```
ana@vm:~/agenda-api$ grep -n "place" app/models.py
19:    place: Mapped[str] = mapped_column(String(200))
ana@vm:~/agenda-api$ uv run alembic revision --autogenerate --rev-id 0002 -m "venue is now place"
INFO  [alembic.runtime.migration] Context impl PostgresqlImpl.
INFO  [alembic.runtime.migration] Will assume transactional DDL.
INFO  [alembic.runtime.plugins] setting up autogenerate plugin alembic.autogenerate.schemas
INFO  [alembic.runtime.plugins] setting up autogenerate plugin alembic.autogenerate.tables
INFO  [alembic.runtime.plugins] setting up autogenerate plugin alembic.autogenerate.types
INFO  [alembic.runtime.plugins] setting up autogenerate plugin alembic.autogenerate.constraints
INFO  [alembic.runtime.plugins] setting up autogenerate plugin alembic.autogenerate.defaults
INFO  [alembic.runtime.plugins] setting up autogenerate plugin alembic.autogenerate.comments
INFO  [alembic.ddl.postgresql] Detected sequence named 'registrations_id_seq' as owned by integer column 'registrations(id)', assuming SERIAL and omitting
INFO  [alembic.ddl.postgresql] Detected sequence named 'events_id_seq' as owned by integer column 'events(id)', assuming SERIAL and omitting
INFO  [alembic.autogenerate.compare.tables] Detected added column 'events.place'
INFO  [alembic.autogenerate.compare.tables] Detected removed column 'events.venue'
Generating /home/ana/agenda-api/migrations/versions/0002_venue_is_now_place.py ...  done
```

**"Detected added column `events.place`", "Detected removed column `events.venue`".** Visto de fora,
renomear parece o mesmo que apagar uma coluna e criar outra, e foi isso que ele escreveu:

```
ana@vm:~/agenda-api$ sed -n '/^def upgrade/,$p' migrations/versions/0002_venue_is_now_place.py
def upgrade() -> None:
    """Upgrade schema."""
    # ### commands auto generated by Alembic - please adjust! ###
    op.add_column('events', sa.Column('place', sa.String(length=200), nullable=False))
    op.drop_column('events', 'venue')
    # ### end Alembic commands ###


def downgrade() -> None:
    """Downgrade schema."""
    # ### commands auto generated by Alembic - please adjust! ###
    op.add_column('events', sa.Column('venue', sa.VARCHAR(length=200), autoincrement=False, nullable=False))
    op.drop_column('events', 'place')
    # ### end Alembic commands ###
```

Rodada como está, numa tabela com linhas:

```
ana@vm:~/agenda-api$ uv run alembic upgrade head 2>&1 | tail -3
sqlalchemy.exc.IntegrityError: (psycopg.errors.NotNullViolation) column "place" of relation "events" contains null values
[SQL: ALTER TABLE events ADD COLUMN place VARCHAR(200) NOT NULL]
(Background on this error at: https://sqlalche.me/e/21/gkpj)
```

**Este é o caso de sorte.** A coluna nova não pode ser nula, então adicioná-la a três linhas que não
têm valor falhou, e o PostgreSQL desfez a migração inteira: o "transactional DDL" que o Alembic
anunciou toda vez quer dizer que uma migração que falha não deixa nada pela metade. Numa tabela vazia,
ou com uma coluna que aceita nulo, o mesmo arquivo teria rodado sem uma palavra e **jogado fora todos
os locais**.

O conserto é dizer o que se quis. Troque as duas funções por uma renomeação em cada sentido:

```
ana@vm:~/agenda-api$ sed -n '/^def upgrade/,$p' migrations/versions/0002_venue_is_now_place.py
def upgrade() -> None:
    op.alter_column("events", "venue", new_column_name="place")


def downgrade() -> None:
    op.alter_column("events", "place", new_column_name="venue")
ana@vm:~/agenda-api$ uv run alembic upgrade head
INFO  [alembic.runtime.migration] Context impl PostgresqlImpl.
INFO  [alembic.runtime.migration] Will assume transactional DDL.
INFO  [alembic.runtime.migration] Running upgrade 0001 -> 0002, venue is now place
ana@vm:~/agenda-api$ psql agenda_api -c "select slug, place from events"
      slug      |          place           
----------------+--------------------------
 django-night   | Community Centre, room 3
 async-workshop | Public Library, lab 2
 testing-dojo   | Community Centre, room 3
(3 rows)
```

Os locais passaram. O `alembic history` mostra a cadeia, e o `downgrade -1` anda um passo para trás:

```
ana@vm:~/agenda-api$ uv run alembic history
0001 -> 0002 (head), venue is now place
<base> -> 0001, events and registrations
ana@vm:~/agenda-api$ uv run alembic downgrade -1
INFO  [alembic.runtime.migration] Context impl PostgresqlImpl.
INFO  [alembic.runtime.migration] Will assume transactional DDL.
INFO  [alembic.runtime.migration] Running downgrade 0002 -> 0001, venue is now place
```

A API ainda diz `venue` em todo lugar, então esta renomeação foi só uma demonstração. Com o banco na
`0001`, apague o arquivo e volte o `venue` no model. Depois, o **`alembic check`**, que compara models e
banco sem escrever arquivo nenhum:

```
ana@vm:~/agenda-api$ rm migrations/versions/0002_venue_is_now_place.py
ana@vm:~/agenda-api$ uv run alembic check
INFO  [alembic.runtime.migration] Context impl PostgresqlImpl.
INFO  [alembic.runtime.migration] Will assume transactional DDL.
INFO  [alembic.runtime.plugins] setting up autogenerate plugin alembic.autogenerate.schemas
INFO  [alembic.runtime.plugins] setting up autogenerate plugin alembic.autogenerate.tables
INFO  [alembic.runtime.plugins] setting up autogenerate plugin alembic.autogenerate.types
INFO  [alembic.runtime.plugins] setting up autogenerate plugin alembic.autogenerate.constraints
INFO  [alembic.runtime.plugins] setting up autogenerate plugin alembic.autogenerate.defaults
INFO  [alembic.runtime.plugins] setting up autogenerate plugin alembic.autogenerate.comments
INFO  [alembic.ddl.postgresql] Detected sequence named 'registrations_id_seq' as owned by integer column 'registrations(id)', assuming SERIAL and omitting
INFO  [alembic.ddl.postgresql] Detected sequence named 'events_id_seq' as owned by integer column 'events(id)', assuming SERIAL and omitting
No new upgrade operations detected.
```

"No new upgrade operations detected": models e tabelas concordam. Um projeto roda `alembic check` na
CI para que um model alterado sem migração quebre o build em vez do deploy.

## O que ler com atenção

Renomear tabelas e colunas é o caso comum. A documentação do Alembic mantém a lista completa em
*What does Autogenerate Detect (and what does it not detect?)*, e ela inclui restrições sem nome e
algumas mudanças de tipo. E nenhuma comparação de esquemas consegue escrever uma **migração de
dados**, uma mudança nas próprias linhas, como preencher uma coluna nova a partir de uma antiga: essas
são escritas à mão, com `op.execute`, dentro dos mesmos arquivos.
