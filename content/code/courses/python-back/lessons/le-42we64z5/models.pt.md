Um **modelo** descreve uma tabela como uma classe Python: cada atributo é uma coluna, e o Django
escreve o SQL. O agenda tem dois, os eventos e as inscrições neles. Troque o `events/models.py`:

## De uma classe a uma tabela

O `makemigrations` compara os modelos com o que as migrações até ali descrevem, e escreve uma nova
migração para a diferença. O `sqlmigrate` imprime o SQL que uma migração vai rodar, sem rodá-lo:

```
ana@vm:~/agenda$ uv run python manage.py makemigrations events
Migrations for 'events':
  events/migrations/0001_initial.py
    + Create model Event
    + Create model Registration
ana@vm:~/agenda$ uv run python manage.py sqlmigrate events 0001
BEGIN;
--
-- Create model Event
--
CREATE TABLE "events_event" ("id" bigint NOT NULL PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY, "title" varchar(200) NOT NULL, "slug" varchar(50) NOT NULL UNIQUE, "starts_at" timestamp with time zone NOT NULL, "venue" varchar(200) NOT NULL, "capacity" integer NOT NULL CHECK ("capacity" >= 0));
--
-- Create model Registration
--
CREATE TABLE "events_registration" ("id" bigint NOT NULL PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY, "name" varchar(100) NOT NULL, "email" varchar(254) NOT NULL, "created_at" timestamp with time zone NOT NULL, "event_id" bigint NOT NULL, CONSTRAINT "one_registration_per_email" UNIQUE ("event_id", "email"));
CREATE INDEX "events_event_slug_b44b2c04_like" ON "events_event" ("slug" varchar_pattern_ops);
ALTER TABLE "events_registration" ADD CONSTRAINT "events_registration_event_id_75b6f198_fk_events_event_id" FOREIGN KEY ("event_id") REFERENCES "events_event" ("id") DEFERRABLE INITIALLY DEFERRED;
CREATE INDEX "events_registration_event_id_75b6f198" ON "events_registration" ("event_id");
COMMIT;
```

Tudo o que está nos modelos está ali: colunas de identidade `bigint` que o Django acrescentou como
chaves primárias, um `UNIQUE` no slug e a restrição com nome em `(event_id, email)`, o `CHECK` que
veio do `PositiveIntegerField`, e uma chave estrangeira das inscrições para os eventos com um índice.
**Este é o momento de ler o SQL**, antes de ele rodar. Um índice faltando aqui é uma página lenta
daqui a seis meses.

```
ana@vm:~/agenda$ uv run python manage.py migrate events
Operations to perform:
  Apply all migrations: events
Running migrations:
  Applying events.0001_initial... OK
```

## Os eventos, como linhas

Os três eventos da aula 3 agora vão para a tabela. Um script curto faz isso, e roda de novo sem
problema: o `update_or_create` acha a linha pelo slug e a atualiza, ou cria se não houver. Salve como
`seed.py` em `~/agenda`:

```python
# seed.py
from datetime import datetime
from zoneinfo import ZoneInfo

from events.models import Event

SAO_PAULO = ZoneInfo("America/Sao_Paulo")
EVENTS = [
    ("django-night", "Django Night", datetime(2026, 11, 12, 19, 0), "Community Centre, room 3", 40),
    ("async-workshop", "Async Python workshop", datetime(2026, 11, 19, 14, 0), "Public Library, lab 2", 12),
    ("testing-dojo", "Testing dojo", datetime(2026, 11, 26, 19, 0), "Community Centre, room 3", 20),
]

for slug, title, starts_at, venue, capacity in EVENTS:
    event, created = Event.objects.update_or_create(
        slug=slug,
        defaults={
            "title": title,
            "starts_at": starts_at.replace(tzinfo=SAO_PAULO),
            "venue": venue,
            "capacity": capacity,
        },
    )
    print("created" if created else "updated", event.slug, event.pk)
```

O `manage.py shell` lê um script da entrada como se você o tivesse digitado:

```
ana@vm:~/agenda$ uv run python manage.py shell < seed.py
14 objects imported automatically (use -v 2 for details).

created django-night 1
created async-workshop 2
created testing-dojo 3
```

A linha sobre objetos importados é do shell, como na aula 2. Com os eventos no banco, o
`events/data.py` não tem mais trabalho; ele sai quando as views pararem de importá-lo, na penúltima
seção. Pergunte ao PostgreSQL o que ele gravou:

```
ana@vm:~/agenda$ psql agenda -c "SELECT id, slug, starts_at, capacity FROM events_event"
 id |      slug      |       starts_at        | capacity 
----+----------------+------------------------+----------
  1 | django-night   | 2026-11-12 19:00:00-03 |       40
  2 | async-workshop | 2026-11-19 14:00:00-03 |       12
  3 | testing-dojo   | 2026-11-26 19:00:00-03 |       20
(3 rows)

ana@vm:~/agenda$ psql agenda -c "SHOW timezone"
     TimeZone      
-------------------
 America/Sao_Paulo
(1 row)
```

**`19:00:00-03` é 19:00 em São Paulo, três horas atrás de UTC**, e o fuso aparece porque a coluna é
`timestamp with time zone`. O PostgreSQL guarda o instante e o imprime no fuso da sessão, que nesta
máquina é o de São Paulo. O Django o lê de volta como um valor em UTC, e o filtro `date` do template
o converte para o `TIME_ZONE` na página, então 19:00 na página é 19:00 na sala.
