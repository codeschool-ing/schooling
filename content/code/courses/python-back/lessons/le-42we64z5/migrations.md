---
title: Migrations are the history of the schema
version: 1
---

A migration is a Python file describing one change to the database, and the migrations of an app,
in order, are **the history of its tables**. They are code: committed with the change that needed
them, reviewed, and run on every machine the project runs on, so a colleague's database and the
production one end up with the same tables. Django records which have been applied:

```
ana@vm:~/agenda$ uv run python manage.py showmigrations events
events
 [X] 0001_initial
```

## A change to a model

Events need a description. Add one line to `Event`, after `capacity`:

```
ana@vm:~/agenda$ grep -n -A1 'capacity = ' events/models.py
10:    capacity = models.PositiveIntegerField()
11-    description = models.TextField(blank=True)
```

`blank=True` lets a form leave it empty. Ask for a migration and read what it wrote:

```
ana@vm:~/agenda$ uv run python manage.py makemigrations events
Migrations for 'events':
  events/migrations/0002_event_description.py
    + Add field description to event
ana@vm:~/agenda$ cat events/migrations/0002_event_description.py
# Generated by Django 6.1.2 on 2026-10-16 23:11

from django.db import migrations, models


class Migration(migrations.Migration):

    dependencies = [
        ('events', '0001_initial'),
    ]

    operations = [
        migrations.AddField(
            model_name='event',
            name='description',
            field=models.TextField(blank=True),
        ),
    ]
```

One operation, `AddField`, and a dependency on `0001_initial`, which is how Django knows the order.
The SQL is more interesting than the Python:

```
ana@vm:~/agenda$ uv run python manage.py sqlmigrate events 0002
BEGIN;
--
-- Add field description to event
--
ALTER TABLE "events_event" ADD COLUMN "description" text DEFAULT '' NOT NULL;
ALTER TABLE "events_event" ALTER COLUMN "description" DROP DEFAULT;
COMMIT;
```

**Existing rows need a value for a `NOT NULL` column**, so the column is added with a default of the
empty string, which fills the three events, and the default is then dropped, because Django keeps
defaults in Python rather than in the database. On a table of a few rows that is instant. On a table
of millions, adding a column with a default is a question for the database's documentation before it
is a migration, and `sqlmigrate` is how you find out what you would be asking it to do.

```
ana@vm:~/agenda$ uv run python manage.py migrate events
Operations to perform:
  Apply all migrations: events
Running migrations:
  Applying events.0002_event_description... OK
```

## Three rules

- **Commit migrations, and never edit one that has been applied anywhere else.** A changed migration
  that already ran on a colleague's machine does not run again there, so the two databases quietly
  differ. A mistake is fixed with a new migration.
- **Every model change gets its migration in the same commit.** This command fails when a model
  changed and nobody ran `makemigrations`, which makes it a good check for CI:

```
ana@vm:~/agenda$ uv run python manage.py makemigrations --check --dry-run
No changes detected
```

- **Data changes are migrations too.** Filling a new column from an old one is a migration with a
  `RunPython` operation, so it runs once, in order, on every database. `seed.py` was not a migration
  because the three events are this course's sample data, which no production database should get.
