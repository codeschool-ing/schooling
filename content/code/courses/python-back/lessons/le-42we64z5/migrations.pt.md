---
title: Migrações são o histórico do esquema
version: 1

Uma migração é um arquivo Python que descreve uma mudança no banco, e as migrações de um app, em
ordem, são **o histórico das tabelas dele**. Elas são código: versionadas junto com a mudança que as
pediu, revisadas, e rodadas em toda máquina onde o projeto roda, para que o banco de um colega e o de
produção terminem com as mesmas tabelas. O Django registra quais já foram aplicadas:

```
ana@vm:~/agenda$ uv run python manage.py showmigrations events
events
 [X] 0001_initial
```

## Uma mudança num modelo

Os eventos precisam de uma descrição. Acrescente uma linha a `Event`, depois de `capacity`:

```
ana@vm:~/agenda$ grep -n -A1 'capacity = ' events/models.py
10:    capacity = models.PositiveIntegerField()
11-    description = models.TextField(blank=True)
```

O `blank=True` deixa um formulário mandá-la vazia. Peça uma migração e leia o que ela escreveu:

```
ana@vm:~/agenda$ uv run python manage.py makemigrations events
Migrations for 'events':
  events/migrations/0002_event_description.py
    + Add field description to event
ana@vm:~/agenda$ cat events/migrations/0002_event_description.py
# Generated by Django 6.1.2 on 2026-10-16 23:11

from django.db import migrations, models


class Migration(migrations.Migration):

    dependencies = [
        ('events', '0001_initial'),
    ]

    operations = [
        migrations.AddField(
            model_name='event',
            name='description',
            field=models.TextField(blank=True),
        ),
    ]
```

Uma operação, `AddField`, e uma dependência de `0001_initial`, que é como o Django sabe a ordem. O
SQL é mais interessante que o Python:

```
ana@vm:~/agenda$ uv run python manage.py sqlmigrate events 0002
BEGIN;
--
-- Add field description to event
--
ALTER TABLE "events_event" ADD COLUMN "description" text DEFAULT '' NOT NULL;
ALTER TABLE "events_event" ALTER COLUMN "description" DROP DEFAULT;
COMMIT;
```

**Linhas existentes precisam de um valor para uma coluna `NOT NULL`**, então a coluna é acrescentada
com o texto vazio como padrão, que preenche os três eventos, e depois o padrão é retirado, porque o
Django guarda padrões no Python e não no banco. Numa tabela de poucas linhas isso é instantâneo. Numa
tabela de milhões, acrescentar uma coluna com padrão é uma pergunta para a documentação do banco antes
de ser uma migração, e o `sqlmigrate` é como você descobre o que estaria pedindo a ele.

```
ana@vm:~/agenda$ uv run python manage.py migrate events
Operations to perform:
  Apply all migrations: events
Running migrations:
  Applying events.0002_event_description... OK
```

## Três regras

- **Versione as migrações, e nunca edite uma que já foi aplicada em outro lugar.** Uma migração
  alterada que já rodou na máquina de um colega não roda de novo lá, então os dois bancos ficam
  diferentes em silêncio. Um erro se corrige com uma migração nova.
- **Toda mudança de modelo leva a migração no mesmo commit.** Este comando falha quando um modelo
  mudou e ninguém rodou o `makemigrations`, o que faz dele uma boa conferência para o CI:

```
ana@vm:~/agenda$ uv run python manage.py makemigrations --check --dry-run
No changes detected
```

- **Mudanças de dados também são migrações.** Preencher uma coluna nova a partir de uma antiga é uma
  migração com uma operação `RunPython`, para rodar uma vez, em ordem, em todo banco. O `seed.py` não
  foi uma migração porque os três eventos são os dados de exemplo deste curso, que nenhum banco de
  produção deve receber.
