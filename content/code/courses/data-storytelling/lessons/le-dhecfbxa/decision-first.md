---
title: Start from the decision, not the data
version: 1
---

The commonest way an analysis goes wrong as a project is that **it starts from the data**: there is a
table, somebody is curious, and the work expands to fill whatever time is available. The fix is to start
from the decision the analysis is supposed to inform, and work backwards to the data.

## The question behind the question

Paulo asked *why do new subscribers leave?* That is a question about the world. The decision behind it was
narrower: **is there something operations can change this quarter that would keep more of them?** Marina's
second attempt started from that sentence, and it ruled out half the work before it began. Pricing,
marketing campaigns and product range might all affect cancellations; none of them was Paulo's to change,
so none of them was in scope.

Each branch is a hypothesis that, if true, would lead to a different action, and each names **the data that
would test it**. Marina's tree had five. Two were outside operations (price, the food itself) and were
noted for other teams. Two were tested quickly and set aside: region alone, and the month of joining. One,
the first delivery, survived, and it became the analysis.

## The test for any piece of work

Before starting any part of an analysis, ask: **what would we do differently depending on the answer?** If
the answer is "nothing", the work may be interesting and it is not this project. Marina had planned a week
on cancellations by pet species. Asked that question, it had no action attached in operations, and it
moved to a list of things to look at later.

This is the same discipline lesson 2 applied to evidence and lesson 7 applied to dashboard tiles, applied
earlier: **to the work itself, before it is done**, when cutting it is cheapest.
