Uma **réplica de leitura** é um segundo servidor PostgreSQL que guarda uma cópia dos dados do
primeiro e a mantém em dia reaplicando, em ordem, cada mudança que o primeiro grava. O primeiro
servidor é o **primário**: recebe todas as escritas. A réplica, ou **standby**, recusa escritas e
responde leituras. Aponte para a réplica os relatórios, as páginas de busca e os painéis, e o
primário gasta processador e cache com o que só ele pode fazer.

A crença a corrigir primeiro é a de que uma réplica é uma segunda cópia que se lê como se fosse a
primeira. Ela é uma cópia **de um momento que já passou**, quase sempre alguns milissegundos atrás e
às vezes bem mais, e esta aula inteira trata dessa diferença. A seção 03 a mede; a seção 04 mostra o
que ela faz com um usuário; a seção 05 mostra o que a réplica faz com o primário em troca.

As aulas 11 a 13 de `db-reliability` cuidam da replicação de verdade: slots de replicação, commit
síncrono, monitoração e alertas, e a aula 15 de lá é o failover, quando uma réplica vira o primário.
Esta aula monta a menor réplica que funciona, na mesma máquina virtual, e olha para ela pelo lado do
desempenho: o que ela tira do primário e o que devolve.

## Como a cópia fica em dia

Toda mudança que o PostgreSQL faz é escrita primeiro no **write-ahead log**, o WAL, antes de tocar
uma tabela, e é assim que um servidor se recupera depois de uma queda: reaplica o log. Uma réplica é
um servidor que está se recuperando para sempre. Ela se conecta ao primário, recebe o WAL conforme
ele é escrito, processo chamado **replicação por streaming**, e o reaplica. Nada no primário precisa
ser configurado para isso no PostgreSQL 16 como o Ubuntu o instala: o `wal_level` já é `replica`, e
o primário já aceita até dez conexões de replicação.

## Um segundo cluster na mesma máquina

Na aula 1, o `pg_lsclusters` mostrou um **cluster**, `16 main`, na porta 5432. As ferramentas do
Ubuntu rodam vários lado a lado, cada um com o seu diretório de dados, a sua configuração e a sua
porta. Crie um segundo, chamado `replica`, na porta 5433:

```
ana@vm:~$ sudo pg_createcluster 16 replica --port 5433
```

O `pg_createcluster` fez um cluster vazio, configurou-o e o deixou `down`. O diretório de dados dele
precisa virar uma cópia do diretório do primário. Esvazie-o e preencha com o **`pg_basebackup`**, que
copia os arquivos de um servidor em funcionamento por uma conexão de replicação:

```
ana@vm:~$ sudo -u postgres rm -rf /var/lib/postgresql/16/replica
ana@vm:~$ time sudo -u postgres pg_basebackup -D /var/lib/postgresql/16/replica -R -X stream -c fast

real	0m11.063s
user	0m0.442s
sys	0m5.928s
ana@vm:~$ sudo cat /var/lib/postgresql/16/replica/postgresql.auto.conf
# Do not edit this file manually!
# It will be overwritten by the ALTER SYSTEM command.
shared_preload_libraries = 'pg_stat_statements'
primary_conninfo = 'user=postgres passfile=''/var/lib/postgresql/.pgpass'' channel_binding=prefer host=''/var/run/postgresql'' port=5432 sslmode=prefer sslcompression=0 sslcertmode=allow sslsni=1 ssl_min_protocol_version=TLSv1.2 gssencmode=prefer krbsrvname=postgres gssdelegation=0 target_session_attrs=any load_balance_hosts=disable'
```

A cópia levou **11 segundos**, e ela tem todos os bancos do cluster, `market_base` e `postgres`
além do `market`: uma réplica física copia um cluster inteiro, nunca um banco só. Três opções fizeram
o trabalho. O `-X stream` copia o WAL escrito durante o backup, para que a cópia seja consistente. O
`-c fast` pede ao primário um checkpoint imediato em vez de esperar o próximo. E o `-R` escreve as
duas coisas que transformam uma cópia numa réplica: um arquivo chamado `standby.signal`, que manda o
servidor subir em recuperação e ficar nela, e a linha `primary_conninfo` que se vê no
`postgresql.auto.conf`, que diz de onde fazer o streaming. Ela se conecta como `postgres` pelo socket
local, o que a autenticação padrão do Ubuntu já permite para replicação.

A linha `shared_preload_libraries` veio junto com a cópia: a réplica também tem o
`pg_stat_statements`, e mantém o próprio placar das leituras que atende. Ligue-a:

```
ana@vm:~$ sudo systemctl start postgresql@16-replica
ana@vm:~$ pg_lsclusters
Ver Cluster Port Status Owner    Data directory                 Log file
16  main    5432 online postgres /var/lib/postgresql/16/main    /var/log/postgresql/postgresql-16-main.log
16  replica 5433 online postgres /var/lib/postgresql/16/replica /var/log/postgresql/postgresql-16-replica.log
```

Os dois clusters estão `online`. Numa instalação de verdade a réplica é uma segunda máquina e o
`primary_conninfo` cita o endereço do primário; todo o resto desta aula é igual.

## O que a réplica faz e o que não faz

Conecte-se a ela com `-p 5433`. Ela tem os mesmos papéis, então você entra como você mesmo, e as
mesmas linhas:

```
market=# SELECT pg_is_in_recovery();
 pg_is_in_recovery 
-------------------
 t
(1 row)

Time: 0.797 ms

market=# SELECT count(*) FROM orders;
  count  
---------
 2000000
(1 row)

Time: 81.578 ms

market=# UPDATE orders SET status = 'cancelled' WHERE id = 1;
ERROR:  cannot execute UPDATE in a read-only transaction
Time: 1.364 ms
```

O `pg_is_in_recovery()` diz `t`, e é assim que um programa pergunta com que tipo de servidor está
falando. A contagem são os dois milhões de pedidos do primário, lidos em **82 milissegundos** pelos
processos e pelo cache da própria réplica. E uma escrita é recusada, `cannot execute UPDATE in a
read-only transaction`: toda transação num standby é somente leitura, peça a aplicação o que pedir.

Essa recusa é a primeira coisa em torno da qual uma aplicação precisa ser construída. **Alguma coisa
precisa decidir, consulta a consulta, para qual servidor ela vai.** A maioria das aplicações faz isso
com duas configurações de conexão: uma para o primário, usada por toda escrita e toda transação, e
uma para as réplicas, usada pelas leituras escolhidas. Drivers e poolers conseguem rotear por a
transação ser somente leitura ou não, mas a decisão de quais leituras podem ir para uma cópia
atrasada não é uma que um driver possa tomar por você, e a seção 04 mostra por quê.

## Do lado do primário

O primário lista cada réplica que faz streaming a partir dele no `pg_stat_replication`:

```
market=# \x on
Expanded display is on.

market=# SELECT * FROM pg_stat_replication;
-[ RECORD 1 ]----+------------------------------
pid              | 3345
usesysid         | 10
usename          | postgres
application_name | 16/replica
client_addr      | 
client_hostname  | 
client_port      | -1
backend_start    | 2026-10-10 22:49:36.778083-03
backend_xmin     | 
state            | streaming
sent_lsn         | 1A/0
write_lsn        | 1A/0
flush_lsn        | 1A/0
replay_lsn       | 1A/0
write_lag        | 00:00:00.000141
flush_lag        | 00:00:00.000141
replay_lag       | 00:00:00.000141
sync_priority    | 0
sync_state       | async
reply_time       | 2026-10-10 22:49:36.785012-03

Time: 7.642 ms
```

Uma linha, `state` `streaming`, `sync_state` `async`. **Assíncrona** quer dizer que o primário não
espera pela réplica antes de dizer a um cliente que o commit deu certo: um commit é durável no
primário e está a caminho da réplica. É isso que impede a réplica de deixar as escritas mais lentas,
e é também por isso que ela pode estar atrasada. As quatro colunas `_lsn` são posições no WAL, e as
três colunas `_lag` dizem o quanto cada passo está atrasado, em tempo. Aqui elas são todas iguais e
os atrasos são uma fração de milissegundo, porque nada está sendo escrito. A próxima seção escreve.
