A **read replica** is a second PostgreSQL server that holds a copy of the first one's data and keeps
it current by replaying, in order, every change the first one writes. The first server is the
**primary**: it takes every write. The replica, or **standby**, refuses writes and answers reads.
Point the reports, the search pages and the dashboards at the replica, and the primary spends its
processors and its cache on what only it can do.

The belief to correct first is that a replica is a second copy you can read as if it were the
first. It is a copy **of a moment that has already passed**, usually a few milliseconds ago and
sometimes much longer, and the whole of this lesson is about the difference. Section 03 measures
it; section 04 is what it does to a user; section 05 is what the replica does to the primary in
return.

`db-reliability` lessons 11 to 13 own replication properly: replication slots, synchronous commit,
monitoring and alerting, and lesson 15 there is failover, where a replica becomes the primary. This
lesson builds the smallest replica that works, on the same virtual machine, and looks at it for
performance: what it takes off the primary and what it gives back.

## How the copy is kept current

Every change PostgreSQL makes is first written to the **write-ahead log**, the WAL, before it
touches a table, which is how a server recovers after a crash: it replays the log. A replica is a
server that is permanently recovering. It connects to the primary, receives the WAL as it is
written, a process called **streaming replication**, and replays it. Nothing on the primary has to
be configured for this on PostgreSQL 16 as Ubuntu installs it: `wal_level` is already `replica`, and
the primary already accepts up to ten replication connections.

## A second cluster on the same machine

In lesson 1, `pg_lsclusters` showed one **cluster**, `16 main`, on port 5432. Ubuntu's tools can
run several side by side, each with its own data directory, configuration and port. Create a second
one, called `replica`, on port 5433:

```
ana@vm:~$ sudo pg_createcluster 16 replica --port 5433
```

`pg_createcluster` made an empty cluster, configured it and left it `down`. Its data directory has to become a copy of the primary's instead. Empty it and fill it with **`pg_basebackup`**, which
copies a running server's files over a replication connection:

```
ana@vm:~$ sudo -u postgres rm -rf /var/lib/postgresql/16/replica
ana@vm:~$ time sudo -u postgres pg_basebackup -D /var/lib/postgresql/16/replica -R -X stream -c fast

real	0m11.063s
user	0m0.442s
sys	0m5.928s
ana@vm:~$ sudo cat /var/lib/postgresql/16/replica/postgresql.auto.conf
# Do not edit this file manually!
# It will be overwritten by the ALTER SYSTEM command.
shared_preload_libraries = 'pg_stat_statements'
primary_conninfo = 'user=postgres passfile=''/var/lib/postgresql/.pgpass'' channel_binding=prefer host=''/var/run/postgresql'' port=5432 sslmode=prefer sslcompression=0 sslcertmode=allow sslsni=1 ssl_min_protocol_version=TLSv1.2 gssencmode=prefer krbsrvname=postgres gssdelegation=0 target_session_attrs=any load_balance_hosts=disable'
```

The copy took **11 seconds**, and it holds every database in the cluster, `market_base` and
`postgres` as well as `market`: a physical replica copies a whole cluster, never one database.
Three options did the work. `-X stream` copies the WAL written during the backup, so the copy is
consistent. `-c fast` asks the primary for an immediate checkpoint instead of waiting for the next
one. And `-R` writes the two things that turn a copy into a replica: a file called `standby.signal`,
which tells the server to start in recovery and stay there, and the `primary_conninfo` line you can
see in `postgresql.auto.conf`, which says where to stream from. It connects as `postgres` through the
local socket, which Ubuntu's default authentication already allows for replication.

The `shared_preload_libraries` line came with the copy: the replica has `pg_stat_statements` too,
and keeps its own tally of the reads it serves. Start it:

```
ana@vm:~$ sudo systemctl start postgresql@16-replica
ana@vm:~$ pg_lsclusters
Ver Cluster Port Status Owner    Data directory                 Log file
16  main    5432 online postgres /var/lib/postgresql/16/main    /var/log/postgresql/postgresql-16-main.log
16  replica 5433 online postgres /var/lib/postgresql/16/replica /var/log/postgresql/postgresql-16-replica.log
```

Both clusters are `online`. In a real deployment the replica is a second machine and
`primary_conninfo` names the primary's address; everything else in this lesson is the same.

## What the replica will and will not do

Connect to it with `-p 5433`. It has the same roles, so you log in as yourself, and the same rows:

```
market=# SELECT pg_is_in_recovery();
 pg_is_in_recovery 
-------------------
 t
(1 row)

Time: 0.797 ms

market=# SELECT count(*) FROM orders;
  count  
---------
 2000000
(1 row)

Time: 81.578 ms

market=# UPDATE orders SET status = 'cancelled' WHERE id = 1;
ERROR:  cannot execute UPDATE in a read-only transaction
Time: 1.364 ms
```

`pg_is_in_recovery()` says `t`, which is how a program asks which kind of server it is talking to.
The count is the primary's two million orders, read at **82 milliseconds** on the replica's own
processes and cache. And a write is refused, `cannot execute UPDATE in a read-only transaction`:
every transaction on a standby is read-only, whatever the application asks for.

That refusal is the first thing an application has to be built around. **Something has to decide,
per query, which server it goes to.** Most applications do it with two connection settings, one for
the primary that every write and every transaction uses, and one for the replicas that chosen reads
use. Drivers and poolers can route by whether a transaction is read-only, but the decision of which
reads may go to a copy that is behind is not one a driver can make for you, and section 04 is why.

## On the primary's side

The primary lists every replica streaming from it in `pg_stat_replication`:

```
market=# \x on
Expanded display is on.

market=# SELECT * FROM pg_stat_replication;
-[ RECORD 1 ]----+------------------------------
pid              | 3345
usesysid         | 10
usename          | postgres
application_name | 16/replica
client_addr      | 
client_hostname  | 
client_port      | -1
backend_start    | 2026-10-10 22:49:36.778083-03
backend_xmin     | 
state            | streaming
sent_lsn         | 1A/0
write_lsn        | 1A/0
flush_lsn        | 1A/0
replay_lsn       | 1A/0
write_lag        | 00:00:00.000141
flush_lag        | 00:00:00.000141
replay_lag       | 00:00:00.000141
sync_priority    | 0
sync_state       | async
reply_time       | 2026-10-10 22:49:36.785012-03

Time: 7.642 ms
```

One row, `state` `streaming`, `sync_state` `async`. **Asynchronous** means the primary does not wait
for the replica before telling a client its commit succeeded: a commit is durable on the primary and
on its way to the replica. That is what keeps a replica from slowing down writes, and it is also why
the replica can be behind. The four `_lsn` columns are positions in the WAL, and the three `_lag`
columns are how far behind each step is, in time. Here they are all equal and the lags are a
fraction of a millisecond, because nothing is being written. The next section writes.
