---
title: O que um briefing contém
version: 1
---

Um briefing é curto. Uma página basta, e para um projeto de portfólio meia página é o normal. O que o torna
útil é que responde a seis perguntas, e cada resposta é algo que você vai conferir depois.

| parte | a pergunta que responde | o que dá errado sem ela |
|---|---|---|
| **problema** | o que está errado hoje, nas palavras de quem tem o problema | você constrói a solução de um problema que ninguém tem |
| **usuários** | quem mexe, quantos, com que frequência, em que aparelho | você projeta para si mesmo |
| **deve** | o que precisa fazer para a primeira versão valer | a primeira versão nunca acaba |
| **não deve** | o que o tornaria prejudicial ou inútil | uma regra é descoberta depois de quebrada |
| **fora do escopo** | o que ele não vai fazer, dito em voz alta | toda conversa acrescenta uma funcionalidade |
| **pronto quando** | as verificações que dizem que está terminado | ninguém consegue dizer se está terminado |

Duas dessas linhas trabalham mais do que parece. **Não deve** é onde as regras interessantes se escondem:
*um item nunca pode estar emprestado a duas pessoas ao mesmo tempo* é uma linha num briefing e a parte
mais difícil do loanbook. E **fora do escopo** é a única defesa que um projeto de uma pessoa só tem contra
crescer para sempre; a aula 6 trata de usá-la.

Um briefing não é uma especificação. Não diz qual banco nem qual framework. Essas são decisões suas, e a
aula 16 as registra à parte, com os motivos.
