---
title: Contribuições, e depois
version: 1
---

Um projeto de portfólio não está de fato esperando contribuições, e não deve fingir o contrário com um
`CONTRIBUTING` longo, um código de conduta e modelos de issue para um projeto de uma pessoa só. Isso é o
teatro da aula 8 em outra forma. O que ele deve fazer é menor.

- **Deixe as issues abertas.** Quem avalia e encontra um bug sem ter onde relatá-lo também não tem onde se
  impressionar com a sua resposta. Se alguém abrir uma issue, responda em poucos dias; uma resposta educada e
  específica a um desconhecido é evidência de como você trabalha com colegas.
- **Diga numa linha como contribuir, se for o caso.** *Issues são bem-vindas; este é um projeto de portfólio,
  então posso não aceitar mudanças maiores* é honesto e basta.
- **Decida o que acontece depois da busca por emprego.** Um projeto que você não vai manter pode dizer isso no
  topo do README e ser arquivado, o sentido de *deixado* da aula 2. Um projeto que você continua melhorando é
  evidência em si, e os commits posteriores mostram o que você aprendeu desde então. Os dois estão bem; o que
  pega mal é um projeto que parece mantido e não é, com issues abertas que ninguém responde há um ano.

E uma coisa sobre o resto do perfil: **todo repositório público faz parte do portfólio**, fixado ou não, aula
1. Antes de mandar o link para alguém, olhe o seu perfil do jeito que um desconhecido olharia, sem estar
logado, e decida sobre cada coisa que um desconhecido consegue ver.
