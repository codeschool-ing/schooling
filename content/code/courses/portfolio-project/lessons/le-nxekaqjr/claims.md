---
title: A claim and the evidence for it
version: 1
---

A CV is made of claims. *Python. REST APIs. Docker. SQL.* Every candidate for the same job writes
nearly the same list, and the reader has no way to tell one list from another. A portfolio exists to
turn some of those claims into something that can be checked.

| the claim | what would count as evidence |
|---|---|
| "I know SQL" | a schema with a constraint that does real work, and a query you can explain |
| "I write tests" | tests on the rule most likely to break, that fail when it breaks |
| "I know Docker" | a container file that builds, and a service that runs from it |
| "I care about accessibility" | a form with labels, a keyboard path, and a check that says so |
| "I can deploy" | an address that answers today, or a recorded deploy you can repeat |
| "I work well in a team" | commits and a pull request a stranger can follow |

Look at the right column. None of it is impressive on its own, and none of it needs a large project.
What it has in common is that **a reader can check it without trusting you**. They can run the
tests, open the address, read the commit.

That also tells you what a portfolio is not for. It is not for showing that you have heard of many
things: a claim with no evidence behind it is the same on a CV and in a repository. Ten technologies
in a project's description, of which two do any work, reads as ten claims and two pieces of evidence,
and the reader notices the eight.
