---
title: Turning a tutorial into a project
version: 1
---

A tutorial can be the start of a portfolio project, as long as it is not the end. The test is the
same question: what did you decide that the instructions did not? Three moves make the answer
something other than nothing.

**Change the problem, not the paint.** A different colour scheme or a renamed app is still the same
tutorial. A different problem changes everything below it: the to-do list becomes a register of
equipment loans, and suddenly an item can be lent twice, which no to-do item can. The new problem
brings its own rules, and rules are where decisions come from.

**Add the rule the tutorial did not have.** Every tutorial stops at the happy path. The first rule
you add — a refusal, a limit, a date that makes something overdue — is code nobody wrote for you, and
it needs a test, an error message and a decision about where it lives.

**Take it somewhere the tutorial did not go.** Deploy it, which most tutorials leave as an exercise.
Or make it accessible, or make it survive bad input. Each of those meets problems the tutorial's
author never saw, because they stopped before them.

After those three moves the project is yours, and **the tutorial becomes a line in the README**:
*started from X's tutorial on Y; everything after the first commit is mine*. Saying where it began is
not a weakness. Leaving it out, when a reviewer recognises the file names anyway, is.
