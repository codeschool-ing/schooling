One command reads the three inputs and writes the package:

```
ana@vm:~/boxoffice$ sqlc generate
ana@vm:~/boxoffice$ ls internal/db
db.go
models.go
queries.sql.go
ana@vm:~/boxoffice$ wc -l internal/db/*.go
  32 internal/db/db.go
  12 internal/db/models.go
 102 internal/db/queries.sql.go
 146 total
```

**146 lines of Go from a 16-line file of SQL**, in three files. Each one is worth opening once, because this is
code your program runs, and nothing about it is hidden.

## The row type

```
ana@vm:~/boxoffice$ cat internal/db/models.go
// Code generated by sqlc. DO NOT EDIT.
// versions:
//   sqlc v1.31.1

package db

type Event struct {
	ID    int32
	Name  string
	Seats int32
	Sold  int32
}
```

**`Event` is derived from the table**, one field per column, and `integer` in PostgreSQL is a 32-bit
number, so the fields are `int32`. boxoffice's own `Event` uses `int`, which is 64 bits on this machine.
The two are different types, and section 06 has to convert between them; that conversion turns out to
matter.

## One query

```
ana@vm:~/boxoffice$ sed -n "/^const sellSeats/,/^\`/p" internal/db/queries.sql.go; sed -n "/^type SellSeatsParams/,/^}/p" internal/db/queries.sql.go; sed -n "/^func (q \*Queries) SellSeats/,/^}/p" internal/db/queries.sql.go
const sellSeats = `-- name: SellSeats :one
UPDATE events SET sold = sold + $1
WHERE id = $2 AND seats - sold >= $1
RETURNING id, name, seats, sold
`
type SellSeatsParams struct {
	Quantity int32
	ID       int32
}
func (q *Queries) SellSeats(ctx context.Context, arg SellSeatsParams) (Event, error) {
	row := q.db.QueryRow(ctx, sellSeats, arg.Quantity, arg.ID)
	var i Event
	err := row.Scan(
		&i.ID,
		&i.Name,
		&i.Seats,
		&i.Sold,
	)
	return i, err
}
```

**The SQL is in the generated file, exactly as written**, with `sqlc.arg(quantity)` and `sqlc.arg(id)`
replaced by `$1` and `$2`, the placeholders PostgreSQL understands. The parameters became a struct,
`SellSeatsParams`, with a field per name, which is why a call site reads `Quantity: 2, ID: 1` rather than
two bare numbers in an order somebody has to remember. And the function is what lesson 6 wrote by hand:
`QueryRow`, then `Scan` into every column in order. **The column list and the scan list are now written
by the same program**, so they cannot disagree.

## The glue

```
ana@vm:~/boxoffice$ cat internal/db/db.go
// Code generated by sqlc. DO NOT EDIT.
// versions:
//   sqlc v1.31.1

package db

import (
	"context"

	"github.com/jackc/pgx/v5"
	"github.com/jackc/pgx/v5/pgconn"
)

type DBTX interface {
	Exec(context.Context, string, ...interface{}) (pgconn.CommandTag, error)
	Query(context.Context, string, ...interface{}) (pgx.Rows, error)
	QueryRow(context.Context, string, ...interface{}) pgx.Row
}

func New(db DBTX) *Queries {
	return &Queries{db: db}
}

type Queries struct {
	db DBTX
}

func (q *Queries) WithTx(tx pgx.Tx) *Queries {
	return &Queries{
		db: tx,
	}
}
```

**`DBTX` is the small interface the generated code needs**: the three methods it calls. A
`*pgxpool.Pool` has them, a single `*pgx.Conn` has them, and so does a `pgx.Tx`, a transaction. `New`
wraps any of them, and `WithTx` makes a copy that sends every query through a transaction instead,
which is what lesson 9 will use.

Every file starts with `Code generated by sqlc. DO NOT EDIT.` That line is a Go convention that editors and
linters recognise: **a generated file is changed by changing its inputs and generating
again**, never by hand, or the next `sqlc generate` silently undoes the edit.
