As aulas 6 e 7 ficam em duas pontas. Com o pgx à mão, **você escreve o SQL e o Go que lê os
resultados**: cada coluna listada duas vezes, uma no `SELECT` e outra no `Scan`, mantidas em sincronia
por ninguém além de você. Com o GORM, **você escreve o Go e o ORM escreve o SQL**, e o SQL é o que você
não vê. O sqlc ocupa a terceira posição: **você escreve o SQL, e um programa escreve o Go.**

- **`schema.sql`**, as tabelas, que o boxoffice já tem desde a aula 6;
- **`queries.sql`**, toda consulta de que o programa precisa, cada uma com um nome e um comentário
  dizendo o que devolve;
- **`sqlc.yaml`**, dizendo onde estão esses dois e o que gerar;
- e sai **um pacote Go**, uma função por consulta, com uma struct para os parâmetros e uma struct para
  as linhas, tipadas a partir das colunas.

O sqlc não é uma biblioteca que o seu programa importa em tempo de execução. **Ele roda na sua máquina,
antes do `go build`, como um compilador**, e o que deixa para trás é Go comum que usa o pgx, guardado no
repositório ao lado do código que o chama. Quem lê pode abrir o arquivo gerado e ver exatamente que SQL
cada função envia, porque o SQL é copiado para dentro dele palavra por palavra.

A promessa é que a lista de colunas, a ordem dos parâmetros e os tipos não conseguem mais se descolar do
SQL, porque um programa os deriva dele toda vez que o SQL muda. **A seção 07 mede até onde vai essa
promessa**, e encontra um ponto em que ela para sem a ajuda do banco.
