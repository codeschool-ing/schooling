title: O que o sqlc escreve
version: 1
---

Um comando lê as três entradas e escreve o pacote:

```
ana@vm:~/boxoffice$ sqlc generate
ana@vm:~/boxoffice$ ls internal/db
db.go
models.go
queries.sql.go
ana@vm:~/boxoffice$ wc -l internal/db/*.go
  32 internal/db/db.go
  12 internal/db/models.go
 102 internal/db/queries.sql.go
 146 total
```

**146 linhas de Go a partir de um arquivo de SQL de 16 linhas**, em três arquivos. Vale abrir cada um
uma vez, porque é código que o seu programa roda, e nada nele fica escondido.

## O tipo da linha

```
ana@vm:~/boxoffice$ cat internal/db/models.go
// Code generated by sqlc. DO NOT EDIT.
// versions:
//   sqlc v1.31.1

package db

type Event struct {
	ID    int32
	Name  string
	Seats int32
	Sold  int32
}
```

**O `Event` é derivado da tabela**, um campo por coluna, e `integer` no PostgreSQL é um número de 32
bits, então os campos são `int32`. O `Event` do próprio boxoffice usa `int`, que tem 64 bits nesta
máquina. São tipos diferentes, e a seção 06 precisa converter entre eles; essa conversão acaba fazendo
diferença.

## Uma consulta

```
ana@vm:~/boxoffice$ sed -n "/^const sellSeats/,/^\`/p" internal/db/queries.sql.go; sed -n "/^type SellSeatsParams/,/^}/p" internal/db/queries.sql.go; sed -n "/^func (q \*Queries) SellSeats/,/^}/p" internal/db/queries.sql.go
const sellSeats = `-- name: SellSeats :one
UPDATE events SET sold = sold + $1
WHERE id = $2 AND seats - sold >= $1
RETURNING id, name, seats, sold
`
type SellSeatsParams struct {
	Quantity int32
	ID       int32
}
func (q *Queries) SellSeats(ctx context.Context, arg SellSeatsParams) (Event, error) {
	row := q.db.QueryRow(ctx, sellSeats, arg.Quantity, arg.ID)
	var i Event
	err := row.Scan(
		&i.ID,
		&i.Name,
		&i.Seats,
		&i.Sold,
	)
	return i, err
}
```

**O SQL está no arquivo gerado, exatamente como foi escrito**, com `sqlc.arg(quantity)` e `sqlc.arg(id)`
trocados por `$1` e `$2`, os placeholders que o PostgreSQL entende. Os parâmetros viraram uma struct,
`SellSeatsParams`, com um campo por nome, e é por isso que quem chama escreve `Quantity: 2, ID: 1` em
vez de dois números soltos numa ordem que alguém precisa lembrar. E a função é o que a aula 6 escreveu à
mão: `QueryRow`, depois `Scan` em cada coluna, na ordem. **A lista de colunas e a lista do scan agora são
escritas pelo mesmo programa**, então não têm como discordar.

## A cola

```
ana@vm:~/boxoffice$ cat internal/db/db.go
// Code generated by sqlc. DO NOT EDIT.
// versions:
//   sqlc v1.31.1

package db

import (
	"context"

	"github.com/jackc/pgx/v5"
	"github.com/jackc/pgx/v5/pgconn"
)

type DBTX interface {
	Exec(context.Context, string, ...interface{}) (pgconn.CommandTag, error)
	Query(context.Context, string, ...interface{}) (pgx.Rows, error)
	QueryRow(context.Context, string, ...interface{}) pgx.Row
}

func New(db DBTX) *Queries {
	return &Queries{db: db}
}

type Queries struct {
	db DBTX
}

func (q *Queries) WithTx(tx pgx.Tx) *Queries {
	return &Queries{
		db: tx,
	}
}
```

**`DBTX` é a pequena interface de que o código gerado precisa**: os três métodos que ele chama. Um
`*pgxpool.Pool` tem esses métodos, uma única `*pgx.Conn` também, e um `pgx.Tx`, uma transação, também.
O `New` envolve qualquer um deles, e o `WithTx` faz uma cópia que manda toda consulta por uma transação,
que é o que a aula 9 vai usar.

Todo arquivo começa com `Code generated by sqlc. DO NOT EDIT.` Essa linha é uma convenção do Go que
editores e linters reconhecem: **um arquivo gerado se muda mudando as entradas e gerando de novo**, nunca
à mão, senão o próximo `sqlc generate` desfaz a edição em silêncio.
