Lesson 6 and lesson 7 sit at two ends. With pgx by hand, **you write the SQL and the Go that scans its
results**: every column listed twice, once in the `SELECT` and once in the `Scan`, kept in step by
nobody but you. With GORM, **you write the Go and the ORM writes the SQL**, and the SQL is what you
cannot see. sqlc takes the third position: **you write the SQL, and a program writes the Go.**

- **`schema.sql`**, the tables, which boxoffice already has from lesson 6;
- **`queries.sql`**, every query the program needs, each with a name and a comment saying what it
  returns;
- **`sqlc.yaml`**, saying where those two are and what to generate;
- and out comes **a Go package**, one function per query, with a struct for its parameters and a
  struct for its rows, typed from the columns.

sqlc is not a library your program imports at run time. **It runs on your machine, before `go build`,
like a compiler**, and what it leaves behind is ordinary Go that uses pgx, checked into the repository
beside the code that calls it. A reader can open the generated file and see exactly which SQL each
function sends, because the SQL is copied into it word for word.

The promise is that the column list, the parameter order and the types can no longer drift apart from
the SQL, because a program derives them from it every time the SQL changes. **Section 07 measures how
far that promise goes**, and finds one place where it stops without the database's help.
