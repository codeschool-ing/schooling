Everything boxoffice has answered so far was REST: a client chooses a path and a method, sends JSON,
and reads a status and more JSON. **gRPC starts from a different picture: the client calls a function,
and the function runs on another machine.** The client's code says `client.GetEvent(ctx, req)` and gets
an `*Event` back or an error, as if the server were a package it imported. Everything between, the
connection, the encoding, the path the request travels on, belongs to the library.

Three choices make that work, and each is the opposite of something REST leaves free:

- **The contract comes first, and it is required.** A `.proto` file declares every function, its
  argument and its result, in a language of its own, and **both the server and its clients are
  generated from it**. A REST API may have an OpenAPI description or none; a gRPC service cannot exist
  without its `.proto`.
- **The messages are Protocol Buffers**, a compact binary encoding where every field is a number, not a
  name. Section 04 counts the bytes.
- **The transport is HTTP/2**, always. One connection carries many calls at once, and a call can be a
  stream of messages in either direction, which is how gRPC offers four kinds of call where REST has one.

| kind | the client sends | the server sends | boxoffice's example |
|---|---|---|---|
| **unary** | one message | one message | `GetEvent`: an id in, an event out |
| **server streaming** | one message | many, over time | `Watch`: an event id in, its availability every time it changes |
| **client streaming** | many | one, at the end | `Scan`: the tickets shown at the door, one by one, then a summary |
| **bidirectional** | many | many, independently | a chat; boxoffice has none |

## Who boxoffice's gRPC is for

Browsers do not speak gRPC directly, a point lesson 11 comes back to. **gRPC is for programs talking to
programs**: the ticket scanners at the door, a dashboard in the box office, another service of the venue
that needs to know what is sold. This lesson gives boxoffice a second door for them, a service called
`Seats` on port 9090, beside the HTTP API on 8080, sharing the same store. Lesson 11 asks when such a
second door is worth having.
