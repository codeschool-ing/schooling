**A Parquet file is a table cut into row groups, each group stored column by column, with a footer
at the end that says where every piece is and what is in it.** Twitter and Cloudera started it in
2013, after a paper in which Google described its own columnar storage. It is now the default
file format of many analytical tools, Apache Spark among them.

The pieces, from the largest:

- a **row group** is a slice of the table's rows, tens of thousands to millions of them;
- inside it, a **column chunk** holds one column's values for those rows, and only that column's;
- a column chunk is divided into **pages**, the unit that is encoded and compressed;
- the **footer** holds the schema, and for every column chunk its position in the file, its
  encodings, its compression and its **statistics**: the smallest value, the largest, and how many
  are null.

A reader opens the file at the end. The last bytes say how long the footer is, the footer says what
the file holds, and from there the reader can go straight to the column chunks it needs and pass
over the rest without reading them.

## Looking inside one

This program writes a month of rides to `rides.parquet` in row groups of 20,000, then reads back
only the footer. Save it as `formats/as_parquet.py`:


Fifty thousand rides, in three groups: two of 20,000 and the 10,000 left over. The dates come from
the statistics in the footer, not from the rows; the program never read a single ride back. And
they are what make a Parquet file quick to ask about part of itself. A question about rides after
25 September reads three footer entries, sees that groups 0 and 1 end before that day, and skips
them entirely. The trick is called **predicate pushdown**: the filter is pushed down to the file, so
the file can say which parts cannot match. It works best when the rows are written in the order
people ask about them, as these are, by time.

## Encodings: twelve names, stored once

**Before any compression, Parquet chooses an encoding for each column chunk.** The `start_station`
chunk lists three:

- `RLE_DICTIONARY` is a **dictionary**: the twelve station codes are written once, and each of the
  20,000 rows stores a small number pointing into that list. Runs of the same number are then
  written as the number and a count, which is what *run-length* encoding, RLE, means.
- `PLAIN` is the dictionary itself, written as it is.
- `RLE` here is the bookkeeping for nulls, which costs almost nothing when there are none.

The difference is the last two lines of the run. Encoded and compressed, the column is 10,170 bytes.
Written plainly with no compression, each code takes eight bytes, four for its length and four for
its characters, and 20,000 of them come to 160,049 bytes with their headers. Columnar layout is what
makes the dictionary work: it is built from one column's values, which are alike, and a row format
has no such run to build it from.

`SNAPPY` is the compression pyarrow applies when nobody asks for another. Section 09
compares it with the others. To see a footer for a file somebody else wrote, the same calls work on
any Parquet file: `pq.ParquetFile(path).metadata`, and `.row_group(i).column(j)` beneath it.
