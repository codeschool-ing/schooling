Dois documentos carregam a maior parte do peso no começo de um projeto no estilo PMBOK, e os dois têm equivalentes no trabalho ágil com outros nomes.

## O termo de abertura do projeto

O **termo de abertura** (project charter) é o documento que autoriza formalmente o projeto e dá ao gerente de projeto autoridade para usar os recursos da organização nele. Ele é emitido pelo **patrocinador** — a pessoa ou o grupo que fornece o dinheiro e responde pelo sucesso do projeto — e é curto: o propósito, os objetivos mensuráveis, os requisitos e riscos de alto nível, um orçamento e marcos resumidos, as pessoas envolvidas e os critérios de sucesso.

O valor dele é ser assinado. Um projeto sem termo de abertura é um projeto cujo propósito qualquer um pode reinterpretar, e cujo gerente tem de negociar cada pessoa e cada hora. Um termo de abertura do agendamento online do time Agenda diria, numa página, que o projeto existe para permitir que pacientes agendem fisioterapia pela internet nas trinta clínicas da rede até uma data, com um orçamento, patrocinado por um diretor com nome.

## A estrutura analítica do projeto

A **estrutura analítica do projeto**, ou EAP (em inglês WBS, work breakdown structure), é a **decomposição hierárquica do escopo total** do trabalho que o time precisa fazer para entregar o projeto. O topo é o produto inteiro; o nível seguinte, as principais entregas; abaixo delas, o trabalho é quebrado até cada pedaço — um **pacote de trabalho** — ficar pequeno o bastante para estimar, atribuir e acompanhar.

Duas regras tornam uma EAP útil em vez de decorativa:

- **A regra dos 100%.** Cada nível contém todo o trabalho do nível de cima e nada além. Se a EAP está completa, o projeto é tudo o que está na árvore; o que não está na árvore não está no projeto. É isso que faz da EAP a referência quando alguém pergunta se um trabalho está no escopo.
- **Entregas, não atividades.** Os ramos são coisas que vão existir — a API de horários, as telas de agendamento — e não verbos como *programar* ou *testar*. As atividades vêm depois, quando cada pacote de trabalho é planejado.

Cada pacote de trabalho é descrito num **dicionário da EAP**: o que contém, os critérios de aceite, quem é responsável e a estimativa. A declaração do escopo, a EAP e o dicionário juntos formam a **linha de base do escopo**, que o controle de mudanças protege a partir daí.

## Os equivalentes ágeis

Um time ágil faz a mesma decomposição com outros nomes. A visão do produto ou a Meta do Produto faz o papel do propósito do termo de abertura; épicos e funcionalidades são os níveis de cima da árvore; histórias ficam perto dos pacotes de trabalho. A diferença real é **quando** os níveis de baixo são preenchidos. Uma EAP é quebrada até os pacotes de trabalho durante o planejamento, para o projeto inteiro. Um product backlog é quebrado na hora certa: as próximas Sprints em detalhe, o resto como itens grandes, que é de novo o cone da incerteza da aula 1.
