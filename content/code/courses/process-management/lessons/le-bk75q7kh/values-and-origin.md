Scrum and Kanban say how a team organises its work and say nothing about how the code is written. **Extreme Programming says almost nothing else.** It is the agile method that takes the manifesto's most expensive promise — welcome changing requirements, even late — and asks what a team has to do with its code for that promise to be affordable.

## Where it came from

Kent Beck shaped XP on a payroll project at Chrysler, known as C3, from 1996, with Ron Jeffries and Ward Cunningham among the people around it. His book *Extreme Programming Explained* came out in 1999, and a second edition, written with Cynthia Andres, in 2004. The name describes the idea: take practices everybody agreed were good — reviewing code, testing, integrating, talking to the customer — and turn each one up as far as it will go. If reviewing code is good, review it all the time, by pairing. If testing is good, test before writing the code.

## Five values

The second edition names five values, and every practice is meant to serve at least one of them:

- **Communication** — most problems on a project are somebody not knowing something somebody else knew.
- **Simplicity** — the simplest thing that could work today, not the general solution for a future nobody has seen.
- **Feedback** — find out as early as possible whether you are wrong.
- **Courage** — change code that works, throw code away, say the estimate is wrong.
- **Respect** — added in the second edition; nobody's work is less important than anybody else's.

## The stack of loops

The way to read XP is as a stack of **feedback loops**, each one telling the team it is wrong as early as that kind of mistake can be caught. A typo is caught in seconds by the person sitting beside you. A wrong behaviour is caught in minutes by a test written before the code. A conflict with somebody else's change is caught within hours by integrating constantly. A misunderstood requirement is caught within a week or two, when the customer sees working software.

The outer loops are what every agile method has. **The inner three are what XP added**, and they are the ones that flatten the cost-of-change curve from lesson 1. A team that has them can change working code late because it will know within minutes if the change broke something. A team without them cannot, whatever it calls its process.

The next four sections take the practices in groups: testing first, working in pairs, integrating continuously, and planning in small releases. The last of them is about design, which is where XP has the most to say to an architect.
