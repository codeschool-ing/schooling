The wrong way to choose a collection is by the one you used last time. **The right way starts from
the question the program will ask it most often**, because each interface is built around one
question and each class answers it at a different cost:

Four questions, then, and one interface each:

- "What goes with this key?" is a `Map`. An ISBN to a book, a member id to their loans, a title
  to a count.
- "Is this one in there?" is a `Set`. The titles already reserved, the ISBNs already seen.
- "What is at position n, or what came next?" is a `List`. The loans in the order they were
  made, the lines of a report.
- "Which one is next to leave?" is a queue, lesson 33's subject.

Inside `Map` and `Set`, the hash-based class is the default and the other two buy an order: the
order of arrival, or the sorted order. **Pay for an order only when something reads it**, because
the sorted classes compare elements on every insertion, and the linked ones carry an extra pair of
references per entry.

## Two habits that make the choice cheap to change

**Type the variable with the interface**, `List<Book> loans = new ArrayList<>();`. Every method the
rest of the program calls is then a `List` method, and changing the class later is one word after
`new`. Typed as `ArrayList<Book>`, the variable invites calls that only `ArrayList` has, and the one
word becomes a search through the code.

**Do not make the collection do two jobs.** A `List` searched with `contains` on every loan is a
`Set` written the slow way: `contains` on an `ArrayList` reads every element until it finds one,
where a `HashSet` jumps to a bucket. When a program needs both the order and the fast lookup, a
`LinkedHashSet` or `LinkedHashMap` usually gives it both at once; when it does not, keep two
collections and keep them in step in one method.
