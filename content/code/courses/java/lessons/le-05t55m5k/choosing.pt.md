pergunta que o programa vai fazer a ela com mais frequência**, porque cada interface é construída em
torno de uma pergunta e cada classe a responde a um custo diferente:

Quatro perguntas, então, e uma interface para cada:

- "O que vai com esta chave?" é um `Map`. Um ISBN para um livro, o id de um sócio para os seus
  empréstimos, um título para uma contagem.
- "Este aqui está lá dentro?" é um `Set`. Os títulos já reservados, os ISBNs já vistos.
- "O que está na posição n, ou o que veio em seguida?" é uma `List`. Os empréstimos na ordem em que
  foram feitos, as linhas de um relatório.
- "Qual é o próximo a sair?" é uma fila, o assunto da lição 33.

Dentro de `Map` e de `Set`, a classe baseada em hash é o padrão e as outras duas compram uma ordem: a
ordem de chegada, ou a ordem classificada. **Pague por uma ordem só quando alguma coisa a lê**, porque
as classes ordenadas comparam elementos a cada inserção, e as encadeadas carregam um par extra de
referências por entrada.

## Dois hábitos que barateiam a troca

**Declare a variável com o tipo da interface**, `List<Book> loans = new ArrayList<>();`. Todo método que o resto
do programa chama é então um método de `List`, e trocar a classe depois é uma palavra depois do
`new`. Tipada como `ArrayList<Book>`, a variável convida a chamadas que só o `ArrayList` tem, e a
palavra única vira uma busca pelo código.

**Não faça a coleção cumprir dois papéis.** Uma `List` consultada com `contains` a cada empréstimo é
um `Set` escrito do jeito lento: o `contains` de um `ArrayList` lê cada elemento até achar um, onde
um `HashSet` salta direto para um balde. Quando um programa precisa da ordem e da busca rápida ao
mesmo tempo, um `LinkedHashSet` ou um `LinkedHashMap` costuma dar as duas de uma vez; quando não dá,
mantenha duas coleções e mantenha-as em sincronia num método só.
