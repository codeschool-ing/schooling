---
title: Traceability
version: 1
---

**Traceability** is being able to follow each threat to the requirements that answer it, and each
requirement to the evidence that it holds. Its practical value is one sentence: **it finds the
threat nobody covered and the requirement nobody checks**, and both are invisible in a list of
requirements read on its own.

The join is two CSV files and a short program. `trace.py` reads both, files each requirement
under every threat it names, and prints what it finds:

```schooling-example
{"language": "python", "file": "trace.py", "parts": [{"code": "#!/usr/bin/env python3\n\"\"\"Join threats to requirements: what covers each threat, and what is not covered or not verified.\"\"\"\nimport csv\n\nthreats = {row[\"id\"]: row for row in csv.DictReader(open(\"threats.csv\"))}\nrequirements = list(csv.DictReader(open(\"requirements.csv\")))\n", "note": "Two CSV files, read with the standard library. Threats are kept by id so a requirement can find them."}, {"code": "covered = {tid: [] for tid in threats}\nfor req in requirements:\n    for tid in req[\"threats\"].split():\n        covered[tid].append(req)\n", "note": "Every threat starts with an empty list, and each requirement is added to the list of every threat it names. A threat id that does not exist stops the program here."}, {"code": "for tid, reqs in covered.items():\n    ids = \", \".join(f\"{r['id']} ({r['verified by'] or 'not verified'})\" for r in reqs)\n    print(f\"{tid}  {threats[tid]['stride']}  {ids or '-- no requirement'}\")\n", "note": "One line per threat: its letter, and its requirements with how each is verified."}, {"code": "bare = [tid for tid, reqs in covered.items() if not reqs]\nunverified = [r[\"id\"] for r in requirements if not r[\"verified by\"]]\nprint(f\"\\n{len(threats)} threats, {len(requirements)} requirements\")\nprint(\"no requirement:\", \" \".join(bare) or \"none\")\nprint(\"not verified:  \", \" \".join(unverified) or \"none\")", "note": "The two lists the program exists for: threats with no requirement, and requirements nothing verifies."}]}
```

```
T01  S  R01 (test), R02 (test)
T02  S  R03 (test), R04 (test)

T07  I  R10 (test)
T08  I  R11 (review)
T09  I  R12 (test)
T10  D  R13 (test)
T11  D  R14 (not verified)
T12  E  R15 (review)
T13  E  R16 (review)
T14  E  -- no requirement
T15  S  R06 (test)
T16  I  R17 (not verified), R18 (test)

17 threats, 19 requirements
no requirement: T14
not verified:   R14 R17
```

The last two lines are the reason to run it. **T14 has no requirement, and R14 and R17 are not
verified.** Each is a known gap rather than a forgotten one, and the program will keep saying so
until the files change.

### Why a program and not a spreadsheet

A spreadsheet with a column of threat ids does the same join, once. The program does it every time
it runs, and lesson 15 runs it on every pull request: a new threat added without a requirement, or
a requirement whose test was deleted, makes the check say so on the day it happens. The join is
also checked the other way by construction: a requirement naming a threat id that does not exist
stops the program with an error, because `covered[tid]` has no such key, so a typo in an id cannot
pass quietly.

### Committed with the history

```
(.venv) ana@vm:~/tm/portal-model$ git log --oneline -2
2b965bc Write a requirement for each threat
72b7507 Add the threats the abuse cases found
```

The requirements arrive in the history after the threats they answer, and each later change to
either file is a commit with a date and an author. When an auditor asks, in lesson 14, when the
second factor for staff was decided and why, the answer is a `git log` away.
