## As views da plataforma, ou pixels próprios

**Um app nativo e um app React Native terminam com o mesmo tipo de botão: o da plataforma.** A
documentação do React Native diz isso com todas as letras: em tempo de execução, o React Native cria
as views Android e iOS correspondentes aos componentes. Um `<Button>` no React Native vira um botão
Android no Android e um botão iOS no iOS. Ele tem a cara do sistema, se comporta como ele e muda
quando o sistema muda o visual, sem versão nova do app.

**O Flutter faz o contrário de propósito.** A visão geral da arquitetura descreve o Flutter
contornando as bibliotecas de widgets do sistema em favor do próprio conjunto de widgets, pintado
pelo Impeller, um motor de renderização que é embarcado junto com o aplicativo. A tela é uma
superfície, e cada botão, lista e campo de texto nela são pixels que o Flutter desenhou. Então um app
Flutter tem a mesma cara nos dois celulares, a não ser que peça o estilo de cada plataforma, e um
visual novo do sistema só chega a ele quando o Flutter e o app forem atualizados. O que uma
abordagem chama de fraqueza a outra chama de controle: uma equipe Flutter é dona de cada pixel, e
uma equipe React Native ganha o comportamento da plataforma de graça.

**Um embrulho desenha com um navegador.** A WebView renderiza HTML e CSS exatamente como um navegador
faria, então um botão é o que o CSS da página fez dele, e a rolagem, a seleção de texto e o teclado se
comportam como no navegador do celular. Um PWA dispensa o app em volta e roda no próprio navegador.

**O Kotlin Multiplatform não desenha nada.** Ele compartilha código abaixo da tela, e a tela é o que
a equipe desenhar por cima: views nativas de cada lado, ou o Compose Multiplatform nos dois.

## Onde a lógica roda

A segunda metade da pergunta é onde as regras executam quando o app roda, e a resposta é diferente
para cada um:

| abordagem | onde o código roda no celular |
|---|---|
| nativo | compilado para a plataforma: Kotlin para o runtime do Android, Swift para código de máquina |
| React Native | um motor JavaScript embarcado no app, o Hermes por padrão |
| Flutter | Dart compilado para código nativo, segundo a visão geral dele |
| Kotlin Multiplatform | Kotlin compilado separadamente para cada plataforma que ele atende |
| embrulho web | o motor JavaScript da WebView, o mesmo que roda a página |

**É por isso que "compartilhado" nunca é o app inteiro.** No React Native a lógica é JavaScript e as
views são nativas, então cada atualização de tela atravessa de um para o outro. No Flutter os dois
são Dart, e nada atravessa até o app precisar de algo que só a plataforma tem. Num embrulho tudo
fica na página até um plugin ser chamado. Cada linha dessa tabela move o ponto onde o código
compartilhado para e o código da plataforma começa, e esse ponto é o assunto da próxima etapa.
