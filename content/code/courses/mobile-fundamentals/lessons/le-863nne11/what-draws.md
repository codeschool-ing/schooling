## The platform's views, or pixels of your own

**A native app and a React Native app end up with the same kind of button: the platform's.** React
Native's documentation says it plainly: "At runtime, React Native creates the corresponding Android
and iOS views for those components." A `<Button>` in React Native becomes an Android button on
Android and an iOS button on iOS. It looks like the system's, behaves like it, and changes when the
system changes its look, with no new release of the app.

**Flutter does the opposite on purpose.** Its architectural overview describes Flutter "bypassing the
system UI widget libraries in favor of its own widget set", painted by Impeller, a rendering engine
that "is shipped along with the application". The screen is a surface, and every button, list and
text field on it is pixels that Flutter drew. So a Flutter app looks the same on both phones unless
it asks for each platform's style, and a new system look does not reach it until Flutter and the app
are updated. What one approach calls a weakness the other calls control: a Flutter team owns every
pixel, and a React Native team gets the platform's behaviour for free.

**A wrapper draws with a browser.** The WebView renders HTML and CSS exactly as a browser would, so a
button is whatever the page's CSS made it, and scrolling, text selection and the keyboard behave the
way they do in the phone's browser. A PWA skips the app around it and runs in the browser itself.

**Kotlin Multiplatform does not draw at all.** It shares code below the screen, and the screen is
whatever the team draws on top: native views on each side, or Compose Multiplatform on both.

## Where the logic runs

The second half of the question is where the rules execute when the app runs, and it is a
different answer for each:

| approach | where the code runs on the phone |
|---|---|
| native | compiled for the platform: Kotlin for Android's runtime, Swift to machine code |
| React Native | a JavaScript engine shipped inside the app, Hermes by default |
| Flutter | Dart compiled into native code, according to its overview |
| Kotlin Multiplatform | Kotlin compiled separately for each platform it targets |
| web wrapper | the WebView's JavaScript engine, the same one that runs the page |

**This is why "shared" is never the whole app.** In React Native the logic is JavaScript and the
views are native, so every screen update crosses from one to the other. In Flutter both are Dart and
nothing crosses until the app needs something only the platform has. In a wrapper everything stays
in the page until a plugin is called. Each line of that table moves the place where shared code stops
and platform code starts, and that place is the subject of the next section.
