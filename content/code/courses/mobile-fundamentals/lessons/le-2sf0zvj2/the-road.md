**The wrong picture is a direct line: your server calls the phone, and the app answers.** Your
server cannot reach a phone at all. A phone has no fixed address, it sleeps, it moves between
networks, and lesson 15 showed that keeping a connection open costs battery. So each platform keeps
**one** connection from the phone to its own service, shared by every app on it, and your server
hands its messages to that service. Android's is **Firebase Cloud Messaging (FCM)**, Google's.
Apple's is the **Apple Push Notification service (APNs)**.

A message goes your server → FCM or APNs → the push service on the phone → and then one of two
places. **If it says what to show, a title and a body, and the app is not on screen, the system
shows it in the notification shade without starting your app.** Your code runs when the person taps
it. If
it carries only data, the system hands it to your app in the background, when and if it decides to.
The next section is about those two kinds.

## The address is a token, and it changes

**The service needs to know which app on which phone to deliver to, and that address is a device
token**: a long opaque string the phone gets from FCM or APNs and the app sends to your server. The
server stores it beside the student's account and puts it on every message. A student with a phone
and a tablet has two tokens, and the server keeps both.

**A token is not permanent, and an app that treats it as permanent stops receiving pushes without
any error.** Apple's documentation on registering with APNs, as read on 30 October 2026, puts it as
a rule: never cache device tokens in local storage. APNs issues a new token when the user restores
the device from a backup, installs the app on a new device, or reinstalls the operating system, and
the app should ask for the token each time it launches and send it to the server if it changed.
On Android, the Auto Backup guide quoted in lesson 16 makes the same point from the other side: FCM
makes a new token on every new device, and an old one restored from a backup makes the app behave
unexpectedly.

The other half is the server's: **a token that has stopped working must be thrown away.** When the
app is uninstalled, the service answers the next message to its token with an error saying the
device is not registered any more; Expo's push service calls it `DeviceNotRegistered`, and its
documentation says to stop sending to that token. A server that ignores those answers keeps
addressing letters to an empty house.

## What the road promises, and what it does not

**A push is delivered on a best effort, and late, out of order or not at all are all normal.** Apple's
documentation on sending requests to APNs says APNs may reorder notifications, and that when a device
is offline it stores **only one** notification per app, usually the latest, for up to 30 days or less,
depending on an expiry the server sets. The FCM API's own description, read the same day, says a message for an
offline device is kept for up to **4 weeks** by default, and that messages sharing a *collapse key*
are reduced to the last one when delivery resumes.

What that means for the planner is concrete:

| the message | what can happen to it | so |
|---|---|---|
| "Your SQL session starts in 15 minutes" | it arrives after the session started, when the phone was off | set a short expiry; a late reminder is noise |
| "Ana shared a course with you" | two of them collapse into one | the app shows the list from the server, not from the pushes |
| "Your week changed on another device" | it never arrives | the app refreshes anyway when it opens, as lesson 14 did |

**A push is a hint that something happened, never the record of it.** The data lives on the server,
and the app fetches it; the push only makes that happen sooner. The reminder in the first row has a
better answer still: it does not need a server at all, and two sections on, this lesson builds it on
the phone.
