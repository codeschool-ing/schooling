**A tela pede uma imagem nova num ritmo fixo, e o tempo entre dois pedidos é todo o orçamento de
um quadro.** Uma tela que se atualiza 60 vezes por segundo pede a cada 1000 / 60 milissegundos.
Muitos celulares hoje se atualizam 90 ou 120 vezes por segundo, o que dá a cada quadro menos
tempo, não mais. As contas são curtas o bastante para rodar. Salve isto como `budget.ts` em
`~/planner`:

```typescript
// budget.ts: how long one frame may take at each refresh rate
for (const hz of [60, 90, 120]) {
  const ms = 1000 / hz;
  console.log(`${hz} Hz: ${ms.toFixed(2)} ms per frame`);
}
```

```
ana@dev:~/planner$ node budget.ts
60 Hz: 16.67 ms per frame
90 Hz: 11.11 ms per frame
120 Hz: 8.33 ms per frame
```

**16,67 ms a 60 Hz é o número do título desta aula**, e é um teto para tudo o que a thread
principal faz naquele quadro: o seu tratador, o layout e o desenho do próprio sistema. O seu código
fica com só uma parte. A documentação do Android sobre renderização lenta dá os mesmos três
valores, arredondados para 16, 11 e 8 ms, e diz que um quadro precisa ser renderizado em menos de
16 ms para chegar a 60 quadros por segundo.

## Um quadro atrasado não chega atrasado, ele falta

A imagem errada aqui é a de um quadro que chega um pouco atrasado, então a animação fica um pouco
lenta. **Um quadro que perde o seu espaço não aparece atrasado; ele não aparece.** A documentação
do Android é exata nisso. Estoure a janela em 1 ms e o quadro não é exibido 1 ms depois: o sistema o
descarta inteiro, e a tela continua mostrando a imagem anterior por mais um espaço inteiro. A
documentação do React Native descreve a mesma regra para a thread de JavaScript, com um caso
calculado: um trabalho de 200 ms nessa thread derruba 12 quadros, e toda animação comandada pelo
JavaScript congela durante todo esse tempo.

## Três nomes para três tamanhos de travada

A documentação do Android sobre renderização lenta classifica uma travada pela duração. Vale a pena saber os nomes, porque as ferramentas e a loja os usam:

| quanto tempo um quadro levou | como o Android chama | o que o usuário vê |
|---|---|---|
| mais de 16 ms, menos de 700 ms | um quadro lento | uma lista que dá trancos ao rolar |
| de 700 ms a 5 s | um quadro congelado | um app que parece travado por um instante |
| mais de 5 s, sem responder à entrada | um ANR, *Application Not Responding* | uma caixa de diálogo oferecendo fechar o app |

**O orçamento diminui conforme as telas melhoram.** Um código que cabe com folga em 16,67 ms num
celular de 60 Hz pode perder todos os espaços num de 120 Hz, onde o orçamento é de 8,33 ms. Então a
regra não é "fique abaixo de 16 ms", e sim "mantenha o trabalho lento fora da thread que desenha",
o que as próximas seções tornam concreto.

O primeiro quadro de uma tela nova é a única exceção aceita. A mesma página do Android diz que é
normal esse quadro levar mais de 16 ms, porque a tela precisa ser montada e posicionada antes que
qualquer coisa seja desenhada. Uma lista que trava toda vez que rola não tem essa desculpa.
