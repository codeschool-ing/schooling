**The screen asks for a new picture at a fixed rate, and the time between two requests is the
whole budget for a frame.** A display that refreshes 60 times a second asks every 1000 / 60
milliseconds. Many phones now refresh at 90 or 120 times a second, which gives each frame less
time, not more. The sums are short enough to run. Save this as `budget.ts` in `~/planner`:

```typescript
// budget.ts: how long one frame may take at each refresh rate
for (const hz of [60, 90, 120]) {
  const ms = 1000 / hz;
  console.log(`${hz} Hz: ${ms.toFixed(2)} ms per frame`);
}
```

```
ana@dev:~/planner$ node budget.ts
60 Hz: 16.67 ms per frame
90 Hz: 11.11 ms per frame
120 Hz: 8.33 ms per frame
```

**16.67 ms at 60 Hz is the number in this lesson's title**, and it is a ceiling for everything the
main thread does in that frame: your handler, the layout, and the system's own drawing. Your code
gets only part of it. Android's documentation on slow rendering gives the same three figures,
rounded to 16, 11 and 8 ms, and says that a frame must be rendered in under 16 ms to reach 60
frames per second.

## A late frame is not late, it is missing

The wrong picture here is a frame that arrives a little late, so the animation is a little slow.
**A frame that misses its slot is not shown late; it is not shown at all.** Android's documentation is exact about it. Overrun the window by 1 ms and the frame is not displayed
1 ms late: the system drops it entirely, and the screen keeps showing the previous picture for another
whole slot. React Native's documentation describes the same rule for its JavaScript thread, with
a worked case: work that takes 200 ms on that thread drops 12 frames, and any animation driven
from JavaScript freezes for the whole of it.

That is why jank feels like a stutter rather than a slowdown. A scroll that draws frames 1, 2, 3,
skips 4 to 7 and then draws 8 jumps the list the distance of five frames at once, and the eye
sees the jump.

## Three names for three lengths of stall

Android's documentation on slow rendering sorts a stall by its length. The names are worth having, because the tools and the store report them:

| how long one frame took | what Android calls it | what the user sees |
|---|---|---|
| over 16 ms, under 700 ms | a slow frame | a list that stutters while it scrolls |
| 700 ms to 5 s | a frozen frame | an app that seems stuck for a moment |
| over 5 s, not answering input | an ANR, *Application Not Responding* | a dialog offering to close the app |

**The budget gets smaller as screens get better.** Code that fits comfortably in 16.67 ms on a
60 Hz phone can miss every slot on a 120 Hz one, where the budget is 8.33 ms. So the rule is not
"keep it under 16 ms" but "keep slow work off the thread that draws", which the next sections
make concrete.

The first frame of a new screen is the one allowed exception. Android's same page says it is
normal for that frame to take longer than 16 ms, because the screen has to be built and laid out
before anything can be drawn. A list that stutters every time it scrolls has no such excuse.
