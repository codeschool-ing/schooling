A aula 5 mostrou um valor chegando ao SQL como código. **O SQL é um interpretador entre vários**, e
uma aplicação web comum entrega texto a mais deles do que os autores costumam contar. Esta aula pega
os três que o console da equipe do portal usa:

| interpretador | o que ele lê | seus caracteres especiais, por exemplo |
|---|---|---|
| o **shell** | uma linha de comando | espaços, `;`, `&`, `|`, `$`, aspas, um `-` no começo |
| um diretório **LDAP** | um filtro de busca como `(cn=carla)` | `*`, `(`, `)`, `\` |
| um **motor de templates** (Jinja) | um template como `Hello {{ patient }}` | `{{`, `{%`, `{#` |

A ideia errada é que cada um deles exige um conhecimento especializado do que é perigoso. Os
caracteres perigosos mudam, e **o erro é o mesmo toda vez**: um valor é escrito num texto que um
interpretador vai ler, então parte do valor é lida como programa. E a correção também é a mesma toda
vez: **manter o programa e os valores em canais separados**, como fizeram os marcadores da aula 5.

| interpretador | o canal separado |
|---|---|
| o shell | nenhum shell: uma lista de argumentos passada direto ao programa |
| LDAP | o escape de filtro da biblioteca, que transforma todo caractere especial em dado comum |
| Jinja | o valor passado como **variável** do template, nunca emendado no texto do template |

O escape aparece na linha do meio, e está lá porque filtros LDAP não têm mecanismo de marcadores.
**Onde existe um canal separado, use-o; escape só onde não existe**, e use a função de escape da
biblioteca em vez de escrever a sua, porque quem escreveu a biblioteca leu a especificação e você
tem um prazo.

### Como reconhecer

As três falhas do console da equipe têm a mesma cara num diff: uma f-string, um `+` ou um `.format()`
montando uma string que depois é entregue a algo que a **interpreta**. Buscar `shell=True`,
`os.system`, `search(` e `render_template_string(` no código acha os lugares a olhar. O que olhar em
cada lugar é se alguma coisa na string veio de uma requisição.
