title: Three ways text becomes markup
version: 1

**Cross-site scripting**, XSS, is lesson 5's mistake with the browser as the interpreter. Text that
somebody else chose reaches a page as HTML instead of as text, and the browser builds whatever that
HTML describes, scripts included, with the session and the permissions of whoever is looking at the
page. On the portal that is a patient's account; in the staff console it is a receptionist's, who can
read every patient's bookings.

Lesson 4 taught the defence: **encode every value for the place it is written into**, and let the
template engine do it. This lesson is about where that defence goes missing. XSS is named by **where
the text comes from**, and each source misses the defence in its own way.

- **Reflected.** The text arrives in a request and goes straight back in the response: a search term
  echoed in "no results for …", an error message quoting a parameter. Only the person who sends the
  request sees it, so it needs them to follow a link somebody else wrote.
- **Stored.** The text is saved first, as a message, a name, a note, and shown later to other people.
  One message reaches every member of staff who opens the inbox, and nobody has to click anything
  unusual. It is the most damaging of the three for that reason.
- **DOM-based.** The server never sends the text at all. The page's own JavaScript reads it, from the
  address, from a fragment after `#`, from an API response, and writes it into the page with a
  function that parses HTML. The server's templates can be perfect and the page still vulnerable.

### The witness this lesson uses

A flaw of this kind is proved by showing that **text became markup**, and the plainest markup there
is does that: `<b>` or `<i>`. If a word a patient wrapped in `<b>` comes out bold, the page built an
element from her text, and it would have built any other element just the same. No script is needed
to show it, and none is used here. Each test asks for the opposite: the tags appear on the page as
the characters a person typed.

### Why one fix is not enough

Templates escape by default, so most XSS in modern applications is in one of three places: a value
**marked safe** to get some formatting through, an HTML string **built outside the template** with an
f-string, and **client-side code** that uses `innerHTML`. The portal's inbox has one of each.
