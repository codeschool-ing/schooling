**Cross-site scripting**, XSS, é o erro da aula 5 com o navegador como interpretador. Um texto que
outra pessoa escolheu chega a uma página como HTML em vez de texto, e o navegador constrói o que esse
HTML descrever, scripts incluídos, com a sessão e as permissões de quem está olhando a página. No
portal, é a conta de um paciente; no console da equipe, é a de uma recepcionista, que lê os
agendamentos de todo paciente.

A aula 4 ensinou a defesa: **codificar todo valor para o lugar onde ele é escrito**, e deixar o motor
de templates fazer isso. Esta aula trata de onde essa defesa some. O XSS é nomeado por **de onde vem o
texto**, e cada origem perde a defesa de um jeito próprio.

- **Refletido.** O texto chega numa requisição e volta direto na resposta: um termo de busca repetido
  em "nenhum resultado para …", uma mensagem de erro que cita um parâmetro. Só quem manda a requisição
  o vê, então ele depende de a pessoa seguir um link que outra pessoa escreveu.
- **Armazenado.** O texto é salvo antes, como mensagem, nome ou nota, e mostrado depois a outras
  pessoas. Uma mensagem chega a toda a equipe que abre a caixa de entrada, e ninguém precisa clicar em
  nada estranho. É o mais danoso dos três por isso.
- **Baseado no DOM.** O servidor nunca manda o texto. O próprio JavaScript da página o lê, do endereço,
  de um fragmento depois do `#`, de uma resposta de API, e o escreve na página com uma função que
  interpreta HTML. Os templates do servidor podem estar perfeitos e a página continuar vulnerável.

### A testemunha que esta aula usa

Uma falha desse tipo se prova mostrando que **o texto virou marcação**, e a marcação mais simples que
existe faz isso: `<b>` ou `<i>`. Se uma palavra que uma paciente envolveu em `<b>` sai em negrito, a
página construiu um elemento a partir do texto dela, e construiria qualquer outro do mesmo jeito.
Nenhum script é preciso para mostrar isso, e nenhum é usado aqui. Cada teste pede o contrário: as
tags aparecem na página como os caracteres que alguém digitou.

### Por que uma correção não basta

Templates escapam por padrão, então a maior parte do XSS em aplicações modernas está num de três
lugares: um valor **marcado como seguro** para deixar passar alguma formatação, uma string de HTML
**montada fora do template** com uma f-string, e **código no cliente** que usa `innerHTML`. A caixa de
entrada do portal tem um de cada.
