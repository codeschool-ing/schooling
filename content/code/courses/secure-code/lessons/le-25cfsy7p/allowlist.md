An **allowlist** reverses the question. Instead of listing what is bad, it describes what a valid
value is, and refuses everything else. The description is usually short, because valid values
have a shape: Vereda has four clinics, a day has a real date, a session starts on the hour between
07:00 and 19:00, and a phone has 10 or 11 digits. Whatever nobody predicted falls outside that
description and is refused without anybody having to predict it.

### What a description says

Every field gets the same five questions, in this order, and the first one that fails decides the
answer:

| question | for Vereda's booking | refused, for example |
|---|---|---|
| **is it there?** | all four fields are required | a body with no `phone` |
| **is it the right type?** | text, not a number or a list | `"phone": 11987654321` sent as a number |
| **is it the right length?** | a phone has 10 or 11 characters | `1198765` |
| **is it in range?** | a date that exists; an hour the clinics are open | `2026-11-31`, `23:00` |
| **is it one of the allowed values, or the allowed format?** | one of four clinics; digits only | `paulista`, a phone with a space in it |

The order matters for the error message as much as for the code. Telling a patient their phone
number has the wrong format when they left it empty sends them looking for the wrong mistake.

### Sets beat patterns, and patterns must be anchored

**When the valid values can be listed, list them.** Four clinics are a set, and membership in a
set has no edge cases: `"moema" in CLINICS` is true or false and there is nothing to get wrong. The
same goes for the time slots, thirteen of them, generated by one line of code rather than written
by hand.

When the values cannot be listed, a **regular expression** describes the format, and it has to
describe the **whole** value. Python offers three ways to apply one, and only one of them is
right for validation:

| call | what it checks | for `11987654321 extra` |
|---|---|---|
| `re.search(r"[0-9]{10,11}", s)` | the pattern appears somewhere in `s` | matches, wrongly |
| `re.match(r"[0-9]{10,11}", s)` | the pattern appears at the start of `s` | matches, wrongly |
| `re.fullmatch(r"[0-9]{10,11}", s)` | the pattern is all of `s` | refuses |

`search` and `match` are the commonest way an allowlist quietly turns back into "contains
something valid". `fullmatch` is the one that describes the value. Writing the anchors by hand,
`^[0-9]{11}$`, is close and not the same in Python: `$` also matches just before a final newline,
so `"11987654321\n"` passes it and fails `fullmatch`.

### Parse rather than match, where a parser exists

A date matched by `\d{4}-\d{2}-\d{2}` is a string with the right shape, and `2026-11-31` has the
right shape. **A parser knows what the shape cannot**: `date.fromisoformat("2026-11-31")` raises
`ValueError`, because it knows how many days November has. Where the standard library can parse a
value (a date, a number, an e-mail address through a dedicated library, a URL with
`urllib.parse`), parsing is the validation, and the parsed value is what the program keeps.
