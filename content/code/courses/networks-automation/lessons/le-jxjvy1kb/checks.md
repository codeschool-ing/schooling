Every lesson so far ended with a check: the diff before a commit, the comparison after a push, the
`assert` in lesson 9's playbook. This lesson puts them in order and makes them automatic. **A
change goes through five steps**, and what matters most about each check is which side of the
apply it sits on:

Everything to the left of apply runs on files. It needs no router, takes a fraction of a second,
and when it fails the network has not noticed. **Everything to the right runs against the network**
and can only report a problem the routers already have; its value is that it finds the problems no
file can show, and that it finds them in seconds rather than when somebody calls.

Two kinds of test, then. **Offline tests** read the data and the rendered configurations: is every
value well formed, is any address used twice, does every OSPF interface get its network line.
**Online tests** ask the network whether it does what the data says: are the adjacencies up, is
every branch reachable. The vocabulary varies, pre-checks and post-checks, unit and integration
tests, but the line between them is always the same: whether the test needs the network.

The project is lesson 10's, in a Git repository, with the data in YAML. A pipeline, which lesson
14 builds, runs on a change to files, and files are what this lesson tests. With NetBox as the
source, the same tests run on what `render_nb.py` produces.
