title: O que um pipeline acrescenta

As verificações da aula 13 funcionam quando alguém as roda. **Integração contínua é o arranjo em
que ninguém precisa rodar**: toda mudança enviada ao repositório compartilhado é testada
automaticamente, uma mudança que falha é recusada antes que alguém construa em cima dela, e o que
chega à branch principal é implantado pela mesma maquinaria todas as vezes. A pessoa que faz a
mudança deixa de ser o que garante que as verificações rodaram.

Para uma rede, isso muda três coisas. Os testes rodam em toda mudança, inclusive na feita às
pressas numa sexta-feira. O deploy é o mesmo script não importa quem o dispare, a partir de uma
máquina com credenciais próprias em vez do notebook de alguém. E o histórico do repositório vira o
log de mudanças da rede, com um resultado de teste anexado a cada entrada.

Nesta aula o pipeline é construído com as menores peças que dão conta do trabalho, para que nada
nele fique escondido: um repositório Git no `ctl` fazendo o papel de servidor, e dois **hooks**,
scripts que o Git roda no servidor quando chega um push:

Os dois hooks diferem num ponto que importa. **O `pre-receive` roda antes de o push ser aceito e
pode recusá-lo**; o `post-receive` roda depois, quando os commits já estão no servidor, e só pode
agir sobre eles. Então os testes vão no primeiro e o deploy no segundo. A seção 07 mostra como fica
o mesmo pipeline num serviço de CI hospedado, onde as peças têm nomes próprios.
