The three routers in the lab have configurations that are nearly the same. Each has a hostname, two
interfaces with a description and an address, a loopback, OSPF over its links and the same `line
vty`. **What differs between them fits in about ten values**, and the rest is text that repeats.

A template takes that observation literally. The repeated text is written once, in a file with
holes in it, and the values go in a separate file per router. Rendering fills the holes:

This splits one question into two that are easier to answer. Is the template right? That is
checked once, and holds for every router. Are edge2's values right? That is eleven lines of YAML a
reviewer can read in a minute, instead of 34 lines of configuration in which the one changed line
has to be found.

It also changes what a change is. Adding a router means writing one data file. Changing something
every router has, a timeout or a logging level, means editing the template once and rendering
again. **And a configuration typed by hand on one router stops being the truth**: the truth is the
data and the template, and the router is expected to match what they render. Lesson 11 compares the
two every night; lesson 12 moves the data into NetBox.

The template language here is **Jinja2**, the one Python's network tools share. Ansible's
`template` module renders Jinja2, a Nornir plugin does, NetBox uses it for configuration
templates, and lesson 9's playbooks already used its `{{ }}` for variables. What this lesson
teaches carries over to all of them.
