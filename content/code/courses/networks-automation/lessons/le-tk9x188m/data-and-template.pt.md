Os três roteadores do laboratório têm configurações quase iguais. Cada um tem um hostname, duas
interfaces com descrição e endereço, uma loopback, OSPF nos seus links e a mesma `line
vty`. **O que difere entre eles cabe em uns dez valores**, e o resto é texto que se repete.

Um template leva essa observação ao pé da letra. O texto repetido é escrito uma vez, num arquivo
com buracos, e os valores vão num arquivo separado por roteador. Renderizar preenche os buracos:

Isso divide uma pergunta em duas mais fáceis de responder. O template está certo? Isso é conferido
uma vez, e vale para todo roteador. Os valores do edge2 estão certos? São onze linhas de YAML que um
revisor lê em um minuto, em vez de 34 linhas de configuração nas quais é preciso achar a única linha
que mudou.

Também muda o que é uma mudança. Acrescentar um roteador significa escrever um arquivo de dados.
Mudar algo que todo roteador tem, um timeout ou um nível de log, significa editar o template uma
vez e renderizar de novo. **E uma configuração digitada à mão num roteador deixa de ser a
verdade**: a verdade são os dados e o template, e espera-se que o roteador bata com o que eles
renderizam. A aula 11 compara os dois toda noite; a aula 12 leva os dados para o NetBox.

A linguagem de template aqui é o **Jinja2**, a que as ferramentas de rede do Python compartilham. O
módulo `template` do Ansible renderiza Jinja2, um plugin do Nornir também, o NetBox o usa para
templates de configuração, e os playbooks da aula 9 já usavam o seu `{{ }}` para variáveis. O que
esta aula ensina vale para todos eles.
