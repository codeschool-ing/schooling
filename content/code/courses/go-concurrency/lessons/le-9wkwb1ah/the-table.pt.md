A lição 25 terminou com cinco subtestes, cada um com algumas linhas de preparação, uma chamada e
uma conferência, e cada um diferente dos outros só no texto e nas contagens esperadas. **Quando os
casos diferem só nos dados, código Go escreve os dados como uma tabela e o código uma vez.** É a
forma de teste mais comum no próprio repositório do projeto Go, e a forma que qualquer pessoa
lendo os seus testes vai esperar.

A tabela é um slice de uma struct anônima, um campo por coisa que varia, e um laço que transforma
cada linha num subteste. O `TestCount` reescrito assim, com duas linhas a mais do que a lição 25
tinha, e o arquivo inteiro salvo como `wordcount_test.go`:

O corpo do laço é o subteste antigo, escrito uma vez. O que mudou é onde um caso mora: numa linha,
que quem revisa lê como dado e pode conferir com a especificação linha a linha.

```
ana@vm:~/wordcount$ go test
PASS
ok  	example.com/wordcount	0.003s
```

## O que vai na tabela, e o que não vai

Uma tabela serve quando todo caso passa pelos mesmos passos. **Quando um caso precisa de passos
próprios, ele é um teste separado**, e não uma linha com uma flag que desliga metade do laço. É por
isso que o `TestCountFile` não é uma linha do `TestCount`: ele escreve um arquivo, e uma coluna
`file bool` faria toda outra linha carregar um campo que ignora e o laço carregar um `if` para um
caso só.

Vale o mesmo para expectativas de tipos diferentes. Uma linha com um campo `wantErr` ao lado de
`want` é comum e não tem problema, desde que a maioria das linhas use os dois. Quando uma linha
testa o erro e o resto testa as contagens, o caso do erro fica mais claro sozinho.
