Lesson 25 ended with five subtests, each a few lines of setup, a call and a check, and each
different from the others only in its text and its expected counts. **When the cases differ only
in data, Go code writes the data as a table and the code once.** It is the most common shape of
test in the Go project's own repository, and the shape anybody reading your tests will expect.

The table is a slice of an anonymous struct, one field per thing that varies, and a loop that
turns each row into a subtest. `TestCount` rewritten that way, with two more rows than lesson 25
had, and the whole file saved as `wordcount_test.go`:

The loop body is the old subtest, written once. What changed is where a case lives: in a row,
which a reviewer reads as data and can check against the specification line by line.

```
ana@vm:~/wordcount$ go test
PASS
ok  	example.com/wordcount	0.003s
```

## What goes in the table, and what does not

A table fits when every case goes through the same steps. **When a case needs steps of its own,
it is a separate test**, not a row with a flag that switches half the loop off. That is why
`TestCountFile` is not a row of `TestCount`: it writes a file, and a `file bool` column would
mean every other row carries a field it ignores and the loop carries an `if` for one case.

The same goes for expectations of different kinds. A row with a `wantErr` field beside `want` is
common and fine, as long as most rows use both. When one row tests the error and the rest the
counts, the error case reads more clearly on its own.
