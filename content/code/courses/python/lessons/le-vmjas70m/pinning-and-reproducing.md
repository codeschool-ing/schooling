```sh
requirements.txt:  requests==2.31.0
```

```sh
Monday:     urllib3 2.8.0
Thursday:   urllib3 2.9.0        ← nobody changed anything
```

**`requests` is pinned and the install is not reproducible.** It declares `urllib3 (<3, >=1.21.1)`
and `pip` takes the newest thing that fits, which is whatever the index held at the moment you
ran it.

Most of the time this is fine and occasionally it is the whole Thursday: a transitive dependency
released a version, your build machine picked it up, and the failure is in a library nobody on
the team has read.

## What a lock file is

A second file, generated, listing **every** package — direct and transitive — at one exact
version, usually with a hash of the file that was downloaded. It is not written by hand and it is
not the file you edit.

```sh
requirements.in     what you ask for        ← edited by a person
requirements.txt    what that resolves to   ← generated, committed
```

```sh
pip-compile requirements.in          # writes requirements.txt, fully pinned
pip-sync requirements.txt            # makes the environment match it exactly
```

```sh
# requirements.txt — autogenerated by pip-compile
certifi==2026.7.22
    # via requests
charset-normalizer==3.5.1
    # via requests
idna==3.20
    # via requests
requests==2.31.0
    # via -r requirements.in
urllib3==2.8.0
    # via requests
```

**Look at the annotations.** They are the thing `pip freeze` cannot produce: one line says
`via -r requirements.in`, and it is the only package anybody chose. The other four say which
package dragged them in, so the file answers "may I delete this line" without anybody having to
work it out.

`pip-tools` is the old way of doing this with `pip`, and the naming is confusing on purpose:
the generated file is called `requirements.txt` so that `pip install -r` keeps working for
anybody who has not heard of any of this.

## Both files are committed

The input says what the project needs and is reviewed by people. The output says what was
installed and is reviewed by nobody, and it is what makes two machines identical.

A pull request that changes the generated file without changing the input is an upgrade of
something transitive, which is exactly the change you want to be able to see.

## `--require-hashes`

```sh
requests==2.31.0 \
    --hash=sha256:58cd2187c01e70e6e26505bca751777aa9f2ee0b7f4300988b709f44e013003f
```

With hashes in the file, `pip` refuses anything whose bytes do not match. It is what stops a
compromised index serving you a different file under the same version number, and it is worth
turning on for anything that deploys.

## And the honest summary

`pip` alone can do all of this and none of it is its default. The tools in the next lesson do it
without being asked, which is most of why they exist.
