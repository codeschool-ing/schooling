**A GraphQL client is a cache with a network connection behind it.** Lesson 9's `request` sent a query
and handed back the answer, and kept nothing. Every screen that needed a session asked the server again,
and nothing told the course list that a session on the course page had changed. A client keeps every
object it has received, answers from that memory when it can, and tells every part of the page that
reads an object when the object changes.

| | lesson 9's `request` | a client such as Apollo or Relay |
|---|---|---|
| a second request for the same data | goes to the server | answered from the cache |
| a mutation's answer | returned to the caller | written into the cache, so every query showing that object updates |
| two components asking at once | two requests | one request, shared |
| a change that the server refuses | the screen stays wrong | an optimistic change is taken back |
| the code you add to the page | twelve lines | a library of its own, measured in this lesson |

The two clients in this lesson make the same core promise and differ in what they ask of you. **Apollo
Client** works with any schema and any framework, including none, and lets you organise queries as you
like. **Relay**, which Meta uses for its own apps, needs a schema that follows its conventions and a
compiler in the build, and in return makes every component declare exactly the fields it reads.

The planner moves to Apollo here, because it runs in plain TypeScript and against the server from
lesson 9 as it is. Relay is shown, and not run: it only works in React, and the planner has no framework.
