**Um diagrama de casos de uso responde a duas perguntas ao mesmo tempo: quem interage com o
sistema, e que objetivos alcança com ele.** Ele também desenha onde o sistema termina, que é a
utilidade que as pessoas esquecem que ele tem. Não diz nada sobre como qualquer coisa funciona por
dentro.

## Quatro elementos

- Um **ator** é um papel desempenhado por alguém ou por algo fora do sistema: um passageiro, um
  agente de guichê, o gateway de pagamento. Ele é desenhado como um boneco de palitos, mesmo quando
  o ator é outro sistema, e nomeia um **papel**, não uma pessoa: Tainá comprando a própria passagem
  está agindo como passageira.
- Um **caso de uso** é um objetivo que um ator alcança por meio do sistema, nomeado com um verbo do
  ponto de vista do ator: *comprar uma passagem*, *embarcar um passageiro*. É desenhado como uma
  elipse.
- A **fronteira do sistema** é um retângulo em volta dos casos de uso, com o nome do sistema. Tudo o
  que está dentro é o que está sendo construído; os atores ficam sempre do lado de fora.
- Uma **associação** é uma linha simples entre um ator e um caso de uso de que ele participa.

O ator que inicia um caso de uso para alcançar o próprio objetivo é o **ator principal**, e em geral
fica à esquerda. Um ator de que o sistema precisa para terminar o caso de uso, como o gateway de
pagamento, é um **ator de apoio**, em geral à direita.

## Include, extend e generalização

Duas setas tracejadas deixam um caso de uso se referir a outro, e elas apontam em sentidos opostos:

- **`«include»`** vai do caso de uso base para aquele que ele sempre usa. *Comprar uma passagem*
  inclui *receber o pagamento*, e *vender no guichê* também. É assim que um passo comum a vários
  casos de uso é escrito uma vez só.
- **`«extend»`** vai do comportamento opcional para o caso de uso base que ele pode estender.
  *Aplicar um cupom de desconto* estende *comprar uma passagem*: dá para comprar sem cupom. O caso
  de uso base não sabe da extensão, e é por isso que a seta aponta para ele.

Atores podem ser generalizados com uma seta de ponta vazada: um *agente de guichê* pode fazer tudo o
que um *passageiro* faz, num guichê, e mais.

1. **Casos de uso que são telas ou funções.** *Tela de login*, *validar CPF*, *gravar no banco* são
   passos, não objetivos. Um caso de uso é algo que um ator reconheceria como valendo a pena fazer.
2. **Setas entre casos de uso mostrando ordem.** Um diagrama de casos de uso não tem tempo. *Buscar
   viagens*, depois *escolher assento*, depois *pagar* é um diagrama de atividades, da aula 4,
   desenhado na notação errada.
3. **O banco de dados como ator.** O banco de reservas está dentro do sistema. Um ator está fora
   dele, por definição; pôr partes internas fora da fronteira tira o sentido da fronteira.
4. **Include usado como decomposição.** Quebrar *comprar uma passagem* em cinco pedaços com
   `«include»` é escrever um programa em elipses. O include é para comportamento que é de fato
   compartilhado.

## O texto é o caso de uso de verdade

O diagrama é um sumário. **O caso de uso em si é texto**: quem é o ator principal, o que precisa ser
verdade antes de ele começar, o cenário principal de sucesso em passos numerados, e as extensões,
os pontos em que outra coisa pode acontecer. Em *comprar uma passagem*, o passo 4 pode ser *o
sistema segura o assento por dez minutos*, e a extensão 4a *o assento foi pego por outro passageiro
nesse meio-tempo: o sistema oferece os assentos livres mais próximos*. *Writing Effective Use
Cases*, de Alistair Cockburn, é a referência clássica para esse texto, e a aula 6 volta a ele quando
escreve requisitos funcionais.

**Desenhe você também.** Desenhe o diagrama de casos de uso do embarque da Carcará: o motorista
conferindo passagens na porta, um passageiro sem passagem comprando uma com o motorista, e o que
acontece quando o celular está sem sinal. Decida quem são os atores antes de desenhar qualquer
elipse.
