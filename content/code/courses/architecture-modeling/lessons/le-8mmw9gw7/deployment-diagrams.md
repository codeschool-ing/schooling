**A deployment diagram shows the physical side: the machines and environments the software runs on,
what is installed on each, and how they are connected.** It answers the questions operations asks:
*what runs where?*, *what talks to what over the network?*, *what is lost if this machine goes?*

## The notation

- A **node** is a three-dimensional box: something that can run software. UML separates two kinds,
  marked with keywords: a **`«device»`**, a physical piece of hardware such as a driver's phone, and
  an **`«executionEnvironment»`**, a software environment that hosts other software, such as a
  container runtime, a virtual machine or a managed database service.
- Nodes **nest**: an execution environment drawn inside a device runs on it.
- An **artifact** is a concrete file that gets deployed: `ticketing-api.jar`, a container image, an
  app package. It is a rectangle with the keyword `«artifact»`, drawn inside the node it is deployed
  to.
- A **communication path** is a solid line between nodes, labelled with the protocol: `HTTPS`,
  `PostgreSQL wire protocol`.

The diagram says, in a way the component diagram could not:

- The ticketing API runs as **three replicas** in a container cluster in one cloud region. The
  multiplicity on the node says so; the component diagram had only one *Ticketing*.
- The booking database is a **managed service** in the same region, a node of its own, and every
  replica reaches it over the network.
- The **boarding app runs on 300 drivers' phones**, each with a local copy of the day's tickets for
  its bus. That local store is why boarding works on a road with no signal, and it is invisible on
  every other diagram in this lesson.
- The payment gateway is **somebody else's node**, reached over the internet, drawn without anything
  inside it, because Carcará does not know or control what runs there.

## Mistakes

- **Logical parts drawn as nodes.** *Pricing* drawn as a 3D box claims it is a machine. If it is a
  module inside the ticketing service, it belongs inside the artifact, or on the component diagram
  instead.
- **Lines with no protocol.** On a deployment diagram, the protocol is the point: it decides the
  firewall rules, the encryption and what breaks when a port is closed.
- **One box per server, at scale.** Forty identical nodes drawn forty times hides the one fact a
  reader needs, which is *forty*. Draw one and write the count.
- **The diagram of last year.** Infrastructure changes more often than the domain model. A
  deployment diagram is the first to go stale, which is why lesson 12 shows how to generate one, and
  lesson 11 how to know when one has died.

**Draw it yourself.** Draw the deployment of the station back office: the agents' desktop computers
in 26 bus stations, the receipt printer at each counter, and the same ticketing API in the cloud.
Decide what the agents' computers need locally if the station's internet connection drops.
