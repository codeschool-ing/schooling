title: How class diagrams go wrong

**Most bad class diagrams are correct UML that answers the wrong question.** The marks are right
and the picture is still useless, because it shows the database, or every class, or a relationship
the domain does not have.

1. **The diamond on the wrong end.** Here the filled diamond sits beside *Ticket*, which says that a
   ticket is the whole and owns its booking. A reader who knows UML reads exactly that. The diamond
   always goes on the side of the whole.
2. **The schema in disguise.** `bookingId: Long` on *Ticket*, beside the line to *Booking*, is a
   foreign key column. In a class diagram the line *is* the reference; writing the key as well says
   it twice, and says it in the database's terms rather than the domain's.
3. **Composition where the part outlives the whole.** *Trip* drawn as a composed part of *Ticket*
   says that deleting one ticket deletes the departure, with forty-three other passengers on it. A
   trip is shared, and outlives every ticket that points at it.
4. **Navigability nobody decided.** Arrowheads on both ends of the passenger–booking line say that a
   booking holds its passenger and a passenger holds a list of every booking they ever made. The
   second is a decision with a cost, and here nobody made it. Draw an arrowhead only where the
   direction is a decision.
5. **Every getter and setter.** Twelve `get` and `set` operations on *Passenger* bury the two
   operations that matter, and they tell the reader nothing the attribute list did not.

## Too much, and too little

Two scale errors are as common as the notation errors:

- **The whole service in one diagram.** A class diagram generated from eighty classes shows that
  the code has eighty classes. If the reader needs that, the code is a better place to look. If the
  question is about a domain concept, draw the five or six classes that answer it.
- **Boxes with names and nothing else.** A diagram of class names joined by plain lines, with no
  multiplicity and no roles, says that these things are related and nothing more. The numbers are
  the cheapest part to draw and often the most important: `0..1` against `1` is the difference
  between *a passenger may have a loyalty card* and *every passenger must have one*.

## Check it against the code, both ways

A class diagram makes claims the code can confirm or deny. Before you share one, check each line
against the source: does `Ticket` actually hold a reference to `Trip`? Does deleting a `Booking`
delete its tickets? **A domain diagram that disagrees with the code teaches the next reader the
wrong model**, and it does so with the authority of a formal notation. When the code is wrong
instead, the diagram has found a bug, which is one of the better reasons to draw it.
