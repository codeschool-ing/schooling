**Um diagrama de sequência mostra as mensagens que passam entre os participantes para realizar um
cenário, na ordem em que acontecem.** O tempo corre de cima para baixo. É o diagrama para qualquer
pergunta que tenha um *e depois*: o que acontece quando o passageiro aperta *pagar*, qual chamada
espera por qual, e onde um timeout cairia.

## A notação

- Uma **linha de vida** é um participante: uma caixa no alto com o nome dele, e uma linha tracejada
  descendo. Participantes podem ser pessoas, serviços, bancos de dados ou objetos. Dê a eles os
  nomes que têm no resto da documentação, `API de passagens` em vez de `API`.
- Uma **mensagem** é uma seta de uma linha de vida para outra. A ponta da seta diz de que tipo:
  - uma **ponta cheia** é uma mensagem **síncrona**: quem manda espera a resposta;
  - uma **ponta aberta** é uma mensagem **assíncrona**: quem manda segue em frente;
  - uma **linha tracejada com ponta aberta** é uma **resposta**.
- Uma **ativação**, ou especificação de execução, é uma barra fina sobre a linha de vida que mostra
  quando aquele participante está ocupado tratando uma mensagem.
- Um **fragmento combinado** é uma moldura com rótulo em volta de parte da sequência: **`alt`** para
  alternativas, com uma condição em cada uma, **`opt`** para uma parte que pode não acontecer,
  **`loop`** para repetição, **`par`** para partes que rodam ao mesmo tempo, e **`ref`** para apontar
  para outro diagrama em vez de desenhá-lo aqui.

Leia de cima para baixo:

1. O app do passageiro manda `POST /bookings` para a API de passagens e espera.
2. A API pede ao store de assentos que bloqueie o assento 14 daquela viagem por dez minutos. O store
   responde *bloqueado*, ou responderia *ocupado* e o passageiro escolheria de novo.
3. A API grava a reserva no banco de reservas com o status *aguardando pagamento*, e só então
   responde ao app com `201 Created`.
4. O app manda o pagamento, e a API chama o gateway de pagamento, que cobra o cartão.
5. O fragmento `alt` se divide pela resposta do gateway: **aprovado** marca a reserva como *paga* e
   responde ao app com a passagem; **recusado** libera o bloqueio e responde com o motivo.

As duas metades são pedidos separados de propósito: o assento é bloqueado antes de o dinheiro se
mexer, então o passageiro nunca paga por um assento que outra pessoa pegou primeiro.

## O que deixar de fora

Um diagrama de sequência cresce depressa. Três regras o mantêm legível:

- **Um cenário por diagrama.** O caminho feliz e as duas falhas que importam, num `alt`, e não todos
  os desvios que o código tem. Um diagrama com seis fragmentos aninhados é um programa, e o programa
  é mais fácil de ler.
- **Um nível de participante.** Serviços falando com serviços, ou classes falando com classes, mas
  não as duas coisas na mesma página. Os níveis de zoom da aula 3 dizem o mesmo sobre caixas.
- **Mensagens de resposta só onde carregam alguma coisa.** Uma resposta que é só *ok* pode ficar
  implícita; uma resposta de que o passo seguinte depende, como *bloqueado* ou *recusado*, é
  desenhada e nomeada.

**Desenhe você também.** Desenhe a sequência de um passageiro cancelando uma passagem paga mais de
três horas antes da partida: o app, a API de passagens, o banco de reservas, o gateway de pagamento
para o estorno, e o serviço de notificações que manda o e-mail. Decida quais mensagens precisam
esperar e quais não precisam, e desenhe as pontas de seta para dizer isso.
