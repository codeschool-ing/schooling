**A sequence diagram shows the messages that pass between participants to carry out one scenario,
in the order they happen.** Time runs down the page. It is the diagram for any question that
contains *and then*: what happens after the passenger presses *pay*, which call waits for which, and
where a timeout would land.

## The notation

- A **lifeline** is a participant: a box at the top with its name, and a dashed line going down.
  Participants can be people, services, databases or objects. Name them as they are named in the
  rest of the documentation, `Ticketing API` rather than `API`.
- A **message** is an arrow from one lifeline to another. The arrowhead says what kind:
  - a **filled arrowhead** is a **synchronous** message: the sender waits for the answer;
  - an **open arrowhead** is an **asynchronous** message: the sender carries on;
  - a **dashed line with an open arrowhead** is a **reply**.
- An **activation**, or execution specification, is a thin bar on a lifeline showing when that
  participant is busy handling a message.
- A **combined fragment** is a labelled frame around part of the sequence: **`alt`** for
  alternatives with a condition on each, **`opt`** for a part that may not happen, **`loop`** for
  repetition, **`par`** for parts that run at the same time, and **`ref`** to point at another
  diagram instead of drawing it here.

Read it from the top:

1. The passenger app sends `POST /bookings` to the ticketing API and waits.
2. The API asks the seat-hold store to hold seat 14 on that trip for ten minutes. The store answers
   *held*, or it would answer *taken* and the passenger would choose again.
3. The API writes the booking to the booking database with the status *pending payment*, and only
   then answers the app with `201 Created`.
4. The app sends the payment, and the API calls the payment gateway, which charges the card.
5. The `alt` fragment splits on the gateway's answer: **approved** marks the booking *paid* and
   answers the app with the ticket; **declined** releases the hold and answers with the reason.

The two halves are separate requests on purpose: the seat is held before the money moves, so the
passenger never pays for a seat somebody else got first.

## What to leave out

A sequence diagram grows fast. Three rules keep it readable:

- **One scenario per diagram.** The happy path and the two failures that matter, in an `alt`, not
  every branch the code has. A diagram with six nested fragments is a program, and the program is
  easier to read.
- **One level of participant.** Services talking to services, or classes talking to classes, but not
  both on the same page. Lesson 3's zoom levels make the same point for boxes.
- **Return messages only where they carry something.** An answer that is just *ok* can be left
  implicit; an answer the next step depends on, like *held* or *declined*, is drawn and named.

**Draw it yourself.** Draw the sequence for a passenger cancelling a paid ticket more than three
hours before departure: the app, the ticketing API, the booking database, the payment gateway for
the refund, and the notification service that sends the e-mail. Decide which messages must wait and
which need not, and draw the arrowheads to say so.
