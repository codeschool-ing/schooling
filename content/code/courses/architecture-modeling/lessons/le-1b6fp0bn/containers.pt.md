**O diagrama de containers abre a caixa do sistema e mostra as partes que rodam separadamente
dentro dela: as aplicações e os armazenamentos de dados, a tecnologia que cada uma usa e como elas
conversam entre si.** É o diagrama que engenheiros mais usam, porque responde às perguntas que
aparecem toda semana: *onde mora este dado?*, *o que chama o quê?*, *o que temos de implantar?*

## Um container não é um container Docker

A palavra causa mais confusão do que qualquer outra coisa no C4, então vale resolver isso primeiro.
No C4, um **container é qualquer coisa que precisa estar rodando para o sistema funcionar**: uma
aplicação no servidor, uma single-page app rodando num navegador, um app móvel, um banco de dados,
um armazenamento de arquivos, uma fila de mensagens, uma função serverless. É uma fronteira de
execução.

**Não** é um container Docker, e o C4 escolheu a palavra antes de o Docker torná-la famosa. Um
container do C4 pode rodar num container Docker, numa máquina virtual ou num celular. Dez
containers Docker rodando dez réplicas da API de passagens são **um** container do C4, desenhado uma
vez, porque são cópias da mesma coisa. É no diagrama de implantação que os dez aparecem.

Um teste que resolve a maioria dos casos: **dá para implantar, iniciar ou parar isso sozinho?** Se
sim, provavelmente é um container. Se é uma biblioteca ou um módulo compilado dentro de outra coisa,
é um componente, um nível abaixo.

Cada elemento traz quatro coisas: um **nome**, o **tipo** entre colchetes com a sua **tecnologia**,
e uma **descrição** de uma linha do que é responsabilidade dele. Cada linha diz o que faz e como.
Lido por inteiro, o diagrama responde a perguntas que o de contexto não respondia:

- O app web do passageiro e o app móvel são **dois containers**, porque são construídos, lançados e
  executados separadamente, embora os dois falem com a mesma API.
- Os bloqueios de assento ficam no **Redis**, separados das reservas no **PostgreSQL**. Um bloqueio
  é temporário e muito acessado; uma reserva é permanente e precisa sobreviver a qualquer coisa. Dois
  stores, para dois tipos de dado.
- A API de passagens **publica eventos** num broker de mensagens, e o worker de notificação os
  consome. É por isso que um provedor de SMS lento não deixa a compra lenta, e a linha tracejada diz
  que a API não espera.
- O app de embarque fala com um serviço de **sincronização de embarque**, e não diretamente com a
  API de passagens. Ele baixa a lista de passagens de cada ônibus antes da partida e envia as
  leituras quando tem sinal.

## Quanto pôr nele

Um sistema com cinquenta containers não cabe numa página legível, e não precisa caber. Três
estratégias, em ordem de preferência:

1. **Desenhe os containers de uma pergunta.** A figura acima é *o que participa da venda e da
   conferência de passagens*. Um segundo diagrama de containers poderia mostrar relatórios e
   financeiro.
2. **Agrupe por fronteira.** Containers de times diferentes podem ficar dentro de fronteiras
   tracejadas com nome, o que também mostra a quem perguntar.
3. **Divida o sistema.** Se um único diagrama de containers não pode ser desenhado sem virar um mapa
   de tudo, o *sistema de software* talvez sejam na verdade dois, cada um merecendo o seu próprio
   contexto.

**Desenhe você também.** Acrescente ao diagrama de containers o app web de back office da Carcará,
usado pelos agentes de guichê: o que ele chama, e ele precisa de um banco de dados próprio? Escreva
o rótulo de cada linha que acrescentar, e depois confira cada uma com o teste de leitura da aula 1.
