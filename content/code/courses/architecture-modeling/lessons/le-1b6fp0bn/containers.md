**The container diagram opens the system box and shows the separately running parts inside it:
the applications and the data stores, what technology each one uses, and how they talk to each
other.** It is the diagram engineers use most, because it answers the questions that come up every
week: *where does this data live?*, *what calls what?*, *what do we have to deploy?*

## A container is not a Docker container

The word causes more confusion than anything else in C4, so it is worth settling first. In C4, a
**container is anything that must be running for the system to work**: a server-side application,
a single-page app running in a browser, a mobile app, a database, a file store, a message queue, a
serverless function. It is a runtime boundary.

It is **not** a Docker container, and C4 chose the word before Docker made it famous. A container in
C4 may run in a Docker container, or on a virtual machine, or on a phone. Ten Docker containers
running ten replicas of the ticketing API are **one** C4 container, drawn once, because they are
copies of the same thing. The deployment diagram is where the ten appear.

A test that settles most cases: **could it be deployed, started or stopped on its own?** If yes, it
is probably a container. If it is a library or a module compiled into something else, it is a
component, one level down.

Each element carries four things: a **name**, the **type** in brackets with its **technology**, and
a one-line **description** of what it is responsible for. Each line carries what it does and how.
Read together, the diagram answers questions the context diagram could not:

- The passenger web app and the mobile app are **two containers**, because they are built,
  released and run separately, even though both talk to the same API.
- Seat holds live in **Redis**, separate from bookings in **PostgreSQL**. A hold is temporary and
  hot; a booking is permanent and must survive anything. Two stores, for two kinds of data.
- The ticketing API **publishes events** to a message broker and the notification worker consumes
  them. That is why a slow SMS provider does not slow down a purchase, and the dashed line says the
  API does not wait.
- The boarding app talks to a **boarding sync** service, not to the ticketing API directly. It
  downloads each bus's ticket list before departure and uploads the scans when it has signal.

## How much to put on it

A system with fifty containers will not fit on one readable page, and does not need to. Three
strategies, in order of preference:

1. **Draw the containers for one question.** The figure above is *what takes part in selling and
   checking tickets*. A second container diagram could show reporting and finance.
2. **Group by boundary.** Containers owned by different teams can sit inside named dashed
   boundaries, which also shows who to ask.
3. **Split the system.** If a single container diagram cannot be drawn without becoming a map of
   everything, the *software system* may really be two, each deserving its own context.

**Draw it yourself.** Add Carcará's back-office web app for station agents to the container
diagram: what does it call, and does it need its own database? Write the label for every line you
add, then check each one against lesson 1's reading test.
