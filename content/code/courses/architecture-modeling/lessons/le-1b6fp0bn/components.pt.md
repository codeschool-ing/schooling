**O diagrama de componentes abre um container e mostra os seus principais blocos estruturais, pelo
que cada um responde, e como eles interagem entre si e com os containers em volta.** É para o time
que trabalha naquele container, e para qualquer pessoa que precise mudá-lo sem quebrá-lo.

## O que conta como componente

Um componente é **um agrupamento de funcionalidades relacionadas atrás de uma interface bem
definida**, rodando dentro de um container e sem poder ser implantado sozinho. Num serviço em Kotlin
ou Java, muitas vezes é um conjunto de classes atrás de uma interface, ou um pacote; em Go, um
pacote; num monólito modular, um módulo. Não é cada classe: um diagrama de componentes da API de
passagens com oitenta caixas é o código, mal desenhado.

O diagrama mostra as sete partes principais da API:

- dois **controllers** recebem as requisições HTTP, um para reservas e outro para pagamentos;
- o **serviço de reservas** guarda as regras: um assento só pode ser bloqueado uma vez, uma reserva
  expira depois de dez minutos sem pagamento, um cancelamento feito mais de três horas antes da
  partida é reembolsado;
- o **cliente de bloqueios**, o **cliente de cotação** e o **adaptador de pagamento** embrulham, cada
  um, uma dependência externa, para que o serviço nunca fale HTTP nem Redis ele mesmo;
- o **tratador de webhook** recebe as confirmações de pagamento que o gateway manda depois.

Os containers nas bordas são os mesmos do diagrama de containers, desenhados aqui só onde um
componente fala com eles. É assim que os níveis ficam consistentes: **uma relação num nível precisa
ser explicada por relações no nível de baixo**. A seta única do diagrama de containers, da API de
passagens para o gateway de pagamento, aparece aqui como a seta que sai do adaptador de pagamento.

## Quando desenhá-lo, e quando não

O próprio Simon Brown aconselha que o diagrama de componentes é opcional, e ele é o primeiro a ficar
desatualizado, porque os componentes mudam a cada refatoração. Dois casos justificam desenhá-lo à
mão:

- **o container é complexo e importante**, e gente nova vive perguntando como ele é organizado;
- **uma mudança está sendo projetada** que move responsabilidades entre componentes, e os desenhos
  de antes e depois são o jeito mais claro de discuti-la.

Para todo o resto, um diagrama de componentes é um bom candidato a ser **gerado a partir do
código**, o que a aula 12 mostra com o Structurizr. Gerado, ele nunca erra sobre o que existe;
desenhado à mão, ele pode dizer o que se pretendia, coisa que o código não diz.
