**The component diagram opens one container and shows its major structural building blocks, what
each is responsible for, and how they interact with each other and with the containers around
them.** It is for the team that works on that container, and for anybody who has to change it
without breaking it.

## What counts as a component

A component is **a grouping of related functionality behind a well-defined interface**, running
inside one container and not deployable on its own. In a Kotlin or Java service it is often a set
of classes behind one interface, or a package; in Go, a package; in a modular monolith, a module.
It is not every class: a component diagram of the ticketing API with eighty boxes is the code, drawn
badly.

The diagram shows the API's seven main parts:

- two **controllers** receive HTTP requests, one for bookings and one for payments;
- the **booking service** holds the rules: a seat can be held once, a booking expires after ten
  minutes unpaid, a cancellation more than three hours before departure is refunded;
- the **seat-hold client**, the **fare quote client** and the **payment adapter** each wrap one
  outside dependency, so that the service never talks HTTP or Redis itself;
- the **webhook handler** receives the payment confirmations that the gateway sends later.

The containers around the edges are the same ones as on the container diagram, drawn here only
where a component talks to them. That is how the levels stay consistent: **a relationship at one
level must be explained by relationships at the level below**. The container diagram's single arrow
from the ticketing API to the payment gateway appears here as the arrow from the payment adapter.

## When to draw it, and when not

Simon Brown's own advice is that the component diagram is optional, and it is the first diagram to
go stale, because components change with every refactoring. Two cases justify drawing it by hand:

- **the container is complex and important**, and new people keep asking how it is organised;
- **a change is being designed** that moves responsibilities between components, and the before and
  after pictures are the clearest way to discuss it.

For everything else, a component diagram is a good candidate for being **generated from the code**,
which lesson 12 shows with Structurizr. Generated, it is never wrong about what exists; drawn by
hand, it can say what was intended, which the code cannot.
