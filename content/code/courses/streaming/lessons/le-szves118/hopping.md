title: Hopping windows
version: 1

**A hopping window has a size and an advance, and when the advance is shorter than the size the
windows overlap, so one event belongs to several.** "Sales in the last ten minutes, updated every
five" is a hopping window of size 10 and advance 5. Tumbling windows are the special case where
the advance equals the size.

The reason to want one is the weakness the last section ended on. Sales 4 and 5, at 09:05:00 and
09:06:20, and sales 1 to 3 just before them, are one busy stretch of six minutes; five-minute
tumbling windows split it three and two, and neither window looks busy. A ten-minute window that
starts every five minutes is guaranteed to contain any stretch of up to five minutes whole, in at
least one of its windows.

Each window starts at a multiple of the advance and lasts for the size. An event at `t` is in
every window that started at or before `t` and has not ended yet: **size ÷ advance windows, when
the size is a multiple of the advance**. Here that is two. Sale 3, at 09:03:55, is in the windows
starting 08:55 and 09:00; sale 4, at 09:05:00, is in those starting 09:00 and 09:05, and not in
the one starting 08:55, which ended at 09:05:00 exactly.

```
ubuntu@stream:~/work$ python windows.py hopping 10 5
```

Six windows where tumbling had four, and the counts add up to twenty, twice the ten sales,
because each sale was counted in two windows. **A hopping window's results cannot be summed**,
which is the first thing that goes wrong when one is fed to a report that adds rows together. The
09:00 to 09:10 window has six sales, the busy stretch whole, which no five-minute window showed.

The first and last windows deserve a look. 08:55 to 09:05 exists although the shops opened at
nine, because sale 1 at 09:00:40 falls in it; the window is a slice of the clock, not of the
day's trading. 09:20 to 09:30 holds only sale 10, and so does 09:15 to 09:25. Every event creates
the windows it belongs to, and a single sale late in the morning creates two.

## What it costs

Overlap multiplies work and state. With size 60 minutes and advance 1 minute, every event is
added to sixty windows, and sixty windows per key are open at any moment. An engine with a
running count per window pays sixty times what a tumbling hour pays, which is why "the last hour,
updated every second" is usually built some other way: a tumbling window of a minute, and the
last sixty of them added up when somebody asks.

## The word is not the same everywhere

Flink calls this window **sliding**: `SlidingEventTimeWindows.of(size, slide)`. So does Spark's
`window(column, "10 minutes", "5 minutes")`, and so does a lot of writing about streaming. Kafka
Streams calls it **hopping**, `TimeWindows.ofSizeWithNoGrace(size).advanceBy(advance)`, and keeps
the word sliding for something different, which the next section shows. This course uses Kafka
Streams' names because they keep the two ideas apart. When you read "sliding window" anywhere
else, check which one is meant.
