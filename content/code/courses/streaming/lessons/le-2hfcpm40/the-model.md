The programs in lessons 9 to 11 did everything by hand: they read events one at a time, kept a
dictionary of open windows, moved a watermark and decided when a window was finished. **Spark
Structured Streaming lets you write the same count as an ordinary query over a table, and takes
over the rest**: reading the topic, keeping the open windows, remembering where it stopped, and
starting again from there after a crash.

The common wrong picture is that Spark handles each sale the moment it arrives, the way your own
consumer did. **By default it does not.** It waits, gathers whatever has arrived since the last
time, and processes that slice as one small batch job. Then it does it again. Each slice is a
**micro-batch**, and the gap between them, from a few hundred milliseconds to minutes, is the
latency you pay for everything else Spark gives you.

## The unbounded table

Spark's model is a table that rows are appended to and never removed from. Every sale that reaches
the topic is one more row at the bottom of it. You write a query against that table as if it were
complete, with `select`, `where`, `groupBy` and the rest, and Spark never runs it over the whole
table. **It runs the query incrementally**: each micro-batch reads only the rows that are new, and
combines them with what it kept from the batches before.

What it keeps is called **state**. A query that only picks columns and filters rows needs none: a
row goes in, a row comes out. A query that counts sales per five-minute window needs the running
count of every window that might still receive a sale, and that state grows until something says a
window is finished. The something is the watermark from lesson 11, which Spark implements for you
and which section 05 of this lesson puts to work.

## Three questions every query answers

A streaming query in Spark is a query plus three decisions, and each has its own section here:

| decision | the question | where |
|---|---|---|
| **output mode** | after a batch, which rows of the result go out: new ones, changed ones, or all of them | section 05 |
| **checkpoint** | where Spark writes what it has read and what it has finished, so a restart knows where to begin | section 06 |
| **trigger** | when the next batch starts: on a timer, as soon as possible, once over what is there, or continuously | section 07 |

The fourth part is the **sink**, the place the results go: the console in most of this lesson, then
Kafka and files in section 08. Whether a sink can take the same batch twice without harm is what
decides if the whole query is exactly-once, which is lesson 7's word reaching a real engine.

## Two Spark streaming APIs, and which one this is

Spark has had two streaming APIs. The first, **Spark Streaming**, with its `DStream` objects, worked
on batches of Java objects and knew nothing of event time. It was deprecated in Spark 3.4 and
this course does not use it. **Structured Streaming**, the second, is built on DataFrames and
SQL, so the same functions that work on a table of last year's sales work on the stream. A search
for help finds both, and the way to tell them apart is the word `readStream`: the new API has it
and the old one does not.

Spark is not the only engine that takes this job. Lesson 13 shows Flink, which handles one record at
a time instead of in slices, and Kafka Streams, which is a library inside your own program rather
than an engine beside it. This lesson stays with Spark, because the micro-batch is the easiest of
the three to watch: each batch is printed, numbered, and can be read like a table.
