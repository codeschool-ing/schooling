The dashboard from lesson 18 was designed for a laptop. Its reader, Horta's director, mostly opens it
on a phone, between meetings, holding it in one hand. That is not an edge case: for many people the
phone is where a dashboard is read most often.

A phone held upright is about 360 to 430 CSS pixels wide. A CSS pixel is the browser's unit of
layout, not a dot on the screen: a phone with a sharp display packs two or three physical pixels into
each one, so the numbers to design with are these small ones.

There are two ways to put a 960-pixel dashboard on a 360-pixel screen:

**Shrinking** keeps the layout and scales everything down by 360 ÷ 960 = 0.375. A label drawn at 10
pixels arrives at 3.75, which nobody can read without zooming, and zooming a dashboard means panning
around it like a map. This is what a page does when it does not say it was made for phones, and it
is what an image of a dashboard does on any screen.

**Reflowing** keeps the sizes and changes the layout. The blocks that sat side by side now sit one
above another, each as wide as the screen. The reader scrolls down instead of zooming in, which is
the movement a phone is built for.

## What changes and what does not

Reflowing changes **where** things go and sometimes **which chart** is used. It does not change the
questions the dashboard answers or the order of their importance. The rest of this lesson is the
detail:

- the order the blocks stack in;
- which charts survive a narrow screen and which need replacing;
- the controls a finger has to hit;
- how a page tells the browser to do all this.
