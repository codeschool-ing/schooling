The usual reading of a diamond is "a decision": the flow reaches it, somebody chooses, one path is
taken. That covers one kind of gateway out of four, and only when it splits. **A gateway is a rule
about tokens, and the same diamond does a different thing when it splits a flow and when it joins
one.** Getting the join wrong is the most common way a BPMN diagram breaks, and it breaks without
an error message.

## The token game

BPMN 2.0 describes its behaviour with an imaginary object, the **token**. A start event creates a
token. The token travels along sequence flows; when it reaches an activity the activity runs, and
when the activity finishes the token moves on. An end event consumes the token, and **a process
instance is complete when no tokens are left in it**. Several tokens can be alive in one instance at
once, which is what "two things happening in parallel" means in this notation.

That is all there is to it, and it is enough to predict what any diagram will do. Put a finger on
the start event and move it along the arrows; when a gateway would create a second token, use a
second finger. An engine does exactly this, and a diagram you have walked with your fingers holds
no surprises for one.

## Four gateways, each with a split and a join

| gateway | marker | as a split | as a join |
|---|---|---|---|
| exclusive (XOR) | X | exactly one outgoing path, the first whose condition is true | passes every token straight through, without waiting |
| parallel (AND) | + | one token on every outgoing path, no conditions | waits for a token on every incoming path, then sends one on |
| inclusive (OR) | circle | a token on each path whose condition is true: one, some or all | waits for every token that is still on its way |
| event-based | pentagon | waits for events; the first to happen takes the token | (not used as a join) |

**The exclusive split** evaluates the conditions on its outgoing flows and sends the token down one
of them. One flow can be marked as the **default**, with a short slash across its start, and it is
taken when no condition is true. Without a default, an instance where nothing is true has nowhere
to go, and the specification treats that as an exception. Conditions should not overlap either:
with two of them true, one path is taken and which one depends on the order the engine evaluates
them in, which is not something a reader can see on the page.

**The parallel split** has no conditions at all. A token leaves on every outgoing flow, so three
outgoing flows make three tokens. In the onboarding diagram, the quality visit and the bank account
registration are independent, so neither waits for the other; that alone takes about a week out of
the thirty days, because the bank part used to start only after the visit report was filed.

**The inclusive split** is the one people reach for least and need more often than they think. Each
outgoing flow whose condition is true gets a token. At Serra Alta, after the documents are checked,
a farm more than 15 km from any existing truck route needs a route survey by the Rota team, and a
farm whose cooling tank has no calibration certificate needs a tank inspection. A farm can need
one, both or neither, so the split is inclusive, with a default flow for "no extra checks". An
exclusive gateway there would send a farm that needs both down only one path.

**The event-based gateway** chooses by what happens rather than by data. The flows leaving it lead
to catching events, and the first event to occur wins; the others are withdrawn. "Signed contract
received" against "thirty days have passed" is the classic case, and the section on timers and
errors draws it.

## The joins, and why they must match

A join is where tokens meet, and each kind of join counts them differently. **A parallel join
waits until a token has arrived on every incoming flow and then sends one token on. An exclusive
join does not wait at all: every token that arrives passes through.** An inclusive join waits for
the tokens that can still arrive, which means it has to look back at what the matching split did.
That last behaviour is the hardest one for engines to implement and for readers to predict, and it
is the reason the rule below exists.

Pair a split with the wrong join and the token game gives you one of two failures.

**A parallel split joined by an exclusive gateway runs the next step twice.** Both tokens reach the
exclusive join, the join passes each one through, and every activity after it runs once per token.
This was in Joana's first draft. She had joined the visit and the bank registration with an X,
because "only one path continues", and Denise, walking it with two fingers, pointed out that the
approval question would be asked twice and an approved farm would be sent two contracts. In a
diagram with a three-way parallel split and the same mistake, the step after the join runs three
times.

**An exclusive split joined by a parallel gateway waits for ever.** The split sent one token down one
path. The parallel join counts its incoming flows, sees two, and waits for the second token, which
was never created. Nothing fails. The instance sits in the engine as *running*, its task list shows
nothing to do, and the only sign is a farm that phones three weeks later to ask what happened.
**A deadlocked instance looks exactly like a slow one**, which is why this mistake survives testing
that only checks for errors.

There is a third shape of the first mistake that has no gateway in it at all. Two sequence flows
drawn straight into one task, with no diamond, behave like an exclusive join: each token that
arrives starts the task again. BPMN calls this uncontrolled flow. It is legal, it is sometimes what
you mean, as when a correction loops back to the start of a check, and when you mean a join it is a
duplicate waiting to happen.

## Draw in blocks

The safest habit is to close every split with a join of the same kind, so the diagram is made of
nested blocks: a parallel split and its parallel join, an inclusive split and its inclusive join, an
exclusive split and its exclusive merge. The notation does not require it, and an exclusive split
whose paths end in different end events needs no join at all. **But a split whose matching join is
of another kind is the place to look first in any diagram that misbehaves**, and a reviewer can
check it without running anything.

Denise's own rule of thumb is shorter: if two arrows meet, say out loud how many tokens can arrive
there and what should happen to each one. That question found the duplicate contract in Joana's
draft, and it found two more errors in the version the suite had been running since 2014.
