The mapping is where a migration's decisions are written down. It is tempting to treat it as the
code that moves the data, and to let the decisions live in that code. **The mapping is a document
first and code second**: one row per field of the target, saying where its value comes from, what
happens to it on the way, and who agreed. The code implements the document, and when the two
disagree the document is what gets argued about.

## The mapping specification

A mapping specification is a table. Each row names a target field, the source field or fields it
comes from, the rule that turns one into the other, and the owner who signed the rule. Part of the
one for Coleta's farm master looks like this:

| target field | source in Coleta | rule | owner |
|---|---|---|---|
| `farm_id` | none | new identifier, generated by the new system | Joana |
| `legacy_code` | farm code | copied unchanged, kept for as long as anybody looks things up in Coleta | Sebastião |
| `tax_id` | CPF or CNPJ | copied; refused if the check digits fail | finance |
| `municipality` | municipality, free text | translated to the IBGE code through the municipality table | Sebastião |
| `vendor` | SAP vendor number | copied; refused if SAP has blocked that vendor | finance |
| `bank_account` | bank account | **not migrated**: SAP's vendor master is the only source | finance |
| `litres` (history) | litres × 100, an integer | divided by 100, stored with two decimals | Sebastião |
| `collected_on` (history) | date, eight digits, day first | read as day, month, year; refused if it is not a real date | Sebastião |
| lab results (history) | fat, protein, cell count, bacterial count | copied; units checked against Cláudia's table | Cláudia |

Three things in that table are worth noticing.

**Keep the old key.** `legacy_code` costs one column and answers every question of the form "which
farm in Coleta was this?" during the months when people still look things up there. Without it,
the only way back from a new record to an old one is matching names, which is the join by prose
that lesson 13's anti-corruption layer exists to avoid.

**A field can be mapped to nothing.** Coleta's bank account looks like data and is a fossil. The
profile showed it disagreed with SAP for 412 farms, and SAP is where finance maintains bank
details. Migrating it would create a third copy and, sooner or later, a payment to the wrong one.

**Units are a rule like any other.** Coleta stores litres as hundredths in an integer, because in
1996 that was how you kept decimals exact. The new system stores a decimal. Either is correct; a
load that copies the integer straight across is wrong by a factor of a hundred and loads
perfectly.

## Translation tables and merges

Where the source holds free text or old codes, the rule is a lookup. **A translation table maps
every value the profile found to the value the target expects**, and is a file the owner can read
and sign:

| Coleta's spelling | farms | IBGE municipality |
|---|---|---|
| `SANTOS DUMONT` | 61 | Santos Dumont |
| `STOS DUMONT` | 9 | Santos Dumont |
| `S. DUMONT` | 4 | Santos Dumont |
| `SANTOS DUMOND` | 1 | Santos Dumont |

The table has 97 rows, one per spelling, and the load refuses any spelling that is not in it. That
refusal matters: **a translation table with a default row turns tomorrow's new misspelling into a
farm in the wrong town**, silently.

The 7 duplicate farms are a translation of keys rather than values. A merge table names, for each
pair, the code that survives and the code that disappears; the duplicate's collection history is
re-keyed to the survivor. Sebastião wrote the table by hand, because only he knew which code each
farm actually used, and he signed each of the 7 rows.

## Defaults, and what not to migrate

A target field the source cannot fill needs a decision, and the easy one is a default. **A default
is a value somebody will later believe.** If a farm with no route had been given route 1 to satisfy
a mandatory field, the new route planner would have sent a truck to it. Where the source has
nothing, the honest values are a blank the target allows, or a refusal that sends the row back to
its owner.

The same applies to rows. Not everything in the old system belongs in the new one:

- **history outside the period** goes to the archive: the 182 farms with no collection in six
  years, and about 10.5 million old collection rows;
- **orphans** go to the archive with a note, since nothing in the new system can refer to them;
- **fields with a better master elsewhere**, like the bank account, go nowhere.

Each exclusion is a rule in the specification. The reconciliation later in this lesson has to
account for every source row, and a row that was left out on purpose needs a rule to point at.

## Where to cleanse

The profile found dirty data; the mapping has to say where it gets clean. There are three places,
and they are not equivalent.

| where | what it means | good for | the price |
|---|---|---|---|
| at the source | the owner corrects the old system before the move | facts that are wrong: an invalid CPF, a stale vendor number | the old system's screens and its owner's time |
| in flight | the transformation corrects the value on its way | format and code: spellings, units, layouts, merges | the old system stays dirty; the rule runs at every load |
| after the load | the owner corrects the new system | anything found late, by people using it | the new system starts dirty, in front of its users |

Joana's first instinct was to do everything in flight. At the fintech she came from, a data fix
was a script in the migration, and the source was a database nobody would ever read again.
Sebastião pointed out the difference. **Coleta keeps running for months after the farm master
moves**, because lesson 13's strangler moves one capability at a time, and every night it still
writes the file SAP loads. An invalid CPF corrected only in flight stays invalid in Coleta, in
every file it writes, until the day it is switched off. A fact that is wrong is corrected where it
lives.

So Serra Alta split the work by kind. **Wrong facts are corrected at the source by their owner:**
finance fixed the 9 CPFs and the 4 blocked vendors in Coleta's own screens. **Wrong forms are
translated in flight:** the municipalities, the units, the dates and the 7 merges, all by tables
that are part of the specification. Nothing was planned for after the load, which is not the same
as nothing happening there; the last section of this lesson is about what did.

**A reject file is a work queue, not a log.** Every rejected row carries its reason and goes to the
person who owns the rule it broke: an invalid CPF to finance, an unknown spelling to Sebastião, a
lab result in the wrong unit to Cláudia. A rejected row nobody owns stays rejected, and a farm with
no record in the new system is a farm that is not paid.

## Who signs

**The data belongs to the business, not to the migration team.** The team can write a rule; only
the owner can say it is the right rule. At Serra Alta the specification has three signatures on
it. Cláudia signs everything about quality, because the lab results decide what a farm is paid for
its milk. Finance signs the tax ids, the vendor link and anything that ends in a payment. Sebastião
signs what each Coleta field means, because he is the only person who knows.

A signature is on a version of the specification, and each rehearsal runs a named version. When a
rehearsal shows that a rule was wrong, the rule changes in the document, the owner signs again, and
the next rehearsal runs the new version. That loop is the subject of the next section.
