title: Coordinated omission, and percentiles that do not average
version: 1

Every generator in this lesson so far has worked the same way: a worker sends a request, waits
for the answer, and only then sends the next. Lesson 3's virtual users with think time work that
way too. It is called a **closed** model, because the number of requests in flight is fixed by
the number of workers. It has a flaw that is easy to miss and that flatters every result it
touches.

**When the system stalls, a closed generator stops asking.** Each worker is stuck waiting on the
slow answer, so during the slowest second of the test almost no requests are sent, and almost no
slow timings are recorded. The generator and the system have agreed, without meaning to, to leave
the bad moment out of the sample. Gil Tene named this **coordinated omission**. A real user does
not coordinate: the people who arrive at the box office during a stall arrive anyway, and each of
them waits.

## Seeing it happen

The program below asks for `/health` about fifty times a second for ten seconds, in one of two
modes. `closed` waits for each answer and then 20 ms more. `open` gives every request a time it
is due, 20 ms apart, and times it **from when it was due**, so a request that could not be sent
on time because the one before it was stuck is charged for the wait.

Save it as `~/boxoffice/omission.py`:

To make the box office stall on cue, the command below stops the server's process for one
second, three seconds into the run, and then lets it carry on. `pkill -STOP` freezes a process
without ending it, the way a long garbage-collection pause or a stuck disk freezes a real server,
and `pkill -CONT` releases it. The pattern `^python3 app.py$` matches the server started as
`python3 app.py` and nothing else. While the process is frozen the operating system still accepts
connections for it, so requests wait instead of failing. Type it in the terminal where you run
the tests, with the server running in the other one:

```
ana@nft:~/boxoffice$ (sleep 3; pkill -STOP -f '^python3 app.py$'; sleep 1; pkill -CONT -f '^python3 app.py$') & python3 omission.py closed
closed: 403 requests, 1 of them over 100 ms
p50 1.9  p90 2.7  p95 3.2  p99 5.8  max 1007.7 ms
p95 of each second: 2.9 2.8 4.6 2.1 2.6 3.3 4.4 3.8 3.0 2.4
the mean of those ten: 3.2 ms
```

```
ana@nft:~/boxoffice$ (sleep 3; pkill -STOP -f '^python3 app.py$'; sleep 1; pkill -CONT -f '^python3 app.py$') & python3 omission.py open
open: 501 requests, 47 of them over 100 ms
p50 1.9  p90 42.8  p95 520.0  p99 902.3  max 997.0 ms
p95 of each second: 6.1 4.3 959.3 902.3 3.5 6.3 3.3 4.2 2.5 2.4
the mean of those ten: 189.4 ms
```

The same server, the same one-second pause, two reports.

The closed run made 403 requests. **One of them took over 100 ms**: the request that was in
flight when the pause began, at 1007.7 ms, and nothing else, because no other request was sent
during that second. Its p99 is 5.8 ms. By the numbers it printed, the pause barely happened.

The open run made 501, one every 20 ms whether the server answered or not, and **47 of them took
over 100 ms**. Those are the requests that were due while the server was frozen, about fifty in a
second at this rate. Each waited from its due time until the server came back, the first nearly a
second and the last almost nothing. Its p95 is 520.0 ms and its p99 902.3 ms. That is what fifty
people arriving during the pause experienced.

Both programs measured honestly what they measured. The closed one answers *how long did the
server take once it got a request*; the open one answers *how long did a user arriving on
schedule wait*, and **the second is the one a requirement is about**. A closed generator is fine
for finding how much the system can do, as in the sweep of the section before this one. For
judging response times against a requirement at a given arrival rate, use a generator that keeps
the schedule: k6's `constant-arrival-rate` and `ramping-arrival-rate` executors start each
iteration on time, using as many virtual users as they need, and report `dropped_iterations` when
they run out of them. A dropped iteration is a user the test failed to send, and it belongs in
the report.

## Percentiles do not average

The last two lines of each report are a second lesson in the same data. `omission.py` computed
the p95 of each second on its own, and then the mean of those ten numbers, the way a dashboard
that stores one p95 per interval and averages them would:

| | open run |
|---|---|
| p95 of the whole run | 520.0 ms |
| mean of the ten per-second p95s | 189.4 ms |

**The mean of the percentiles is not a percentile of anything.** Eight quiet seconds had a p95
of a few milliseconds, two seconds had 959.3 and 902.3, and averaging gives each second one
vote, however many requests it held and wherever they fell. The answer, 189.4 ms, is a time no
group of users waited: it is not the p95 of the run, and not of any second in it. In the closed
run the same averaging gives 3.2 ms, and the pause has vanished twice over.

The same mistake turns up with machines. When two load generators each report a p95, the p95 of
the whole test is not their average, and nothing computed from the two numbers alone recovers it.
**Merge the raw timings, or histograms with the same bins, and compute the percentile once.**
k6 can write every sample to a file with `--out json=…`, and the tools of lessons 4 to 7 each
keep their raw results for the same reason. A mean of means is safe once each is weighted by its
number of requests; a mean of percentiles, of medians or of maxima is a new number with no
meaning.
