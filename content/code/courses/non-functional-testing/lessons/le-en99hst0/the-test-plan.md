A JMeter test is a **test plan**: a tree of elements, saved as an XML file with the extension
`.jmx`. Each element belongs to one of a few families, and the family decides when it runs and
what it applies to. Learning JMeter is mostly learning those families and the rule for their
scope; the hundreds of individual elements are variations inside them.

| family | what it does | in this plan |
|---|---|---|
| **thread group** | the virtual users: how many, how fast they start, for how long | `visitors` |
| **sampler** | sends one request and records one sample: its time, its size, its status | `GET /shows`, `GET /shows/{id}` |
| **config element** | sets something up for the samplers: defaults, variables, data from a file | the box office's address, `show ids` |
| **assertion** | checks a sample's response and marks the sample failed if the check fails | `says how many seats are left` |
| **timer** | waits before a sampler runs; the think time of lesson 3 | `think 1 to 2 s` |
| **listener** | collects and displays the samples: tables, graphs, trees | none, and the next section says why |

**Scope is the tree.** An element applies to the samplers at its own level and below it. The
assertion here sits inside `GET /shows/{id}`, so it checks that sampler and no other; the timer
sits at the thread group's level, so it runs before both samplers. Put the timer inside one
sampler and only that sampler waits.

## The plan

Each thread of this plan is one visitor of the box office's sale: it fetches the list of shows,
then one show's page, thinking for one to two seconds before each request, for as long as the
test lasts. The show comes from a file of ids, so the requests spread across the twenty shows on
sale instead of hammering one. Make the file first, in `~/loadtest`:

```
ana@nft:~/loadtest$ seq 981 1000 > shows.csv
ana@nft:~/loadtest$ head -3 shows.csv; wc -l shows.csv
981
982
983
20 shows.csv
```

Then the plan itself, with `nano plan.jmx`. It is as short as JMeter allows: the GUI saves every
property of every element, and a plan written by hand can leave out the ones at their default.

Three things in it come straight from lesson 3. The thread group is a **closed model**, with
twenty users unless the command line says otherwise. The timer is a **think time** with random
spread, so the users do not tick in step. And the ramp of five seconds keeps the first second from
being a spike nobody asked for.

The timer is also where JMeter can approach the **pacing** of lesson 3. A **Constant Throughput
Timer** in place of the random one holds each thread, or the whole group, to a number of samples a
minute, waiting only as long as it takes to stay on that rate. It is still a closed model
underneath, and it cannot send faster than the threads it has once the server slows; it only stops
them sending faster than you asked.
