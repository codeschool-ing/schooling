O **OWASP Top 10** é uma lista das dez categorias de risco que mais importam em aplicações web,
publicada pela OWASP Foundation a cada poucos anos. Ela é montada com dados que organizações
fornecem sobre o que acharam nas aplicações que testaram, junto com uma pesquisa entre pessoas que
trabalham na área, e cada categoria reúne dezenas de fraquezas mais específicas sob um nome. É a
lista de onde uma conversa sobre segurança parte, e aquela sobre a qual vão perguntar a um testador.

É fácil pedir a ela a coisa errada. **O Top 10 é um documento de conscientização, não uma norma e
não uma lista de verificação.** Nada consegue "estar em conformidade com o Top 10": uma categoria
como *Insecure Design* nomeia um tipo de falha, não um requisito que alguém consiga verificar. Ela
serve para a pergunta de que um plano de teste precisa primeiro, *onde devemos olhar?*, e responde
essa pergunta para a aplicação média. A sua não é média, então a lista é onde o plano começa, não
onde termina.

## A lista de 2025

A edição atual é o **Top 10:2025**. As categorias, com o que dá errado em cada uma, nas palavras de
um plano de teste e não de uma equipe de segurança:

| | categoria | o que dá errado |
|---|---|---|
| A01 | Broken Access Control | alguém lê ou faz o que não é seu: a reserva de outro cliente, uma página da equipe, uma requisição que o servidor manda em nome dele |
| A02 | Security Misconfiguration | o código está certo e o jeito como foi implantado não: cabeçalhos faltando, páginas de depuração ligadas, padrões deixados como vieram |
| A03 | Software Supply Chain Failures | algo de que a aplicação é feita, ou com que é construída, é vulnerável ou foi adulterado |
| A04 | Cryptographic Failures | dados que deviam estar protegidos não estão, ou estão mal: senhas guardadas de forma fraca, tráfego sem cifra |
| A05 | Injection | uma entrada é lida como parte de um comando: SQL, HTML, uma linha de shell |
| A06 | Insecure Design | a defesa nunca foi projetada, então nenhum código poderia acertá-la |
| A07 | Authentication Failures | provar quem alguém é dá errado: senhas fáceis de adivinhar, tentativas sem limite, sessões que nunca acabam |
| A08 | Software or Data Integrity Failures | código ou dados recebem confiança sem conferir de onde vieram |
| A09 | Security Logging & Alerting Failures | um ataque acontece e nada o registra, ou é registrado e ninguém fica sabendo |
| A10 | Mishandling of Exceptional Conditions | um erro que ninguém previu vaza detalhes, ou deixa o sistema num estado inseguro |

## O que mudou desde 2021

A edição anterior foi o Top 10:2021, e as pessoas com quem você trabalha talvez ainda citem os
números dela. A maioria das categorias é a mesma ideia numa posição nova; três mudanças valem ser
conhecidas pelo nome.

- **A falsificação de requisição do lado do servidor agora faz parte da A01.** Em 2021 ela tinha
  um lugar só dela, A10. Um servidor que busca um endereço fornecido pelo usuário, e assim alcança
  algo que o usuário não alcançaria, é uma falha de controle de acesso, e é aí que 2025 a arquiva.
- **A A03, Software Supply Chain Failures, é nova, e mais ampla do que o que ela substitui.** A A06
  de 2021, *Vulnerable and Outdated Components*, tratava de usar uma biblioteca com uma falha
  conhecida. A categoria de 2025 cobre também o resto da cadeia: uma dependência adulterada antes
  de você baixá-la, um build comprometido, uma ferramenta do pipeline que roda com acesso demais.
- **A A10, Mishandling of Exceptional Conditions, é nova.** Erros que vazam um stack trace, código
  que falha *aberto* e deixa uma requisição passar quando algo inesperado acontece, um recurso
  largado pela metade. É a categoria que o serviço de contas deste curso tinha em mente no
  `guarded`, e a que um testador consegue sondar mais barato.

O resto mudou de lugar. Security Misconfiguration subiu de A05 para A02, Injection caiu de A03 para
A05, e a A09 agora fala em *alerting*, alerta, onde antes dizia *monitoring*, o que é uma palavra
melhor para o que faltava: um registro sobre o qual ninguém é avisado não é uma defesa.

## Por trás dele: o ASVS

Quando o plano precisa de requisitos que dê para verificar de fato, o documento a usar é o outro da
OWASP: o **Application Security Verification Standard**, o **ASVS 5.0.0**, publicado em maio de
2025. É uma lista numerada de requisitos, cada um escrito para que um testador consiga conferi-lo,
agrupados em capítulos como autenticação, gestão de sessão, autorização, e log de segurança e
tratamento de erros. Cada requisito pertence a um de **três níveis**:

| nível | para |
|---|---|
| 1 | a primeira camada que toda aplicação deveria ter, quase toda conferível de fora |
| 2 | aplicações que guardam dados pessoais ou dinheiro, que é a maioria delas |
| 3 | aquelas em que uma falha é catastrófica: saúde, infraestrutura crítica, grandes somas |

O jeito como os dois se encaixam é simples. **O Top 10 diz onde olhar; o ASVS diz o que conferir
quando você chega lá.** Um plano de teste escolhe um nível alvo, o nível 2 para uma bilheteria que
guarda contas e reservas, depois pega cada categoria do Top 10, acha os capítulos do ASVS por trás
dela e escreve os requisitos que se aplicam como casos de teste. A próxima seção faz isso para o
`account.py` e a bilheteria.
