The **OWASP Top 10** is a list of the ten categories of risk that matter most in web applications,
published by the OWASP Foundation every few years. It is built from data that organisations
contribute about what they found in the applications they tested, together with a survey of
people who work in the field, and each category gathers dozens of more specific weaknesses under
one name. It is the list a security conversation starts from, and the one a tester will be asked
about.

It is easy to ask it for the wrong thing. **The Top 10 is an awareness document, not a standard
and not a checklist.** Nothing can "comply with the Top 10": a category such as *Insecure Design*
names a kind of failure, not a requirement anybody can verify. What it is good for is the question
a test plan needs answered first, *where should we look?*, and it answers that question for the
average application. Yours is not average, so the list is where the plan starts, not where it
ends.

## The 2025 list

The current edition is the **Top 10:2025**. Its categories, with what goes wrong in each, in the
words of a test plan rather than of a security team:

| | category | what goes wrong |
|---|---|---|
| A01 | Broken Access Control | somebody reads or does what is not theirs: another customer's booking, a staff page, a request the server sends on their behalf |
| A02 | Security Misconfiguration | the code is fine and the way it is deployed is not: headers missing, debug pages on, defaults left in place |
| A03 | Software Supply Chain Failures | something the application is built from, or built with, is vulnerable or has been tampered with |
| A04 | Cryptographic Failures | data that should be protected is not, or is protected badly: passwords stored weakly, traffic unencrypted |
| A05 | Injection | input is read as part of a command: SQL, HTML, a shell line |
| A06 | Insecure Design | the defence was never designed, so no code could have got it right |
| A07 | Authentication Failures | proving who somebody is goes wrong: guessable passwords, unlimited attempts, sessions that never end |
| A08 | Software or Data Integrity Failures | code or data is trusted without checking where it came from |
| A09 | Security Logging & Alerting Failures | an attack happens and nothing records it, or it is recorded and nobody is told |
| A10 | Mishandling of Exceptional Conditions | an error nobody planned for leaks detail, or leaves the system in an unsafe state |

## What changed since 2021

The previous edition was the Top 10:2021, and the people you work with may still quote its
numbers. Most categories are the same idea in a new position; three changes are worth knowing by
name.

- **Server-side request forgery is now part of A01.** In 2021 it had a place of its own, A10. A
  server that fetches an address its user supplied, and so reaches something the user could not,
  is an access-control failure, and that is where 2025 files it.
- **A03, Software Supply Chain Failures, is new, and wider than what it replaces.** 2021's A06,
  *Vulnerable and Outdated Components*, was about using a library with a known flaw. The 2025
  category also covers the rest of the chain: a dependency that was tampered with before you
  downloaded it, a compromised build, a tool in the pipeline that runs with too much access.
- **A10, Mishandling of Exceptional Conditions, is new.** Errors that leak a stack trace, code
  that fails *open* and lets a request through when something unexpected happens, a resource left
  in a half-finished state. It is the category this course's account service was written with in
  mind, in `guarded`, and the one a tester can probe most cheaply.

The rest moved. Security Misconfiguration climbed from A05 to A02, Injection fell from A03 to A05,
and A09 now names *alerting* where it used to say *monitoring*, which is a better word for what
was missing: a record that nobody is told about is not a defence.

## Behind it: the ASVS

When the plan needs requirements that can actually be verified, the document to use is OWASP's
other one: the **Application Security Verification Standard**, **ASVS 5.0.0**, published in May
2025. It is a numbered list of requirements, each written so that a tester can check it, grouped
in chapters such as authentication, session management, authorisation, and security logging and
error handling. Each requirement belongs to one of **three levels**:

| level | for |
|---|---|
| 1 | the first layer every application should have, most of it checkable from outside |
| 2 | applications that hold personal data or money, which is most of them |
| 3 | the ones where a failure is catastrophic: health, critical infrastructure, large sums |

The way the two fit together is simple. **The Top 10 says where to look; the ASVS says what to
check when you get there.** A test plan names a target level, level 2 for a box office that holds
accounts and bookings, then takes each Top 10 category, finds the ASVS chapters behind it, and
writes the requirements that apply as test cases. The next section does that for `account.py` and
the box office.
