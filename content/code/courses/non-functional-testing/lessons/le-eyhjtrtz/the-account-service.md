The box office from lesson 1 has no idea who anybody is. A booking carries a `customer` field, and
whatever a request writes there is believed: anyone can book in anyone's name, and anyone can read
anything. That was right for measuring speed. It leaves nothing for a security test to hold, so
this third adds a companion service that does have identities: **`account.py`**, on port 8001
beside the box office on 8000, with its own SQLite file and nothing from outside Python's
standard library.

**It is a correct, defended application, and nothing in it is broken on purpose.** Every defence a
security tester is asked about is in it once, in its simplest honest form: passwords stored as
salted hashes, sessions that end, bookings only their owner can read, SQL that treats input as
data, HTML that treats it as text, a form protected against being posted from another site, and an
upload that is checked for what it is. The next five lessons test it. What you build in this
lesson is the service and the first suite of tests that prove each defence holds.

Two of its lines carry a comment that names them: `# owner check` and `# role check`. Three more
are marked the same way: `# CSRF check`, `# content check` and `# rate limit`. **Each marked line
is one defence**, and each has a test whose whole job is to fail the day that line stops doing its
work. The comments are there so that a person, and in a minute a command, can find them.

| defence | where it lives | the lesson that tests it in depth |
|---|---|---|
| only the owner reads a booking; only staff read the list | `# owner check`, `# role check` | 17 |
| sessions expire and end at logout; passwords hashed with a salt | `who`, `login`, `scrypt` | 17 |
| nothing secret in the file; configuration from the environment | the first lines | 18 |
| errors and refusals logged; nothing about the software leaked | `guarded`, `refuse`, `version_string` | 19 |
| SQL parameters, escaped HTML, a CSRF token, uploads checked by content | `page`, `cancel`, `upload` | 20 |

## Running it

Start it, and leave it running, in a terminal of its own:

```
ana@nft:~/boxoffice$ python3 account.py
account on http://127.0.0.1:8001
```

**This terminal now belongs to the account service.** Open a second one with
`multipass shell nft`, go to `~/boxoffice`, and ask it something. An account, a sign-in that keeps
the token in a file, a booking, and the booking read back:

```
ana@nft:~/boxoffice$ curl -s localhost:8001/health
{"ok": true}
ana@nft:~/boxoffice$ curl -s -X POST localhost:8001/register -d '{"name": "ana", "password": "correct horse battery"}'
{"ok": true}
ana@nft:~/boxoffice$ curl -s -X POST localhost:8001/login -d '{"name": "ana", "password": "correct horse battery"}' | jq -r .token > ~/ana.token
ana@nft:~/boxoffice$ curl -s -X POST localhost:8001/bookings -H "Authorization: Bearer $(cat ~/ana.token)" -d '{"show_id": 990, "seat": 12, "holder": "Ana Lima"}'
{"id": 1}
ana@nft:~/boxoffice$ curl -s localhost:8001/bookings/1 -H "Authorization: Bearer $(cat ~/ana.token)"
{"show_id": 990, "seat": 12, "holder": "Ana Lima"}
ana@nft:~/boxoffice$ curl -s -w '%{http_code}\n' localhost:8001/bookings/1
{"error": "sign in first"}
401
```

The sign-in printed nothing because its answer went into `~/ana.token`, a random string from
`secrets.token_urlsafe`. Every request after it sends that string in an `Authorization` header,
and the last one shows what happens without it: a `401` and one plain sentence. **The token goes
in a header and never in the address**, for a reason lesson 17 gives.

The service writes its database to `data/account.db`, next to the box office's. Delete that file
whenever you want to start again from no accounts at all; the service makes a new one when it
starts.
