Security tools are sold under a cloud of acronyms, and most of them name **where the tool looks**
rather than what it is looking for. Once you know the five places, every product page sorts itself
into one of five boxes, and the useful question becomes which box a team has left empty.

| | it reads | it runs | finds well | cannot see | examples |
|---|---|---|---|---|---|
| **SAST**, static analysis | the source code, without running it | on every change, in seconds | SQL built by joining strings, `shell=True`, a weak hash, a dangerous function | anything decided at run time, and a check that is simply missing | Bandit, Semgrep, CodeQL, SonarQube |
| **SCA**, software composition analysis | the list of dependencies and their versions | on every change, and on a schedule | a library version with a published advisory | your own code | pip-audit, npm audit, OWASP Dependency-Check, Dependabot |
| **secret scanning** | every file, and every past commit | before a commit, and on every push | keys, tokens and passwords that were committed | a secret that never reached the repository | gitleaks, TruffleHog, GitHub secret scanning |
| **DAST**, dynamic analysis | the running application, over HTTP, from outside | against a deployed copy, in minutes to hours | missing headers, input echoed back, error pages, misconfiguration | code no request reaches | OWASP ZAP, Burp Suite |
| **IAST**, interactive analysis | the running application, from an agent inside the process | while the functional tests run | which line a request reached, with what data | code the tests never exercise | Contrast, Seeker |

**SAST** is the closest to code review: it knows the language and looks for shapes that are
usually a mistake. It is fast and runs early, and it reports many findings that turn out to be
fine in context, which is why it needs somebody to read it. **DAST** is the opposite end. It knows
nothing about the code and sends requests like a browser would, so what it reports is real
behaviour. But it is slow, it finds only what its requests happen to reach, and it may only be
pointed at a deployment you have permission to test. **IAST** sits between the two: an agent
loaded into the application watches what happens during the tests you already run, so its
findings come with the line of code attached. It is the least common of the five, mostly
commercial, and tied to particular languages.

**SCA** needs one thing the others do not: **it has to run on a schedule as well as on every
change.** Your code can stay the same for a month while somebody publishes an advisory against a
library it uses, and on that day the same commit goes from clean to vulnerable without anybody
touching it. Lesson 21 runs `pip-audit` and reads what it reports. **Secret scanning** is the one
that must run before anything reaches a shared repository, because a secret that has been pushed
has to be treated as known; lesson 18 runs `gitleaks`, on a repository and on its history.

## What no scanner can tell you

Take the owner check out of `account.py` and run every tool in the table. The SQL is still
parameterised, the dependencies are still the standard library, there is no secret in the file,
and a DAST scan sees a route that answers `200` to a signed-in customer, which is what a route is
supposed to do. **Nothing in any of the five boxes knows that a booking belongs to somebody.** That
rule lives in the business, and the only thing that checks it is a test somebody wrote with two
customers in it. Scanners cover the mistakes that look the same in every application; the tests
in this course cover the ones that are particular to yours.
