que um visitante faz: olha um espetáculo, lê por um momento, reserva um assento e às vezes ouve que
o assento já foi. **O script abaixo é essa jornada, com o requisito da aula 1 escrito nele como
limites**, para a própria execução dizer se a bilheteria passou. Crie-o com
`nano ~/k6/boxoffice.js`; o botão de copiar leva o arquivo inteiro, sem as notas.

## Onde cada parte roda

Um script do k6 é lido em duas etapas. **O
código de inicialização roda uma vez por usuário virtual, antes de qualquer carga; a função padrão
roda uma vez por iteração**, enquanto o cenário durar. O k6 não deixa a primeira etapa mandar
requisições, e um arquivo curto mostra o que ele diz quando uma tenta:

```javascript
// k6/init.js
import http from 'k6/http';

const shows = http.get('http://127.0.0.1:8000/shows').json();

export default function () {
  console.log(shows.length);
}
```

A execução para antes de qualquer carga, com o código de saída 107, que o k6 usa para um erro no
script. Dados de que o teste precisa do servidor antes de começar ficam numa função chamada
`setup()`, que o k6 roda uma vez, entre a inicialização e a carga, e cujo valor de retorno ele
entrega a cada iteração; os scripts desta aula não precisam de uma. Quando o cenário termina, o k6
junta todas as amostras no resumo, compara os limites e escolhe o código de saída.

**Com usuários virtuais em laço, quem dita o ritmo é o servidor.** Um usuário virtual começa a
próxima iteração só quando a anterior terminou, então, se as respostas ficam lentas, começam menos
iterações, e a carga cai justamente quando o sistema está sofrendo. **Com uma taxa de chegada,
quem dita o ritmo é o relógio.** Três jornadas começam a cada segundo, aconteça o que tiver
acontecido com as três anteriores, e o k6 pega um usuário virtual livre do conjunto para cada uma.
Se nenhum está livre, ele inicia outro, até `maxVUs`; passando disso, a jornada nem começa e é
contada como descartada. A aula 6 chama esses dois de modelo fechado e modelo aberto, e a aula 8
mostra o que o fechado esconde nos números.

Qual escrever depende do que o requisito conta. "50 requisições por segundo", a carga da frase da
aula 1, é uma taxa, então é um executor por taxa de chegada. "200 pessoas com a página aberta" é
um número de usuários, e usuários virtuais em laço com tempo de reflexão são o jeito honesto de
modelar isso.

## Checks e limites são coisas diferentes

Os dois aparecem no script e os dois imprimem um visto ou um xis, então é fácil confundir:

| | um check | um limite |
|---|---|---|
| onde | dentro da iteração, sobre uma resposta | em `options`, sobre uma métrica da execução inteira |
| o que pergunta | esta resposta está certa? | esta estatística está dentro do limite? |
| quando falha | é contado, e o teste segue | a execução sai com um código diferente de zero |

**Um check que falha não reprova o teste.** Se a reserva começasse a responder 500, todo check
`booked or taken` mostraria um xis, e quem reprovaria a execução seria o limite de
`http_req_failed`, não os checks. Um check sobre o corpo, como `seats left is a number`, não tem
esse reforço: um 200 com o corpo errado reprova o check e não ultrapassa limite nenhum. Para os
checks decidirem o resultado, dê a eles um limite próprio, `checks: ['rate>0.99']`, que deixa
falhar menos de um check em cada cem.
