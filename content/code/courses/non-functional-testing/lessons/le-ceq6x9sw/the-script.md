The first script asked one question over and over. A test worth keeping does what a visitor
does: looks at a show, reads for a moment, books a seat, and gets told sometimes that the seat is
gone. **The script below is that journey, with lesson 1's requirement written into it as
thresholds**, so that the run itself says whether the box office passed. Create it with
`nano ~/k6/boxoffice.js`; the copy button takes the whole file without the notes.

## Where each piece runs

A k6 script is read in two stages. **The init
code runs once per virtual user, before any load; the default function runs once per
iteration**, for as long as the scenario lasts. k6 does not let the first stage send requests,
and a short file shows what it says when one tries:

```javascript
// k6/init.js
import http from 'k6/http';

const shows = http.get('http://127.0.0.1:8000/shows').json();

export default function () {
  console.log(shows.length);
}
```

```

```

The run stops before any load, with exit code 107, which k6 uses for an error in the script. Data
a test needs from the server before it starts belongs in a function called `setup()`, which k6
runs once, between the init code and the load, and whose return value it hands to every
iteration; this lesson's scripts do not need one. When the scenario ends, k6 collects every sample
into the summary, compares the thresholds and chooses its exit code.

**With looping virtual users, the server sets the pace.** A virtual user starts its next
iteration only when the last one has finished, so if the answers slow down, fewer iterations
start, and the load falls exactly when the system is struggling. **With an arrival rate, the
clock sets the pace.** Three journeys start every second whatever happened to the last three, and
k6 takes a free virtual user from the pool for each. If none is free, it starts another, up to
`maxVUs`; past that, the journey is not started at all and is counted as dropped. Lesson 6 calls
these the closed and the open model, and lesson 8 shows what the closed one hides in its numbers.

Which one to write depends on what the requirement counts. "50 requests a second", the load in
lesson 1's sentence, is a rate, so it is an arrival-rate executor. "200 people with the page
open" is a number of users, and looping virtual users with think time are the honest way to
model that.

## Checks and thresholds are different things

Both appear in the script and both print a tick or a cross, so they are easy to confuse:

| | a check | a threshold |
|---|---|---|
| where | inside the iteration, on one response | in `options`, on a metric of the whole run |
| what it asks | is this answer right? | is this statistic inside the limit? |
| when it fails | counted, and the test carries on | the run exits with a non-zero code |

**A check that fails does not fail the test.** If the booking started answering 500, every
`booked or taken` check would show a cross, and what would fail the run is the `http_req_failed`
threshold, not the checks. A check on the body, like `seats left is a number`, has no such
backup: a 200 carrying the wrong body fails the check and crosses no threshold. To make checks
decide the result, give them a threshold of their own, `checks: ['rate>0.99']`, which lets fewer
than one check in a hundred fail.
