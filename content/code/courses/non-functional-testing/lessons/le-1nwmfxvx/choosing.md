Lessons 4 to 6 have pointed four tools at the same box office. **None of them is the best load tester.** They differ in who can read the test, where
it lives, and which model of load comes naturally to it, and those are the questions that decide.

## What a user is, in each

The word *user* means two different things in these tools, and reading one tool's numbers with
the other's meaning misjudges the run:

A Gatling user is a visitor: it arrives, does the journey once and leaves, so the number to
set is how many arrive each second. A Locust user, like a k6 virtual user in `constant-vus`, stays for the whole test and starts its next task after its
wait, so the number to set is how many are inside at once. **Twenty users in Gatling and twenty
users in Locust are different loads**, and only one of them is the load in lesson 1's sentence,
which counts requests a second.

## Side by side

| | JMeter (lesson 4) | k6 (lesson 5) | Gatling | Locust |
|---|---|---|---|---|
| the test is | an XML plan, edited in a window | a JavaScript file | a Java, Kotlin, Scala or JavaScript class | a Python file |
| runs on | Java | one Go program | Java, through Maven or Gradle | Python |
| load model it writes most easily | threads that loop: closed | either, by executor | users a second: open | users that loop: closed |
| pass or fail | assertions on each response; a verdict on a percentile is added on top | `thresholds`, exit code 99 | `assertions`, the build fails | written in a hook, as in this lesson |
| a diff in code review | hard to read | reads like code | reads like code | reads like code |

## How to choose

**Start from the team's language.** A load test that only one person can change is a load test
that stops being changed when that person is busy. A team writing Python will read a locustfile
on the first day; a Java team already has the JDK, the editor and the build that Gatling uses;
k6 asks only for JavaScript, which most teams with a web front end can already read.

**Then ask whether the test will be reviewed.** All three code-based tools put the test in a file
whose diff says what changed: a threshold moved from 200 to 300 is one line in a pull request,
where somebody can ask why. JMeter's XML can be committed too, and a diff of it is a page of
attributes nobody reviews.

**Then ask which load the requirement names.** "50 requests a second" is an open model, and
Gatling's `injectOpen` and k6's arrival-rate executors say it directly. "200 people with the page
open" is a closed one, which Locust and looping virtual users say directly. Every tool can be
pushed into the other model, but the one it writes most easily is the one people end up running.
Lesson 8 shows what a closed model hides when the system stalls.

None of these is a reason to rewrite a suite that works. A team with a JMeter plan that runs in
the pipeline and fails when it should has the thing this course is about, whichever tool wrote it.
