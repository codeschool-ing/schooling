As aulas 4 a 6 apontaram quatro ferramentas para a mesma bilheteria. **Nenhuma delas é o melhor
gerador de carga.** Elas diferem em quem consegue ler o teste, onde ele mora e qual modelo de carga
sai natural nela, e essas são as perguntas que decidem.

## O que é um usuário, em cada uma

Um usuário do Gatling é um visitante: chega, faz a jornada uma vez e vai embora, então o número a
definir é quantos chegam por segundo. Um usuário do Locust, como um usuário virtual do k6 em
`constant-vus`, fica o teste inteiro e começa a próxima tarefa depois da sua espera, então o número
a definir é quantos estão dentro ao mesmo tempo. **Vinte usuários no Gatling e vinte usuários no
Locust são cargas diferentes**, e só uma delas é a carga da frase da aula 1, que conta requisições
por segundo.

## Lado a lado

| | JMeter (aula 4) | k6 (aula 5) | Gatling | Locust |
|---|---|---|---|---|
| o teste é | um plano em XML, editado numa janela | um arquivo JavaScript | uma classe em Java, Kotlin, Scala ou JavaScript | um arquivo Python |
| roda em | Java | um programa Go | Java, pelo Maven ou pelo Gradle | Python |
| modelo de carga que escreve mais fácil | threads em laço: fechado | os dois, conforme o executor | usuários por segundo: aberto | usuários em laço: fechado |
| aprovado ou reprovado | asserções em cada resposta; um veredito sobre percentil vem por cima | `thresholds`, código de saída 99 | `assertions`, o build reprova | escrito num hook, como nesta aula |
| um diff na revisão de código | difícil de ler | lê-se como código | lê-se como código | lê-se como código |

## Como escolher

**Comece pela linguagem do time.** Um teste de carga que só uma pessoa consegue mudar é um teste de
carga que para de mudar quando essa pessoa está ocupada. Um time que escreve Python lê um locustfile
no primeiro dia; um time de Java já tem o JDK, o editor e o build que o Gatling usa; o k6 pede só
JavaScript, que a maioria dos times com um front-end web já lê.

**Depois pergunte se o teste vai ser revisado.** As três ferramentas baseadas em código põem o teste
num arquivo cujo diff diz o que mudou: um limite que passou de 200 para 300 é uma linha num pull
request, onde alguém pode perguntar por quê. O XML do JMeter também pode ir para o repositório, e um
diff dele é uma página de atributos que ninguém revisa.

**Depois pergunte qual carga o requisito nomeia.** "50 requisições por segundo" é um modelo aberto,
e o `injectOpen` do Gatling e os executores por taxa de chegada do k6 dizem isso direto. "200 pessoas
com a página aberta" é um fechado, que o Locust e os usuários virtuais em laço dizem direto. Toda
ferramenta pode ser empurrada para o outro modelo, mas o que ela escreve mais fácil é o que as
pessoas acabam rodando. A aula 8 mostra o que um modelo fechado esconde quando o sistema trava.

Nada disso é motivo para reescrever uma suíte que funciona. Um time com um plano do JMeter que roda
no pipeline e reprova quando deve tem aquilo de que este curso trata, seja qual for a ferramenta que
o escreveu.
