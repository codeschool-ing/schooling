A common picture of a SIEM is a product you buy and switch on. **A SIEM is a pipeline**, and every
product sold under the name is an implementation of the same five stages. The name, *security
information and event management*, says little; the stages say everything:

**Collection** receives what lesson 3 shipped: syslog, agents on Windows machines, API pulls from cloud
services. **Normalisation** turns each source's own wording into one set of named fields, so that the
firewall's `SRC=` and SSH's `from` both become `src_ip`. **Enrichment** adds what no line knew: which
department owns an address, whether a server holds personal data, whether an address appears on a list
of known bad ones. **Storage** keeps the result indexed for the retention the policy set. And
**correlation** runs rules over the stored events and raises **alerts** for a person to read.

Two things follow from the drawing. **A question can only be asked about a field that an earlier stage
produced**: if the parser never extracted the account name, no rule can count accounts. And **every stage
can lose information quietly**: a line the parser does not recognise, a time stamp read in the wrong zone,
an enrichment list that is out of date. A SIEM that says how many lines it failed to parse is telling the
truth about itself; one that says nothing is not necessarily parsing everything.

The products differ in scale, interface and price, and they change every year. This course names none of
them. It builds the pipeline in miniature, in files you can read: a Python script for normalisation, a
SQLite table for storage, and **Sigma** for rules, an open rule format that converts into the query
language of most SIEMs. What you learn about each stage carries over to whichever product you meet.
