At temperature 0 the stand-in picks its highest-scoring label, so the same prompt gives the same
replies on every run. Above 0 it samples, as lesson 8 showed. Here is the same prompt run twice at
temperature 1, changing nothing but the seed:

```
ana@lab:~/triage$ pl run prompts/v3-examples.txt cases/dev.jsonl --set temperature=1 --out runs/hot-a.jsonl
40 calls, prompt 1d9c6ec4, written to runs/hot-a.jsonl
ana@lab:~/triage$ pl run prompts/v3-examples.txt cases/dev.jsonl --set temperature=1 --seed 7 --out runs/hot-b.jsonl
40 calls, prompt 1d9c6ec4, written to runs/hot-b.jsonl
ana@lab:~/triage$ pl compare runs/hot-a.jsonl runs/hot-b.jsonl
runs/hot-a.jsonl         passes 31/40
runs/hot-b.jsonl         passes 28/40
fixed 5, broken 8, still passing 23, still failing 4
broken: t06 t11 t15 t23 t30 t32 t34 t36
sign test on the 13 that changed: p = 0.581
```

31 and 28. Thirteen messages changed between two runs of one prompt. Had those been two prompts, the
first would look three cases better, and **one run each is all most comparisons ever get.**

A test that passes and fails the same input on different calls is what programmers call flaky.
Here the flakiness is not a defect in the test; it is the thing being measured.

## A rate over samples

So report a rate. `--samples 5` calls the model five times per message:

```
ana@lab:~/triage$ pl run prompts/v3-examples.txt cases/dev.jsonl --samples 5 --set temperature=1 --out runs/hot.jsonl
200 calls, prompt 1d9c6ec4, written to runs/hot.jsonl
ana@lab:~/triage$ pl check runs/hot.jsonl
check      pass  fail
json        200     0
fields      200     0
labels      200     0
category    151    49
urgency     140    60
all         140    60
ana@lab:~/triage$ pl check runs/hot.jsonl --failures | grep -E "^t(05|14|21|23)[ #]"
t05    category  returns, expected other
t05#1  category  billing, expected other
t05#3  category  delivery, expected other
t05#4  category  billing, expected other
t14    urgency   normal, expected low
t14#1  urgency   normal, expected low
t14#2  urgency   normal, expected low
t14#3  urgency   normal, expected low
t14#4  urgency   normal, expected low
t21#2  category  billing, expected returns
t23#1  category  account, expected returns
t23#2  category  account, expected returns
t23#3  category  delivery, expected returns
t23#4  category  billing, expected returns
```

140 of 200 calls passed, a rate of 0.70, against 36 of 40 at temperature 0. **The per-case view
says more than the total.** `t14` failed five calls of five, which is not flaky at all: it is the
stable disagreement about urgency it was at temperature 0. `t21` failed one call in five, `t05` and
`t23` four, and `t23` passes every time at temperature 0.

Those are three different findings. A case that fails every call is a defect in the prompt, or in
the label, and one run finds it. A case that fails some calls is a rate, and only samples find it.
A case that passes at temperature 0 and fails above it says the setting is part of the prompt.

## What it costs

Five samples is five times the calls: 200 instead of 40, and lesson 16 puts a price on each. It is
still the cheaper mistake. With real models, even temperature 0 does not always give identical
replies from one call to the next, so the habit protects you there too. **Never report a
comparison between two prompts from one run of each** when either was sampled; report the rates,
and the number of samples beside them.
