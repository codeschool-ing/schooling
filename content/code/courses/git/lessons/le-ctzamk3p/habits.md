None of this needs a new process. It needs a few habits, most of which you already met in this course with a
different name.

## Before building

- **Read the ticket with the others, not alone.** Lesson 16's three amigos is exactly this; add the designer
  when the ticket changes a screen. Ten minutes with Marta, Paulo and Diego on #38 would have caught all
  three surprises.
- **Ask for the design, and for the states it does not show.** What does the page say when the code is wrong,
  when the card is used up, when the name is forty characters long? Paulo would rather answer now than
  redraw later.
- **Ask how it can go wrong.** *"What happens if somebody spends more than the balance?"* is a question
  Diego would ask, and so can you.
- **Ask how anybody will know it worked.** Marta usually has an answer (fewer calls to the shop, more
  orders on Saturdays), and it tells you which part matters most if something has to be dropped.

## While building

- **Show it early.** A draft pull request (lesson 12), a screenshot in the team's chat on the second day,
  two minutes at a desk: *"is this what you meant?"*. Some teams deploy every pull request to its own
  preview address so product and design can click through it before review.
- **Say what you are assuming**, in the ticket or the pull request: *"I've assumed gift cards work online
  too"*. An assumption written down is one somebody can correct.

## When handing over

- **Tell QA what changed and how to try it.** Lesson 12's pull request description had *To check:* for this
  reason. Diego tests better knowing where the risk is than guessing.
- **Disagree with information, not refusals.** When Marta asks for something expensive, the useful answer
  is the cost and an alternative: *"online balances need changes to the till, about two sprints; shop-only is
  three days"*. Then she can decide, which is her job.

## The thread through the course

This course began with a folder of copies of one report. It ends with a whole team, a board, and a ticket
passing through everybody's hands. What connects them is the same idea at every scale: **keep a record, make changes
small, show them to somebody else early, and agree in advance what "done" means.** Git does the first of those
for you. The rest is the team.
