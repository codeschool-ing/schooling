## Bare metal

**On bare metal, one operating system owns the machine.** Its kernel talks to the hardware
directly, and every program on the machine shares that kernel, the installed libraries and one
filesystem. It is the fastest arrangement, because nothing sits between a program and the
hardware, and the one with the least separation: two programs that need two versions of the same
library are back in lesson 1's fight.

## Virtual machine

**A virtual machine adds a hypervisor, which pretends to be hardware.** Each VM gets virtual
processors, virtual memory and a virtual disk, and boots a complete operating system on them,
kernel and all. The separation is strong: a VM can run a different operating system from its
neighbours, Windows next to Linux, because it has its own kernel. The cost is that each VM carries
that whole operating system. It boots like a computer, it keeps its own kernel in memory, and it
reserves the memory and disk it was given whether or not it uses them.

There are two places a hypervisor can sit. **Type 1** runs directly on the hardware and is what
cloud providers and data centres use; KVM in Linux, Xen, VMware ESXi and Hyper-V are examples.
**Type 2** runs as a program on an ordinary operating system, like VirtualBox on a laptop. The
difference matters to whoever runs the hardware; for the stacks above, both draw a guest operating
system on top.

## Container

**A container moves the line up to the kernel**: one kernel for the whole machine, and above it,
each container gets its own filesystem, its own libraries, its own process list and network. There
is no hypervisor and no second kernel, so nothing boots. Starting a container is starting a
process, and a container that does nothing costs about as much as a process that does nothing.
The next section measures both.

## They are layered in practice, not chosen between

**The three are not rivals, and most containers in production run inside virtual machines.** A
cloud provider rents out VMs, and companies run their containers on those VMs. The VM separates
customers from each other, with the hypervisor's strong boundary; the containers separate
programs inside one customer's machine, cheaply.

This course's own lab is an instance of it. The machine every transcript was recorded on is a
virtual machine, with no hypervisor available inside it, so this lesson can start containers and
measure them, and cannot start a VM to compare. Everything said about VMs here is said without a
transcript, and lesson 5 meets a VM again: on Windows and macOS, Docker Desktop runs its Linux
kernel inside one.
