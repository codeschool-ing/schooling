---
title: Why the order matters
version: 1
---

**React does not know the names of your state variables. It knows their order.** When `App` calls
`useState` five times, React keeps five slots for it, numbered one to five, and on the next render it
hands back slot one to the first call, slot two to the second, and so on. Nothing in
`const [monday, setMonday] = useState(…)` tells React that this is `monday`; the only thing it can go
by is that this was the first call.

That is the whole reason for rule one. **A hook that is called on one render and skipped on the next
shifts every hook after it into the wrong slot.** The state for "is the course screen open" lands in
the hook that expected the list of sessions, the effect for the title receives the dependencies of
the keyboard listener, and every one of those mismatches is a value of the wrong kind in the wrong
place.

The order is the same on every render only if every hook is called on every render. A condition, a
loop with a varying count, or a `return` above a hook each make the count depend on the data, and
data changes.

Why such a design? The alternative is a key per hook, `useState('monday', …)`, and keys collide: two
custom hooks that both happen to call their state `'open'` would share it. Order cannot collide,
because each component's list is its own. It costs one rule, and a linter can check the rule.
