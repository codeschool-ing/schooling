**O SwiftUI decide quando rodar um body de novo observando o que o body leu, e essa observação é um
framework que também roda no Linux.** Ele se chama Observation, vem com o Swift, e a macro
`@Observable` que a aula 7 põe no modelo do planner vem dele. Esta seção faz o papel do SwiftUI à mão:
rodar um body registrando o que ele lê, e rodá-lo de novo só se uma dessas coisas mudou. É um modelo do
que o SwiftUI faz com dados observáveis, não o próprio SwiftUI, e é pequeno o bastante para ler
inteiro.

Salve isto como `bodies.swift` em `~/l03`:

```
ana@vm:~/l03$ swift bodies.swift
frame: body run 1 -> SQL Databases: 50 min
frame: body run 2 -> SQL Databases: 60 min
frame: nothing to redo
frame: body run 3 -> SQL: 45 min
```

**Mudar `notes` não rodou nada**, porque o body nunca a leu: o terceiro quadro achou a tela limpa.
**Duas mudanças entre quadros rodaram o body uma vez**, porque a primeira marcou a tela como suja e a
segunda a achou já marcada; o quadro então desenhou as duas. O SwiftUI agrupa do mesmo jeito: as
mudanças feitas durante uma volta do laço principal são desenhadas juntas na seguinte.

O modelo é pequeno de propósito. O SwiftUI rastreia cada view separadamente, guarda a identidade de
toda view entre quadros, e decide o que redesenhar pela árvore inteira; nada disso está aqui. O que
está aqui é a regra de que depende a terceira linha da tabela da seção 04, e ela rodou: **um body só é
consultado de novo sobre o que leu.**
