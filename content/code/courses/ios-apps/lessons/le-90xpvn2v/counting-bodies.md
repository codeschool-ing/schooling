**SwiftUI decides when to run a body again by watching what the body read, and the watching is a
framework that also runs on Linux.** It is called Observation, it ships with Swift, and the
`@Observable` macro lesson 7 puts on the planner's model comes from it. This section plays SwiftUI's
part by hand: run a body while recording what it reads, and run it again only if one of those things
changed. It is a model of what SwiftUI does for observable data, not SwiftUI itself, and it is small
enough to read whole.

Save this as `bodies.swift` in `~/l03`:

```
ana@vm:~/l03$ swift bodies.swift
frame: body run 1 -> SQL Databases: 50 min
frame: body run 2 -> SQL Databases: 60 min
frame: nothing to redo
frame: body run 3 -> SQL: 45 min
```

**Changing `notes` ran nothing**, because the body never read it: the third frame found the screen
clean. **Two changes between frames ran the body once**, because the first change marked the screen
dirty and the second found it already marked; the frame then drew both. SwiftUI batches the same way:
the changes made during one turn of the main loop are drawn together on the next.

The model is small on purpose. SwiftUI tracks each view separately, keeps the identity of every view
between frames, and decides what to redraw down the whole tree; none of that is here. What is here is
the rule the third row of section 04's table depends on, and it ran: **a body is asked again only
about what it read.**
