---
title: Why a position is not an identity
version: 1
---

**A row identified by its position changes identity whenever a row above it is inserted or
deleted, and everything SwiftUI kept for it goes with the position, not with the row.** The belief
to drop is that identity only matters for animation. It matters for state: a row's `@State`, a text
field's half-typed text, whether its notes are open, which row is selected. SwiftUI keeps those by
identity, and an identity that moves takes them to the wrong row.

That can be shown without SwiftUI, because the question is only *which row does this state belong
to*. Make a directory, `~/rows`, and save this as `identity.swift` in it:

```
ana@vm:~/rows$ swift identity.swift
before
  SQL, joins         by position: -     by id: -
  Mobile, lifecycle  by position: open  by id: open
  SQL, indexes       by position: -     by id: -
after the first row is deleted
  Mobile, lifecycle  by position: -     by id: open
  SQL, indexes       by position: open  by id: -
```

**After the delete, the open notes moved to `SQL, indexes`**, a row the person never touched, while
`Mobile, lifecycle` closed. Nothing in the program was wrong except the choice of key. Kept by id,
the state stayed on its row.

In a real list the symptoms are the same and harder to trace: a toggle that jumps to the next row
after a delete, a text field showing somebody else's draft, a row that does not animate out because
SwiftUI saw its content change rather than the row disappear. Every one comes from writing
`ForEach(0..<plan.sessions.count)` or `ForEach(Array(plan.sessions.enumerated()), id: \.offset)`
instead of `ForEach(plan.sessions)`.
