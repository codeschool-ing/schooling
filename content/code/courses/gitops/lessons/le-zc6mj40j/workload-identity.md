**The cloud trusts the cluster the way Vault did in lesson 9, only further away.** Kubernetes signs
every ServiceAccount token with a key of its own, and it can publish the public half at an address,
as an OpenID Connect issuer. A cloud account told to trust that issuer can then accept a
ServiceAccount token as proof of identity, exchange it for short-lived cloud credentials, and apply
its own permissions to them. Nothing long-lived ever reaches the cluster.

Each cloud names the arrangement differently and asks for a different mapping:

| | the mapping, from ServiceAccount to cloud identity | where it is written |
|---|---|---|
| **AWS** | an IAM role whose trust policy names the cluster's issuer and the ServiceAccount; called IRSA, or EKS Pod Identity in its newer form | the role's trust policy, or an association in EKS |
| **Google Cloud** | Workload Identity Federation: an IAM binding that gives the ServiceAccount, as a principal, a role on the secret | the binding, on the project or the secret |
| **Azure** | Workload Identity: a federated credential on a managed identity, naming the issuer and the ServiceAccount | the managed identity |

Two consequences matter in a GitOps repository. **The cloud side is infrastructure as code**, in the
same Terraform that made the cluster, and the `iac` course is where it belongs; the cluster side is
a ServiceAccount, sometimes with an annotation naming the cloud identity, and lives in `fleet` like
everything else. And **the permission is per ServiceAccount**, so production's `bulletin` can be
allowed one secret and nothing else, the same shape as lesson 9's Vault policy. A ServiceAccount
shared by every workload in a namespace would share every permission with it, which is lesson 11's
subject.

The lab has no cloud account, so none of this was run for the course; the stores in the previous
section are where it would be used, and the Vault store is the same exchange on your own machine.
