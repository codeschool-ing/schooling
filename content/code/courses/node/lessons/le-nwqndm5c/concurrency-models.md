**All six servers answered ten slow requests in about a second, once PHP had ten processes.** They got
there in four different ways, and the differences show the moment the work stops being waiting and
becomes computing.

| language | what serves each request | while it waits |
|---|---|---|
| Node | one thread, the event loop | the request is a callback; the thread serves others |
| Python | a thread per request, in `ThreadingHTTPServer` | the thread sleeps; the others run |
| Go | a goroutine per request, spread over every processor | the goroutine sleeps; Go runs another on that thread |
| Java | a virtual thread per request | the same idea as a goroutine |
| PHP | a process per request, from a pool | the process sleeps; another takes the next request |
| C# | a task on a pool of threads, with `await` | the thread is returned to the pool, as in Node |

## When the work is computing

Lesson 10 counted primes, and found that Node uses one processor unless it is given workers. The same
count in Python, with four threads:


```
ana@dev:~/server/other/python$ python3 primes.py
one thread: 148933 primes in 7.40 s
four threads: 148933 primes in 7.46 s
```

**Four threads were no faster than one.** Python has a **global interpreter lock**, the *GIL*: only one
thread runs Python code at a time, whatever the number of processors. Threads help Python wait and do
not help it compute, which is Node's position reached from the other side; the answer for computing is
the same too, several processes, which is what `multiprocessing` and `gunicorn`'s workers are. Python
3.13 added a build without the lock as an experiment and 3.14 made it supported, but the `python3` of
Ubuntu 24.04 has it.

And in Go, with four goroutines:


```
ana@dev:~/server/other/primes$ go run .
one goroutine: 664579 primes in 4.591s
four goroutines: 664579 primes in 1.534s
```

**Four goroutines were three times faster than one**, the same gain lesson 10's four workers gave,
with no worker file, no messages and no copying: goroutines share the program's memory and run on
every processor. That is also why Go has the bugs lesson 10's `counter.js` showed, and why it has a
race detector, `go run -race`, to find them.

One goroutine took longer than Node's one thread did on the same ten million. That says more about
this loop than about either language: it is mostly integer division, Go's `int` is 64 bits wide, and
V8 kept these small numbers as 32-bit integers, whose division this processor does faster. **A benchmark of one loop measures that loop**, which is the reason to measure your own
program rather than read a table of languages.
