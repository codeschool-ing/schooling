**Not yet is still the answer for most people finishing this course.** The courses after it in the
track, databases, APIs, architecture and the rest, are written for somebody who can build a service in
one language, any of the four the track offers, and you will do their work in Node. Every hour of it
is an hour of depth that the next language will reuse.

The moment for a second language is the one lesson 1 named, when Node is no longer what you are
struggling with. When that moment comes, the choice is usually made by the work rather than by the language:

| you find yourself | the language it points to | why |
|---|---|---|
| writing infrastructure, command-line tools, a service that must use every processor | **Go** | one binary, cheap concurrency, the language of the tools themselves |
| near data, analysis or machine learning | **Python** | the libraries are there, and the people are |
| in a large company with long-lived systems | **Java** or **C#** | what they are built in, with the tooling big teams rely on |
| maintaining or extending sites built on WordPress or Laravel | **PHP** | the code already exists, and a great deal of it |

**Learn the second one the way this course taught the first**: not its syntax from a tutorial, but one
real service in it, from configuration to shutdown, with its own tests and its own package manager.
The table in the last section is a checklist for that service, and every row of it has an answer in
each of the five.

One thing transfers that no table shows. This course asked you, lesson after lesson, to read the error
the runtime printed before guessing at it, to look in the documentation for what a function does, and
to measure instead of believing a claim, including the claims in this course. That habit is the part
of it that does not care which language it meets next.
