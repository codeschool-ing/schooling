processos.** Eles chegaram lá de quatro jeitos diferentes, e as diferenças aparecem no momento em que o
trabalho deixa de ser esperar e passa a ser calcular.

| linguagem | o que atende cada pedido | enquanto ele espera |
|---|---|---|
| Node | uma thread, o event loop | o pedido é um callback; a thread atende outros |
| Python | uma thread por pedido, no `ThreadingHTTPServer` | a thread dorme; as outras rodam |
| Go | uma goroutine por pedido, espalhadas por todo processador | a goroutine dorme; o Go roda outra naquela thread |
| Java | uma virtual thread por pedido | a mesma ideia de uma goroutine |
| PHP | um processo por pedido, de um pool | o processo dorme; outro pega o próximo pedido |
| C# | uma task num pool de threads, com `await` | a thread volta ao pool, como no Node |

## Quando o trabalho é calcular

A aula 10 contou primos, e viu que o Node usa um processador a menos que receba workers. A mesma
contagem em Python, com quatro threads:


```
ana@dev:~/server/other/python$ python3 primes.py
one thread: 148933 primes in 7.40 s
four threads: 148933 primes in 7.46 s
```

**Quatro threads não foram mais rápidas que uma.** O Python tem uma **trava global do interpretador**, o
*GIL*: só uma thread roda código Python por vez, qualquer que seja o número de processadores. As threads
ajudam o Python a esperar e não o ajudam a calcular, que é a posição do Node vista do outro lado; a
resposta para calcular também é a mesma, vários processos, que é o que são o `multiprocessing` e as
workers do `gunicorn`. O Python 3.13 trouxe uma versão sem a trava como experimento e o 3.14 a tornou
suportada, mas o `python3` do Ubuntu 24.04 tem a trava.

E em Go, com quatro goroutines:

```schooling-example

 {"code": "// main.go: the prime count from lesson 10, on one goroutine and then on four.\npackage main\n\nimport (\n\t\"fmt\"\n\t\"sync\"\n\t\"time\"\n)\n\nfunc countPrimes(from, to int) int {\n\tcount := 0\n\tfor n := max(from, 2); n < to; n++ {\n\t\tprime := true\n\t\tfor d := 2; d*d <= n; d++ {\n\t\t\tif n%d == 0 {\n\t\t\t\tprime = false\n\t\t\t\tbreak\n\t\t\t}\n\t\t}\n\t\tif prime {\n\t\t\tcount++\n\t\t}\n\t}\n\treturn count\n}"},
 {"code": "func main() {\n\tconst N = 10_000_000\n\tt := time.Now()\n\tfmt.Printf(\"one goroutine: %d primes in %v\\n\", countPrimes(0, N), time.Since(t).Round(time.Millisecond))\n\n\tparts := make([]int, 4)\n\tvar wg sync.WaitGroup\n\tt = time.Now()\n\tfor i := range 4 {\n\t\twg.Add(1)\n\t\tgo func() {\n\t\t\tdefer wg.Done()\n\t\t\tparts[i] = countPrimes(i*N/4, (i+1)*N/4)\n\t\t}()\n\t}\n\twg.Wait()\n\ttotal := parts[0] + parts[1] + parts[2] + parts[3]\n\tfmt.Printf(\"four goroutines: %d primes in %v\\n\", total, time.Since(t).Round(time.Millisecond))\n}", "note": "**O `go func() { … }()` inicia uma goroutine**, e o `WaitGroup` espera as quatro, como o `Promise.all` esperou. ```
```

```
ana@dev:~/server/other/primes$ go run .
one goroutine: 664579 primes in 4.591s
four goroutines: 664579 primes in 1.534s
```

**Quatro goroutines foram três vezes mais rápidas que uma**, o mesmo ganho que as quatro workers da aula
10 deram, sem arquivo de worker, sem mensagens e sem cópia: as goroutines dividem a memória do programa
e rodam em todo processador. É também por isso que o Go tem os bugs que o `counter.js` da aula 10
mostrou, e por isso tem um detector de corridas, o `go run -race`, para achá-los.

Uma goroutine levou mais tempo do que a thread única do Node levou com os mesmos dez milhões. Isso diz
mais sobre este loop do que sobre as duas linguagens: ele é quase só divisão de inteiros, o `int` do Go
tem 64 bits, e o V8 guardou esses números pequenos como inteiros de 32 bits, cuja divisão este
processador faz mais rápido. **Um benchmark de um loop mede aquele loop**, e é por isso que vale medir o
seu próprio programa em vez de ler uma tabela de linguagens.
