title: Which one, for what
version: 1
---

**Most Node services need none of this lesson's machinery to be fast.** One process answers thousands
of requests that are waiting on the network, the disk or a database, because waiting costs it nothing.
The tools of this lesson are for the two things one process cannot do: run another program, and
compute on more than one processor.

| the problem | the tool | the price |
|---|---|---|
| run `git`, `ffmpeg`, a script in another language | `execFile`, or `spawn` for long output | a process per run; never a shell with outside input |
| one slow calculation blocks the loop | a worker thread, or a pool of them | data copied in and out |
| many slow calculations, all the time | a pool, sized to the processors | a queue when they are all busy |
| use every processor for the whole server | `cluster`, or several copies behind a load balancer | **nothing may be kept in memory between requests** |
| a long-running helper that may crash | a child process with `fork` | about 40 MB and a start-up per child |
| keep the service running | systemd, or the platform | none in the code, if it stops on `SIGTERM` |

**Two orders of preference are worth keeping.** Measure first: a loop that is blocked shows up as
requests that take longer than their work, and lesson 2's `monitorEventLoopDelay` measures it directly.
Then move the least: a pool for one slow route is a smaller change than a cluster for the whole
service, and a cluster is a smaller change than splitting the service into several.

On a container platform the last two rows often merge. The platform runs several copies of a
one-process service and restarts each one, which is `cluster` and systemd done from outside, with the
same condition: a service whose state lives elsewhere can be copied, and one that keeps it in memory
cannot.
