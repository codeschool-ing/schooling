---
title: How Memcached spends its memory
version: 1
---

Memcached does not ask the operating system for memory one value at a time. It takes **pages of one
megabyte** and cuts each page into chunks of one size. Pages cut into 96-byte chunks belong to slab
class 1, pages of 120-byte chunks to class 2, and so on up, each size about 1.25 times the one before.
A copy started with `-vv` prints the classes and exits when `timeout` stops it:

```
ana@web:~$ timeout 1 memcached -u memcache -vv -p 11299 -l 127.0.0.1 2>&1 | grep 'slab class' | sed -n '1,4p;$p'
slab class   1: chunk size        96 perslab   10922
slab class   2: chunk size       120 perslab    8738
slab class   3: chunk size       152 perslab    6898
slab class   4: chunk size       192 perslab    5461
slab class  39: chunk size    524288 perslab       2
```

**A value goes into the smallest chunk that holds it**, together with its key and a header of a few
dozen bytes. A 1,000-byte value lands in class 12, whose chunks are 1,184 bytes, and the gap is memory
that nothing uses.

To see it fill, shrink it to 8 megabytes, and look at what the restart does to the values stored so
far:

```
ana@web:~$ sudo sed -i 's/^-m 64$/-m 8/' /etc/memcached.conf && sudo systemctl restart memcached
ana@web:~$ printf 'get stock:2 views\r\n' | nc -q1 127.0.0.1 11211
END
```

**A restart empties Memcached.** The stock and the counter of the earlier sections are gone, because
nothing was ever written to disk. Now this program writes twenty thousand values of a thousand bytes,
about 20 MB, into 8 MB:

```python
import sys

from pymemcache.client.base import Client

mc = Client(("127.0.0.1", 11211))
count, size = int(sys.argv[1]), int(sys.argv[2])
for i in range(count):
    mc.set(f"filler:{i}", b"x" * size, noreply=False)
print("written", count, "values of", size, "bytes")
```

All 20,000 writes succeeded. 12,920 older values were evicted to make room, 7,080 remain, and they fill
the eight pages of class 12, all eight megabytes. **Memcached evicts rather than refuse a write**: it
behaves as lesson 8's `allkeys-lru` out of the box, and `-M` is the switch that makes it refuse
instead, which a cache rarely wants.

```
ana@web:~/work$ printf 'get filler:0\r\nget filler:19999\r\n' | nc -q1 127.0.0.1 11211 | cut -c1-40
END
VALUE filler:19999 0 1000
xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
END
```

The first value written was evicted and the last is there. The least recently used order is kept **per
slab class**, so a new 1,000-byte value pushes out an old one from class 12 even if class 3 is full of
values nobody reads. Memcached moves pages between classes in the background when the mix of sizes
changes, which softens this, but a cache whose value sizes change abruptly can still evict in one class
while another sits idle.

```
ana@web:~/work$ python3 -c 'from pymemcache.client.base import Client; Client(("127.0.0.1", 11211)).set("big", b"x" * 2_000_000, noreply=False)' 2>&1 | tail -1
pymemcache.exceptions.MemcacheServerError: b'object too large for cache'
```

**No value may be larger than a megabyte**, the page size, unless `-I` raises it. A program that caches
a large page fragment without checking gets this error, or, with replies switched off, nothing at all,
which is what the next section is about.
