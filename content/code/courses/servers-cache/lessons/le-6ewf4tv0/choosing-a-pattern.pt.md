| padrão | num erro de leitura | numa gravação | bom para | o risco |
|---|---|---|---|---|
| cache-aside | a aplicação carrega e guarda | banco, depois apaga a chave | a maioria das leituras da maioria dos dados | uma cópia velha até o tempo de vida acabar |
| read-through | a camada de cache carrega e guarda | (combinado com um dos de baixo) | um lugar só para mudar o cache | o mesmo, num lugar só |
| write-through | como no read-through | banco, depois grava o cache | valores lidos logo depois de mudar | dois escritores deixando o valor mais velho |
| write-behind | do cache | cache agora, banco depois | muitas gravações baratas: contadores, curtidas | perder gravações junto com o cache |
| write-around | como no cache-aside | só o banco; o cache enche na próxima leitura | dados gravados uma vez e lidos raramente | um erro de cache depois de cada gravação |

**O write-around é o que o `update_price` fez** quando apagou a chave em vez de gravá-la: a gravação
contornou o cache, e o cache encheu de novo na leitura seguinte. Na prática, cache-aside nas leituras e
write-around nas gravações são um padrão só com dois nomes, e é o ponto de partida certo para quase
toda aplicação.

Saia dele só por um motivo que você saiba nomear: write-through quando a primeira leitura depois de uma
mudança precisa ser rápida, write-behind quando o banco não dá conta das gravações e perder algumas é
aceitável. **Cada passo para longe compra velocidade com um jeito novo de errar**, e a última coluna da
tabela é a lista desses jeitos.
