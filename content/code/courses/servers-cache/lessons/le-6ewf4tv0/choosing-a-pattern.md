
| pattern | on a read miss | on a write | good for | the risk |
|---|---|---|---|---|
| cache-aside | the application loads and stores | database, then delete the key | most reads of most data | a stale copy until the lifetime ends |
| read-through | the cache layer loads and stores | (combined with one of the below) | one place to change caching | the same, in one place |
| write-through | as read-through | database, then set the cache | values read right after they change | two writers leaving the older value |
| write-behind | from the cache | cache now, database later | many cheap writes: counters, likes | losing writes with the cache |
| write-around | as cache-aside | database only; the cache fills on the next read | data written once and rarely read | a miss after every write |

**Write-around is what `update_price` did** when it deleted the key instead of setting it: the write
went around the cache, and the cache filled again on the next read. In practice cache-aside on reads and
write-around on writes are one pattern under two names, and it is the right starting point for nearly
every application.

Move away from it only for a reason you can name: write-through when the first read after a change must
be fast, write-behind when the database cannot keep up with the writes and losing a few is acceptable.
**Each step away buys speed with a new way to be wrong**, and the table's last column is the list of
those ways.
