**Read a branch as a claim you can check.** "Reads one item by key, at any scale" is what DynamoDB
was built for, and it is also what it demands: a workload that cannot name its keys in advance is not
on that branch, however much it would like to be. "Transactions and joins" is the relational branch,
and it is the default for the data a business runs on, because most of a business's rules are
relationships between rows. "Questions over all of history" is the analytical branch, which is a
different machine from the one that answers a customer.

## What each store answers

The six questions, answered per store, in the words of the lessons that taught them:

| store | access pattern | latency | consistency | scale | you operate | price follows |
|---|---|---|---|---|---|---|
| S3 | whole objects by key, listed by prefix | tens of milliseconds | strong for each object | no limit that matters | classes, life cycles, permissions | gigabytes stored, requests, bytes out |
| RDS, Aurora | rows by any indexed column, joins, transactions | milliseconds | strong, with transactions | one writer, growing by a bigger machine | sizes, versions, indexes, failover | instance hours, storage, I/O |
| DynamoDB | one item or one key's items, by key | single-digit milliseconds | eventual or strong per read; transactions in a narrower form | spreads across partitions | keys and indexes, capacity mode | requests or provisioned units, storage |
| ElastiCache | a key, again and again | under a millisecond | whatever the cache's invalidation gives | memory of the nodes | nodes, eviction, invalidation | node hours, or data and ECPUs |
| Kinesis, MSK | records appended and read in order | under a second end to end | ordered per shard or partition | shards or brokers | shards, consumers, retention | shard or broker hours, data |
| Redshift | scans and joins over large tables | seconds | as of the last load | nodes or RPUs | distribution and sort keys, loads | node hours or RPU-hours |
| Athena | SQL over files where they lie | seconds | as of the files | as big as the lake | partitions, formats, files | terabytes scanned |

**Two rows are not stores in the usual sense.** Kinesis and MSK keep data for a retention period and
then let it go: they are where events travel, and lessons 20 to 23 landed them in S3, which is where
they are stored. ElastiCache keeps data only until it is evicted or the node restarts, which makes it
a copy, never the store of record. Lesson 13 put it in front of a database for exactly that reason.

**The cells that read "a narrower form" or "as of the last load" are where choices are lost.**
DynamoDB's transactions cover a bounded number of items, and they cost twice the request units of
ordinary writes; Redshift answers about the data loaded into it, and an analyst who needs the order
placed a minute ago is asking the wrong store. Each of those is a sentence a design review should
say out loud.
