Property wrappers and result builders are fixed rewrites: the compiler knows the rules for `@` with a
wrapper and for a block with a builder, and applies them. **A macro is a rewrite somebody else wrote**:
a small program that the compiler runs while it compiles yours, which receives a piece of your code
and returns new code to add to it. You use one with `#name(…)` in an expression, or `@Name` on a
declaration.

This course has already met one in passing. `#expect`, which lesson 18 uses in every test, is a macro.
In `ios-apps` the most important one is `@Observable`, which turns a class into a model that SwiftUI
watches for changes. SwiftUI is not here, and **`@Observable` is**: it lives in the `Observation`
module, which ships with the toolchain on Linux too.

```swift
// Observed.swift
import Observation

@Observable
final class WeekModel {
    var minutes = 0
}

let model = WeekModel()
withObservationTracking {
    print("the screen reads \(model.minutes)")
} onChange: {
    print("minutes is about to change: draw again")
}
model.minutes = 45
model.minutes = 90
print("now \(model.minutes)")
```

```
ana@vm:~/sw/l16$ swiftc Observed.swift -o observed && ./observed
the screen reads 0
minutes is about to change: draw again
now 90
```

`withObservationTracking` runs its first closure and remembers every observable property that closure
read: here, `minutes`. When one of them is about to change, it calls the second closure. That is what
SwiftUI does with a view's `body`: it reads the model while drawing, and draws again when what it read
changes. **The `onChange` closure ran once, for the first of two writes**, because tracking is
one-shot: whoever wants to hear about the next change tracks again, which SwiftUI does each time it
redraws.

## Looking inside

A property wrapper hides its expansion; a macro's can be printed. The compiler flag
`-dump-macro-expansions` writes everything every macro produced, 85 lines for this one class, and
`sed` keeps two pieces of it: the new storage, and the getter that `minutes` now has.

```
ana@vm:~/sw/l16$ swiftc -Xfrontend -dump-macro-expansions Observed.swift -o observed 2>&1 | sed -n '/private  var _minutes/p; /^    get {/,/^    }/p'
private  var _minutes  = 0
    get {
      access(keyPath: \.minutes)
      return _minutes
    }
```

**`minutes` is no longer a stored property.** The macro moved the value to `_minutes` and gave
`minutes` a getter that first calls `access(keyPath:)`, which is how `withObservationTracking` learnt
that the closure read it. The setter, further down in the full dump, calls `withMutation`, which is how
`onChange` heard about the write. It is the same idea as section 03's wrapper, a hidden store behind a
property with code in front of it, generated by a program instead of by a rule of the language.

## What a macro is not

- **It is not a text substitution.** A macro receives your code already parsed, and what it returns is
  type-checked like code you wrote. A macro cannot produce something that would not compile by hand.
- **It does not change what you wrote.** It adds declarations, accessors or expressions where its
  author said it would; your `var minutes = 0` is still there, now with accessors attached.
- **It is not magic at run time.** Everything happened while compiling, and `-dump-macro-expansions`
  shows all of it. When a macro's behaviour surprises you, read the expansion before reading anything
  else.

Writing a macro of your own needs a separate package built on Apple's `swift-syntax` library, and that
is beyond this course; using them well needs only what this section showed. In Xcode, right-clicking a
macro and choosing Expand Macro shows the same expansion inline. That menu was not used here, since
Xcode is not on Linux.
