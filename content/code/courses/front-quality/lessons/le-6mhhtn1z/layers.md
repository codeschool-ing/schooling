- **`src/planner.ts` is unit-test material.** Every function takes values and returns a value, so a
  test calls it and compares, with no page at all. Whether `weekTotal` adds the right sessions is a
  question about arithmetic and dates, and nothing above this layer answers it better. Lesson 2.
- **`src/view.ts` needs a page, but not a browser.** It creates elements, listens for clicks and
  reads a form, so its tests run it inside **jsdom**, a page simulated in Node: the DOM without
  layout, without CSS and without a screen. A test types a number into the Minutes field, presses
  *Add session*, and reads the new total. Lessons 2 and 3.
- **`src/main.ts`, `index.html`, `style.css` and `courses.json` are only together in a browser.**
  Whether the page loads, fetches its data, draws, and stays usable is a question for a real
  Chromium, driven by Playwright against the dev server. Lesson 4.
- **Every `.ts` file is read by the type checker first**, before any test runs: the static layer of
  the trophy, and the next section.

## What each layer cannot see

The map matters as much for what it leaves out. **jsdom computes no layout**, so a component test
cannot tell you that a button is covered by another element, or that a colour is unreadable. A unit
test of `weekTotal` cannot tell you that the total is never shown. And an end-to-end test, which sees
all of that, sees it slowly and points at nothing in particular when it fails.

Two things in this list are not tests of behaviour at all, and they get layers of their own in the
second and third parts of this course. **Security** is tested where the flaw is, in a unit test
when it is a rule and in the browser when only the browser enforces it, as with the headers of
lesson 8. **Accessibility** is checked by a machine on every page in lesson 10, and by a person with
a keyboard and a screen reader in lessons 11 and 12, because some of it no machine can decide.

## How many of each

This course ends with about forty tests in the planner, and the proportions are the argument above
applied rather than a target. Most are unit and component tests that run in under two seconds
together; a handful are end-to-end tests that take several seconds each. A suite whose fast part is
fast is one people run before every commit, and a suite people do not run catches nothing.
