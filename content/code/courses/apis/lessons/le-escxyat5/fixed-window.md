---
title: The fixed window and its edge
version: 1
---

**A fixed window cuts time into equal slices and counts each client's requests inside the current
slice.** Ten requests per ten seconds means: a counter per client, set back to zero whenever a new
ten-second slice begins, and a refusal for any request that would take it past ten.

It is the first limiter anybody writes, and for good reasons. The state per client is two numbers,
which window it is and how many so far. The check is one comparison. And the client can be told
exactly when the count resets, because the window's end is a fixed point on the clock.

`limits.py` has one, for comparison, behind the argument `window`. Its windows are aligned to the
clock: the window number is the time in seconds divided by ten, so every window starts on a second
that is a multiple of ten.

## The edge

The wrong picture is "ten per ten seconds" read as "never more than ten in any ten seconds". A
fixed window promises less than that. It limits each slice, and nothing stops a client from using
the end of one slice and the start of the next. Ten requests in the last second of a window, ten in
the first second of the next one, and both windows are within their limit: **twenty requests in two
seconds, double the limit, all accepted.**

That was measured, not worked out. The section "A burst against it" sends thirty requests, a tenth
of a second apart, timed to start one second before a window ends, first at `limits.py window` and
then at the token bucket of the plain `limits.py`:

The fixed window accepted the first ten, reset at the boundary, and accepted ten more before
refusing anything. The token bucket, configured for the same ten per ten seconds on average,
accepted its ten and then one per second as tokens came back.

A client does not have to be clever to land on the edge. **When windows are aligned to the clock,
every client's counter resets at the same instant**, and every client that was refused near the end
of a window retries at the start of the next. Traffic arrives in a spike at the top of each window,
which is the opposite of what the limit was meant to produce. Starting each client's window at its
own first request spreads the resets out, and leaves the edge where it was: the client still gets
two windows' worth across its own boundary.

When is a fixed window right, then? When the limit is generous compared with what the service can
take, so double for a moment does no harm, and when the simplicity is worth more than the
precision. A daily quota is the usual case: nobody minds that a client can spend the last minute of
Monday and the first minute of Tuesday back to back. `limits.py` uses a fixed window for exactly
that, with windows a day long.
