---
title: Logging out, and why it works at once
version: 1
---

A session ends when its row does. **Logging out is deleting the row**, and from that moment the id in
any cookie, anywhere, is a key to nothing. The server can do it at any time and needs nobody's
cooperation.

The intuitive version is the other way round: logging out means the browser deletes its cookie. The
browser does delete it, because the server asks, but that is housekeeping. A cookie copied before the
logout, by malware on the laptop, by a proxy that logged headers, or by the person who used the
computer before you, would still work if the server had kept the row. What makes a logout real is the
server forgetting.

To see the difference, keep a copy of the jar before logging out. `kept.txt` plays the copy that
somebody else made:

```
ana@api:~/shelf$ cp jar.txt kept.txt
```

Logout is a `POST`, and like every `POST` in `sessions.py` apart from login it needs the session's
CSRF token in a header. The `$( … )` inside the command asks `/me` for it first; the next section is
about why the check exists.

```
ana@api:~/shelf$ curl -si -b jar.txt -c jar.txt -X POST localhost:8000/logout -H "X-CSRF-Token: $(curl -s -b jar.txt localhost:8000/me | jq -r .csrf)"
HTTP/1.1 204 No Content
Server: BaseHTTP/0.6 Python/3.12.3
Date: Sat, 10 Oct 2026 04:31:06 GMT
Content-Length: 0
Set-Cookie: sid=; Path=/; Max-Age=0; HttpOnly; Secure; SameSite=Lax
```

The answer sets the cookie again with an empty value and `Max-Age=0`, which is how a server tells a
client to drop one; there is no header for deleting a cookie. curl obeys, and the jar is empty:

```
ana@api:~/shelf$ cat jar.txt
# Netscape HTTP Cookie File
# https://curl.se/docs/http-cookies.html
# This file was generated by libcurl! Edit at your own risk.
```

The copy still holds the old id. The server no longer knows it:

```
ana@api:~/shelf$ curl -s -b kept.txt localhost:8000/me
{"error": "sign in first"}
```

In the table, ana's row is gone. The one left is bruno's, from the `shop.test` login in the previous
section, and logging ana out did not touch it:

```
ana@api:~/shelf$ sqlite3 shelf.db 'SELECT user_id, expires FROM sessions'
2|1791608466
```

## Every other way a session ends

The same move, deleting rows, covers each case a real application has to handle:

| event | what the server deletes |
|---|---|
| the user logs out | that session's row |
| the session reaches `expires` | nothing at once: the lookup ignores the row, and a cleanup job deletes old rows later |
| the user changes their password | **every** session of that user except the current one, since the change may be because somebody else got in |
| an administrator blocks an account | every session of that user |
| a breach of the session store | the whole table, and everybody logs in again |

**The price is one lookup per request.** Every request to `/me` or `/wishlist` reads a row by its
primary key. On one machine that costs almost nothing. With ten servers behind a load balancer they
all need the same table: a shared database, or a store such as Redis that every server can reach.
That shared store is the argument for tokens, and the comparison at the end of the lesson weighs it.
