---
title: O logout, e por que ele vale na hora
version: 1
---

Uma sessão acaba quando a linha dela acaba. **Fazer logout é apagar a linha**, e a partir desse
momento o id em qualquer cookie, em qualquer lugar, é a chave de nada. O servidor pode fazer isso a
qualquer hora e não depende da colaboração de ninguém.

A versão intuitiva é a inversa: fazer logout é o navegador apagar o cookie. O navegador apaga, porque
o servidor pede, mas isso é arrumação. Um cookie copiado antes do logout, por um malware no notebook,
por um proxy que registrava cabeçalhos ou pela pessoa que usou o computador antes de você,
continuaria funcionando se o servidor tivesse mantido a linha. O que torna um logout real é o
servidor esquecer.

Para ver a diferença, guarde uma cópia do pote antes de sair. O `kept.txt` faz o papel da cópia que
outra pessoa fez:

```
ana@api:~/shelf$ cp jar.txt kept.txt
```

O logout é um `POST`, e como todo `POST` do `sessions.py` além do login ele precisa do token CSRF da
sessão num cabeçalho. O `$( … )` dentro do comando pede o token ao `/me` primeiro; a próxima seção
explica por que essa verificação existe.

```
ana@api:~/shelf$ curl -si -b jar.txt -c jar.txt -X POST localhost:8000/logout -H "X-CSRF-Token: $(curl -s -b jar.txt localhost:8000/me | jq -r .csrf)"
HTTP/1.1 204 No Content
Server: BaseHTTP/0.6 Python/3.12.3
Date: Sat, 10 Oct 2026 04:31:06 GMT
Content-Length: 0
Set-Cookie: sid=; Path=/; Max-Age=0; HttpOnly; Secure; SameSite=Lax
```

A resposta define o cookie de novo com valor vazio e `Max-Age=0`, que é como um servidor diz ao
cliente para descartar um; não existe cabeçalho para apagar cookie. O curl obedece, e o pote fica
vazio:

```
ana@api:~/shelf$ cat jar.txt
# Netscape HTTP Cookie File
# https://curl.se/docs/http-cookies.html
# This file was generated by libcurl! Edit at your own risk.
```

A cópia ainda tem o id antigo. O servidor não o conhece mais:

```
ana@api:~/shelf$ curl -s -b kept.txt localhost:8000/me
{"error": "sign in first"}
```

Na tabela, a linha de ana sumiu. A que sobrou é de bruno, do login em `shop.test` na seção anterior,
e o logout de ana não mexeu nela:

```
ana@api:~/shelf$ sqlite3 shelf.db 'SELECT user_id, expires FROM sessions'
2|1791608466
```

## Todas as outras formas de uma sessão acabar

O mesmo gesto, apagar linhas, cobre cada caso que uma aplicação de verdade precisa tratar:

| evento | o que o servidor apaga |
|---|---|
| o usuário faz logout | a linha daquela sessão |
| a sessão chega ao `expires` | nada na hora: a consulta ignora a linha, e uma rotina de limpeza apaga as antigas depois |
| o usuário troca a senha | **todas** as sessões dele menos a atual, já que a troca pode ser porque outra pessoa entrou |
| um administrador bloqueia uma conta | todas as sessões daquele usuário |
| um vazamento do armazenamento de sessões | a tabela inteira, e todo mundo entra de novo |

**O preço é uma consulta por requisição.** Toda requisição a `/me` ou `/wishlist` lê uma linha pela
chave primária. Numa máquina só isso não custa quase nada. Com dez servidores atrás de um balanceador
de carga, todos precisam da mesma tabela: um banco compartilhado, ou um armazenamento como o Redis
que todos alcancem. Esse armazenamento compartilhado é o argumento a favor dos tokens, e a
comparação no fim da aula o pesa.
