---
title: Where the server remembers you
version: 1
---

HTTP forgets. Every request arrives on its own, and nothing in the protocol links it to the one
before. Lesson 7 dealt with that by sending a credential on every request: a password with Basic, or
an API key. A person does not type a password for every page, so after one successful
login the server hands back **something the client sends instead**, and each later request carries
it. The whole question of this lesson is what that something is, and where the server keeps the
fact that you logged in.

The common picture is that this is a choice between old and new: sessions are what websites did, and
a JWT is the modern, more secure replacement. Neither half is true. Both are a secret the client
presents on every request, and whoever presents it is you. **What differs is where the state lives.**

- In a **session**, the server keeps a row: this id belongs to user 1 until a given moment. The
  client holds only the id, a random string that means nothing on its own. Checking a request means
  looking the id up.
- In a **token** such as a JWT, the server keeps nothing about the login. The token itself says who
  you are and until when, and it is signed with a key only the server holds. Checking a request means
  checking the signature.

Everything else in the lesson follows from that one difference:

| | session | signed token |
|---|---|---|
| the client holds | a random id | the claims and a signature |
| the server keeps | one row per login | one key |
| checking a request | a lookup | a computation with the key |
| ending a login | delete the row | wait for the expiry, or keep state after all |

The last row is where the debate actually is, and the section on revocation is about it.

A second confusion is worth clearing now: **this is not a choice between a cookie and a header.** A
cookie is a way to carry a value, and so is the `Authorization` header. A session id can travel in a
header, and a JWT can travel in a cookie. The lesson keeps them in their usual places, the session in
a cookie and the token in `Authorization: Bearer`, and the sections on CSRF and on storage say what
changes when the carrier changes.

You will build both. `sessions.py` signs you in with a session cookie, and `tokens.py` with a JWT.
Both answer on `127.0.0.1:8000`, like `rest.py`, so one runs at a time. They need only what lesson 1
left on your machine: `db.py`, `shelf.db` and the packages, `python3-jwt` among them. They add their
own tables to `shelf.db` and leave the books alone.
