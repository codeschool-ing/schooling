---
title: Onde o servidor lembra de você
version: 1
---

O HTTP esquece. Cada requisição chega sozinha, e nada no protocolo a liga à anterior. A aula 7
resolveu isso mandando uma credencial em toda requisição: uma senha com Basic, ou uma chave de API.
Uma pessoa não digita a senha a cada página, então, depois de um login bem-sucedido, o servidor
devolve **algo que o cliente envia no lugar dela**, e cada requisição seguinte o leva. A questão
inteira desta aula é o que é esse algo, e onde o servidor guarda o fato de que você entrou.

A imagem comum é que se trata de escolher entre o velho e o novo: sessões eram o que os sites
faziam, e o JWT é o substituto moderno e mais seguro. Nenhuma das metades é verdade. Os dois são um
segredo que o cliente apresenta a cada requisição, e quem o apresenta é você. **O que muda é onde
mora o estado.**

- Numa **sessão**, o servidor guarda uma linha: este id pertence ao usuário 1 até um certo momento.
  O cliente guarda só o id, uma string aleatória que sozinha não significa nada. Conferir uma
  requisição é procurar o id.
- Num **token** como o JWT, o servidor não guarda nada sobre o login. O próprio token diz quem você
  é e até quando, e vem assinado com uma chave que só o servidor tem. Conferir uma requisição é
  conferir a assinatura.

Todo o resto da aula sai dessa diferença:

| | sessão | token assinado |
|---|---|---|
| o cliente guarda | um id aleatório | as claims e uma assinatura |
| o servidor guarda | uma linha por login | uma chave |
| conferir uma requisição | uma consulta | um cálculo com a chave |
| encerrar um login | apagar a linha | esperar o vencimento, ou afinal guardar estado |

A última linha é onde o debate realmente está, e a seção sobre revogação trata dela.

Vale desfazer agora uma segunda confusão: **esta não é uma escolha entre cookie e cabeçalho.** Um
cookie é um jeito de transportar um valor, e o cabeçalho `Authorization` também. Um id de sessão
pode viajar num cabeçalho, e um JWT pode viajar num cookie. A aula os mantém nos lugares de costume,
a sessão num cookie e o token em `Authorization: Bearer`, e as seções sobre CSRF e sobre
armazenamento dizem o que muda quando o meio de transporte muda.

Você vai construir os dois. O `sessions.py` faz o login com um cookie de sessão, e o `tokens.py`
com um JWT. Os dois respondem em `127.0.0.1:8000`, como o `rest.py`, então roda um de cada vez. Eles
precisam só do que a aula 1 deixou na sua máquina: `db.py`, `shelf.db` e os pacotes, entre eles o
`python3-jwt`. Acrescentam as próprias tabelas ao `shelf.db` e não mexem nos livros.
