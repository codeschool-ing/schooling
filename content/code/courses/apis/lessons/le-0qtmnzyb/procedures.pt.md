**No REST uma requisição nomeia uma coisa; numa chamada de procedimento remoto ela nomeia uma
ação.** O `GET /v1/books/1` da aula 1 diz "este livro" e deixa o método dizer o que fazer com ele.
Uma chamada de procedimento remoto diz `Reserve`, entrega os argumentos e espera um valor de retorno,
como se a função estivesse no mesmo programa. Uma biblioteca de cada lado transforma a chamada numa
mensagem, envia, e transforma a resposta de volta num valor.

A ideia é mais velha que a web, e a imagem errada dela é mais velha ainda: **a de que uma chamada
remota é uma chamada de função comum que por acaso está longe.** Não é, e os sistemas que tentaram
fazê-la parecer uma, CORBA e Java RMI entre eles, ficaram lembrados por isso. Uma chamada local não
perde a rede no meio do caminho, não leva quarenta segundos porque outra máquina está ocupada, e não
dá certo do outro lado enquanto a resposta se perde na volta. Uma chamada remota pode fazer as três
coisas, e um código que finge o contrário não tem plano para o dia em que acontecer.

**O gRPC é a chamada de procedimento remoto que a maioria das empresas usa hoje**, e ele é construído
em torno dessa diferença, não contra ela. O Google o publicou em 2015 como a versão aberta do sistema
que usava entre os próprios serviços. Toda chamada leva um prazo, termina com um status de uma lista
fixa e é descrita de antemão num contrato a partir do qual os dois lados são gerados. O contrato é
escrito em **Protocol Buffers**, o formato do Google para descrever e codificar mensagens, e esse é
o assunto das duas próximas seções.

Três diferenças decidem quase tudo o que vem nesta aula:

| | REST | GraphQL | gRPC |
|---|---|---|---|
| **a requisição nomeia** | um recurso, pelo endereço | os campos que o cliente quer | um procedimento de um serviço |
| **o contrato** | opcional; a aula 6 escreve um | um schema, obrigatório | um arquivo `.proto`, obrigatório |
| **o que trafega** | JSON, legível a olho | JSON, legível a olho | binário, legível com o schema |
| **por baixo** | HTTP/1.1 ou HTTP/2 | HTTP, geralmente um endereço só | HTTP/2, e nada mais |

As duas últimas linhas são os custos, e a seção sobre a escolha volta a elas. As duas primeiras são
o ponto: **um cliente gRPC não consegue enviar uma requisição que o contrato não descreve**, porque
ele nunca monta requisição nenhuma. Ele chama uma função gerada, e a função só existe se o contrato
disser.

A livraria ganha um programa novo nesta aula, e não uma reescrita do antigo. O depósito dela precisa
responder quantos exemplares de um livro há na estante, segurar exemplares para um pedido, avisar os
caixas quando um nível muda e receber entregas. **A API REST do shelf fica onde a aula 1 a deixou**,
e o depósito é um segundo serviço ao lado dela, que é como o gRPC costuma chegar numa empresa: entre
dois programas dela mesma, não na frente dos clientes.
