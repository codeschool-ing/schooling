The flow that matters most has two halves. **The first half runs through the browser and ends
with a code; the second runs straight from the client to the authorization server and turns the
code into tokens.** Anything the browser carries may be read by somebody else, so nothing it
carries is enough on its own.

The steps, by the numbers in the drawing, with the reason for each:

- Steps 1 and 2. The client sends the browser to `/authorize`. It does not ask for your password;
  it builds an address with what it wants and redirects you there.
- Step 3. You deal with the authorization server directly. You sign in on its page and answer its
  question about this client, and the client sees neither.
- Step 4. The authorization server sends the browser back to the client's registered
  `redirect_uri`, with `code` and `state` added.
- Step 5. The client checks `state`. It is the random value the client put in the address in step
  1, and it has to come back unchanged. Without that check, a page somewhere else could send your
  browser to the callback with a code of its own choosing, and the app would attach somebody
  else's account to your session.
- Steps 6 and 7. The client exchanges the code at `/token`, directly, with its own credentials and
  the PKCE verifier the next section explains, and the tokens come back. This request never
  touches the browser.
- Steps 8 and 9. The client calls the API with `Authorization: Bearer` and the access token.

The address in step 1 carries the whole request. These are the parameters `idp.py` reads:

| parameter | what it says | why it is there |
|---|---|---|
| `response_type=code` | "send me a code" | the only response type this lesson's server, and OAuth 2.1, accept |
| `client_id` | which app is asking | to look up what the app may have and where its codes may go |
| `redirect_uri` | where to send the browser back | compared with the registered one exactly, character by character |
| `scope` | what the app wants to do | the upper limit of what the token will allow |
| `state` | a random value the client keeps | the check in step 5 |
| `code_challenge`, `code_challenge_method` | the PKCE challenge | the next section |
| `nonce` | a random value for the ID token | OpenID Connect, in the section of that name |

## Why a code, and not the token

**Sending the access token straight back in step 4 would be simpler, and it was allowed once.**
The trouble is the channel. A redirect is an address in the browser, and addresses end up in the
history, in server logs and in the `Referer` header of the next page; a token placed there is a
token placed in all of those.

A code survives that exposure because of what it is not good for. It works once, and `idp.py`
keeps it for sixty seconds. It is bound to one client and one `redirect_uri`. And it is useless
without the second request, which needs the client's credentials and the verifier, neither of
which ever passed through the browser.

**The `redirect_uri` is checked exactly for the same reason.** If an authorization server accepted
any address that started with the registered one, or matched a pattern, a code could be sent to a
page the client does not control. `idp.py` compares the whole string, and an address it does not
know gets an error page and no redirect at all. The section that runs the flow by hand shows that refusal.
