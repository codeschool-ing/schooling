The dictionary says what a column means. **Lineage** says where it came from: which source columns, through which
transformations, and where it goes next. It answers two questions that come up every week:

- **"Can I trust this number?"** Follow it back to the source and see every step that touched it.
- **"What breaks if I change this?"** Follow a source column forward and see every table, mart and dashboard that reads
  it. Lesson 11's renamed `discount_cents` was exactly this question asked too late.

For `net_cents` the lineage is short, and every step of it is in this course. Three columns of the shop system's order
lines and the status of the order are copied as they were into staging, combined by one expression in `20_fact_sales.sql`,
and summed by the sales team's mart. The filter matters as much as the arithmetic. A cancelled order's lines never reach
`fact_sales`, which is why `net_cents` excludes them, and lineage that showed only the arithmetic would hide it.

Lineage at this level is **column-level lineage**, and it is expensive to keep by hand. In practice it is extracted:

- **From the SQL itself.** A tool that parses each `CREATE TABLE … AS SELECT` knows which input columns each output column
  is computed from. dbt builds a table-level graph of every model from its references, and catalogue tools parse queries
  for the column level.
- **From the pipelines as they run.** OpenLineage, an open standard under the Linux Foundation, defines events that a
  scheduler or an engine emits when a job reads and writes, so lineage is recorded as a side effect of running.

Either way, lineage belongs in the same place as the dictionary, because the two answer one question between them:
**what is this, and how did it get here?**
