---
title: Rows, or columns
version: 1
---

A table is a grid, and a disk is a line. Every database has to decide in which order to write the
grid's cells onto the line, and there are two obvious orders.

**By row**: all the columns of the first row, then all the columns of the second, and so on. That is
what PostgreSQL does. A page of 8 kB holds as many whole rows as fit, and each row is stored with a
small header of its own.

**By column**: all the values of the first column, then all the values of the second, and so on, in
blocks of many thousands of rows. That is what DuckDB does, and BigQuery, Snowflake, Redshift, ClickHouse
and every file in Parquet format.

Neither order is better in general. Each is better at one of lesson 1's two workloads:

- **The till** writes one whole row, and reads one whole row back by its key. By row, that row is in one
  place. By column, it is in eleven places, one per column, each in a block of thousands of other rows.
- **The report** reads a few columns of every row. By column, those few columns are each one contiguous
  stretch of disk, and the others are never touched. By row, every page holds every column, so reading
  one column means reading all of them.

This lesson measures the second difference and then the first. The second turns out to be much larger
than "reads fewer columns" suggests, because of what storing a column together makes possible:
compression.
