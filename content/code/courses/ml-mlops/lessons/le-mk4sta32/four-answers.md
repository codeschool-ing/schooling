A modeller will name a task by the algorithm: "a gradient-boosted classifier", "a two-tower
recommender". **The platform cares about something plainer: what shape the answer has, what it is
keyed by, and when the right answer becomes known.** Four tasks cover almost every model a data
platform is asked to serve, and they differ on exactly those three things.


| task | the question | what comes out | keyed by |
| --- | --- | --- | --- |
| **classification** | which kind is this? | a category, and usually a probability for each | one entity: a member |
| **regression** | how much? | a number on a scale | one entity |
| **clustering** | which ones go together? | a group number, with no meaning until a person gives it one | one entity, but only within one run |
| **recommendation** | what next? | a ranked list of other things | a pair: a member and a title |

Two cells in that table cause more trouble in production than the rest put together.

**A cluster's number means nothing across runs.** Retrain k-means next month and the readers of
crime may be group 3 instead of group 6. A report that stored "group 6" last month and compares it
with "group 6" this month is comparing two different things, and nothing fails. A platform that
stores cluster ids stores them **with the run that produced them**, the way lesson 7 versions a
model.

**A recommendation is keyed by a pair, not by a member.** Ponto Final has eighty titles, so every
member has eighty possible scores, and the table of all of them for every member is eighty times
the size of the members table. Serving one usually means computing it at request time, which lesson
8 meets as a choice between batch and real time.

The rest of this lesson builds one of each on the same shop, and puts a number beside each one.
Section 06 then asks the question every number in it needs: compared with what?
