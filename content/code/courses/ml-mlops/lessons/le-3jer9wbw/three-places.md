**Deployment is deciding where a model's answers are computed, and when.** There are three answers,
and they differ less in technology than in a single question: how old may the answer be when
somebody reads it?

| | **batch** | **real time** | **at the edge** |
| --- | --- | --- | --- |
| when it runs | on a schedule, for everybody | when a request arrives, for one | on the device, when it is asked |
| where the answer goes | a table | the response to the request | the device's own screen or logic |
| how old the answer is | up to a day | as old as its features | as old as the model on the device |
| what it needs | the offline store, a scheduler | the online store, a service that is always up | the model copied to the device, features available there |
| what goes wrong | a run that did not happen | a slow or failing request | a device running last year's model |

**Batch is the default, and most models should never leave it.** A table of scores computed
overnight is cheap, easy to check and easy to rerun, and it fits any decision taken on a schedule:
marketing sends vouchers once a month, so a score computed last night is as good as one computed
this second. The lapse model is a batch model.

**Real time earns its cost when the answer depends on something that just happened**, or when
nobody knows in advance whom to score: the recommender of lesson 2, which should change the moment
a member buys a book, or a fraud check on a payment that did not exist a second ago. The member
page that shows a lapse score is a weaker case, and section 11 weighs it.

**The edge is for when there is no network to rely on**, or the answer has to come faster than a
round trip allows, or the data must not leave the device. It is the least common of the three for a
data platform, and the one with the hardest update problem.
