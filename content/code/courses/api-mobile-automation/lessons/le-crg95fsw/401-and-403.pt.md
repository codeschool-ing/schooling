title: 401 e 403, e uma matriz de quem pode fazer o quê

**Um `401` diz que o servidor não sabe quem você é; um `403` diz que ele sabe, e a resposta é não.**
O primeiro é sobre autenticação, provar uma identidade, e o segundo sobre autorização, decidir o que
essa identidade pode fazer. A lição 1 notou que os nomes estão trocados, *Unauthorized* para o
primeiro. A diferença não é acadêmica: um cliente que recebe `401` deveria buscar um token novo e
tentar de novo, e um que recebe `403` deveria parar, porque um token novo para o mesmo cliente vai
ser recusado do mesmo jeito.

## A matriz

Autorização se testa como uma tabela: todo tipo de chamador de um lado, toda operação em cima, e o
status esperado em cada célula. Cada célula é um teste. Para os pedidos do boxoffice os chamadores
são os dois clientes e ninguém, então uma pequena função que imprime só o código de status poupa
digitação; digite-a uma vez, como o `order` da lição 2:

```
ana@laptop:~/boxoffice$ code() { curl -s -o /dev/null -w '%{http_code}\n' "$@"; }
```

`"$@"` repassa tudo o que vem escrito depois de `code`, então ela aceita qualquer endereço e
qualquer opção. Garanta que `TOKEN` e `AUDITOR` estão novos, como a seção 04 disse no fim.
Primeiro o `ci-tests`, que pode tudo, criando um pedido e lendo-o de volta:

```
ana@laptop:~/boxoffice$ code localhost:8080/v1/orders -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' -d '{"show_id":"sh-101","seats":1}'
201
ana@laptop:~/boxoffice$ code localhost:8080/v1/orders/ord-1001 -H "authorization: Bearer $TOKEN"
200
```

Depois o `auditor`, contra esse mesmo pedido:

```
ana@laptop:~/boxoffice$ code localhost:8080/v1/orders -H "authorization: Bearer $AUDITOR" -H 'content-type: application/json' -d '{"show_id":"sh-101","seats":1}'
403
ana@laptop:~/boxoffice$ code localhost:8080/v1/orders/ord-1001 -H "authorization: Bearer $AUDITOR"
404
ana@laptop:~/boxoffice$ code -X DELETE localhost:8080/v1/orders/ord-1001 -H "authorization: Bearer $AUDITOR"
404
```

E cada credencial na porta a que ela não pertence: a chave da equipe num pedido, e um token no
relatório da equipe:

```
ana@laptop:~/boxoffice$ code localhost:8080/v1/orders/ord-1001 -H 'X-Api-Key: lab-only-staff-key'
401
ana@laptop:~/boxoffice$ code localhost:8080/v1/reports/sales -H "authorization: Bearer $TOKEN"
401
```

Juntando tudo, com as requisições que dispensam captura própria porque toda requisição sem token é
recusada antes de qualquer outra coisa ser olhada:

| chamador | criar um pedido | ler `ord-1001` | cancelar `ord-1001` | o relatório de vendas |
|---|---|---|---|---|
| token do `ci-tests` | `201` | `200` | `204` | `401` |
| token do `auditor` | `403` | `404` | `404` | `401` |
| sem token | `401` | `401` | `401` | `401` |
| chave da equipe | `401` | `401` | `401` | `200` |

Leia a linha do `auditor` com calma, porque duas das células não são o que o nome do cliente sugere.

**O `403` está certo.** O token do auditor é válido e o escopo dele não tem `orders:write`, então o
servidor conhece o chamador e recusa o ato. A resposta também diz isso no cabeçalho:

```
ana@laptop:~/boxoffice$ curl -si localhost:8080/v1/orders -H "authorization: Bearer $AUDITOR" -H 'content-type: application/json' -d '{"show_id":"sh-101","seats":1}' | grep -iE '^HTTP|^www'
HTTP/1.1 403 Forbidden
www-authenticate: Bearer error="insufficient_scope", error_description="this token may not create orders"
```

`insufficient_scope` é o erro que a RFC 6750 nomeia exatamente para este caso, e ele diz ao cliente
que o que ajudaria é um token com mais escopo, não uma cópia nova do mesmo.

**Os dois `404` são uma pergunta.** O boxoffice deixa um cliente ler só os próprios pedidos, e o
auditor não tem nenhum, então para ele o `ord-1001` não existe. Para um cliente chamado *auditor*,
com o escopo `orders:read`, isso parece um cliente que não consegue ler nada. O código é coerente
consigo mesmo; se ele bate com o que o teatro queria, só quem escreveu o requisito pode responder.
**A matriz achou isso, e o relatório certo pergunta em vez de afirmar**: o auditor consegue fazer
isto, é o que se pretendia?

O `404`, em vez de um `403`, é uma escolha deliberada que vale reconhecer. Responder `403` ao pedido
de outra pessoa confirmaria que existe um pedido com aquele id; `404` não entrega nada. O mesmo
raciocínio fez a chave errada e a chave ausente parecerem iguais na seção 02.

## Um defeito na palavra Bearer

O esquema no cabeçalho `Authorization` é `Bearer`, e o HTTP diz que o nome de um esquema **não
diferencia maiúsculas de minúsculas** (RFC 9110, §11.1): `bearer`, `Bearer` e `BEARER` são o
mesmo. Algumas bibliotecas cliente o escrevem em minúsculas. O boxoffice, recebendo exatamente o
token que funcionou acima:

```
ana@laptop:~/boxoffice$ curl -si localhost:8080/v1/orders/ord-1001 -H "authorization: bearer $TOKEN" | grep -iE '^HTTP|^www'
HTTP/1.1 401 Unauthorized
www-authenticate: Bearer error="invalid_token", error_description="no bearer token"
```

`no bearer token`, para uma requisição que leva um. O boxoffice compara a palavra letra por letra, o
que o padrão diz que ele não deve fazer. Um cliente que manda `bearer` fica trancado do lado de fora
com uma mensagem que não diz nada útil a quem o escreveu, e ninguém acharia isso por uma tela. A
correção é um `toLowerCase()`, e o teste é a requisição acima com o status esperado `200`.
