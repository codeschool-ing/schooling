title: 401 and 403, and a matrix of who may do what

**A `401` says the server does not know who you are; a `403` says it knows, and the answer is no.**
The first is about authentication, proving an identity, and the second about authorisation,
deciding what that identity may do. Lesson 1 noted that the names are backwards, *Unauthorized* for
the first. The difference is not academic: a client that gets `401` should fetch a new token and try
again, and one that gets `403` should stop, because a new token for the same client will be refused
the same way.

## The matrix

Authorisation is tested as a table: every kind of caller down one side, every operation across the
top, and the expected status in each cell. Each cell is a test. For boxoffice's orders the callers
are the two clients and nobody at all, so a small function to print only the status code saves
typing; type it once, like lesson 2's `order`:

```
ana@laptop:~/boxoffice$ code() { curl -s -o /dev/null -w '%{http_code}\n' "$@"; }
```

`"$@"` passes on everything written after `code`, so it takes any address and any options. Make sure
`TOKEN` and `AUDITOR` are fresh, as section 04 ended by saying. First `ci-tests`, which may do
everything, creating an order and reading it back:

```
ana@laptop:~/boxoffice$ code localhost:8080/v1/orders -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' -d '{"show_id":"sh-101","seats":1}'
201
ana@laptop:~/boxoffice$ code localhost:8080/v1/orders/ord-1001 -H "authorization: Bearer $TOKEN"
200
```

Then `auditor`, against that same order:

```
ana@laptop:~/boxoffice$ code localhost:8080/v1/orders -H "authorization: Bearer $AUDITOR" -H 'content-type: application/json' -d '{"show_id":"sh-101","seats":1}'
403
ana@laptop:~/boxoffice$ code localhost:8080/v1/orders/ord-1001 -H "authorization: Bearer $AUDITOR"
404
ana@laptop:~/boxoffice$ code -X DELETE localhost:8080/v1/orders/ord-1001 -H "authorization: Bearer $AUDITOR"
404
```

And each credential at the door it does not belong to: the staff key on an order, and a token on the
staff report:

```
ana@laptop:~/boxoffice$ code localhost:8080/v1/orders/ord-1001 -H 'X-Api-Key: lab-only-staff-key'
401
ana@laptop:~/boxoffice$ code localhost:8080/v1/reports/sales -H "authorization: Bearer $TOKEN"
401
```

Put together, with the requests that need no further capture because every one without a token is
refused before anything else is looked at:

| caller | create an order | read `ord-1001` | cancel `ord-1001` | the sales report |
|---|---|---|---|---|
| `ci-tests` token | `201` | `200` | `204` | `401` |
| `auditor` token | `403` | `404` | `404` | `401` |
| no token | `401` | `401` | `401` | `401` |
| staff key | `401` | `401` | `401` | `200` |

Read the `auditor` row slowly, because two of its cells are not what the client's name suggests.

**The `403` is right.** The auditor's token is valid and its scope lacks `orders:write`, so the
server knows the caller and refuses the act. The answer says so in its header too:

```
ana@laptop:~/boxoffice$ curl -si localhost:8080/v1/orders -H "authorization: Bearer $AUDITOR" -H 'content-type: application/json' -d '{"show_id":"sh-101","seats":1}' | grep -iE '^HTTP|^www'
HTTP/1.1 403 Forbidden
www-authenticate: Bearer error="insufficient_scope", error_description="this token may not create orders"
```

`insufficient_scope` is the error RFC 6750 names for exactly this case, and it tells the client that
a token with more scope, not a fresh copy of the same one, is what would help.

**The two `404`s are a question.** boxoffice lets a client read only its own orders, and the auditor
has none, so `ord-1001` does not exist as far as it is concerned. For a client called *auditor* with
the scope `orders:read`, that looks like a client that can read nothing at all. The code is
consistent with itself; whether it matches what the theatre wanted is something only the people who
wrote the requirement can answer. **The matrix found it, and the right report asks rather than
asserts**: here is what the auditor can do, is that intended?

The `404`, rather than a `403`, is a deliberate choice worth recognising. Answering `403` to
somebody else's order would confirm that an order with that id exists; `404` gives away nothing.
The same reasoning made the wrong key and the missing key look alike in section 02.

## A defect in the word Bearer

The scheme in the `Authorization` header is `Bearer`, and HTTP says the name of a scheme is
**case-insensitive** (RFC 9110, §11.1): `bearer`, `Bearer` and `BEARER` are the same. Some
client libraries write it in lower case. boxoffice, given exactly the token that worked above:

```
ana@laptop:~/boxoffice$ curl -si localhost:8080/v1/orders/ord-1001 -H "authorization: bearer $TOKEN" | grep -iE '^HTTP|^www'
HTTP/1.1 401 Unauthorized
www-authenticate: Bearer error="invalid_token", error_description="no bearer token"
```

`no bearer token`, for a request that carries one. boxoffice compares the word letter for letter,
which the standard says it must not. A client that sends `bearer` is locked out with a message that
tells its author nothing useful, and nobody would find it from a screen. The fix is one
`toLowerCase()`, and the test is the request above with the expected status `200`.

## Tidying up

```
ana@laptop:~/boxoffice$ code -X DELETE localhost:8080/v1/orders/ord-1001 -H "authorization: Bearer $TOKEN"
204
```
