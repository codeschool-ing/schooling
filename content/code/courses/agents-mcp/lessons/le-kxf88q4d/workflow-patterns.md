- **Chaining.** The output of one call is the input of the next: write an answer, then translate it, then check its tone. Each call does one small job, which makes each easier to test.
- **Routing.** One call classifies the input, and code sends it down a fixed branch. Section 05 builds one for Marginalia's messages.
- **Parallelisation.** The same input goes to several calls at once: three reviewers of one reply, or one call per section of a long document. Code combines the results, by voting or by concatenation.
- **Orchestrator and workers.** One call splits a task into parts and a worker call handles each part. **The number of parts is decided by the model**, which is why this pattern sits closest to an agent; lesson 6 builds the agent version.
- **Evaluator and optimiser.** One call writes, another judges against stated criteria, and the writer revises until the judge accepts or a limit is reached. The loop is real, and so is its exit condition, which is code.

**None of the five lets the model choose which tools exist or decide, step by step, what to do next.** That is the line lesson 1 drew, and it is what makes these patterns cheaper to run and easier to test: you know every path in advance because you wrote it.

## Why the patterns come before the agent

Two reasons, and both are practical. A workflow fails in a place you can point at: the router mislabelled the message, the second call in the chain dropped a fact. An agent fails somewhere in a sequence it made up, and finding the step means reading a trace. And a workflow's cost is a sum you can write down before running it, which an agent's is not.

So the order this course recommends, with the article, is to reach for the simplest pattern that works, measure it, and replace a fixed path with a model's choice only where the measurement shows the fixed path missing cases that matter.
