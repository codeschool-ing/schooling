**Agents as tools.** One agent, the orchestrator, stays in charge of the conversation. To another agent it looks like a tool: it has a name (`ask_orders`), a description and a schema with one argument (`question`). Calling it runs the specialist's whole loop, and the specialist's final answer comes back as the tool's result. The orchestrator then decides what to do next, perhaps asking another specialist, perhaps answering. The customer only ever talks to the orchestrator.

**Handoff.** A triage agent reads the conversation and transfers it to a specialist, which takes over: it receives the conversation, works on it with its own tools and answers the customer itself. The triage agent is out of the loop from then on. Its tool, `transfer_to_orders`, takes no arguments, because what moves is the conversation, not a question.

| | agents as tools | handoff |
|---|---|---|
| who answers the customer | the orchestrator | the specialist |
| what the specialist receives | one question, written by the orchestrator | the conversation |
| what comes back | an answer, as a tool result | nothing: control does not return |
| good for | tasks with several parts to combine | routing a conversation to the right owner |
| the risk | the orchestrator's question and the specialist's answer lose detail | the specialist must handle everything that follows, including topics outside its tools |

Lesson 2's router is a handoff without the agents: one model call that decides which branch owns the message. A triage agent is the same idea where the owner is an agent rather than a fixed procedure. And lesson 2's orchestrator-and-workers pattern is agents as tools, with the orchestrator deciding how many questions to ask.

The OpenAI Agents SDK calls these two exactly **agents as tools** and **handoffs**; the Claude Agent SDK's subagents are agents as tools; Google's ADK has both, as an agent tool and as transfer between sub-agents. Lessons 8 to 10 show each.
