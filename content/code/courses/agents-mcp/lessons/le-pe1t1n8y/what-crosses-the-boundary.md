**Going in, with agents as tools: one question.** The orchestrator writes it, so its quality is the orchestrator's. *"Has order M-1043 shipped?"* is a good question; *"Check the customer's order"* would have left the specialist without the id. A specialist cannot ask the customer for something the question left out, because it cannot see the customer. Good orchestrator prompts tell it to make each question self-contained: ids, dates and constraints included.

**Coming back: one answer.** By default the specialist's final text, and nothing else: not the tool calls it made, not the results it read. The orchestrator trusts a summary of work it never saw. Section 08 shows that summary failing.

**In a handoff: the conversation.** Here the risk is the opposite one. The receiving agent may get more than it needs, including other agents' tool results and personal data, and it pays to read all of it on every request.

## Rules that follow

- **Make the question carry its own context.** Ids, the customer's exact constraint, what has already been tried.
- **Decide what an answer must contain.** A free-text sentence is the weakest form. A structured answer (status, facts, sources) or the evidence the host attaches (section 08) lets the receiving agent check instead of trust.
- **Pass the least data that does the job.** A specialist that only needs an order id should not receive the customer's address because it happened to be in the conversation. `ai-security` lesson 22 makes the same argument for data sent to a model at all; between agents it applies again at every boundary.
- **Record what crossed.** The trace should show each question and each answer at the boundary, because that is where a wrong answer is most often born.
