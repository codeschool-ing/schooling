title: ALTER SYSTEM, and the file that wins
version: 1

There is a third file, and it is the one that catches people. `ALTER SYSTEM` changes a parameter
from inside `psql`, with no editor and no `sudo`, by writing it into **`postgresql.auto.conf`,
a file in the data directory that the server reads after every other file**. Coming last, it
wins. A value set there overrides `postgresql.conf` and everything in `conf.d`, and nothing in
either of those files tells you so.

## What it does

Try the same typo as before, and then the correct value:

```
ana@db:~$ psql
ana=# ALTER SYSTEM SET work_mem = '64mb';
ERROR:  invalid value for parameter "work_mem": "64mb"
HINT:  Valid units for this parameter are "B", "kB", "MB", "GB", and "TB".

ana=# ALTER SYSTEM SET work_mem = '16MB';
ALTER SYSTEM

ana=# SELECT pg_reload_conf();
 pg_reload_conf 
----------------
 t
(1 row)

ana=# SHOW work_mem;
 work_mem 
----------
 16MB
(1 row)

ana=# \q
ana@db:~$ sudo cat /var/lib/postgresql/16/main/postgresql.auto.conf
# Do not edit this file manually!
# It will be overwritten by the ALTER SYSTEM command.
work_mem = '16MB'
```

Two differences from editing a file are visible at once. **`ALTER SYSTEM` checks the value before
it writes anything**: the typo that a file accepted until the next reload is refused here, with
the same hint. And it still applies nothing by itself. It wrote one line into the file, and
`pg_reload_conf()` applied it, exactly as a reload applies a line you typed in `conf.d`; a
`postmaster` parameter set this way waits for a restart in the same way.

Only a superuser may run it, unless granted the right for one parameter, and the file's own first line says how to treat it: the command
rewrites the whole file each time, so a line added by hand disappears at the next `ALTER SYSTEM`.

## Who wins

Now put a different value for the same parameter in your `conf.d` file, reload, and ask the
server which one it used:

```
ana@db:~$ echo 'work_mem = 8MB' | sudo tee -a /etc/postgresql/16/main/conf.d/50-course.conf
work_mem = 8MB
ana@db:~$ sudo systemctl reload postgresql
ana@db:~$ psql
ana=# SELECT seqno, sourcefile, sourceline, setting, applied
ana-#   FROM pg_file_settings
ana-#  WHERE name = 'work_mem';
 seqno |                    sourcefile                    | sourceline | setting | applied 
-------+--------------------------------------------------+------------+---------+---------
    27 | /etc/postgresql/16/main/conf.d/50-course.conf    |          4 | 8MB     | f
    28 | /var/lib/postgresql/16/main/postgresql.auto.conf |          3 | 16MB    | t
(2 rows)

ana=# SHOW work_mem;
 work_mem 
----------
 16MB
(1 row)

ana=# \q
```

`pg_file_settings` lists every line of every file in the order the server read them, and
`seqno` is that order. The `conf.d` line was read 27th and the `ALTER SYSTEM` one 28th, so
**`applied` is false for the first and true for the second**, and the 8 MB somebody just typed
does nothing. Picture a colleague who edits `conf.d`, reloads, sees no change, and starts to
suspect the server. The query above is the answer, and `sourcefile` in `pg_settings` gives the
same answer for the value in use.

The rule that avoids it is a choice per server, written down: **either files or `ALTER SYSTEM`,
not both**. This course uses files, because they can be read without connecting, compared between
two servers and kept in git (lesson 23). `ALTER SYSTEM` is the right tool where there is no
shell, and the wrong one to use now and then on a server whose configuration otherwise lives in
files.

## Below the files: a database, a role, a session

Three more layers sit under the files, and they are kept inside the database rather than on
disk. `ALTER DATABASE … SET` attaches a value to one database, `ALTER ROLE … SET` to one role,
and `SET` changes it for the current session only:

```
ana@db:~$ psql
ana=# ALTER DATABASE shop SET work_mem = '32MB';
ALTER DATABASE

ana=# ALTER DATABASE shop SET shared_buffers = '1GB';
ERROR:  parameter "shared_buffers" cannot be changed without restarting the server

ana=# \c shop
You are now connected to database "shop" as user "ana".

shop=# SELECT setting, unit, source FROM pg_settings WHERE name = 'work_mem';
 setting | unit |  source  
---------+------+----------
 32768   | kB   | database
(1 row)

shop=# SET work_mem = '64MB';
SET

shop=# SELECT setting, unit, source FROM pg_settings WHERE name = 'work_mem';
 setting | unit | source  
---------+------+---------
 65536   | kB   | session
(1 row)

shop=# ALTER DATABASE shop RESET work_mem;
ALTER DATABASE

shop=# ALTER SYSTEM RESET work_mem;
ALTER SYSTEM

shop=# SELECT pg_reload_conf();
 pg_reload_conf 
----------------
 t
(1 row)

shop=# \q
ana@db:~$ sudo cat /var/lib/postgresql/16/main/postgresql.auto.conf
# Do not edit this file manually!
# It will be overwritten by the ALTER SYSTEM command.
```

The database's value applies **when a connection to it starts**, which is why `\c shop` came
before the check, and `source` says `database`. The `SET` replaced it for this session alone,
and the next connection gets 32 MB again. A role's value works the same way and, where a role and
a database both set one, the role's wins. A `postmaster` parameter cannot be set like this at all:
`shared_buffers` is one pool of memory for every database, and the refusal says why in the words
of the previous section.

The two `RESET`s at the end took everything back out. `ALTER SYSTEM RESET` removed the line,
and `postgresql.auto.conf` is back to its two comments. The whole order, with the values this
section gave `work_mem`:
