---
title: ALTER SYSTEM, e o arquivo que vence
version: 1
---

Existe um terceiro arquivo, e é ele que pega as pessoas. O `ALTER SYSTEM` muda um parâmetro de
dentro do `psql`, sem editor e sem `sudo`, escrevendo-o no **`postgresql.auto.conf`, um arquivo no
diretório de dados que o servidor lê depois de todos os outros**. Como vem por último, ele vence.
Um valor definido ali sobrepõe o `postgresql.conf` e tudo que está no `conf.d`, e nada nesses
arquivos avisa você disso.

## O que ele faz

Tente o mesmo erro de antes, e depois o valor certo:

```
ana@db:~$ psql
ana=# ALTER SYSTEM SET work_mem = '64mb';
ERROR:  invalid value for parameter "work_mem": "64mb"
HINT:  Valid units for this parameter are "B", "kB", "MB", "GB", and "TB".

ana=# ALTER SYSTEM SET work_mem = '16MB';
ALTER SYSTEM

ana=# SELECT pg_reload_conf();
 pg_reload_conf 
----------------
 t
(1 row)

ana=# SHOW work_mem;
 work_mem 
----------
 16MB
(1 row)

ana=# \q
ana@db:~$ sudo cat /var/lib/postgresql/16/main/postgresql.auto.conf
# Do not edit this file manually!
# It will be overwritten by the ALTER SYSTEM command.
work_mem = '16MB'
```

Duas diferenças em relação a editar um arquivo aparecem de cara. **O `ALTER SYSTEM` confere o
valor antes de escrever qualquer coisa**: o erro que um arquivo aceitou até o próximo reload é
recusado aqui, com a mesma dica. E ele continua sem aplicar nada sozinho. Escreveu uma linha no
arquivo, e o `pg_reload_conf()` a aplicou, exatamente como um reload aplica uma linha que você
digitou no `conf.d`; um parâmetro `postmaster` definido assim espera um restart do mesmo jeito.

Só um superusuário pode rodá-lo, a menos que tenha recebido o direito para um parâmetro, e a
primeira linha do próprio arquivo diz como tratá-lo: o comando reescreve o arquivo inteiro a cada
vez, então uma linha acrescentada à mão some no próximo `ALTER SYSTEM`.

## Quem vence

Agora ponha um valor diferente para o mesmo parâmetro no seu arquivo do `conf.d`, dê reload e
pergunte ao servidor qual ele usou:

```
ana@db:~$ echo 'work_mem = 8MB' | sudo tee -a /etc/postgresql/16/main/conf.d/50-course.conf
work_mem = 8MB
ana@db:~$ sudo systemctl reload postgresql
ana@db:~$ psql
ana=# SELECT seqno, sourcefile, sourceline, setting, applied
ana-#   FROM pg_file_settings
ana-#  WHERE name = 'work_mem';
 seqno |                    sourcefile                    | sourceline | setting | applied 
-------+--------------------------------------------------+------------+---------+---------
    27 | /etc/postgresql/16/main/conf.d/50-course.conf    |          4 | 8MB     | f
    28 | /var/lib/postgresql/16/main/postgresql.auto.conf |          3 | 16MB    | t
(2 rows)

ana=# SHOW work_mem;
 work_mem 
----------
 16MB
(1 row)

ana=# \q
```

O `pg_file_settings` lista toda linha de todo arquivo na ordem em que o servidor as leu, e
`seqno` é essa ordem. A linha do `conf.d` foi lida em 27º lugar e a do `ALTER SYSTEM` em 28º,
então **`applied` é falso para a primeira e verdadeiro para a segunda**, e os 8 MB que alguém
acabou de digitar não fazem nada. Imagine um colega que edita o `conf.d`, dá reload, não vê
mudança e começa a desconfiar do servidor. A consulta acima é a resposta, e o `sourcefile` no
`pg_settings` dá a mesma resposta para o valor em uso.

A regra que evita isso é uma escolha por servidor, por escrito: **ou arquivos ou `ALTER SYSTEM`,
não os dois**. Este curso usa arquivos, porque dá para lê-los sem conectar, compará-los entre dois
servidores e guardá-los no git (lição 23). O `ALTER SYSTEM` é a ferramenta certa onde não há
shell, e a errada para usar de vez em quando num servidor cuja configuração, no resto, mora em
arquivos.

## Abaixo dos arquivos: um banco, um papel, uma sessão

Mais três camadas ficam abaixo dos arquivos, e são guardadas dentro do banco, não no disco. O
`ALTER DATABASE … SET` prende um valor a um banco, o `ALTER ROLE … SET` a um papel, e o `SET` o
muda só para a sessão atual:

```
ana@db:~$ psql
ana=# ALTER DATABASE shop SET work_mem = '32MB';
ALTER DATABASE

ana=# ALTER DATABASE shop SET shared_buffers = '1GB';
ERROR:  parameter "shared_buffers" cannot be changed without restarting the server

ana=# \c shop
You are now connected to database "shop" as user "ana".

shop=# SELECT setting, unit, source FROM pg_settings WHERE name = 'work_mem';
 setting | unit |  source  
---------+------+----------
 32768   | kB   | database
(1 row)

shop=# SET work_mem = '64MB';
SET

shop=# SELECT setting, unit, source FROM pg_settings WHERE name = 'work_mem';
 setting | unit | source  
---------+------+---------
 65536   | kB   | session
(1 row)

shop=# ALTER DATABASE shop RESET work_mem;
ALTER DATABASE

shop=# ALTER SYSTEM RESET work_mem;
ALTER SYSTEM

shop=# SELECT pg_reload_conf();
 pg_reload_conf 
----------------
 t
(1 row)

shop=# \q
ana@db:~$ sudo cat /var/lib/postgresql/16/main/postgresql.auto.conf
# Do not edit this file manually!
# It will be overwritten by the ALTER SYSTEM command.
```

O valor do banco vale **quando uma conexão a ele começa**, e é por isso que o `\c shop` veio antes
da conferência, e o `source` diz `database`. O `SET` o substituiu só para esta sessão, e a próxima
conexão recebe 32 MB de novo. O valor de um papel funciona do mesmo jeito e, quando um papel e um
banco definem os dois, vence o do papel. Um parâmetro `postmaster` não pode ser definido assim:
o `shared_buffers` é um único bloco de memória para todos os bancos, e a recusa diz por quê com
as palavras da seção anterior.

Os dois `RESET` do fim tiraram tudo de volta. O `ALTER SYSTEM RESET` removeu a linha, e o
`postgresql.auto.conf` voltou aos seus dois comentários. A ordem inteira, com os valores que esta
seção deu ao `work_mem`:
