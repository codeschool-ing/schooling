---
title: pg_stat_statements, and the restart it needs
version: 1
---

**`pg_stat_statements` keeps one row for every distinct statement the server has run**: how many
times, how long in total, how many rows. It answers the question a DBA is asked most often, *what
is the database spending its time on*, with numbers rather than a guess. This section installs it
and reads its top lines. Reading them well is a subject of its own, and it belongs to db-performance
lesson 2.

## Created, and not working

The extension creates like any other, and then refuses to answer:

```
shop=# CREATE EXTENSION pg_stat_statements;
CREATE EXTENSION

shop=# SELECT count(*) FROM pg_stat_statements;
ERROR:  pg_stat_statements must be loaded via shared_preload_libraries
```

The view exists; the code that fills it is not running. It has to be in the server from the first
moment, because it hooks into every backend and keeps its counts in shared memory that is sized at
start. So it goes in `shared_preload_libraries`, and the server is restarted.

## One letter, and the server does not start

`ALTER SYSTEM` checks that the value is a list of names. It does not check that a library by that
name exists, and nothing reads the list until the next start. Here is the same command with the
last letter missing:

```
shop=# ALTER SYSTEM SET shared_preload_libraries = 'pg_stat_statement';
ALTER SYSTEM
```

```sh
sudo systemctl restart postgresql@16-main
```

The restart stops the server and the start fails. The cluster is down and the log says why:

```
ana@db:~$ pg_lsclusters
Ver Cluster Port Status Owner    Data directory              Log file
16  main    5432 down   postgres /var/lib/postgresql/16/main /var/log/postgresql/postgresql-16-main.log
ana@db:~$ sudo tail -n 4 /var/log/postgresql/postgresql-16-main.log
2026-10-10 04:38:49.459 -03 [233] FATAL:  could not access file "pg_stat_statement": No such file or directory
2026-10-10 04:38:49.460 -03 [233] LOG:  database system is shut down
pg_ctl: could not start server
Examine the log output.
```

**Every connection now fails, and `ALTER SYSTEM` cannot repair it**, because it needs a running
server to talk to. The value lives in `postgresql.auto.conf` in the data directory, which lesson 5
showed is a plain file that the server reads after `postgresql.conf`. With the server down, editing
it by hand is the way out:

```
ana@db:~$ sudo cat /var/lib/postgresql/16/main/postgresql.auto.conf
# Do not edit this file manually!
# It will be overwritten by the ALTER SYSTEM command.
shared_preload_libraries = 'pg_stat_statement'
ana@db:~$ sudo sed -i 's/pg_stat_statement'"'"'/pg_stat_statements'"'"'/' /var/lib/postgresql/16/main/postgresql.auto.conf
ana@db:~$ sudo systemctl restart postgresql@16-main
ana@db:~$ pg_lsclusters
Ver Cluster Port Status Owner    Data directory              Log file
16  main    5432 online postgres /var/lib/postgresql/16/main /var/log/postgresql/postgresql-16-main.log
```

The quoting in the `sed` line only exists to put a single quote inside a single-quoted string;
`sudo nano` on the same file does the same job. **The habit worth taking from this is to check the
name before the restart**: `ls /usr/lib/postgresql/16/lib/pg_stat_statements.so` costs a second,
and on a production server the restart is the part that costs.

## What the application asks

```
shop=# SHOW shared_preload_libraries;
 shared_preload_libraries 
--------------------------
 pg_stat_statements
(1 row)

shop=# SELECT pg_stat_statements_reset();
 pg_stat_statements_reset 
--------------------------
 
(1 row)
```

`pg_stat_statements_reset()` empties the counts, so what follows measures only the workload below.
Something has to run first. `pgbench`, which came with the server, runs any SQL file as fast as it
can from several connections at once. Save this as `workload.sql`:

```sql
-- workload.sql: three queries an application might send to shop, for pgbench
\set cid random(1, 50000)
SELECT id, status, total_cents FROM orders WHERE customer_id = :cid ORDER BY created_at DESC LIMIT 10;
SELECT name, country FROM customers WHERE id = :cid;
SELECT count(*) FROM orders WHERE status = 'cancelled' AND total_cents > 49000;
```

`\set` is pgbench's own command: it picks a customer at random on every run, and `--random-seed`
makes the sequence the same each time. `-c 4` is four connections and `-t 50` is fifty runs of the
file on each, so every statement runs 200 times:

```
ana@db:~$ pgbench -n -c 4 -t 50 --random-seed=1 -f workload.sql shop
pgbench: setting random seed to 1
pgbench (16.15 (Ubuntu 16.15-0ubuntu0.24.04.1))
transaction type: workload.sql
scaling factor: 1

number of failed transactions: 0 (0.000%)

```

`-n` skips the vacuum pgbench otherwise runs on its own test tables, which `shop` does not have.
Now the counts:

```
shop=# SELECT calls, round(total_exec_time) AS total_ms,
shop-#        round(mean_exec_time::numeric, 2) AS mean_ms, rows,
shop-#        left(query, 50) AS query
shop-#   FROM pg_stat_statements
shop-#  ORDER BY total_exec_time DESC
shop-#  LIMIT 5;
 calls | total_ms | mean_ms | rows |                       query                        
-------+----------+---------+------+----------------------------------------------------
   200 |    25217 |  126.09 |  200 | SELECT count(*) FROM orders WHERE status = $1 AND 
   200 |      178 |    0.89 |  200 | SELECT name, country FROM customers WHERE id = $1
   200 |       98 |    0.49 | 2000 | SELECT id, status, total_cents FROM orders WHERE c
     1 |        0 |    0.07 |    1 | SELECT pg_stat_statements_reset()
(4 rows)
```

Three things to recognise in that table, and nothing more for now.

**The constants are gone.** Two hundred different customer ids became one row with `$1`, because
the extension groups statements by their shape after parsing. That is what makes the numbers
useful: an application sends the same query with a thousand different values, and a thousand rows
of one call each would say nothing.

**Total time and mean time answer different questions.** On the recording machine the count over
`orders` ran for 25217 ms in all, 126.09 ms a call, while the customer lookup by primary key took
0.89 ms a call. Ordered by total, the top row is
the one where an improvement saves the server the most; ordered by mean, the top row is the one a
user waits for longest.

**The numbers count since the last reset.** A clean restart keeps them, written to disk at
shutdown and read back at start; a crash loses them. `pg_stat_statements.max`, 5000 by default, is how many distinct statements it remembers
before it starts forgetting the least used. What to do about the top row — the plan, the missing
index — is db-performance's lessons 2 and 3.
