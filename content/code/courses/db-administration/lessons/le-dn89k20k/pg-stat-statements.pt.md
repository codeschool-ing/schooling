---
title: pg_stat_statements, e o restart que ele pede
version: 1
---

**O `pg_stat_statements` guarda uma linha para cada comando distinto que o servidor rodou**: quantas
vezes, quanto tempo no total, quantas linhas. Ele responde à pergunta que um DBA mais ouve, *com o
que o banco está gastando o tempo*, com números em vez de palpite. Esta seção o instala e lê as
primeiras linhas. Lê-las bem é um assunto à parte, e pertence à lição 2 de db-performance.

## Criada, e sem funcionar

A extensão é criada como qualquer outra, e depois se recusa a responder:

```
shop=# CREATE EXTENSION pg_stat_statements;
CREATE EXTENSION

shop=# SELECT count(*) FROM pg_stat_statements;
ERROR:  pg_stat_statements must be loaded via shared_preload_libraries
```

A view existe; o código que a preenche não está rodando. Ele precisa estar no servidor desde o
primeiro instante, porque se pendura em todo backend e guarda as contagens em memória compartilhada
dimensionada na partida. Então ele vai em `shared_preload_libraries`, e o servidor é reiniciado.

## Uma letra, e o servidor não sobe

O `ALTER SYSTEM` confere que o valor é uma lista de nomes. Ele não confere se existe uma biblioteca
com esse nome, e ninguém lê a lista até a próxima partida. Aqui está o mesmo comando com a última
letra faltando:

```
shop=# ALTER SYSTEM SET shared_preload_libraries = 'pg_stat_statement';
ALTER SYSTEM
```

```sh
sudo systemctl restart postgresql@16-main
```

O restart para o servidor e a partida falha. O cluster está parado e o log diz por quê:

```
ana@db:~$ pg_lsclusters
Ver Cluster Port Status Owner    Data directory              Log file
16  main    5432 down   postgres /var/lib/postgresql/16/main /var/log/postgresql/postgresql-16-main.log
ana@db:~$ sudo tail -n 4 /var/log/postgresql/postgresql-16-main.log
2026-10-10 16:46:09.571 -03 [233] FATAL:  could not access file "pg_stat_statement": No such file or directory
2026-10-10 16:46:09.571 -03 [233] LOG:  database system is shut down
pg_ctl: could not start server
Examine the log output.
```

**Toda conexão agora falha, e o `ALTER SYSTEM` não consegue consertar**, porque precisa de um
servidor rodando para conversar. O valor mora no `postgresql.auto.conf`, no diretório de dados, que
a lição 5 mostrou ser um arquivo comum que o servidor lê depois do `postgresql.conf`. Com o servidor
parado, editá-lo à mão é a saída:

```
ana@db:~$ sudo cat /var/lib/postgresql/16/main/postgresql.auto.conf
# Do not edit this file manually!
# It will be overwritten by the ALTER SYSTEM command.
shared_preload_libraries = 'pg_stat_statement'
ana@db:~$ sudo sed -i 's/pg_stat_statement'"'"'/pg_stat_statements'"'"'/' /var/lib/postgresql/16/main/postgresql.auto.conf
ana@db:~$ sudo systemctl restart postgresql@16-main
ana@db:~$ pg_lsclusters
Ver Cluster Port Status Owner    Data directory              Log file
16  main    5432 online postgres /var/lib/postgresql/16/main /var/log/postgresql/postgresql-16-main.log
```

As aspas na linha do `sed` só existem para pôr uma aspa simples dentro de uma string entre aspas
simples; um `sudo nano` no mesmo arquivo faz o mesmo serviço. **O hábito que vale tirar daqui é
conferir o nome antes do restart**: `ls /usr/lib/postgresql/16/lib/pg_stat_statements.so` custa um
segundo, e num servidor de produção o restart é a parte que custa.

## O que a aplicação pergunta

```
shop=# SHOW shared_preload_libraries;
 shared_preload_libraries 
--------------------------
 pg_stat_statements
(1 row)

shop=# SELECT pg_stat_statements_reset();
 pg_stat_statements_reset 
--------------------------
 
(1 row)
```

O `pg_stat_statements_reset()` zera as contagens, então o que vem a seguir mede só a carga abaixo.
Alguma coisa precisa rodar antes. O `pgbench`, que veio com o servidor, roda qualquer arquivo SQL o
mais rápido que consegue, de várias conexões ao mesmo tempo. Salve isto como `workload.sql`:

```sql
-- workload.sql: three queries an application might send to shop, for pgbench
\set cid random(1, 50000)
SELECT id, status, total_cents FROM orders WHERE customer_id = :cid ORDER BY created_at DESC LIMIT 10;
SELECT name, country FROM customers WHERE id = :cid;
SELECT count(*) FROM orders WHERE status = 'cancelled' AND total_cents > 49000;
```

O `\set` é um comando do próprio pgbench: ele sorteia um cliente a cada execução, e o
`--random-seed` faz a sequência ser a mesma toda vez. `-c 4` são quatro conexões e `-t 50` são
cinquenta execuções do arquivo em cada uma, então cada comando roda 200 vezes:

```
ana@db:~$ pgbench -n -c 4 -t 50 --random-seed=1 -f workload.sql shop
pgbench: setting random seed to 1
pgbench (16.15 (Ubuntu 16.15-0ubuntu0.24.04.1))
transaction type: workload.sql
scaling factor: 1
query mode: simple
number of clients: 4
number of threads: 1
maximum number of tries: 1
number of transactions per client: 50
number of transactions actually processed: 200/200
number of failed transactions: 0 (0.000%)
latency average = 102.582 ms
initial connection time = 15.554 ms
tps = 38.993059 (without initial connection time)
```

O `-n` pula o vacuum que o pgbench roda por conta própria nas tabelas de teste dele, que o `shop`
não tem. Agora as contagens:

```
shop=# SELECT calls, round(total_exec_time) AS total_ms,
shop-#        round(mean_exec_time::numeric, 2) AS mean_ms, rows,
shop-#        left(query, 50) AS query
shop-#   FROM pg_stat_statements
shop-#  ORDER BY total_exec_time DESC
shop-#  LIMIT 5;
 calls | total_ms | mean_ms | rows |                       query                        
-------+----------+---------+------+----------------------------------------------------
   200 |    19739 |   98.69 |  200 | SELECT count(*) FROM orders WHERE status = $1 AND 
   200 |       25 |    0.13 | 2000 | SELECT id, status, total_cents FROM orders WHERE c
   200 |       16 |    0.08 |  200 | SELECT name, country FROM customers WHERE id = $1
     1 |        0 |    0.06 |    1 | SELECT pg_stat_statements_reset()
(4 rows)
```

Três coisas para reconhecer nessa tabela, e nada mais por enquanto.

**As constantes sumiram.** Duzentos ids de cliente diferentes viraram uma linha com `$1`, porque a
extensão agrupa os comandos pela forma depois do parse. É isso que torna os números úteis: uma
aplicação manda a mesma consulta com mil valores diferentes, e mil linhas de uma chamada cada não
diriam nada.

**Tempo total e tempo médio respondem perguntas diferentes.** Na máquina da gravação, a contagem
sobre `orders` rodou 19739 ms ao todo, 98.69 ms por chamada, enquanto a busca do cliente pela chave
primária levou 0.08 ms por chamada. Ordenada pelo total, a linha do topo é aquela em que uma melhoria
poupa mais o servidor; ordenada pela média, a linha do topo é a que um usuário espera por mais tempo.

**Os números contam desde o último reset.** Um restart limpo os mantém, gravados em disco no
desligamento e lidos de volta na partida; uma queda os perde. O `pg_stat_statements.max`, 5000 por
padrão, é quantos comandos distintos ele lembra antes de começar a esquecer os menos usados. O que
fazer com a linha do topo — o plano, o índice que falta — é das lições 2 e 3 de db-performance.
