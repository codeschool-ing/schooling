---
title: The server cannot speak first
version: 1
---

Every exchange in HTTP starts with the client. The browser sends a request, the server sends a response,
and the exchange is over. That fits most of a shop: the customer asks for a page and gets it. It does
not fit the moments when **the news is on the server's side**: an order leaves the warehouse, a payment
is confirmed, the last bag of coffee is bought by somebody else, a support agent replies in a chat.

There are four ways around it, and they run from "ask often" to "keep a line open":

| technique | how the browser learns of an event | what it costs |
| --- | --- | --- |
| **polling** | it asks every few seconds, and usually hears "nothing new" | a request per client per interval, whatever happens |
| **long polling** | it asks, and the server holds the request open until there is news, then answers | one held request per client; a new request after each answer |
| **Server-Sent Events** | one response that never ends; the server writes each event into it | one open connection per client, server to client only |
| **WebSocket** | the connection is upgraded from HTTP to a channel both sides can send on | one open connection per client, both directions |

Two more are worth knowing by name. **Webhooks** solve the same problem between servers: the payment
gateway calls the shop's URL when a payment settles, instead of the shop asking. **WebTransport**, on
HTTP/3, is the newer, lower-level relative of WebSockets, still rare in shops.

The lab builds the four in one small service, so they can be compared on the same events.
