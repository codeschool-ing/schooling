---
title: O servidor não pode falar primeiro
version: 1
---

Toda troca no HTTP começa pelo cliente. O navegador manda uma requisição, o servidor manda uma resposta, e
a troca acaba. Isso serve à maior parte de uma loja: o cliente pede uma página e a recebe. Não serve aos
momentos em que **a novidade está do lado do servidor**: um pedido sai do armazém, um pagamento é
confirmado, o último pacote de café é comprado por outra pessoa, um atendente responde num chat.

Há quatro jeitos de contornar isso, e eles vão de "perguntar sempre" a "manter uma linha aberta":

| técnica | como o navegador fica sabendo de um evento | o que custa |
| --- | --- | --- |
| **polling** | pergunta a cada poucos segundos, e em geral ouve "nada de novo" | uma requisição por cliente por intervalo, aconteça o que acontecer |
| **long polling** | pergunta, e o servidor segura a requisição aberta até haver novidade, depois responde | uma requisição segurada por cliente; uma nova depois de cada resposta |
| **Server-Sent Events** | uma resposta que nunca termina; o servidor escreve cada evento nela | uma conexão aberta por cliente, só do servidor para o cliente |
| **WebSocket** | a conexão é promovida de HTTP a um canal em que os dois lados podem mandar | uma conexão aberta por cliente, nas duas direções |

Mais dois valem a pena conhecer pelo nome. Os **webhooks** resolvem o mesmo problema entre servidores: o
gateway de pagamento chama a URL da loja quando um pagamento é liquidado, em vez de a loja perguntar. O
**WebTransport**, sobre HTTP/3, é o parente mais novo e de mais baixo nível dos WebSockets, ainda raro em
lojas.

O laboratório constrói os quatro num serviço pequeno, para poderem ser comparados nos mesmos eventos.
