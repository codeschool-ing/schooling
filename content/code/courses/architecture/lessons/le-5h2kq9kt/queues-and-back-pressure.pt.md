A aula 5 descreveu o **nivelamento de carga por fila** (*queue-based load levelling*): uma fila entre uma
fonte irregular e um worker constante deixa o worker ser dimensionado pela média e não pelo pico. A loja
recebe pedidos assim: `POST /order` põe o pedido numa fila e responde `202 Accepted` na hora, e um worker
trata dez pedidos por segundo atrás dela.

Mande uma rajada de cem pedidos, todos de uma vez, e pergunte à loja como foi quando a fila esvaziar:

```
ana@vm:~/lab/bulkheads$ docker compose up -d
 Container bulkheads-stock-1 Running 
 Container bulkheads-shop-1 Recreate 
 Container bulkheads-shop-1 Recreated 
 Container bulkheads-shop-1 Starting 
 Container bulkheads-shop-1 Started 
ana@vm:~/lab/bulkheads$ $L burst 100
orders     202: 100                 median    13 ms, slowest   133 ms
ana@vm:~/lab/bulkheads$ sleep 11; curl -s localhost:8002/orders
handled 100, waiting 0, longest wait 9.9 s
```

Todo pedido foi aceito, rápido, que é para isso que a fila serve. Mas **o último esperou 9,9 segundos**
antes de ser tratado. Cem pedidos a dez por segundo são dez segundos de trabalho, e a fila transformou a
rajada em espera, que é a única coisa em que uma fila consegue transformá-la. Com uma rajada de 10.000, o
último pedido espera dezesseis minutos, todos ouviram "aceito", e a memória da fila cresce o tempo todo.

**Uma fila sem limite não elimina a sobrecarga; ela a esconde**, como atraso, de todos que poderiam ter
feito alguma coisa. A janela da aula 9 tinha a mesma forma: o comprimento da fila vezes o tempo por item.

## Um limite, e dizer isso

Reinicie a loja com espaço para vinte pedidos, e mande a mesma rajada:

```
ana@vm:~/lab/bulkheads$ QUEUE=20 docker compose up -d
 Container bulkheads-stock-1 Running 
 Container bulkheads-shop-1 Recreate 
 Container bulkheads-shop-1 Recreated 
 Container bulkheads-shop-1 Starting 
 Container bulkheads-shop-1 Started 
ana@vm:~/lab/bulkheads$ $L burst 100
orders     202: 23, 503: 77         median    16 ms, slowest  1063 ms
ana@vm:~/lab/bulkheads$ sleep 4; curl -s localhost:8002/orders
handled 23, waiting 0, longest wait 2.1 s
```

Vinte e três foram aceitos (o worker tirou alguns da fila enquanto a rajada ainda chegava, o que abriu
espaço para outros tantos), e esperaram
**2,1 segundos no máximo**. Os outros 77 foram recusados na hora com `503` e `Retry-After: 2`. Isso é
**back pressure**: o limite do sistema volta a quem está produzindo o trabalho, no momento em que é
alcançado, para o produtor ir mais devagar, tentar depois, ou avisar uma pessoa. Um pedido recusado é uma
resposta clara em milissegundos; um aceito que é tratado em dezesseis minutos é uma promessa que a loja
não conseguiu cumprir.

A back pressure existe em toda camada, com nomes diferentes:

| camada | como a pressão volta |
| --- | --- |
| TCP | a janela do receptor encolhe, e o remetente para de mandar |
| HTTP | `429` ou `503` com `Retry-After` |
| Kafka | consumidores puxam, então um consumidor lento simplesmente fica para trás; o produtor não fica sabendo de nada, e o lag é o que observar |
| RabbitMQ | uma fila com `x-max-length` recusa ou descarta; um broker com pouca memória bloqueia os publicadores |
| reactive streams (Reactor, RxJava, Akka Streams) | o consumidor pede os próximos *n* itens, e o produtor não manda mais que isso |

A linha do Kafka é a que se esquece. Um log que nunca recusa é uma fila sem limite: absorve qualquer
rajada, e o lag do consumidor, da aula 9, é o único lugar onde a pressão aparece.
