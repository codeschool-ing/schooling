Lesson 5 described **queue-based load levelling**: a queue between a spiky source and a steady worker
lets the worker be sized for the average rather than the peak. The shop takes orders that way:
`POST /order` puts the order on a queue and answers `202 Accepted` at once, and one worker handles ten orders
a second behind it.

Send a burst of a hundred orders, all at once, and ask the shop how it went once the queue is empty:

```
ana@vm:~/lab/bulkheads$ docker compose up -d
 Container bulkheads-stock-1 Running 
 Container bulkheads-shop-1 Recreate 
 Container bulkheads-shop-1 Recreated 
 Container bulkheads-shop-1 Starting 
 Container bulkheads-shop-1 Started 
ana@vm:~/lab/bulkheads$ $L burst 100
orders     202: 100                 median    13 ms, slowest   133 ms
ana@vm:~/lab/bulkheads$ sleep 11; curl -s localhost:8002/orders
handled 100, waiting 0, longest wait 9.9 s
```

Every order was accepted, quickly, which is what the queue is for. But **the last one waited 9.9
seconds** before it was handled. A hundred orders at ten a second is ten seconds of work, and the queue
turned the burst into waiting, which is the only thing a queue can turn it into. With a burst of
10,000, the last order waits sixteen minutes, every one of them was told "accepted", and the queue's
memory grows the whole time.

**An unbounded queue does not remove overload; it hides it**, as delay, from everybody who could have
done something about it. Lesson 9's window had the same shape: the queue's length times the time per
item.

## A bound, and saying so

Restart the shop with room for twenty orders, and send the same burst:

```
ana@vm:~/lab/bulkheads$ QUEUE=20 docker compose up -d
 Container bulkheads-stock-1 Running 
 Container bulkheads-shop-1 Recreate 
 Container bulkheads-shop-1 Recreated 
 Container bulkheads-shop-1 Starting 
 Container bulkheads-shop-1 Started 
ana@vm:~/lab/bulkheads$ $L burst 100
orders     202: 23, 503: 77         median    16 ms, slowest  1063 ms
ana@vm:~/lab/bulkheads$ sleep 4; curl -s localhost:8002/orders
handled 23, waiting 0, longest wait 2.1 s
```

Twenty-three were accepted (the worker took a few off the queue while the burst was still arriving,
which made room for as many more), and they waited **2.1 seconds at most**. The other 77 were refused at once with `503` and
`Retry-After: 2`. That is **back pressure**: the system's limit travels back to whoever is producing the
work, at the moment it is reached, so the producer can slow down, try later, or tell a person. A
refused order is a clear answer in milliseconds; an accepted one that is handled in sixteen minutes is a
promise the shop could not keep.

Back pressure exists at every layer, under different names:

| layer | how the pressure goes back |
| --- | --- |
| TCP | the receiver's window shrinks, and the sender stops sending |
| HTTP | `429` or `503` with `Retry-After` |
| Kafka | consumers pull, so a slow consumer simply falls behind; the producer is told nothing, and lag is what to watch |
| RabbitMQ | a queue with `x-max-length` refuses or drops; a broker short of memory blocks its publishers |
| reactive streams (Reactor, RxJava, Akka Streams) | the consumer asks for the next *n* items, and the producer sends no more than that |

The Kafka row is the one people forget. A log that never refuses is a queue without a bound: it absorbs
any burst, and the consumer's lag, from lesson 9, is the only place the pressure shows.
