Toda requisição deste laboratório foi para um endereço, `localhost:8080`, e o gateway decidiu que
instância a respondia. Esse é o primeiro trabalho do gateway, **rotear**: o cliente conhece um endereço,
e o gateway transforma um caminho como `/stock` numa instância do serviço certo, achada no registro.

Como toda requisição passa por ele, o gateway também é o lugar natural para tudo o que toda requisição
precisa e nenhum serviço deveria implementar separadamente:

| trabalho | por que no gateway |
| --- | --- |
| rotear por caminho ou host | os clientes conhecem um endereço; os serviços podem se mudar e se dividir atrás dele |
| terminar o TLS | os certificados moram num lugar, renovados num lugar |
| conferir quem chama | um token é validado uma vez, e os serviços recebem uma identidade conferida |
| limitar taxas | por cliente, antes de qualquer serviço gastar alguma coisa, como a aula 12 argumentou |
| pôr um id de requisição | todo serviço registra o mesmo id para a mesma requisição, aula 7 do curso `scale` |
| moldar respostas para um cliente | um **backend for frontend**: um gateway por tipo de cliente, celular e web |

Dois avisos vêm junto. O gateway agora está **no caminho de toda requisição**, então tem de estar pelo
menos tão disponível quanto qualquer coisa atrás dele, o que significa várias instâncias atrás de um
balanceador simples. E ele atrai lógica: quando há um lugar por onde toda requisição passa, regras de
negócio se infiltram nele, um desconto aqui, um caso especial ali, até ele virar um monólito sem dono.
**Mantenha o gateway no trabalho transversal**; qualquer coisa que saiba o que é um pedido pertence a um
serviço.

Os produtos: gateways baseados em **Kong**, **Traefik**, **NGINX** e **Envoy** rodam em qualquer lugar; o
**AWS API Gateway**, o **Google API Gateway** e o **Azure API Management** são gerenciados; e a **Gateway
API** do Kubernetes é o jeito padrão de configurar qualquer um deles dentro de um cluster.
