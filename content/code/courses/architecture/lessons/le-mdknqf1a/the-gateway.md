Every request in this lab went to one address, `localhost:8080`, and the gateway decided which instance
answered it. That is the gateway's first job, **routing**: the client knows one address, and the
gateway turns a path such as `/stock` into an instance of the right service, found in the registry.

Because every request passes through it, the gateway is also the natural place for everything that
every request needs and no service should implement separately:

| job | why at the gateway |
| --- | --- |
| route by path or host | the clients know one address; services can move and split behind it |
| terminate TLS | certificates live in one place, renewed in one place |
| check who is calling | a token is validated once, and the services receive a verified identity |
| limit rates | per client, before any service spends anything, as lesson 12 argued |
| add a request id | every service logs the same id for the same request, lesson 7 of the `scale` course |
| shape responses for one client | a **backend for frontend**: one gateway per kind of client, phone and web |

Two warnings come with it. The gateway is now **on the path of every request**, so it has to be at
least as available as anything behind it, which means several instances behind a plain load balancer.
And it attracts logic: once there is one place every request passes through, business rules creep into
it, a discount here, a special case there, until it is a monolith nobody owns. **Keep the gateway to
cross-cutting work**; anything that knows what an order is belongs in a service.

The products: **Kong**, **Traefik**, **NGINX** and **Envoy**-based gateways run anywhere; **AWS API
Gateway**, **Google API Gateway** and **Azure API Management** are managed; and Kubernetes's **Gateway
API** is the standard way to configure any of them inside a cluster.
