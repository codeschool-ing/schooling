---
title: Where is the stock service?
version: 1
---

In lesson 2 the catalogue called `http://stock:8000`, and Docker's own DNS turned `stock` into the one
container's address. That is **discovery by configuration**: somebody writes the address down, and
everything works while the address does not change.

In production it changes all the time. There are several instances of the stock service for capacity
and for failures. An autoscaler adds two at lunchtime and removes them at night. A deploy replaces every
instance with a new one, at a new address. A machine dies and its instances start somewhere else. And
some instances are running but unwell: started and not yet ready, or up and unable to reach their
database. A list of addresses in a file is out of date within the hour.

So a system with many services keeps a **service registry**: a small database of which instances exist
for each service, where they are, and whether each is healthy at this moment. Instances are added to it
when they start and removed when they stop or fail their checks, and everything that needs to call a
service asks it.

There are two places the asking can happen:

| | client-side discovery | server-side discovery |
| --- | --- | --- |
| who asks the registry | the caller, through a library | a load balancer or gateway in between |
| who chooses the instance | the caller | the thing in between |
| what the caller knows | the registry's address | one address, the one in between |
| examples | Netflix's Eureka with its client; a service mesh's sidecar (lesson 15) | Kubernetes Services; a gateway like the lab's |
| the cost | a library in every language the services are written in | one more hop, and one more thing that must stay up |

The lab does server-side: the services register themselves, and a gateway reads the registry and does
the choosing. It also shows the client side, with a small program that asks the registry directly.
