title: Adding a shard
version: 1

A sharded system grows by adding shards, and the router's function, `crc32(customer) % 2`, has the
number of shards in it. Change it to 3 and ask how many customers would now live somewhere else:

```
ana@vm:~/lab/shards$ $R moves 3
27 of 40 customers change shard going from 2 shards to 3
```

**27 of 40**, two thirds, which is what modulo predicts: going from N shards to N + 1, a key keeps its
shard only by coincidence. Every one of those customers' orders has to be copied to its new shard while
the shop keeps running, and until the copy is done the router has to know which customers have moved.
Adding one machine to grow by a third moves two thirds of the data.

There are two well-known ways around it, and both are in products you will use:

- **Many fixed partitions, fewer machines.** Split the keys into many more partitions than you have
  machines, say 12 or 256, and never change that number; a partition is the unit that moves. Adding a
  machine means handing it some whole partitions from the others, and no key ever changes partition.
  This is Kafka's model, where a topic's partition count is chosen up front for this reason, and how
  Elasticsearch and Couchbase spread data.
- **Consistent hashing.** Place the machines and the keys on the same circle of hash values, and give
  each key to the next machine round the circle. A new machine takes over the keys between it and its
  neighbour, so only about 1/N of the keys move. This is Dynamo's design, and Cassandra's.

Either way, **choosing the number of partitions is the decision that is expensive to change**, much
like the shard key, so it is usually set well above what is needed today.

## Moving data while it is used

Whatever decides where keys go, the move itself is the same careful sequence: copy the partition to its
new machine, keep copying the changes made during the copy, switch the router for that partition, and
only then delete the old copy. Databases that shard themselves do this for you, and it still costs
network and disk while it runs. In the lab's router, nothing does it, which is the point at which most
teams stop writing their own.
