O laboratório guarda os pedidos da Quitanda do jeito do event sourcing, num servidor PostgreSQL: uma
tabela `events` para o lado de escrita e dois modelos de leitura ao lado. Um programa pequeno roda os
comandos, constrói os modelos de leitura, e mostra um pedido em qualquer versão. Ele fica em
`~/lab/events`:

```sh
mkdir -p ~/lab/events && cd ~/lab/events
```

`schema.sql`:

```schooling-example
{"language": "sql", "file": "schema.sql", "parts": [{"code": "CREATE TABLE events (\n    position bigserial PRIMARY KEY,\n    stream   text NOT NULL,\n    version  int NOT NULL,\n    type     text NOT NULL,\n    data     jsonb NOT NULL,\n    at       timestamptz NOT NULL DEFAULT now(),\n    UNIQUE (stream, version)\n);\n\nCREATE TABLE order_summary (\n    id     text PRIMARY KEY,\n    status text NOT NULL,\n    items  int NOT NULL,\n    cents  int NOT NULL\n);\n\nCREATE TABLE units_sold (\n    product text PRIMARY KEY,\n    units   int NOT NULL\n);\n\nCREATE TABLE checkpoint (\n    projection text PRIMARY KEY,\n    position   bigint NOT NULL\n);", "note": "O lado de escrita é uma tabela, `events`, e ela nunca é atualizada: toda mudança num pedido é uma linha nova. `(stream, version)` é única, então dois escritores não conseguem acrescentar os dois a versão 3 do mesmo pedido. O lado de leitura são duas tabelas construídas a partir dos eventos, e um checkpoint dizendo até onde a construção chegou."}]}
```

Suba o banco, dê uns dez segundos, e guarde numa variável o comando do programa:

```sh
docker compose up -d
O="docker compose --progress quiet run --rm tools python orders.py"
```
