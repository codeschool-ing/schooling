---
title: Four ways to render a page
version: 1
---

**A SvelteKit page can be rendered on the server, in the browser, or both, and the server's rendering
can happen on each request or once, at build time.** Every page of the planner so far has had the
default: the server renders the HTML for the first request, and the browser **hydrates** it, runs the
same components over the HTML it received and takes over from there. Lesson 13 watched the second half
happen when a universal load function printed its line in both places.

Two **page options**, `ssr` and `csr`, switch the halves on and off, and a third, `prerender`, moves the
server's half to build time. They are exported from a `+page.js`, `+page.server.js`, `+layout.js` or
`+layout.server.js`, and a layout's value applies to every page under it unless a page says otherwise:

| `ssr` | `csr` | `prerender` | the first response | JavaScript in the browser |
|---|---|---|---|---|
| `true` | `true` | `false` | HTML rendered for this request | hydrates it, then handles every click |
| `true` | `false` | `false` | HTML rendered for this request | **none** |
| `false` | `true` | `false` | an empty page | renders everything |
| `true` | either | `true` | HTML rendered **when the site was built**, from a file | as `csr` says |

**The default is the right answer for the planner's own pages**, and the rest of this lesson shows why
by trying the others. The page that can do with less is About: it has no data, no state, no form and
nothing to click except two links, so it needs no JavaScript at all and can be written to a file once,
when the application is built.

To see what each option really sends, the measurements in this lesson are taken from a **build**, the
code as it would be deployed, rather than from the dev server, which adds its own scripts to every page
so that it can update them as you save. A build needs an adapter that produces something runnable, and
the planner does not have one yet. The next section fixes that.
