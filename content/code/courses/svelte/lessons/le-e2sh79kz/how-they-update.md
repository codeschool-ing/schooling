title: How each one finds out what changed
version: 1
---

**When `minutes` changes, the paragraph must say so, and the four frameworks find that paragraph in
four different ways.** Lesson 2 described two of them; the other two sit between.

**Svelte compiles the answer in.** The compiler reads the component, sees that one text node depends on
`minutes`, and writes an effect that sets that text node when `minutes` changes, as lesson 1 read in the
compiled output. At run time a signal knows who reads it, and a change runs exactly the code that
depends on it. Nothing else in the component runs again.

**React runs the component again.** A change of state calls the whole `Counter` function once more,
which returns a new description of the page, and React compares it with the previous one, the virtual
DOM of lesson 2, to find the text that differs. Everything in the function body runs on every change,
which is why React has `useMemo` and `useCallback` for work that should not be repeated, and why the
rules of hooks exist: the order of the calls is how React tells one `useState` from the next. The React
course spends lessons 3 to 7 on this model and lesson 21 on keeping it fast.

**Vue tracks reads with proxies and then re-renders the component.** A `ref` or a `reactive` object
records which component read it, much as a Svelte signal does, so Vue knows exactly which components a
change affects. Inside each of those it re-runs the template's render function and compares virtual DOM,
with the compiler marking which parts of the template can never change so that the comparison skips
them. It is a middle position: precise about which component, comparing within it. Vue 3.6, a release
candidate as this is written, adds a second way to compile components, Vapor mode, which updates the
DOM directly as Svelte does. Vue's course covers the reactivity system in lessons 2 to 4.

**Angular has signals, and an older model beside them.** Its signals work as Svelte's do: a read is
tracked, and a change marks exactly what depends on it. Underneath, Angular grew up with **zone.js**,
which noticed every event and timer in the page and checked every component for changes afterwards;
new applications now run without it, and the generator used for the counter here made one that does.
Code written over the last decade still runs with it, and the Angular course gives lesson 6 to signals
and lesson 7 to change detection, zones included.

**None of this is visible in a counter**, and little of it in the planner: all four update a page of
this size faster than a person can see. It matters in two places. One is a page with a great deal on
it, where re-running and comparing large components costs real time and the frameworks that track
reads precisely have less to do. The other is the code a person writes. In React, the component
function runs again and again, so it has to be written to survive that; in Svelte the script runs once,
which is why `$state` can be a plain `let` and why lesson 3's warning was about reading a value outside
the places that track it, rather than about running too often.
