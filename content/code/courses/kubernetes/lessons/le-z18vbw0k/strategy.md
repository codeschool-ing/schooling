title: Two numbers decide how pods are replaced
version: 1

A Deployment changes versions by creating a new ReplicaSet and moving the replicas across, a few at a
time. **How many at a time is set by two fields under `strategy.rollingUpdate`:**

- `maxSurge` is how many pods may exist **above** `replicas` during the change.
- `maxUnavailable` is how many of the `replicas` may be **not ready** during the change.

Both take a number or a percentage, and both default to `25%`. The shop below uses four replicas, at most
one extra and none missing:

```schooling-example

```

```
ana@laptop:~/shop$ kubectl apply -f shop.yaml
deployment.apps/shop created
service/shop created
ana@laptop:~/shop$ kubectl get rs -l app=shop
NAME              DESIRED   CURRENT   READY   AGE
shop-6ff4fb647d   4         4         4       3s
```

With those numbers there is only one way to proceed. The controller may add one pod, so it does. It may
not lose one, so no old pod goes until the new one is ready. Then it may add another, and so on:

Setting both to `0` is refused, because then nothing could ever move. Raising `maxSurge` makes the change
faster and needs room on the nodes for the extra pods. Raising `maxUnavailable` needs no room and runs
the service on fewer pods while it lasts. **The first spends capacity; the second spends headroom.**

## Counting the requests

To see what an update costs a client, the next block sends three hundred requests to the Service, a
tenth of a second apart, from the `probe` pod. Three seconds in, the image is changed from a second
terminal; that command appears after the count because the count only prints when it ends:

```
ana@laptop:~/shop$ kubectl exec probe -- sh -c "for i in \$(seq 300); do wget -qO- -T 2 shop || echo FAILED; sleep 0.1; done" | cut -d" " -f1,2 | sort | uniq -c
wget: download timed out
      1 FAILED
     40 shop 1.0
    259 shop 1.1
ana@laptop:~/shop$ kubectl set image deployment/shop shop=shop:1.1
deployment.apps/shop image updated
ana@laptop:~/shop$ kubectl get rs -l app=shop
NAME              DESIRED   CURRENT   READY   AGE
shop-6ff4fb647d   0         0         0       37s
shop-7b9858cc8f   4         4         4       31s
```

The old ReplicaSet is still there with `0` replicas. That is what makes going back possible, and the
last section uses it. One request out of three hundred failed, and the error was a timeout. The next
section is about that one request.

`strategy.type` has one other value, `Recreate`, which removes every old pod before creating any new
one. It means downtime, and it exists for the application that cannot run two versions at once, such as
one that migrates its database on start.
