A aula 1 disse que o modelo do Terraform tem quatro partes: uma descrição, um provider para cada API,
um plano que você lê antes de qualquer coisa acontecer, e um state que lembra o que foi feito. **Cada
ferramenta desta aula mantém quase tudo isso e muda uma ou duas partes**, e esse é o jeito mais
rápido de não confundi-las. O OpenTofu não muda nenhuma das quatro; muda a licença e quem decide. O
CloudFormation leva o motor e o state para dentro da AWS. O CDK troca a descrição por um programa que
escreve uma para o CloudFormation. O Pulumi troca a descrição por um programa e mantém o motor, os
providers e um state próprio.

Os mesmos fatos numa tabela, com a licença sob a qual cada uma é distribuída, lida dos arquivos que
esta aula abriu onde o laboratório os tinha:

| | você escreve | o passo de revisão | o state fica em | nuvens | licença, mantenedor |
|---|---|---|---|---|---|
| **Terraform** | HCL | `terraform plan` | um arquivo, num backend à sua escolha | qualquer uma com provider | BSL 1.1, HashiCorp (IBM) |
| **OpenTofu** | HCL | `tofu plan` | o mesmo arquivo, criptografável | qualquer uma com provider | MPL 2.0, um projeto da Linux Foundation |
| **CloudFormation** | YAML ou JSON | um change set | a stack, dentro da AWS | AWS | um serviço, AWS |
| **AWS CDK** | TypeScript, JavaScript, Python, Java, C#, Go | `cdk diff` | a stack, dentro da AWS | AWS | Apache 2.0, AWS |
| **Pulumi** | as mesmas linguagens, ou YAML | `pulumi preview` | Pulumi Cloud, um bucket ou um diretório | qualquer uma com provider | Apache 2.0, Pulumi |

## O que decide na prática

**Se tudo o que você gerencia é AWS.** A infraestrutura da loja não é só AWS: a aula 2 encontrou
providers que geram um nome aleatório e escrevem um arquivo local, e uma empresa de verdade soma DNS,
uma CDN, monitoramento e a organização no GitHub. O CloudFormation e o CDK alcançam a AWS. Terraform,
OpenTofu e Pulumi alcançam qualquer coisa que tenha um provider, e por isso uma única configuração
consegue guardar tudo isso.

**Quem deve guardar o state.** Com o CloudFormation e o CDK não há state para você armazenar, travar,
criptografar ou perder, e boa parte da aula 7 fica sem ter onde se aplicar. É uma economia real para
um time pequeno que vive numa só conta da AWS.

**Em que linguagem o time deve escrever.** O HCL é limitado de propósito: tem expressões e não tem
comandos, então uma configuração consegue dizer o que deve existir e não consegue fazer mais nada no
caminho. Uma linguagem de uso geral dá classes, testes na mesma linguagem e um gerenciador de pacotes,
e também todas as maneiras de um programa deixar de ser uma descrição. Nenhuma das duas é melhor; elas
falham de jeitos diferentes.

**A licença, para alguns.** Para uma empresa que usa o Terraform na própria infraestrutura, a
concessão da BSL cobre o que ela faz. Ela importa para uma empresa que vende Terraform a terceiros, e
para quem quer a ferramenta governada por uma fundação e não por um fornecedor. São esses os motivos
de o OpenTofu existir, e a criptografia do state é um recurso que dá a um time comum um motivo próprio.

**O custo de mudar de ideia.** Do Terraform para o OpenTofu é barato hoje, como esta aula mediu: os
mesmos arquivos e o mesmo state. Qualquer outra mudança é reescrever a descrição e importar cada
recurso existente para o state da ferramenta nova, o trabalho que a aula 8 fez para um bucket, repetido
para tudo. Escolha com isso em mente, e conte com viver com a escolha.
