Lesson 1 said Terraform's model has four parts: a description, a provider for each API, a plan you
read before anything happens, and a state that remembers what was made. **Each tool in this lesson
keeps most of that and changes one or two parts**, and that is the quickest way to hold them apart.
OpenTofu changes none of the four; it changes the licence and who decides. CloudFormation moves the
engine and the state into AWS. The CDK replaces the description with a program that writes one for
CloudFormation. Pulumi replaces the description with a program and keeps the engine, the providers
and a state of its own.

The same facts as a table, with the licence each one ships under, read from the files this lesson
opened where the lab had them:

| | you write | the review step | state kept in | clouds | licence, maintainer |
|---|---|---|---|---|---|
| **Terraform** | HCL | `terraform plan` | a file, in a backend you choose | any with a provider | BSL 1.1, HashiCorp (IBM) |
| **OpenTofu** | HCL | `tofu plan` | the same file, encryptable | any with a provider | MPL 2.0, a Linux Foundation project |
| **CloudFormation** | YAML or JSON | a change set | the stack, inside AWS | AWS | a service, AWS |
| **AWS CDK** | TypeScript, JavaScript, Python, Java, C#, Go | `cdk diff` | the stack, inside AWS | AWS | Apache 2.0, AWS |
| **Pulumi** | the same languages, or YAML | `pulumi preview` | Pulumi Cloud, a bucket or a directory | any with a provider | Apache 2.0, Pulumi |

## What decides it in practice

**Whether everything you manage is AWS.** The shop's infrastructure is not only AWS: lesson 2 met
providers that generate a random name and write a local file, and a real company adds DNS, a CDN,
monitoring and its GitHub organisation. CloudFormation and the CDK reach AWS. Terraform, OpenTofu and
Pulumi reach anything that has a provider, which is why one configuration can hold all of it.

**Who should keep the state.** With CloudFormation and the CDK there is no state for you to store,
lock, encrypt or lose, and most of lesson 7 has nothing to apply to. That is a real saving for a
small team that lives in one AWS account.

**What language the team should write in.** HCL is limited on purpose: it has expressions and no
statements, so a configuration can say what should exist and cannot do anything else on the way. A
general-purpose language gives you classes, tests in the same language and a package manager, and also every way a program can stop
being a description. Neither is better; they fail differently.

**The licence, for some.** For a company using Terraform on its own infrastructure, the BSL's grant
covers what it does. It matters to a company that sells Terraform to others, and to anybody who wants
the tool governed by a foundation rather than by a vendor. Those are the reasons OpenTofu exists, and
state encryption is a feature that gives an ordinary team a reason of its own.

**The cost of changing your mind.** Terraform to OpenTofu is cheap today, as this lesson measured:
the same files and the same state. Every other move is a rewrite of the description and an import of
every existing resource into the new tool's state, the work lesson 8 did for one bucket, repeated for
everything. Choose with that in mind, and expect to live with the choice.
