Lesson 18 configures machines from Ana's laptop: Ansible connects over SSH, does its work and
leaves, and nothing happens again until she runs it again. The three tools in this lesson were
mostly built the other way round. **An agent lives on every machine, asks a server what that
machine should look like, and applies the answer, on a timer, whether or not anybody is watching.**

That reads like a detail of transport, SSH in one case and an agent's connection in the other. It
decides more than transport: who starts the conversation decides how often the description is
compared with the machine, and that decides how long a hand edit survives.

## Pull: the agent asks

Puppet is the clearest case. Its agent, `puppet agent`, runs on each machine, connects to a Puppet
server, sends the facts it has gathered about the machine, and gets back the full list of resources
that machine should have. The defaults say how that conversation is set up:

```
ana@laptop:~$ puppet config print --section agent runinterval server certname
certname = laptop
runinterval = 1800
server = puppet
```

`runinterval` is in seconds: **1800 is a run every thirty minutes**, on every machine, for as long as
the agent is running. `server = puppet` is where the agent looks if nobody tells it otherwise, a host
literally called `puppet`. `certname` is the name the machine is known by; the lab sets it to `laptop`
in Ana's `puppet.conf` so that it matches the prompt. The name matters because the agent
proves who it is with a certificate signed by a certificate authority that, by default, the Puppet
server runs, so adding a machine to a pull setup means a new certificate as well as a new agent.

Chef has the same shape: `chef-client` on each machine, a Chef Infra Server holding the cookbooks,
a run on a timer. **Salt sits in between.** Its agent, the minion, opens a connection to the master and
keeps it open, and the master publishes commands down it; a minion runs what it is sent at once.
That gives Salt the immediacy of a push over a connection the machine opened itself. Salt also has
`salt-ssh` for machines with no minion at all, and Ansible has `ansible-pull` going the other way, so
the line between the two models is a default, not a wall.

## What the timer buys, and what it costs

An agent that runs every half hour is a machine that **puts itself back**. Somebody edits nginx's file
by hand at 10:12; at the next run the agent finds a difference and writes the file as described. With
push, the same edit stays until somebody runs the playbook again, which may be tomorrow and may be
never.

That is the strongest argument for an agent, and it cuts both ways. The edit at 10:12 might have been
the fix for an outage, made at night by the person on call. The agent undoes it with the same
confidence it undoes a mistake, because it has no way to tell them apart. **A pull setup only works if
everybody knows that the description is the one place a change can last**, which is the cure lesson 1
named for drift, enforced twice an hour.

The costs are the ones you would expect from software on every machine. The agent has to be installed,
upgraded and kept running; the server has to be run, backed up and reachable by every machine; the
certificates have to be issued and revoked. Push needs none of that, and pays instead at the moment of
the run: the control machine must reach every target then, over SSH, with a key that works.

## Without a server

All three tools can also run on one machine with no server, reading the description from its own
disk: `puppet apply`, `salt-call --local`, and Chef's local mode. That is how this lesson runs them,
because the lab is one laptop. The resources, the language and the run are the same; only the
question "where does the description come from" has a different answer.
