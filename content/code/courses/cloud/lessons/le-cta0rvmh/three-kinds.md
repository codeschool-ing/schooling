---
title: Three interfaces, not three disks
version: 1
---

The picture most people bring is that storage is a disk: something with a capacity in gigabytes
that a machine writes files onto. In a cloud that picture fits one of three services and misleads
about the other two. What separates them is not the hardware underneath, which you never see. It
is **the interface a program uses to reach the data**, and with it the kind of address each piece
of data has.

**Block storage** hands a machine a device. The operating system sees an empty disk of the size
you chose, and does with it what it does with any disk: partitions it or not, formats it with
ext4, XFS or NTFS, mounts it. From then on the filesystem belongs to the operating system, and the
storage service only knows numbered blocks. It is asked to read block 2048 or write block 2049,
and it has no idea that those blocks hold part of `/var/lib/postgresql/data/base/16384/2619`.

**File storage** hands many machines one filesystem. The service owns the directories, the file
names and the permissions, and machines mount it over a network filesystem protocol: NFS on Linux,
SMB on Windows. Two web servers that both mount it at `/shared` see the same files, and a file one
of them writes the other can open a moment later. A piece of data is addressed by its path.

**Object storage** hands out no disk and no filesystem. A program sends a whole object, a file's
bytes plus some metadata, to a bucket over HTTP, under a name called a key, and asks for it back by
the same key. There is no mount, no directory and no open file: `PUT` stores an object whole, `GET`
returns it whole, `LIST` names what is there. Anything that can make an authenticated HTTP request
is a client, from an application server to a browser holding a signed link.

The address is the difference to hold on to, because every later section follows from it:

| | addressed by | who runs the filesystem | the three big providers call it |
|---|---|---|---|
| block | a block number on one volume | your operating system | EBS, Azure Managed Disks, Persistent Disk |
| file | a path | the service | EFS, Azure Files, Filestore |
| object | a key in a bucket | nobody, there is none | S3, Azure Blob Storage, Cloud Storage |

A consequence that surprises people coming from a laptop: **the same file can live in any of the
three, and what changes is what you may do to it.** A 2 GB log on a block volume can be appended to
a line at a time by the one machine that has it attached. On a file share several machines can read
it while one of them appends. In an object store nobody appends to it at all; a longer log is a new
object, written whole.

The product names in the table are the same three shapes sold by the providers lesson 3 compared.
This lesson uses AWS's names and prices, because AWS's price list is the one this course can read
without an account, and the shapes carry over to the other two. The consoles, limits and flags of
each belong to the vendor courses, `aws-foundations`, `azure-foundations` and `gcp-foundations`.
