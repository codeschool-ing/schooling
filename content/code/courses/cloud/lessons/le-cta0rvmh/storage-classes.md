Most objects are read far less after their first weeks than during them. Logs get read in the week
something goes wrong and almost never after; last year's invoices get read when an auditor asks.
Object stores price that difference as **storage classes**: the same bucket, the same keys, and a
setting per object that trades a lower price for keeping it against a higher price, or a longer
wait, for reading it.

The four S3 lines in the sheet are four classes, from the capture in the section on three prices:

| class | name in the API | USD per GB-month, `sa-east-1` | `us-east-1` |
|---|---|---|---|
| Standard | `STANDARD` | 0.04050 | 0.02300 |
| Standard-Infrequent Access | `STANDARD_IA` | 0.02210 | 0.01250 |
| Glacier Instant Retrieval | `GLACIER_IR` | 0.00830 | 0.00400 |
| Glacier Flexible Retrieval | `GLACIER` | 0.00765 | 0.00360 |

A terabyte kept for a month in São Paulo costs 1,000 × 0.04050 = 40.50 in Standard and
1,000 × 0.00765 = 7.65 in Glacier Flexible Retrieval.

## The catch is on the way out

**The cheaper classes charge for reading, and for leaving early.** Neither shows in the sheet, which
carries only the storage line, so this section describes them and gives no amounts. Going down the
table, three things change:

- A **retrieval fee** per GB read, which Standard does not charge. Standard-IA charges one and Glacier
  Instant Retrieval a higher one, so an object read often ends up dearer in Standard-IA than it would
  have been in Standard once the reads are added.
- A **minimum storage duration**: 30 days for Standard-IA, 90 for both Glacier classes. An object
  deleted or moved on sooner is billed as though it had stayed the minimum. Standard-IA and Instant
  Retrieval also bill any object smaller than 128 KB as though it were 128 KB, which makes them a
  poor home for millions of tiny files.
- A **delay**. An object in Glacier Flexible Retrieval cannot be read with a `GET` until it has been
  restored, a request that takes minutes to hours depending on the speed you pay for. Instant
  Retrieval, as its name says, answers in milliseconds like Standard.

## Lifecycle rules move objects by age

Nobody moves objects between classes by hand. A **lifecycle rule** is configuration on the bucket
that says: for objects matching this filter, after so many days move them to this class, and after
so many more delete them. The store applies it in the background. Here is a rule for application logs
written under `logs/`, in the JSON shape S3's lifecycle configuration takes. It was written for this
lesson and applied nowhere, since there is no account:

The days count from the object's creation, not from the previous move. The sequence has to respect
the minimums, and S3 enforces one of them itself: it refuses a rule that moves objects into
Standard-IA before they are 30 days old.

**A lifecycle rule cannot know whether anybody will want the object back.** Tuned to how the data is
read, it removes most of a storage bill without anybody touching an object. Pointed at the wrong
prefix, it sends to Glacier Flexible Retrieval the images a website serves, and the site breaks for
the first visitor who asks for one.
