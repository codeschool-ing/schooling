**Uma página que espera vinte respostas, uma após a outra, paga a ida e volta vinte vezes.** Essa
frase é a seção inteira, e os números da seção anterior a tornam concreta.

Pegue uma página cujo código no servidor chama uma API, lê a resposta e só então decide o que
perguntar em seguida, vinte vezes antes de poder responder. Isso é comum: uma lista de pedidos, depois
o cliente de cada pedido, depois o endereço de cada cliente, cada chamada esperando a anterior. Ponha a
API em três lugares e use os pisos que o programa imprimiu:

| onde a API roda | piso por ida e volta | vinte em sequência |
|---|---|---|
| Fortaleza | 23,7 ms | 20 × 23,7 = 474 ms |
| Norte da Virgínia | 76,6 ms | 20 × 76,6 = 1.532 ms |
| Frankfurt | 98,3 ms | 20 × 98,3 = 1.966 ms |

Esses são pisos, com uma rede perfeita e uma API que responde em tempo zero. A página real é mais
lenta em todas as linhas. **Mesmo o piso põe o caso da Virgínia acima de um segundo e meio.**

## Largura de banda não é a alavanca

A correção errada é a primeira que a maioria procura: um link mais rápido. Calcule o que ele compra.
Digamos que cada resposta tenha 2 KB, ou seja, 16.000 bits. Num link de 100 Mbit/s ela leva
16.000 / 100.000.000 s = 0,16 ms para chegar depois que começa a fluir; num link dez vezes mais
rápido, 0,016 ms. **A melhoria economiza 0,144 ms por chamada**, 2,9 ms em vinte chamadas, de 1.532. O
link nunca foi o problema. O tempo é gasto esperando a luz cruzar um continente e voltar, e esse tempo
não tem nada a ver com a largura do cano.

Largura de banda decide quanto demora uma transferência grande: um backup, um vídeo, a cópia de um
banco de dados. Latência decide quanto demora uma conversa, e quase tudo o que uma aplicação faz é
conversa.

**Uma conexão nova acrescenta idas e voltas próprias.** O curso `networks` mostrou o que acontece antes
do primeiro byte de um pedido HTTPS: um handshake TCP, uma ida e volta, depois um handshake TLS 1.3,
mais uma. Só então o pedido sai e a resposta volta. Numa conexão nova até a Virgínia são três idas e
voltas, pelo menos 3 × 76,6 = 229,8 ms, antes da primeira resposta. Um código que abre uma conexão
nova para cada uma das suas vinte chamadas paga isso sessenta vezes, não vinte.

## As correções que funcionam

Toda correção que funciona faz uma de duas coisas: diminui o número de viagens ou encurta cada viagem.

- Menos idas e voltas. Peça tudo numa chamada em vez de vinte: uma API que devolve os pedidos com os
  clientes e os endereços, uma consulta com join em vez de um laço que consulta. A última linha da
  figura é essa correção, o trabalho de vinte viagens pelo preço de uma.
- Chamadas em paralelo, quando não dependem umas das outras. Vinte pedidos independentes enviados de
  uma vez terminam em cerca de uma ida e volta, não vinte. Isso só funciona quando a próxima pergunta
  não precisa da resposta anterior.
- Conexões reaproveitadas, para que os handshakes sejam pagos uma vez e não por chamada. O keep-alive
  do HTTP e os pools de conexão existem para isso.
- Uma região mais próxima, que encurta todas as viagens de uma vez. É a única correção que ajuda um
  código que você não pode mudar.
- Deixar juntas as partes que conversam muito. Se o código do servidor e o banco de dados conversam
  vinte vezes por página, eles pertencem à mesma região, de preferência à mesma zona, onde cada uma
  dessas viagens é uma fração pequena de milissegundo de distância. Um servidor web em São Paulo lendo
  um banco na Virgínia transforma cada consulta numa viagem continente acima.

A última é um erro fácil de cometer sem querer: alguém cria o banco na região que o console estava
mostrando por acaso, e a aplicação na região certa. **Onde estão os seus outros sistemas** é uma das
perguntas do checklist da próxima seção exatamente por isso.
