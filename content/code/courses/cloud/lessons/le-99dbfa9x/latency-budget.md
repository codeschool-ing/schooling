title: Why round trips cost more than bandwidth

**A page that waits for twenty answers, one after another, pays the round trip twenty times.** The
numbers from the previous section make that concrete.

Take a page whose server code calls an API, reads the answer, then decides what to ask next, twenty
times before it can reply. This is ordinary: a list of orders, then each order's customer, then each
customer's address, each call waiting for the one before. Put the API in three places and use the
floors the program printed:

| where the API runs | floor per round trip | twenty in sequence |
|---|---|---|
| Fortaleza | 23.7 ms | 20 × 23.7 = 474 ms |
| Northern Virginia | 76.6 ms | 20 × 76.6 = 1,532 ms |
| Frankfurt | 98.3 ms | 20 × 98.3 = 1,966 ms |

Those are floors, with a perfect network and an API that answers in no time at all. The real page is
slower in every row. **Even the floor puts the Virginia case past a second and a half.**

## Bandwidth is not the lever

The wrong fix is the one most people reach for first: a faster link. Work out what it buys. Say each
answer is 2 KB, which is 16,000 bits. On a 100 Mbit/s link it takes 16,000 / 100,000,000 s = 0.16 ms
to arrive once it is flowing; on a link ten times faster, 0.016 ms. **The upgrade saves 0.144 ms per
call**, 2.9 ms over twenty calls, out of 1,532. The link was never the problem. The time is spent
waiting for light to cross a continent and come back.

Bandwidth decides how long a large transfer takes: a backup, a video, a copy of a database. Latency
decides how long a conversation takes, and most of what an application does is conversation.

**A new connection adds round trips of its own.** The `networks` course showed what happens before the
first byte of an HTTPS request: a TCP handshake, one round trip, then a TLS 1.3 handshake, one more.
Only then does the request go out and the answer come back. On a fresh connection to Virginia that is
three round trips, at least 3 × 76.6 = 229.8 ms, before the first answer. Code that opens a new
connection for each of its twenty calls pays that sixty times over, not twenty.

## The fixes that work

Every fix that works does one of two things: it makes fewer trips, or it makes each trip shorter.

- Fewer round trips. Ask for everything in one call instead of twenty: an API that returns the
  orders with their customers and addresses, a query that joins instead of a loop that queries. The
  last row of the figure is that fix, twenty trips' worth of work for the price of one.
- Calls in parallel when they do not depend on each other. Twenty independent requests sent at
  once finish in about one round trip, not twenty. This only works where the next question does not
  need the previous answer.
- Reused connections, so the handshakes are paid once and not per call. HTTP keep-alive and
  connection pools exist for this.
- A closer region, which shortens every trip at once. It is the only fix that helps code you
  cannot change.
- Keep the chatty parts together. If the server code and its database talk twenty times per page,
  they belong in the same region, ideally the same zone, where each of those trips is a small
  fraction of a millisecond of distance. A web server in São Paulo reading a database in Virginia
  turns every query into a trip up the continent.

The last one usually goes wrong by accident: somebody creates the database in whichever region the console happened to be showing, and the application in the right
one. **Where your other systems are** is one of the questions in the next section's checklist for
exactly this reason.
