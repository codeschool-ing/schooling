The name suggests code that runs on nothing. **There are servers, as many as there ever were:
serverless means they are not yours.** You do not choose an instance type, open an SSH session,
apply a kernel patch or decide how many machines should be running at three in the morning. You
hand the provider a function and say what should make it run. The provider finds somewhere to run
it, as many copies at once as the traffic asks for, and none at all when nobody asks.

Three properties follow, and between them they are what the word means in practice:

- You manage no machine. There is no operating system to update, no disk filling up, no instance
  to resize the week a campaign goes out.
- You pay per use. The bill counts calls and the time your code spent running, so a function
  nobody calls adds nothing to the compute bill. Lesson 10 puts this billing model beside the
  others.
- It scales to zero, and up from it. Ten requests arriving together get ten copies of the
  function; a quiet night gets none.

**The third one is the break with lesson 4.** An autoscaling group of virtual machines also grows
and shrinks, but it has a minimum of one or two instances, because something has to be running
when the first request arrives. A function has no minimum: the first request after a quiet hour is
what makes a copy exist. That is why serverless is cheap for quiet workloads, and it has a cost of
its own, which the section on cold starts takes apart.

With PaaS you still decide how many instances of your application run, or at least write the rules
an autoscaler follows. **A function takes that decision away, and what is left to you is your code
and your data.** You still set one number, the memory each copy gets, and on Lambda the share of
processor comes with it in proportion. That is a size, not a count.

## What is still yours

The second wrong picture is that serverless means no operations work. **It means less of one kind
of work and the same amount of the rest.** Four things stay on your side of the line whatever the
provider runs:

- the code and every library it imports. A dependency with a known vulnerability is yours to
  update, whoever runs the machine;
- the permissions the function runs with, which on AWS is an IAM role of exactly the kind lesson 7
  wrote;
- the logs, the alarms and knowing when it fails, which is the `observability` course's subject;
- the bill, which now moves with traffic rather than with the number of machines you chose.

**Serverless is also a wider word than functions.** Providers use it for anything billed per use
that scales without you choosing a size, including queues and some databases. This lesson is about
functions, often called FaaS, for functions as a service, because that is where the model is
clearest and where its limits show first.
