---
title: Where an ACL goes, and in which direction
version: 1
---

An ACL does nothing until it is applied, and where it is applied changes what it means. Two decisions
make the placement: **which router and interface**, and **in or out**.

`in` filters packets as they arrive on the interface, before the router routes them; `out` filters
them as they leave. Inbound is usually preferred: a packet that will be dropped is dropped before the
router spends any work on it, and it is the only direction that can protect the router itself.

The classic rule of thumb for placement follows from what each kind can see:

| kind | place it | because |
|---|---|---|
| **standard** | close to the **destination** | it only knows the source; near the source, denying that source would cut it off from everything, not just the one destination meant |
| **extended** | close to the **source** | it knows the destination and port, so it can drop unwanted traffic early without affecting anything else |

The lab showed the reason for the first row. Had the aim been to keep `guest` away from one server at
head office, the standard ACL on `branch` would have been the wrong tool in the wrong place: it cut
`guest` off from **the whole internet**, because a standard ACL cannot say "only towards that server".

One more habit, learned the hard way on every remote router: **apply an ACL to the interface you are
connected through only with a way back ready.** Lesson 5's scheduled rollback is the Linux version of
that habit; on IOS it is `reload in 5` before the change, cancelled with `reload cancel` once the
change has been tested.
