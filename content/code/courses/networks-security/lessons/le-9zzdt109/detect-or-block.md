---
title: Detecting and blocking are different jobs
version: 1
---

An **intrusion detection system** (IDS) watches traffic and raises an alert when something matches
what it was told to look for. An **intrusion prevention system** (IPS) does the same **and acts on it**,
dropping the packet or the connection before it reaches its destination. The software is often the
same program, Suricata here, and the difference is where it sits and what it is allowed to do.

| | IDS | IPS |
|---|---|---|
| sits | beside the traffic, on a copy: a mirror port, a tap, a flooding segment | **inline**: the traffic passes through it |
| on a match | writes an alert; the traffic continues | drops the traffic, and writes that it did |
| a false positive costs | an alert somebody reads and dismisses | **a legitimate request refused**, an outage for whoever sent it |
| if it fails | nothing: traffic never depended on it | the link stops, or is let through unchecked, by design (last section) |
| its latency | none added | every packet waits for it |

The rows point at one trade. **An IDS can afford to be noisy and an IPS cannot.** An IDS rule that
fires on a hundred harmless requests a day is an irritation; the same rule in an IPS blocks those
hundred customers. So rules are usually born in detection, watched against real traffic, and promoted
to blocking only once their false positives are known to be rare, the same path lesson 3's WAF took
from detection-only to blocking.

The lab has both. `sensor` sits on the DMZ with no address and hears every frame, like the sensor of
lesson 7. For the second half of the lesson, `lab.sh inline` puts a new machine, `ips`, **on the cable
between `fw` and the DMZ**, so nothing reaches the shop from outside without crossing it.
