Um id é um inteiro, e uma rede recebe números, então a tentação é entregar 288 como o número 288.
**Isso diz ao modelo que ` baker` é um pouco mais que ` the`, em 258, e um pouco menos que ` sells`, em
307**, o que não faz sentido: os ids são nomes, e a ordem deles é um acidente do treino. A codificação
honesta dá a cada token uma dimensão própria, um vetor **one-hot** de 500 números com um único 1, e não
põe nenhum token mais perto de outro do que de qualquer outro.

Vetores one-hot são longos e quase inteiros de zeros, e multiplicá-los por uma matriz de pesos é
quase só multiplicar por zero. A primeira camada de um modelo que lê texto pula o desperdício. Ela
guarda uma tabela com uma linha de números por token e, dado um id, **devolve aquela linha**. O PyTorch
a chama de `nn.Embedding`, e a linha é o **embedding** do token. Salve isto como `~/dl/lookup.py`; ele
precisa do `tok.json` que o `tok.py` salvou:

**`equal: True` é o ponto da seção.** Sete ids consultados na tabela dão uma matriz 7 por 8; sete
linhas one-hot de 500 vezes a mesma tabela dão a mesma matriz 7 por 8, até o último bit. Uma camada de
embedding é uma camada linear sem viés cuja entrada é one-hot, calculada indexando em vez de
multiplicando. A tabela é a matriz de pesos dela: 500 linhas de 8, 4.000 parâmetros, e a linha 288 são
os oito números que representam ` baker`.

## Só as linhas que foram lidas aprendem

**Sete linhas de 500 receberam gradiente.** O backward de uma consulta manda o gradiente para as
linhas consultadas e para mais nada, exatamente como o produto one-hot faria: um zero na entrada dá
gradiente zero para o peso que ele encontra. Então, em cada passo de treino, a linha de um token só se
move se aquele token está no lote.

Esse é o custo do vocabulário grande da seção anterior, em concreto. Um token visto uma vez no texto de
treino tem a linha ajustada uma vez, e guarda quase todo o seu começo aleatório. Tokens frequentes ganham
linhas bem treinadas; os raros ficam ruidosos, e o hábito do BPE de montar palavras raras com pedaços
frequentes é parte do que impede que isso pese.

No começo, como o `lookup.py` mostra, as linhas são aleatórias e o modelo não tira nada delas. É o
treino que as põe num lugar útil, e a próxima seção treina algumas.
