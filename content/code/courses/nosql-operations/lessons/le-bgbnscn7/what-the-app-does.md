None of the three anomalies is fixed by waiting for the store to catch up. Each is fixed by
something the application does on purpose, and the three habits below cover most of what a shop
needs. They are cheap, and **each one has to be designed in**, because none of them can be added by a
setting on the server.

## Read your own writes from where you wrote them

The simplest fix for the first anomaly is to send a user's reads to the copy that took their write,
for as long as it might matter. In practice that means **the primary**, for that user, for a short
while after they change something. The shop's address page reads from the primary for the person
who just saved, and the rest of the site may keep reading from replicas.

Two variants are common. The application can remember the time of a user's last write and read from
the primary only within a few seconds of it. Or, in MongoDB, a **causally consistent session**
carries the position of the last write and makes a secondary wait until it has caught up to it;
lesson 9 shows read preferences and the settings behind them. Both fix monotonic reads too, if a
user's reads stick to one copy instead of wandering between replicas.

## Make a retry harmless

Under eventual consistency, and on any network, a client often does not know whether a write
happened: the request timed out, and the write may or may not have been applied. The safe response
is to send it again, which is only safe if **doing it twice has the effect of doing it once**. The
usual way is an id the client makes up before the first attempt:

```
ana@vm:~$ docker exec -it mongo mongosh --quiet shop
shop> db.payments.insertOne({ _id: "pay-1001-a7f3", order: 1001, amount: Decimal128("268.80") })
{ acknowledged: true, insertedId: 'pay-1001-a7f3' }
shop> db.payments.insertOne({ _id: "pay-1001-a7f3", order: 1001, amount: Decimal128("268.80") })
Uncaught 
MongoServerError: E11000 duplicate key error collection: shop.payments index: _id_ dup key: { _id: "pay-1001-a7f3" }
shop> db.payments.countDocuments({ order: 1001 })
1
shop> exit
```

The payment's `_id` was chosen by the application, `pay-1001-a7f3`, before it sent anything. The
retry arrived with the same id and was refused with `E11000 duplicate key error`, and the count of
payments for the order stayed at `1`. **The duplicate-key error is the success case here**: it means
the first attempt had landed, and the application can treat it as "already done". A payment with an
`ObjectId` generated by the server on each attempt would have been charged twice.

## Update only if nobody else did: a version number

The lost update is fixed by making the write conditional on the value the client read. Each product
carries a `version`, and every update both checks it and increments it:

```
ana@vm:~$ docker exec -it mongo mongosh --quiet shop
shop> db.products.insertOne({ _id: "MN-330", name: "27-inch monitor", stock: 1, version: 1 })
{ acknowledged: true, insertedId: 'MN-330' }
shop> db.products.updateOne({ _id: "MN-330", version: 1 }, { $inc: { stock: -1, version: 1 } })
{
  acknowledged: true,
  insertedId: null,
  matchedCount: 1,
  modifiedCount: 1,
  upsertedCount: 0
}
shop> db.products.updateOne({ _id: "MN-330", version: 1 }, { $inc: { stock: -1, version: 1 } })
{
  acknowledged: true,
  insertedId: null,
  matchedCount: 0,
  modifiedCount: 0,
  upsertedCount: 0
}
shop> db.products.findOne({ _id: "MN-330" })
{ _id: 'MN-330', name: '27-inch monitor', stock: 0, version: 2 }
shop> exit
```

Both checkouts read the monitor at version 1 and both sent the same update. The first matched,
took the stock to 0 and the version to 2. The second asked for `version: 1`, which no longer
existed, and got **`matchedCount: 0`**: nothing was changed, and no error was raised. That zero is
the whole mechanism. The application has to look at it, and when it is zero, read the product again
and decide afresh: here, that the monitor is sold out.

This is called **optimistic concurrency**: nobody locks anything, and a conflict is detected at
write time rather than prevented at read time. It works because the filter and the update are one
operation on one document, which MongoDB applies atomically. The same idea appears in Cassandra as a
lightweight transaction, `UPDATE ... IF version = 1`, at a higher price that lesson 17 measures.
