"Eventually consistent" is often heard as "a little bit late", as if the only symptom were a value
that shows up a second after it should. **The symptoms are more specific than that, and they have
names**, because each one breaks a particular expectation a user has, and each has a particular fix.
Three matter most to an application like the shop:

## Read your writes

Ana changes her delivery address and the page reloads showing the old one. Her write went to the
primary; the reload's read went to a replica the write had not reached. **Nothing is wrong with
either copy**, and the replica will have the address a moment later. What broke is the one
expectation every user holds without thinking about it: after I change something, I see my change.

It is the anomaly users report most, because it happens to the person who just acted and is
watching. It is also the cheapest to fix, in the next section.

## Monotonic reads

A client reads twice and the second answer is older than the first. It happens when consecutive
reads land on different replicas that are behind by different amounts: replica 1 already has the
order marked "shipped", replica 2 still says "paid", and the page that refreshes between them shows
the order **going back in time**. Each read on its own is a legitimate answer from a legitimate copy.
The sequence is what makes no sense.

## Lost update

Two clients read the same value, each computes a new one from it, and each writes its result. The
monitor has one unit left; two checkouts read `stock: 1`, both decide the sale can go ahead, and both
write `stock: 0`. **The second write overwrote the first without either noticing**, and the store
now says one unit was sold when two were.

This one does not need replicas at all. It happens on a single server, to any application that
reads, decides in its own memory and writes back, and it is the reason relational databases have
transactions and row locks. In the stores of this course, the read-decide-write cycle has to be made
safe on purpose, and the next section shows the usual way to do it in MongoDB.

## What the three have in common

None of them raises an error. Each is a sequence of individually correct operations, and **each
shows up only under concurrency or replication lag**, which a developer's laptop has very little
of. They surface in production, under load, as complaints that cannot be reproduced. Knowing their
names is what lets someone read a bug report like "I saved it and it was gone, then it came back"
and recognise read-your-writes rather than a broken save button.
