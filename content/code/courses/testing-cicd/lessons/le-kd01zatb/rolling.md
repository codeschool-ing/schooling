title: Replacing instances one at a time
version: 1

A service with more than one instance does not have to stop all of them. A **rolling update**
replaces them a few at a time: take one out of the load balancer, deploy the new release to it,
check it, put it back, move to the next. At every moment most instances are serving, so customers
see no gap.

The cost is in the middle columns. **While the update runs, two versions answer customers at
once**, and the load balancer decides which one each request meets. That is harmless when the new
release only adds something. It is not harmless when:

- the new release writes data the old one cannot read, and a customer's next request lands on an
  old instance;
- the API changed shape, and the page loaded from the new version calls an endpoint the old version
  does not have;
- the two versions disagree about a price, and the same cart shows two totals within a minute.

The rule that keeps a rolling update safe is the one lesson 11 returns to: **every release must be
able to run beside the one before it.** A change that cannot, such as renaming a column, is split
into steps that each can.

## The two numbers that shape it

Orchestrators describe a rolling update with two numbers. Kubernetes calls them `maxUnavailable`,
how many instances may be out of service at once, and `maxSurge`, how many extra instances may be
started above the usual count. With four instances:

- `maxUnavailable: 1, maxSurge: 0` replaces one at a time and never needs a fifth machine, but
  serves with three-quarters of its capacity during the update;
- `maxUnavailable: 0, maxSurge: 1` starts a fifth instance first, so capacity never drops, at the
  price of one more machine for the length of the rollout.

## What it does not give you

A rolling update has no clean way back. Undoing it is another rolling update, in the other
direction, at the same speed. And the decision to stop is left to whoever is watching: nothing in
the strategy itself compares the new instances with the old. The next two strategies address
those two gaps, one each.
