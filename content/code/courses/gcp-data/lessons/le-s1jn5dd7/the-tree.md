**Read a branch as a claim you can check.** "One document by key or index" is what Firestore was
built for, and it is also what it demands: a query it has no index for is refused rather than run slowly.
"One row key, huge throughput" is Bigtable's, and a workload that cannot say what its row key is has
no business on that branch. "Transactions and joins" is the relational branch, and it is the default
for the data a business runs on, because most of a business's rules are relationships between rows.
"Questions over all of history" is the analytical branch, which is a different machine from the one
that answers a customer.

## What each store answers

The six questions, answered per store, in the words of the lessons that taught them:

| store | access pattern | latency | consistency | scale | you operate | price follows |
|---|---|---|---|---|---|---|
| Cloud Storage | whole objects by name, listed by prefix | tens of milliseconds | strong for each object | no limit that matters | classes, life cycles, permissions | GiB stored, operations, bytes out |
| Cloud SQL | rows by any indexed column, joins, transactions | milliseconds | strong, with transactions | one writer, growing by a bigger machine | sizes, versions, indexes, failover | vCPU and memory hours, storage |
| AlloyDB | the same, with a columnar engine for scans | milliseconds | strong, with transactions | one writer, read pools beside it | sizes, pools, versions | vCPU and memory hours, storage used |
| Spanner | rows by key and index, joins, transactions | milliseconds, more across regions | strong, external consistency | spreads across splits | keys, interleaving, capacity | processing units or nodes, storage |
| Firestore | documents by id, queries by index | milliseconds | strong for each document read | spreads with nothing to size | indexes, security rules | documents read, written, deleted, stored |
| Bigtable | rows by key, ranges by prefix | single-digit milliseconds | strong in one cluster, eventual across clusters | nodes | row keys, column families, nodes | node hours, storage |
| Memorystore | a key, again and again | under a millisecond | whatever the cache's invalidation gives | memory of the instance | eviction, invalidation | GiB-hours of capacity |
| Pub/Sub | messages published and pulled | under a second end to end | ordered per ordering key, at least once | nothing to size | subscriptions, acks, dead letters | bytes of throughput, retention |
| BigQuery | scans and joins over large tables | seconds | as of the last load or stream | slots | partitions, clustering, quotas | bytes scanned or slot hours, storage |

**One row is not a store in the usual sense.** Pub/Sub keeps a message until it is acknowledged, or
for its retention period at most, and then lets it go: it is where events travel, and lessons 19 to
22 landed them in Cloud Storage and BigQuery, which is where they are stored. Memorystore keeps data
only until it is evicted or the instance restarts, which makes it a copy, never the store of record,
and lesson 12 put it in front of a database for exactly that reason.

**The cells that read "more across regions" or "as of the last load" are where choices are lost.**
Spanner's consistency across continents is real and paid for in the latency of every write that
crosses one; BigQuery answers about the data loaded into it, and an analyst who needs the order
placed a minute ago is asking the wrong store. Each of those is a sentence a design review should
say out loud.
