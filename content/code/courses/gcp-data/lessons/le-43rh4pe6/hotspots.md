**The obvious key for a click stream is the time, and it is the one that does not scale.** A key
that starts with the timestamp sorts the whole table by time, which reads beautifully for C3, every
event of the last minute in one run. It also sends every new event to the same place, because the
newest key is always the largest. Bigtable spreads a table over its nodes by key range, so a range
that receives every write is one node doing the work of the cluster while the others wait.

## Tablets

**A table is cut into tablets, contiguous ranges of row keys, and each tablet is served by one node
at a time.** Bigtable splits a tablet that grows too large or too busy, and moves tablets between
nodes to balance the load, on its own and without a setting. The data itself lives in Google's
distributed file system, Colossus, not on the node, which is why moving a tablet is fast: only the
responsibility moves. That machinery is what makes "add a node and the table gets faster" true, and
it only helps if the load is spread over many tablets to begin with.

**A split cannot spread a point that moves.** With time first, the hot spot is the end of the table.
Bigtable splits the last tablet in two, the newest key is in the new last one, and the next write
goes there too. Each split leaves behind a tablet nobody writes to, and the cluster's write rate is
the rate of one node. Google's schema guidance names timestamps at the start of a key as the first
thing to avoid, along with sequential ids, which fail the same way.

## Where the next minute lands

The emulator is one process with no tablets and no nodes, so it cannot show this. **What follows is
a model**, and it says so in its first line. It builds yesterday's hour of events under four key
designs and cuts each into ten equal tablets at the keys those rows had. Then it counts where the
next minute's thousand events would go. Save it as `~/gcp/tablets.py`:

**Time first sends all thousand to tablet 9, and reversed time first sends all thousand to tablet
0.** Reversing the timestamp moves the hot spot from the end to the start and does nothing else,
which surprises people who learned the reversed timestamp as a cure. **Customer first spreads them
over all ten**, between 86 and 130 each, because the customers who happen to click in any minute are
scattered across the key space. That is the design of the previous section, and it was chosen for
the reads; it spreads the writes for free.

## Salting, when the reads need time first

**Salting puts a small computed number in front of the key**: here a hash of the customer id modulo
10, so `8#1792184400000#c-17`. Every bucket keeps its rows in time order, and the newest end of each
bucket is a different place in the table. The model's last line is the result: eight tablets took
the minute, two of them taking two buckets' ends each, and tablets 0 and 2 took none because no
bucket ended inside them. **Salting turns one hot spot into ten warm ones**, not into an even load.

**The price is paid by every read.** C3, the last minute across customers, is now ten range reads,
one per bucket, merged by the program. C1 still works, because the salt comes from the customer and
not from the time: c-17's rows are all in one bucket, and the reader computes which. A salt drawn at
random would spread the writes better and leave the reader no way to find a customer except by
reading all ten. Google's documentation also warns against hashing the whole key instead of
prefixing it, because the order of the rows is then lost and no range read means anything.

**For Quitanda the honest answer is the one already chosen**: customer first for the table the app
reads, and C3 left to the warehouse. Salting is the repair for a table whose main reads really are
by time, a monitoring table with one row per minute per sensor, say, where nothing else in the key
could come first.

## Key Visualizer, which the emulator does not have

**On a real instance, Key Visualizer draws the key space against time as a heat map**, one column per
time slice, one row per range of keys, brighter where reads or writes were heavier. A time-first key
draws a bright diagonal line, the hot spot moving along the keys as the clock does; a well-spread key
draws an even haze. It is part of Bigtable, costs nothing extra, and is generated on its own once a
table passes a threshold of size or traffic that the documentation states. It is the instrument for
this section's question on a table you did not design, and nothing local stands in for it.
