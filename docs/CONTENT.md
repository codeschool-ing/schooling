# The content format

`content/` is the source of truth for every school's catalogue. The database is a derived mirror
and only the load job writes it (C-01, C-07).

The material is generated by a person working with an agent, on demand. **The system does not
automate the writing; it automates the checking** — which is the half that has to run without a
person, because it is what stands in for the reviewer nobody is going to be (C-14).

---

## Two rules the whole format exists to enforce

**Nothing joins to anything by prose or by position. Only by a stable id.**

The predecessor joined exercises to lessons by the lesson's *title text*, and keyed translations
by *array position*. Both are quiet failures waiting for an edit: rename a title and the
exercises detach; insert a step and every translation after it shifts onto the wrong thing. One
of those already shipped once, which is why a validator exists for it. With a machine rewriting
titles and inserting steps, they stop being hazards and become certainties. (C-09)

**Order is declared, never inferred from the filesystem.**

No numeric prefixes on directories. `course.json` names its lessons in order; `lesson.json` names
its sections in order. Reordering is one changed line, not a cascade of renames that git shows as
deletions. (C-10)

---

## Layout

```
content/
  code/                                   the school — one directory per tenant
    school.json                           name, accent colour, locales
    tracks/
      frontend.json                       course order, forks, links
      frontend-exam.json                  the track exam
    courses/
      web-fundamentals/
        course.json                       metadata, requires, lesson order
        course.pt.json                    only what is translated
        exam.json                         the course exam
        exam.pt.json
        lessons/
          le-4xwdejgt/                    named for the lesson's id
            lesson.json                   section order and kind
            roles.md                      the prose, in English
            roles.pt.md                   beside it, optional
            packets.md
            exercises.json
            exercises.pt.json             what a student READS, never the key
```

A lesson has no `lesson.pt.json`. Its title is a topic of the course and is translated in
`course.pt.json` under that topic's id; its sections carry their titles in the front matter of
their own prose. Nothing is left in `lesson.json` for a person to read.

**Every `.pt.` file is optional and partial.** The server falls back field by field, so a section
translated in its title but not its body keeps the English body rather than losing the title too.
A missing translation shows up in `ls`, which is the cheapest review there is. (C-11)

## The files

### `school.json`

```json
{
  "id": "code",
  "name": "Programming",
  "accent": "#2F6F4E",
  "locales": ["en", "pt"]
}
```

### `tracks/<id>.json`

The order of courses and the forks. A fork is a step with named options; each option is a list of
course ids.

```json
{
  "id": "frontend",
  "name": "Front-end Development",
  "goal": "…",
  "outcome": "Junior Front-end Developer",
  "courses": [
    "web-fundamentals",
    "html-css",
    { "choice": "the framework",
      "note": "…",
      "options": [
        { "name": "React + TypeScript", "courses": ["react-ts"] },
        { "name": "Angular", "courses": ["angular"] }
      ] },
    "front-quality"
  ],
  "continues": null
}
```

`continues` names another track whose courses this one may assume the student has taken. It is
followed to the end of the chain; a track that continues itself, or continues nothing that
exists, is an error.

### `courses/<id>/course.json`

```json
{
  "id": "web-fundamentals",
  "name": "Web and Internet Fundamentals",
  "category": "foundations",
  "level": "beginner",
  "hours": 40,
  "summary": "…",
  "requires": [],
  "prerequisites": "Everyday computer and internet use.",
  "lessons": ["client-and-server", "packets-and-protocols", "http"]
}
```

**`requires` names only what the student has to know first.** If the reason is "in this track it
comes after that one", it belongs to the track's order instead. Conflating the two cost 18 false
edges once: a course looked as though it needed 500 hours before it, so it could not be reused in
another track, and the site drew arrows at prerequisites the track did not contain.

### `lessons/<id>/lesson.json`

```json
{
  "id": "client-and-server",
  "title": "Client, server and host: who asks and who answers",
  "sections": [
    { "id": "intro",  "kind": "video",   "video": true, "duration": "02 min" },
    { "id": "roles",  "kind": "reading", "materials": ["wf-dns-cheatsheet"] },
    { "id": "drill",  "kind": "practice" }
  ]
}
```

`kind` is `reading`, `video`, `practice` or `assessment`. A `reading` section must have a
Markdown file of the same id; a `video` section may hold the frame with `video: true` before the
video exists; an `assessment` section is appended by the portal and is not written here.

`countable` stays a separate field from `kind`, so progress semantics never have to be inferred
from what a section is.

### The prose — `<section-id>.md`

One file per section, one section per file. Front-matter carries nothing the JSON already knows;
it exists only for what belongs to the prose itself.

```markdown
---
title: The two roles
---

Almost everything that happens on the internet is a conversation between two parties with fixed
roles. The **client** asks; the **server** answers.

The roles belong to the moment, not to the machine. A web server that needs to query a database
becomes the database's client at that instant.
```

A diff on this file is a diff per paragraph, which is the entire reason the catalogue is a file
and not a row (C-01). A paragraph inside a JSON string reviews badly, so prose never lives in
JSON.

### `exercises.json`

Every exercise belongs to a lesson, joins by id, and declares the grader that judges it.

```json
[
  {
    "id": "ex-spr8rdb4",
    "version": 1,
    "section": "roles",
    "type": "quiz",
    "difficulty": "easy",
    "drillable": false,
    "prompt": "A web server needs to query a database to build its response. At that instant, what is it?",
    "hint": "The roles describe the moment of the conversation, not the equipment.",
    "choices": [
      { "text": "The database's client…", "correct": true,  "why": "…" },
      { "text": "Still only a server…",   "correct": false, "why": "…" }
    ]
  }
]
```

`version` is not decoration — see **The loop** below.

Types: `quiz`, `multiple-choice`, `ordering`, `matching`, `code`, `expected-output`,
`expression-answer`, `numeric`, `cloze`, `labelling`. **Every type has a machine grader; that is
the entry requirement.** Free-text essays are out, because nothing can check them and this system
has no reviewer.

### `exercises.pt.json`

Keyed by the question's id, and carrying **only what a student reads**.

```json
{
  "ex-spr8rdb4": {
    "prompt": "Um servidor web consulta um banco de dados…",
    "hint": "Os papéis descrevem o momento, não o equipamento.",
    "choices": [
      { "text": "O cliente do banco de dados", "why": "…" },
      { "text": "Ainda apenas um servidor",    "why": "…" }
    ]
  }
}
```

The translatable fields are `prompt`, `hint`, `trap`, `choices[].{text,why}`, `items`,
`pairs[].{left,right}`, `right_distractors` and `labels` — a list of texts, because a label's
coordinates are not a translator's business.

**Nothing that decides an answer is nameable here.** `correct`, `accept`, `value`, `tolerance`,
the coordinates: a file that mentions one is refused on the pull request, because a translation
that could reach the key would mark the same answer differently in two languages, and nobody
would find it — both screens read perfectly well on their own.

**The lists are matched by position**, which this project forbids almost everywhere. Inside an
exercise a position is already the identity — the key is `choices[2]` and a student's answer
records the index — and both are safe because a question is immutable within its `version`. A
list of a different length is the symptom of an insert, and it fails the build.

### `exam.json`

Exams do not belong to a lesson, so they do not live in one: the course exam is
`courses/<id>/exam.json` and the track exam is `tracks/<id>-exam.json`. Same exercise shape,
drawn from a sealed pool that never reaches the practice globals.

The price of naming a track's final after its track is that a track may not itself be called
`<x>-exam`: such a file is read as the final of `<x>` and never as a track of its own. That would
be silent, so it is not — a `tracks/<x>-exam.json` with no track `<x>` is refused, which catches
both the typo and the track somebody happened to name that way (C-13).

## What CI checks, because CI is the reviewer

The static half runs on every pull request over the files. The executable half runs the answer
keys through the same machinery that grades a student.

**Structure**

- every file matches its schema
- every id is unique within its scope, and every referenced id exists
- no `.md` file is orphaned — **content that was generated and forgotten shows up nowhere else**
  (C-13)
- every `reading` section has prose; a published section with neither prose nor video is an error
- every translation key names an id that exists

**The graph**

- no cycle in `requires`
- every `requires` is satisfiable inside each track that shows the course, following `continues`
  to the end of the chain
- track order is consistent with the forks

**The answers** (C-12)

- `code` — the answer key is executed against its test cases
- `expression-answer` — the accepted expression is parsed and graded against itself, so a key
  that does not parse, a question with no variables, or a variable named after a constant fails
  on a pull request rather than on a screen
- `numeric` — the unit parses and the tolerance is a number
- `cloze` — the accepted set is non-empty after normalisation
- every exercise's payload matches the shape its `type` requires
- the conformance fixtures run against the grader — no longer between two graders (A-09 is
  retired; a client that could mark an answer would be a client holding the key) but between the
  grader and the questions, so a change that alters a verdict has to change a file somebody wrote

A schema check alone would pass a question whose answer key is wrong, which is the one failure
this system cannot absorb.

## The loop: what happens when a question is bad

Item analysis is the reviewer (C-06). A question everyone gets wrong is either excellent or
broken; one everyone gets right measures nothing; one the strong students fail and the weak ones
pass is **inverted**, which is what automatic generation produces when it produces a mistake.

Three movements, in this order of importance:

**1. Quarantine, automatically.** A broken key is harming students now, and the cheapest correct
action is to stop serving it. It is a **threshold, not a decision** — a human decision is exactly
what this system does not have. The question leaves the draw and stops counting until it is
replaced. (C-15)

**2. Version the exercise.** Without it there is no way to know whether the replacement helped.
And it reaches further than the report: **a student's answer records the version it answered**,
or the history lies — comparing December's apple with March's orange. (C-16)

**3. Compare.** With statistics per version, comparing is reading.

**The hard part is not the statistics; it is not reacting to noise.** Three wrong out of three is
chance, not signal. Nothing fires below a minimum sample, and beneath it the console says
*insufficient data* rather than showing a red that means nothing. With few students almost
everything sits in that state for months, and that is correct. (C-17)

Quarantine, replacement and reinstatement are audited events. Provenance already records which
run produced a version; the loop records why this version replaced that one.
